# 05｜按场景选择组合：先找两三个候选，再用自己的任务试

下面给出 **40 个细分场景**。它们是依据前文架构分析提出的优先试用顺序，不是统一实测排行榜。表中“原生”“内置路由”优先遵循产品当前支持；多 Provider 工具中的具体型号，要先通过[第六章](06-模型搭配与成本.md)的兼容性检查。

如果某个型号在你的地区、套餐或界面尚不可选，不必强行绕接；先使用同家族、当前正式支持的对应档位。没有做过工具验证的组合，不能仅凭接口兼容就投入重要工作。

## 5.1 日常编程：改动范围不同，合适的工具也不同

| 编号与场景 | 优先组合 | 另一组值得比较的组合 | 为什么，以及怎样验收 |
|---|---|---|---|
| 01 单文件小 bug，原因大致清楚 | Cline＋Sonnet 5 | Codex＋GPT-5.6 Luna／Terra | 可见的修改与短验证链即可；必须重现旧问题并通过相关检查 |
| 02 偶发 bug，需要读日志、追调用链 | Codex＋GPT-6 Astra／Sol | Claude Code＋可用的 Opus | 调查与执行要连续；保存已排除假设，不能靠“看起来修好了” |
| 03 中型功能，涉及 API、界面和测试 | Claude Code＋Sonnet 5 | Codex＋GPT-5.6 Terra／Sol | 原生工具循环省配置；先定接口，再逐步实现与集成 |
| 04 从零搭项目骨架 | Cursor＋Auto／当前 Composer | Codex＋GPT-5.6 Terra | 编辑器反馈或完整执行都合适；验收启动、构建、示例测试和 README |
| 05 跨模块重构，保持行为不变 | Codex＋GPT-6 Astra | Junie＋当前可用强编程模型 | 需要项目理解与验证；先建立行为基线，再分批迁移 |
| 06 Java／Kotlin／Spring 等复杂 IDE 项目 | Junie＋当前可用 Claude／GPT | Augment＋内置路由 | 复用 IDE 项目结构或跨仓库上下文；确保索引、运行配置正常 |
| 07 依赖升级与数据库迁移 | Kiro＋Sonnet 5／GPT-5.6 Sol | Devin＋原生任务路由 | 明确规范、阶段和回退步骤；在独立环境验证升级路径 |
| 08 前端视觉迭代 | Antigravity＋Gemini 3.8 Flash／3.1 Pro | Cursor＋当前可用视觉模型 | 浏览器验证很重要；检查不同尺寸、交互和异常状态 |
| 09 只有截图，要还原网页 | Codex＋支持图像的当前 GPT | Antigravity＋Gemini 3.1 Pro | 模型看图只是起点，还要浏览器检查、字体和响应式调整 |
| 10 大仓库或跨仓库改动 | Auggie＋内置路由 | Claude Code／Codex＋Augment Context Engine | 先解决相关信息获取；要求列出依赖证据和影响范围 |
| 11 阅读陌生项目、带新人 | Cline＋Sonnet 5 | Qwen Code＋当前 Qwen 推理模型 | 可见的调查过程有教学价值；每项解释给文件与符号出处 |
| 12 代码评审，提出可行动问题 | Copilot 当前评审能力＋原生配置 | Codex＋GPT-5.6 Sol | 重点看漏报与误报；每条意见必须有触发条件和实际影响 |
| 13 单元测试与回归测试补齐 | Claude Code＋Sonnet 5 | Codex＋GPT-5.6 Terra | 测试要验证行为；至少有能在缺陷版本失败的关键测试 |
| 14 重复 issue，批量创建修复 PR | OpenHands＋已验证编程模型 | Copilot 云端代理＋其可用模型 | 环境和交付管理重要；每个任务单独分支、测试、审阅 |
| 15 大功能拆成相对独立模块 | Factory Mission＋强规划模型／经济工作者 | Cline CLI Teams＋分别配置的模型 | 需要共享任务状态；先固定接口与责任边界，再并行 |
| 16 远程服务器、SSH、终端习惯 | Crush＋已适配 Claude／GPT | OpenCode＋已验证的 Qwen／DeepSeek | TUI 与可控工具更自然；确认命令运行在正确主机和目录 |

Neovim 用户可在第 16 类场景中优先比较 Avante 或 CodeCompanion；若通过 ACP 接 Codex／Claude Code，模型仍按对应代理选择。第 14 类异步维护也可把 Jules 原生路由加入试用，保留其当前实验状态的判断。详见 [B17—B20 档案](03B-编辑器与托管工作台.md)。

**这里为什么没有统一推荐“最强模型”？** 第 01 类任务通常很快就能验证，较快模型已经够用；第 02 类错误一旦调查方向错了，会浪费大量人工时间，较强模型更值得试。模型成本应和失败后的返工成本一起算。

## 5.3 写作：小说、报告和技术文档不是同一种任务

| 编号与场景 | 优先组合 | 另一组值得比较的组合 | 为什么，以及怎样验收 |
|---|---|---|---|
| 23 短文章、邮件、中文润色 | Chatbox Chat＋Sonnet 5／Kimi 当前模型 | Cherry Chat＋GPT-5.6 Terra／Qwen | 不需要复杂代理；给目标读者、语气和长度，对照原意检查 |
| 24 小说大纲、人物与世界观 | Cherry／Chatbox＋可用 Claude 或 Kimi | Hermes＋强文本模型 | 重点是设定组织与版本；人物动机、时间线和约束应落成文件 |
| 25 连载小说，跨多章保持一致 | Hermes＋已验证 Claude／Kimi | Chatbox Work＋强文本模型＋项目设定文件 | 需要跨会话资料和可维护状态；每章后更新事件、伏笔和人物状态 |
| 26 工作周报，汇总多份材料 | AnythingLLM＋GPT-5.6 Terra／Kimi | Cherry＋同级文本模型 | 固定资料范围与出处；不能把计划写成已经完成的成绩 |
| 27 管理层报告，需数字与图表 | Codex＋GPT-5.6 Sol | Claude Cowork＋当前原生模型 | 要生成文件并核算数据；核对口径、时间范围、表格与正文一致性 |
| 28 深度行业／竞品研究 | Hermes＋强工具模型＋搜索工具 | Codex＋GPT-6 Astra＋可用检索工具 | 需要来源、时间和矛盾核对；区分事实、厂商主张与作者判断 |
| 29 多篇论文综述 | AnythingLLM＋强长文本模型 | Gemini CLI＋Pro＋文件／搜索工具 | 检索与引用定位比文风重要；每个关键结论回到原论文核对 |
| 30 技术文档随代码更新 | Claude Code＋Sonnet 5 | Codex＋GPT-5.6 Terra | 直接读实现与运行示例；文档命令和接口要能验证 |
| 31 翻译与术语一致性 | Chatbox＋Claude／Qwen 当前文本模型 | Cherry＋GPT-5.6 Terra | 保存术语表和风格样例；逐段核对遗漏、数字、否定与专名 |
| 32 大批量相似文案与固定格式报告 | Dify＋经济文本模型，疑难升级 | n8n＋同等模型节点 | 模板、结构检查和人工抽检更重要；为失败项保留重跑机制 |

**小说推荐的限度。** 本报告没有进行盲评，不能断言某个模型的中文文学风格最好。建议拿同一场景，固定人物设定，分别生成一小段，遮住模型名评价叙事、人物声音和细节。偏好确定以后，再选择最方便保存设定与修改稿件的 Harness。

**研究推荐的限度。** 能联网的模型不等于自动提供可靠参考文献。工具是否返回原文、能否保存检索日期、是否能打开引用页面，往往比模型宣传中的“研究能力”更关键。

## 5.4 知识库、长期助理与团队自动化

| 编号与场景 | 优先组合 | 另一组值得比较的组合 | 为什么，以及怎样验收 |
|---|---|---|---|
| 33 个人资料库，经常查固定文档 | AnythingLLM＋已验证的云端／本地模型 | Cherry＋知识库＋同类模型 | 建立一小组标准问题；答案必须指出支持它的原文 |
| 34 团队共享 AI 入口和多个助手 | LibreChat＋统一模型网关 | LobeHub／Open WebUI＋组织批准模型 | 账户、权限和日志很重要；验证不同用户不能越权读取资料 |
| 35 完全离线的敏感资料整理 | Open WebUI／AnythingLLM＋本地 Qwen3.5-27B 等已验证模型 | Chatbox／Cherry＋内网模型服务 | 全链路检查是否外连；中文质量和工具能力要用自有样本测试 |
| 36 跨设备、消息入口的个人助理 | OpenClaw＋已验证强工具模型 | Hermes Gateway＋相同模型家族 | 需要渠道身份、持续服务和状态；先接一个入口，核对谁能触发动作 |
| 37 周期性收集资料并生成摘要 | Hermes＋经济检索／摘要模型 | n8n＋模型节点 | 需要调度、去重、重试与安静策略；来源没更新时不要重复制造报告 |
| 38 客服或内部制度问答 | Dify＋检索＋文本模型 | AnythingLLM／Open WebUI＋相同生成模型 | 先保证依据正确，证据不足可拒答或转人工；不能用流畅度代替准确性 |
| 39 跨多个应用整理数据、填表、归档 | Goose＋工具调用稳定的模型＋所需连接器 | n8n＋确定流程＋局部 Agent | 连接器和账户权限决定可行性；先生成草稿，再执行不可轻易撤销的步骤 |
| 40 希望助理积累工作方法与偏好 | Hermes＋稳定工具模型 | OpenClaw 或 Chatbox Work＋对应模型 | 记忆要可查看和纠错；定期清理过期偏好与一次性任务事实 |

“完全离线”这一行是部署目标，不是产品名称带来的保证。下载模型、嵌入、联网工具、语音服务、更新和遥测，都应纳入数据路径检查。Qwen3.5-27B 是有官方权重与部署说明的候选，并非对任意电脑都能流畅运行的承诺。[官方模型卡](https://huggingface.co/Qwen/Qwen3.5-27B)

## 5.5 三个可以直接照着组织的工作方案

### 方案一：一个人做中型 Web 项目

选一套主力即可：Codex＋Terra／Sol，或 Claude Code＋Sonnet 5。仓库保存项目说明、运行命令与验收标准。先实现一条最小完整流程，再扩展其他功能。

遇到困难时，先让主代理说明卡点和证据，再提高模型能力；只有前后端接口稳定、任务真的独立时才引入子代理。浏览器验证可以来自原工具或额外连接器，但必须真正走过核心用户路径。

输出至少包含可运行代码、必要测试、启动说明和已知限制。接受代码之前看 diff，部署另作一个明确步骤。

### 方案二：持续写长篇中文小说

用 Cherry／Chatbox 管理对话与稿件，或者用 Hermes 管理跨会话工作。模型先通过小样盲评选定，再固定一段时间，不要每章都换。

建立四份材料：人物表、时间线、世界规则、章节与伏笔账本。每章输入包含本章目标、相关设定与上一章必要信息；生成后先做情节一致性检查，再润色语言。只将确认后的变化写回设定库，避免草稿想法被当成正史。

这里不需要代理任意访问邮件或执行系统命令。工具应围绕读取设定、写稿、对照和保存版本来配。

### 方案三：每月固定业务报告

第一次可以用 Codex／Cowork 等探索数据与报告格式；稳定以后，把数据来源、口径计算和模板沉淀下来。定期生产可用 n8n／Dify 组织，模型负责解释变化与组织语言。

用程序计算数字，用检索找支持材料，让模型解释；三者职责分清。缺数据时标记缺失，不允许模型补造。正式发出之前，人工核对关键指标与敏感表述。这样比每个月让通用代理从头猜流程更容易控制质量。

## 5.6 如果只想装最少的软件

| 你的情况 | 一个合理起点 | 什么时候再增加第二个工具 |
|---|---|---|
| 普通程序员，愿意用终端 | Claude Code 或 Codex 的原生组合 | 需要明显不同的模型、编辑器或远程环境时 |
| 全程依赖 IDE | 当前 IDE 内的 Cline／Copilot／Junie，或 Cursor | 原有入口解决不了长期任务或跨仓库检索时 |
| 喜欢开放与定制 | OpenCode；熟练后再看 Pi／DSH | 能明确说出需要替换哪一个模块时 |
| 主要写作和看资料 | Chatbox 或 Cherry＋一个适合自己的文本模型 | 固定文档库变大，检索成为瓶颈时 |
| 真正需要持续在线助理 | Hermes 或 OpenClaw | 单入口稳定后再加消息渠道和定时任务 |
| 不懂环境，只想做应用原型 | Replit Agent 或同类托管产品 | 项目进入真实业务，需要迁移、治理和专业工程时 |

选型完成的标志不是已经装了最多工具，而是你知道常见任务应该交给哪一个、怎样验收，以及它失效时如何接管。
