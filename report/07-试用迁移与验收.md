# 07｜试用、迁移与验收：把报告变成可执行的选型过程

没有必要把所有产品安装一遍。选出最接近需求的两三个组合，用自己的真实任务验证，比泛泛比较“聪不聪明”更有用。

## 7.1 先写一张选型卡

| 项目 | 示例 |
|---|---|
| 最常见任务 | 修中小 bug、写月报、查内部文档 |
| 环境 | Windows＋VS Code，或 macOS＋JetBrains，或内网服务器 |
| 已有资源 | 哪些订阅、API 账户、模型机器、连接器 |
| 必要能力 | 可以跑测试；必须有来源；需要写文件 |
| 可接受配置负担 | 只会图形界面，或能维护 Docker／CLI |
| 数据要求 | 哪些资料允许发云端，哪些只能内网 |
| 成本目标 | 每月总预算、单项任务可接受费用、人工检查时间 |
| 成功定义 | 通过哪些检查，产物怎样才可以交付 |

不要一开始填“最强模型、无限上下文、全部工具”。这些不是需求，而是还没有明确取舍。

## 7.2 用六个任务组成小型试用集

| 任务 | 主要检验什么 | 通过标准示例 |
|---|---|---|
| 已知原因的小修复 | 基本编辑与验证 | 改动范围合理，相关测试通过 |
| 原因未知但可重现的 bug | 调查与纠错 | 找到根因，解释证据，避免只掩盖现象 |
| 三文件以上的小功能 | 上下文与集成 | 满足需求，接口一致，能够运行 |
| 长任务中断后继续 | 状态恢复 | 保留约束，不重复有副作用的步骤 |
| 带原文的资料报告 | 检索与引用 | 关键结论能追溯，没有编造数字或来源 |
| 一次受限操作与取消 | 权限与生命周期 | 不越界，取消后不留下失控子任务 |

使用脱敏项目、副本或独立工作树。每个组合从相同初始状态开始；模型选择、工具、预算尽量保持可比。随机性较大的任务可重复少量次数，不必为了一个确定的小改动反复跑无意义测试。

## 7.3 记录结果，而不只记录“感觉不错”

建议使用目录中的[评估记录模板](../templates/选型评估记录.csv)。每个任务至少记录：

- 产品与版本、实际模型、Provider、关键参数。
- 是否完成验收，出现了什么错误。
- 人工干预次数，以及干预的内容。
- 总费用、总等待时间、人工检查与返工时间。
- 修改是否容易审查，能否解释依据。
- 中断、恢复、导出和迁移是否正常。

“代理自己说完成了”不算通过。若没有独立检查，就将该任务记为未验证，而不是成功。

### 一个可调整的评分方式

| 维度 | 一般开发任务的示例权重 | 知识报告任务的示例权重 |
|---|---:|---:|
| 结果正确、达到验收 | 40% | 35% |
| 证据与可审查性 | 20% | 30% |
| 人工介入与返工负担 | 15% | 15% |
| 总成本与等待时间 | 15% | 10% |
| 恢复、导出与长期维护 | 10% | 10% |

这些是本报告建议的起始权重，不是行业标准。出现越权、关键数据丢失或无法满足硬性需求时，应先排除该配置，不靠其他高分抵消。

## 7.4 七天以内可以完成的试用安排

| 阶段 | 做什么 | 留下什么 |
|---|---|---|
| 第 1 天 | 明确需求与两个候选，安装并配置 | 选型卡、版本与模型记录 |
| 第 2 天 | 跑小修复与资料任务 | 基本质量和引用问题 |
| 第 3 天 | 跑跨文件任务 | 变更、测试、人工介入记录 |
| 第 4 天 | 测中断恢复、权限与错误 | 生命周期与限制说明 |
| 第 5 天 | 把一个真实日常任务交给候选 | 实际耗时与成本 |
| 第 6 天 | 只针对已发现的问题调一次配置 | 能解释原因的改进 |
| 第 7 天 | 选主力，保留必要备选，导出配置 | 主力工作流与退出方案 |

如果一个产品需要很多“你还要装这个、再改那个”才勉强工作，应把维护成本计入判断。这未必意味着产品不好，但可能不适合你的时间和经验。

## 7.5 三份可以直接复制的任务说明

### 编程任务

```text
目标：修复／实现……
当前现象与复现方法：……
允许修改的范围：……
必须保持不变的行为：……
运行与测试命令：……
验收条件：……

请先检查实际代码与现有状态。必要时提出简短计划，实施后运行相关验证。
最后给出：改了什么、为什么、验证结果、尚未解决的问题。
如果无法验证，请明确标出，不要把推测写成已通过。
```

### 研究与报告任务

```text
读者与用途：……
研究范围与截止日期：……
允许使用的资料与排除范围：……
输出形式与长度：……

请区分可核实事实、来源自己的主张和你的分析。
关键结论给出可打开的原始来源；数字说明口径与日期。
来源有冲突时解释冲突，缺少信息时保留未知。
```

### 长任务检查点

```text
请把以下信息保存到项目内的进度文件：
1. 目标与验收标准。
2. 已确认的事实与来源。
3. 已完成的修改／产物。
4. 已运行的检查及结果。
5. 已排除的方案和原因。
6. 未解决问题、当前阻碍和下一步。
7. 不能重复执行或需要另外确认的外部动作。

恢复任务时先核对当前文件与外部状态，不要只相信旧摘要。
```

## 7.6 迁移时，哪些东西通常容易搬，哪些很难

| 资产 | 可迁移程度 | 建议 |
|---|---|---|
| Markdown 项目规则 | 通常较高 | 保留一份核心规范，再按产品文件名适配 |
| Skills 文档 | 内容通常可搬，元数据与触发语义可能不同 | 检查工具名称、路径和入口差异 |
| MCP 工具连接 | 协议可复用，认证与权限未必相同 | 重新核对凭据和工具白名单 |
| 模型 API 配置 | 需按协议调整 | 不直接复制不明私有字段 |
| 对话导出 | 常能保留阅读记录 | 不等于能恢复原始代理状态 |
| 子代理配置 | 差异大 | 重新定义职责、权限、模型和交接 |
| 检查点与执行日志 | 往往与运行时耦合 | 保留面向人的进度文件和真实产物 |
| 云端项目环境 | 迁移成本较高 | 保存构建说明、数据导出和依赖清单 |

将长期知识保存在可读文件中，往往比把全部工作记忆只留在某个产品私有数据库里更容易迁移。但也不能认为复制一个 JSON 历史文件，就已经复制了凭据、进程、工具状态和远程环境。

## 7.7 新版本来了，应该重测什么

没有必要每次全面重做所有任务。优先复测发生变化的部分：模型别名更新后检查工具与长任务；压缩机制更新后检查恢复；权限默认值变化后检查受限动作；新增团队功能后检查取消、预算和共享文件冲突。

保留一个已知稳定的版本与配置，升级后若真实任务退化，可以有依据地回退。不要只记录“昨天好用、今天不好用”，尽量记录变化前后的具体组合。

## 7.8 按能力选验收项：同一张卡适用于不同产品

下表是建议执行的试用方案，不是本报告已经跑过的结果。只选择候选实际提供、自己又确实需要的能力；没有某项能力不自动代表产品较差。

| 检查点 | 怎样验证 | 通过标准 | 适用例子 |
|---|---|---|---|
| 版本与有效权限 | 记录版本、入口、安装方式和实际生效策略，尝试受限操作 | 行为与配置一致，不靠旧默认值印象 | Claude Code、Codex、Step、Grok、IDE Agent |
| 模型和账单 | 核对实际模型 ID、地区、服务地址及服务侧用量 | 额度和计费渠道一致，界面估算与真实账单分开 | 原生订阅、BYOK、平台路由、Step Plan |
| 工具完整往返 | 读取、修改、执行检查，再故意提供一次无效输入 | 错误可解释，能够纠正，工具结果没有断链 | 所有执行型代理 |
| 多模态输入 | 使用已知内容的图片或其他支持附件 | 实际上传成功，不把模型能力当客户端能力 | Gemini、GPT、Step 等模型与相应入口 |
| 窗口与压缩 | 核对上下文、输出限制和实际压缩行为 | 保留关键约束，不悄悄沿用旧型号窗口 | Kimi、OpenCode、Step、自定义 Provider |
| 中断与恢复 | 留下进度、失败原因和不能重复的动作，退出后继续 | 不重做有副作用的动作，能核对真实文件与外部状态 | Codex、Pi、MiMo、Hermes、目标型产品 |
| 子代理与团队 | 两个独立调查，再测试取消、目录及用量 | 状态可跟踪，权限正确，集成与总费用可解释 | Cline Teams、Factory、Qwen、Step、OmO |
| 安装包与实验能力 | 核对构建、依赖、注册和功能开关 | 不支持时明确识别，不能将源码存在视为启用 | 原生模块、脚本编排、后台代理、ACP 后端 |
| 长期目标 | 暂停、继续、修改目标和结束 | 停止条件有效，最终成果另有检查 | ZCode、Step、任务型平台 |
| 触发与长期在线 | 停止进程、恢复服务、重复触发同一任务 | 明确是否继续、是否重试、是否重复写入 | n8n、Hermes、OpenClaw、本机定时能力 |
| 知识与记忆 | 更新一项事实，重新提问并检查来源 | 旧信息能纠正，资料不足能说明，权限范围正确 | AnythingLLM、Open WebUI、Hermes、Chatbox |
| 交付与迁出 | 打开文件、检查 PR 或测试发布样例，再导出配置 | 产物可用，退出方案清楚，托管范围符合需求 | Replit、StepPage、Copilot、桌面工作台 |

公平比较有两条路线：研究模型时尽量固定 Harness、工具和材料；研究完整产品时允许各自使用原生组合，但同时记录费用、环境和人工介入。比如在同一 OpenCode 中比较 Claude 与 Step，回答的是模型适配问题；比较 Claude Code、Step Code 与 Codex 的原生组合，回答的是整套产品是否适合工作。两类结果应分开保存。
