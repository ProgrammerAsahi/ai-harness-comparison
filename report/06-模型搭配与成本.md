# 06｜模型搭配与成本：选对组合，而不是背一张永久排名

模型目录变化很快。本章型号依据 **2026 年 9 月 22 日** 可读取的官方文档；它们用于说明当前候选，不是永久有效的安装清单。产品界面、地区、账户和 Provider 都可能限制可用型号。

本报告没有购买各家 API 跑统一基准，因此推荐的准确含义是“依据公开适配和任务特征，值得优先试用”。厂商自报成绩只用于了解定位，不用于证明跨产品冠军。

## 6.1 三种搭配证据，强度不同

| 标记 | 依据 | 怎样理解 |
|---|---|---|
| 原生组合 | 模型厂商自己的 Harness，或明确的专门适配 | 通常是最容易建立可工作基线的起点 |
| 官方支持 | 产品文档明确列出 Provider／模型／协议 | 证明有支持路径，不证明每个任务质量相同 |
| 选型推断 | 根据任务、工具与上下文特征提出 | 必须以自己的任务验证，不能冒充实测结论 |

例如 Claude Code＋Claude、Codex＋GPT、Kimi Code＋Kimi 属于原生路线；OpenCode／Cline＋某个目录内模型属于官方支持路线；“用经济型号做摘要，用强型号判断架构”则是工作分配建议。

## 6.2 当前主要模型家族与适合先尝试的角色

| Anthropic：Sonnet 5、Opus 系列、Fable 5.1 | Claude Code；Cursor／Cline／Factory 等已适配入口 | Sonnet 日常；更强 Opus／Fable 候选用于高难任务 | `opus` 别名、版本要求、云供应商映射和 Fable 访问条件不同 |
| Google：Gemini 3.8 Flash、3.1 Pro 等 | Gemini CLI、Antigravity；已支持的多模型产品 | Flash 快速任务；Pro 复杂资料和推理候选 | 预览与正式版、工具和地区可用性分别看 |

| MiMo：V2.5／V2.5-Pro | MiMo Code；已适配的多 Provider 产品 | 原生编程与代理任务、开放模型研究 | 更晚的受限预览不能当作人人已可用 |

### 型号名为什么容易误导

`sonnet`、`opus`、`kimi-for-coding`、`deepseek-flash` 可能是别名。别名让用户自动获得新版本，但降低了实验可重复性。当前 Claude Code 文档甚至按 Provider 列出不同映射；DeepSeek 文档说明部分旧型号名称仍被接受，实际已路由到新模型。

因此在调试或比较时，应保存四项：**Harness 版本、Provider、实际模型 ID／版本、请求参数**。只写“用了 GPT”或“用了 Claude”几乎没有比较价值。[Claude 映射](https://code.claude.com/docs/en/model-config.md)、[DeepSeek 别名](https://api-docs.deepseek.com/quick_start/pricing/)

## 6.3 怎样判断模型适不适合某个 Harness

按这个顺序检查，比一次跑一个庞大任务更有效：

1. **基础输入输出。** 中文、代码、文件片段是否正常；需要图像时，实际请求有没有把图像发送给支持图像的模型。
2. **工具往返。** 能否正确调用一个只读工具，读取结果，再作下一步决定。
3. **编辑与验证。** 能否按该工具要求修改文件，并用正确命令验证。
4. **错误恢复。** 文件不存在、命令失败、工具参数不合法时，能否根据错误调整，而不是重复同一错误。
5. **历史与压缩。** 会话变长或恢复后，是否记得关键约束；工具调用与结果有没有失配。
6. **控制与成本。** 中断能否生效；子任务是否继续烧费；模型窗口、输出上限与 Harness 的估算是否一致。

某些模型需要保留推理状态、签名或特定响应字段。网关如果只转发文本，看起来仍能聊天，却可能破坏长任务。也有服务仅在协议表面兼容，实际不支持某些参数。遇到这种问题应先核对适配层，而不是立即认定模型“变笨”。

## 6.4 开放权重与本地模型：适合什么，不适合什么

本地模型的主要收益是数据路径控制、可定制与不依赖外部推理服务。它并不天然更便宜或更快，尤其是在硬件已经不足、任务又需要很多重试时。

| 已有官方模型卡的候选 | 可搭配的路线 | 本报告建议的初始任务 | 验证重点 |
|---|---|---|---|
| Qwen3-Coder-30B-A3B-Instruct | Qwen Code／OpenCode／Pi＋正确配置的本地服务 | 局部代码问答、小修复、可验收脚本 | 工具模板、上下文、格式和修改正确性 |
| Qwen3.5-27B | Open WebUI／AnythingLLM／Chatbox／Cherry＋本地服务 | 中文资料整理、短报告、检索后的问答 | 中文事实准确性、量化损失、检索质量与速度 |
| gpt-oss-20b | 支持对应格式的本地推理服务＋兼容 Harness | 结构化推理、短工具任务、对照实验 | 服务端格式与工具适配，中文任务另测 |
| 更大型开放模型 | 具备资源的组织推理平台 | 经过容量规划的团队任务 | 权重许可、显存、并发、上下文缓存和运维 |

来源：[Qwen Coder 模型卡](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct/raw/main/README.md)、[Qwen3.5-27B](https://huggingface.co/Qwen/Qwen3.5-27B)、[gpt-oss 模型卡](https://huggingface.co/openai/gpt-oss-20b/raw/main/README.md)。这些是可检验的候选，不是本地模型完整排行榜，也不意味着它们是截至当日最新的所有开放模型。

**硬件的一个简单估算。** 如果有 300 亿参数，粗略按每参数 4 bit 保存，仅权重理论下限约为 15 GB。实际还要加上量化元数据、运行缓冲、上下文缓存等，不能由此推出“16 GB 电脑一定能流畅运行”。不同架构和推理引擎也会改变实际需求。

MoE 模型每步只激活一部分参数，主要影响计算量；不能仅按活跃参数估计全部权重占用。上下文越长、并发越多，也可能越吃内存。先用短上下文测实际资源，再逐步扩展。

**完全本地需要整条链都本地。** 回答模型、嵌入模型、文档解析、搜索、语音、工具与日志都可能是独立服务。尤其知识库工具即使用本地回答模型，也可能仍把文档发给云端嵌入接口。

## 6.5 成本要按“完成一项可接受的任务”来算

一个实用的成本拆解是：

> 总开销 ≈ 订阅与平台费用＋模型输入输出费用＋缓存相关费用＋工具调用费用＋执行环境费用＋人工检查和返工。

同样一次“帮我修 bug”，背后可能调用几十次模型；子代理、摘要、标题生成、检索和重试都可能增加消耗。并行让等待缩短，不会自动让所有分支只收一份费用。

| 表面上很便宜 | 可能遗漏的开销 |
|---|---|
| 模型 Token 单价低 | 失败重试、上下文重复传输、需要更长输出 |
| Harness 免费或源码开放 | 模型 API、机器、网关、连接器和维护时间 |
| 已有某家聊天订阅 | API 未必包含在订阅里；第三方接入资格也可能不同 |
| BYOK | 平台部分能力可能仍另外收费，辅助模型可能不走自己的 Key |
| 本地模型不要 API 费 | 硬件、能源、部署与速度损失 |
| 多代理完成得快 | 总调用量、重复调查与合并成本 |

Qoder 的 Repo Wiki 单独计费就是一个具体例子：主对话使用 BYOK，不代表产品里的所有模型能力都改走同一账户。Factory 文档又说明不同入口对 BYOK 的支持范围不同。因此应读到功能级别，不能只看产品首页的一个词。[Qoder](https://docs.qoder.com/qoder/custom-models.md)、[Factory](https://docs.factory.ai/model-independence/byok.md)

### 缓存与压缩也有取舍

模型服务可能对重复输入提供缓存优惠。稳定的项目规则与工具列表有利于复用；频繁修改系统提示、切模型或更换工具集合，可能降低命中。另一方面，为了缓存而保留大量无关历史，也可能让任务更难理解。

压缩通常需要额外模型调用，且可能丢信息。合理目标是保留足够准确的任务状态，而不是让 Token 指示器始终最低。某次压缩少花了一点钱，却导致代理重做整个调查，整体并不划算。

## 6.6 订阅、API 与网关：使用前把钱和数据的路径画清楚

| 接入方式 | 谁提供模型 | 谁向你计费 | 需要确认什么 |
|---|---|---|---|
| 产品内置订阅／额度 | 平台选择或转售的模型 | 产品平台 | 包含哪些入口、模型、上限和额外费用 |
| 官方 API Key | 模型厂商 | 模型厂商，可能另有平台费 | 模型权限、余额、地域和数据设置 |
| 第三方网关 | 网关路由到上游 | 网关，可能加价或另有规则 | 实际模型、日志、协议转换、失败处理 |
| 本地／内网服务 | 自己部署的模型 | 硬件与运维资源 | 模型格式、版本、许可、容量和出口 |

优先使用产品官方支持的认证方式。不要因为某个不明插件声称能共用订阅，就默认它受到模型厂商支持；也不要将账户凭据交给未经核实的中间服务。

## 6.7 一个简单的升级策略

先用中等档位完成普通任务；若失败，要求代理说明证据和卡点。只有确实需要更复杂推理、更长资料理解或更稳定工具使用时，才升级模型。机械批处理先用小样评估经济模型，达到标准后再放大。

对重要任务，可以让第二个模型或独立代理审查，但它必须查看原始材料与实际结果。只让另一个模型阅读第一份答案，容易变成互相认可，而不是独立验证。

模型升级是解决问题的一条路径；更好的输入、项目说明、工具、检索和验收，常常同样重要。
