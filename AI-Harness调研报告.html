从零理解：模型、Agent 与 Harness

本报告以 2026 年 9 月 22 日的公开资料为观察截面。建议先读本章，再看工具地图；已经有使用经验的读者，可以直接查工具档案和场景推荐。

先用一个例子讲清楚

你对 AI 说：“这个网站的登录有问题，帮我修好。”

普通聊天模型可以给出建议。但是，真正修好网站通常需要先读项目文件，找到登录逻辑，复现问题，修改代码，运行测试，最后解释改了什么。完成这些工作，需要有软件负责把模型和文件、终端、浏览器连接起来，并决定它可以做什么、做到哪一步需要停下来。

这套软件就是我们讨论的 Harness。中文可以理解为“让模型实际干活的运行外壳”。“外壳”并不意味着简单：成熟的 Harness 往往承担了整个工作现场的组织工作。

模型像有能力的工作人员；工具像电脑、文件柜和仪器；Harness 像工作台、流程和权限制度。把它们组合起来，才形成一个可以观察环境、采取行动、根据结果继续行动的 Agent（智能代理）。

这个比喻有一个边界：模型并不是可靠的人类员工。它可能误解任务，遗漏条件，甚至把一份看起来很完整的结果误认为正确。所以，还需要测试、来源核对、差异审查等验收办法。

Agent 模型通过 Harness 使用工具，反复行动以完成任务的系统 不是某一种模型，也不等于一个聊天窗口
Agent loop，代理循环 “看情况→想下一步→调用工具→看结果”的循环 能否恢复、停止、纠错，比能否发起第一轮调用更重要
工具调用，Tool calling 模型提出结构化请求，例如读取文件或执行测试 模型提出请求，真正执行的是软件；权限必须由软件控制
上下文，Context 本轮实际交给模型看的资料 保存在磁盘上的文件、全部聊天记录，不一定都在上下文里
上下文窗口 模型一次能接收的资料上限 窗口大不等于它能同样可靠地使用其中每个细节
Token 模型处理文本时使用的小单位，可能是一个字、词或词的一部分 用量、价格和上下文长度通常按它计；不能简单等同于汉字数
系统提示词，System prompt 给模型的基础工作要求 同一个模型在不同外壳里的行为差异，部分来自这里
规则文件 项目里写给代理看的说明，如 AGENTS.md、CLAUDE.md 适合保存测试命令、项目约定；它不是强制执行的安全边界
会话，Session / Thread 一段可继续、保存和恢复的任务对话 “能找回记录”和“恢复后完整理解之前的工作”是两件事
上下文压缩，Compaction 把长对话整理成较短内容，腾出继续工作的空间 通常会丢细节；要关注保存了哪些决定和未完成事项
检索，Retrieval 从大量资料中找到本次需要的一部分 好比先查目录再翻书，而不是把整间图书馆搬上桌
RAG 先检索资料，再让模型根据资料回答 适合知识库问答；检索错了，回答仍可能错
Embedding，向量表示 把文字转成可用于比较相似程度的数字 常用于语义搜索；不是普通聊天模型的替代品
Reranker，重排模型 再检查搜索结果，把更相关的排到前面 资料多时，改善找资料可能比升级回答模型更有效
记忆，Memory 跨轮次或跨会话保留的事实、偏好和经验 可以是文件、数据库或检索系统，并不等于模型被重新训练
Skill，技能 一份可重复使用的工作说明，有时附带脚本、模板 比如“按公司格式写周报”；通常仍需要模型解释和执行
Plugin / Extension，插件／扩展 为宿主增加能力的一种安装和集成方式 有的只增加提示词，有的能运行程序，两者风险和能力不同
MCP 让代理连接外部工具和数据源的一种通用协议 像工具插座；支持插座并不表示已经安装了所有工具
ACP 让编辑器或界面连接一个完整代理的协议 MCP 常连接“工具”，ACP 常连接“另一个已经会干活的代理”
API / Provider 模型服务接口／提供该接口的服务商 同一个模型可能由多家平台提供，速度、价格和功能支持可能不同
BYOK Bring Your Own Key，自带服务商 API 密钥 外壳费用和模型费用可能分开；订阅会员通常不自动等于 API 额度
OpenAI-compatible 接口模仿 OpenAI 的部分格式 不能据此推断所有工具调用、图片、推理状态和缓存都兼容
子代理，Subagent 主代理委派出去处理一部分工作的代理 通常有独立上下文；是否能写文件、继续对话、再派任务，各工具不同
多代理，Multi-agent 多个代理共同完成工作 可能只是几个并列聊天，也可能有任务板、消息和调度，不能混为一谈
编排，Orchestration 安排谁先做、谁并行做、结果交给谁 工作拆得合理时有效，拆得不合理会增加协调和返工
Checkpoint，检查点 保存某个阶段的状态或文件版本 要查清楚保存的是对话、代码还是运行环境；未必都能恢复
Git / Diff / PR 代码版本管理／修改前后差异／请求合并代码的审查单 是检查代理修改和撤销错误的重要手段
Worktree 同一个代码仓库的另一份独立工作目录 有助于让并行代理不直接争改同一份文件；不是操作系统沙箱
Sandbox，沙箱 用操作系统、容器或虚拟机限制程序可接触的资源 和“模型答应不乱改”“每次点批准”不同，属于实际执行边界
审批，Approval 对某次操作询问是否允许 能增加控制，但点过一次批准不代表之后所有操作都安全
Hook，钩子 在特定时机自动执行的程序或规则 可以在改文件前后检查、记录、阻止操作；具体能力看宿主实现
CLI / TUI 命令行程序／带交互界面的终端程序 适合熟悉终端的人，也容易接入脚本
IDE 集成开发环境，写代码、运行和调试的一体化软件 能把当前文件、报错和项目结构自然交给代理
LSP 编辑器与语言分析服务之间的协议 帮助查符号、类型和错误；不等于理解整个业务
Headless 不打开交互界面，直接从脚本执行 适合批处理和流水线，要另行处理权限、日志和失败
本地运行 Harness 或工具程序运行在自己的电脑上 不代表推理也在本地；调用云模型时相关输入仍会发到服务商
本地模型 模型推理在自己的设备或受控服务器上进行 有硬件和运维要求，尤其不能把超大开放权重模型理解为笔记本可运行
开放权重 可以获得模型参数文件 不等于训练数据公开，也不等于没有使用许可限制
开源／源码可见 前者通常符合开源许可；后者只是能读到源码 商业使用、再分发和做竞争服务的权利可能不同
Benchmark，基准测试 用一组规定任务测系统表现 分数属于“模型＋外壳＋设置＋环境”的组合，不能随意移植
缓存，Cache 重复输入的一部分无需重新完整处理 常影响成本和延迟；频繁换模型或改提示词可能损失缓存
长任务，Long-horizon task 需要很多轮行动、甚至跨会话才能完成的任务 核心问题是状态、目标、恢复和验收，不只是上下文够不够长
SDK 给开发者调用的一组现成程序接口 用它把代理嵌入自己的应用，比从零实现整套循环省事
Runtime，运行时 真正管理代理执行的程序部分 界面相同，运行时仍可能不同
Adapter / Driver，适配器／驱动 把一种模型或代理转换成宿主能理解的接口 协议、工具和状态能否正确衔接，常取决于它
Gateway，网关 位于客户端和后端之间，管理连接、路由或访问的服务 要看它是否保存数据，以及真正把请求发给谁
Profile，配置档案 一组模型、工具、权限或插件的预设 两个人用同一产品、不同配置档案，行为仍可能差很多
Markdown / JSON / TOML 常见的文档／结构化数据／配置文件格式 规则、会话和设置常用这些格式保存，不是新的模型类型
Python / TypeScript / Rust / Go / Lua 编写软件的不同编程语言 能帮助开发者理解源码组织；语言本身不决定代理聪明程度
Node.js / Electron / QuickJS 分别是常用 JavaScript 运行环境、桌面应用框架、另一种 JavaScript 引擎 “脚本引擎被限制”不等于它调用的外部工具也被隔离
Docker / Kubernetes / 虚拟机 容器打包工具／容器管理平台／虚拟的计算机环境 用来准备、隔离和管理任务运行环境，仍需配置权限与网络
CI / CD 自动检查、构建和交付软件的流水线 无界面代理可以进入流水线，但需要失败与验收机制
Webhook 某个系统发生事件后，向另一个系统发通知的接口 可用来自动触发任务，需要辨认事件来源和避免重复执行
RBAC 按角色给用户分配权限 多人工作台需要控制谁能读资料、用工具和改设置
MoE，混合专家模型 每一步只选择部分子网络参与计算的模型结构 活跃参数较少，不等于只需存放那部分权重
量化，Quantization 用更少的数字位数保存模型参数等数据 可减少内存，但效果与速度需按具体实现测试

一次任务究竟经过哪些地方

比如修登录问题时，“测试失败”是工具返回的事实；“可能是登录令牌过期”是模型的判断；“运行这条测试命令是否允许”是 Harness 的职责。分清这三层，才能找到出问题的原因。

同样的模型接到不同 Harness 上，可能看到不同文件、拿到不同工具、收到不同错误反馈，最终表现自然会不同。反过来，即便 Harness 很完善，模型如果不善于遵守工具格式、理解反馈或识别任务完成条件，也仍会卡住。

六个最容易误解的地方

第一，能聊天、能调用一个工具、能持续完成任务，是不同层次。 聊天客户端也能增加 Agent 能力，但需要检查实际执行、状态管理和验收方式；不能只凭产品分类判断“它什么都做不了”。

第二，长上下文不等于长期记忆。 一百万 Token 的窗口仍然有限，而且保留大量历史会增加成本。把关键决定写进项目文件，往往比永远延长聊天更可靠。

第三，多代理不保证更强。 两个人同时调查不同模块可能节约时间；两个人同时重写同一个函数，可能只是制造冲突。判断标准是任务能否独立、结果能否检查。

第四，本地客户端不等于数据不出电脑。 要分别看聊天记录放在哪里、模型在哪里推理、文件如何检索、外部工具由谁执行。

第五，模型能接通不等于适配完成。 接口正确只是第一步。工具参数、错误处理、长对话恢复、图片输入和模型特有的推理状态，都可能影响后续执行。

第六，“自我改进”通常不是训练模型。 在本报告涉及的软件里，它经常指保存经验、编写技能、更新记忆和调整工作流程。模型参数是否改变，是另一件事。

这些解释是本报告的分析框架。对应实现可在 工具档案、架构比较 以及 证据与方法 中核查。

03A｜终端与开放编程代理：从“帮我改一下”到可编排的执行系统

这里的“终端”指主要交互入口，不代表只能在黑色命令行窗口里使用。同一套执行引擎，可能同时服务终端、编辑器、桌面应用和自动化任务。读这一章时，重点看：谁负责组织工作，任务状态怎样保存，工具怎样执行，以及模型能否真正换得动。

本章的模型建议分两种：原生优先表示官方围绕该模型生态提供了直接支持；选型建议表示依据架构和任务提出的试用方案，并非本报告实测出的胜者。型号、权限和订阅差异集中见第六章。难度是作者对安装、配置、运维负担的判断，不是测量成绩。

A01 Claude Code：让强模型直接操作开发环境

定位与理念。 Claude Code 把开发看成一个持续循环：读资料、采取行动、观察结果，再决定下一步。它不像固定流水线那样要求用户事先画好每一步，更依赖模型自己找文件、使用终端、修改代码和验证。它的优势来自 Claude 模型、工具描述、提示和运行环境的配合，而不仅是一个聊天窗口。工作原理

架构怎么理解。 可以把它看成“主对话＋工具执行层＋可插拔工作规范”。项目说明、记忆、Skills 为模型补充做事方法；Hooks 在确定的生命周期节点执行程序；MCP 接入外部工具；子代理拥有独立上下文，完成局部任务后交回结果。Skills 更像工作手册，子代理则像另开一张办公桌，两者不应混为一谈。记忆、子代理、Hooks

它也有 Agent Teams，但团队协作与普通子代理不是同一个功能开关。是否启用、可用界面、并行开销和任务边界都要单独确认。权限审批负责决定能不能做；沙箱进一步限制命令实际接触的文件和网络。允许一次命令，并不等于让全部后续动作永久放行。团队、沙箱

源码边界。 官方 GitHub 仓库可用于查看 README、扩展、发布和问题记录，但不能据此声称已经审计完整的商业运行时。本报告对其内部架构的描述以官方公开行为和接口为边界。官方仓库

怎样上手。 按官方安装页安装，在项目目录运行 claude，先让它解释项目与测试方法，再给一个有明确验收标准的小任务。将稳定的项目约定写进 CLAUDE.md，需要反复执行的方法做成 Skill。首次使用保留审批，熟悉后再按工具、目录和命令缩小授权范围。不要一开始把所有插件都装进去。

模型与适用方向。 原生优先 Claude。当前官方直连别名中，Sonnet 5 适合作为日常起点；复杂设计和长任务再试账户可用的 Opus 或 Fable。不同云供应商的同名别名可能落到不同版本，因此应记录实际模型 ID。适合跨文件修复、项目探索、测试驱动的实现，也能处理目录中的文档和资料。若主要诉求是随意更换各家模型，应优先比较 OpenCode、Pi、Kilo。上手难度：中；深度扩展：中高。模型配置

A02 Codex：把任务、执行环境和审查组织成一套系统

定位与理念。 Codex 的关键不只是生成补丁，而是让代理在明确工作空间中持续执行任务，留下可审查的变更。CLI、编辑器和桌面入口可以提供不同交互方式；不能因为名称相同，就假定每个入口拥有完全一样的功能、模型和权限设置。CLI、工作树

源码揭示的结构。 当前公开核心以 Rust 为主。codex-rs/core 放可复用业务逻辑，app-server 通过结构化协议把任务、回合和输出事件交给界面。通俗地说，界面负责“怎样看和怎样点”，核心负责“任务到底跑到了哪里”。这使桌面交互、自动化客户端和执行逻辑可以分开演进。核心说明、app-server

权限也不是一串提示词。源码将沙箱策略选择、命令转换和执行请求衔接起来；子代理创建时处理父级与请求权限的有效边界，并管理运行容量。其含义是：一个子代理不该因为“另起了会话”就自动获得比父任务更大的权限。具体平台使用的沙箱实现有所不同，部署时要看对应系统说明。沙箱适配、子代理创建

上下文与分工。 AGENTS.md、Skills、记忆与历史压缩分别解决项目规则、可复用方法、跨任务信息和当前窗口容量问题。压缩有本地／远端处理路径，不等于原始文件消失。工作树能够减少并行改代码时的文件冲突，但最后仍要集成、检查测试和审阅变更。压缩实现、自定义、子代理文档

怎样上手。 在应用中打开仓库，或安装 CLI 后在项目目录运行 codex；先检查工作目录、模型和执行权限。用“重现问题→提出原因→修改→运行相关检查→解释 diff”的完整任务开始。稳定规则放进 AGENTS.md，多个独立改动再考虑独立工作树。不要把某个桌面版本的按钮名当成所有部署都适用的命令。

模型与适用方向。 原生优先当前官方 GPT 系列：日常先试 GPT-5.6 Terra，重复且容易验收的任务试 Luna，较深推理和成品质量需求试 Sol，最复杂的长任务试 GPT-6 Astra。选择必须以所在产品实际开放的模型为准。自定义 Provider 可以接入其他服务，但“接口能调用”不等于工具格式、推理状态和长任务行为已经同等优化。适合完整功能实现、迁移、复杂调试、需要反复运行验证的任务。上手难度：中；工作树和自动化管理：中高。模型说明、配置

A03 Gemini CLI：把 Google 模型和检索能力带进终端

定位与理念。 Gemini CLI 是开放的终端代理，面向 Gemini 生态。适合希望保留命令行工作习惯，又需要联网查资料、多模态输入和项目操作的用户。Google 账户、API Key、Vertex AI 等接入方式对应的计费、限额和组织管理方式不同，不能统一概括为“免费无限用”。项目说明

源码结构。 核心客户端处理对话和模型流，调度器处理工具批次、策略判断、审批和执行状态。模型说“执行这个工具”和工具真的执行，中间隔着一个明确的调度层。例如工具策略可以直接拒绝，也可以转入询问，正在运行的批次还会影响后续队列。客户端、调度器

这类分层的价值在于，终端界面不需要自己理解每一种工具的全部生命周期。项目上下文、扩展、MCP 和权限机制则围绕这条执行链提供能力。它仍然是能操作环境的代理，不是把 Google 搜索结果拼进聊天框那么简单。

怎样上手。 按官方说明安装 @google/gemini-cli，进入项目运行 gemini，选择认证方式；用 GEMINI.md 写项目规则。先验证文件读取、命令执行、模型选择和联网工具是否按预期工作，再添加扩展。只有确实需要访问浏览器或其他业务系统时，才接入相应工具。

模型与适用方向。 原生优先 Gemini。当前官方目录中的 Gemini 3.8 Flash 可作为快速任务候选，复杂任务比较账户可用的 Pro 型号，例如 3.1 Pro Preview；预览型号要单列记录。适合带检索的开发、资料到代码的转换、图片辅助理解，以及 Google Cloud 生态。若核心需求是跨厂商随时替换，OpenCode／Qwen Code 的入口通常更直接。上手难度：中。当前 Gemini 模型

A04 Qwen Code：在熟悉的终端代理结构上扩大模型与渠道覆盖

定位与理念。 Qwen Code 既服务 Qwen 生态，也重视多协议接入。当前版本已不宜只用“Gemini CLI 的中文分支”概括：历史来源解释了部分结构，但现有模型配置、团队功能和入口已经继续演化。README

架构与特色。 模型客户端中可以看到压缩、上下文精简和目标预算相关逻辑；代理工具则把子任务的生命周期、权限、会话和工作目录纳入管理。它不是简单将请求中的模型名替换成 Qwen。客户端

一个有代表性的源码细节是：某些 shell 沙箱环境只允许在同一工作空间内运行子代理，工作树、另选工作目录和队友功能会受到限制；前台子代理也需要处理父任务取消的向下传播。由此可见，宣传页上的“支持子代理”“支持沙箱”，并不保证两者在每一种组合中完全可用。代理工具

怎样上手。 按官方文档安装并运行 qwen，通过认证配置选择 Qwen 或其他支持的 Provider。先设项目规则和模型，再开长任务、记忆或团队功能。接本地 Ollama／vLLM 时，除了地址，还要核实模型实际上下文、工具调用格式和服务端模板；服务启动成功只是第一步。文档仓库

模型与适用方向。 原生优先 Qwen 的编程／推理模型，当前服务目录包括 Qwen3.8 系列；跨厂商接入以文档支持的协议为准。若重视开放权重和本地试验，可测试 Qwen3-Coder-30B-A3B-Instruct 这类有官方模型卡的模型，但不要期待小模型承担和最大云端模型一样的长链条任务。适合中文开发协作、多协议部署、国内服务接入和本地模型探索。难度：中；自建推理服务：高。Qwen 模型目录、本地候选模型卡

A05 Kimi Code：围绕 Kimi 的长任务体验重新组织执行核心

先辨认项目。 本报告使用的是 MoonshotAI/kimi-code。旧 kimi-cli 的架构介绍不能直接套到新代码。当前仓库是 TypeScript 多包结构，agent-core-v2 是需要重点看的执行核心；发布的独立程序也不意味着用户必须先搭建 Node 开发环境。当前仓库

设计重心。 Kimi Code 将终端任务、编辑器连接、工具和独立子任务组合起来。ACP 让编辑器可以接入同一类代理会话，插件与 Hooks 扩展行为，不同子代理承担探索、规划和实现。它更接近一套完整开发助手，而不是模型 API 的薄转发层。

源码中的关键点。 历史压缩根据上下文预算触发，并为下一步留出空间；压缩边界还要避开没有完成的工具交换。为什么要这样做？如果只留下“调用工具”的消息，却丢掉对应结果，下一轮模型会看到一段断裂的对话。长上下文管理首先是状态正确性问题，然后才是节省 Token。压缩策略、模型请求层

怎样上手。 安装当前 Kimi Code，运行 kimi，使用 /login 和 /model 完成登录、模型选择。需要在支持的编辑器中使用时，按 ACP 文档配置 kimi acp。先让它处理可验收的小模块，再引入项目指令、插件和独立探索代理。自定义 Provider 时检查协议和模型能力，而不只填入一个名字。Provider 配置

模型与适用方向。 原生优先 Kimi。当前文档区分 K3 的不同上下文档位；kimi-for-coding 别名目前指向 K2.8 Preview，不能把这个别名永久当作某个固定旧版本。复杂、资料量大的任务可先试可用的 K3，日常工作比较 K2.8 路线。适合中文项目沟通、长资料辅助开发和 Kimi 订阅用户。上手难度：中。模型说明、更新记录

A06 MiMo Code：按模型家族调整工具，而非假定所有模型用同一套手势

定位与理念。 MiMo Code 继承了可辨认的 OpenCode 结构，同时加入自己的模型适配、记忆和任务模式。最值得关注的不是支持多少模型，而是承认：不同模型训练时学会的工具习惯可能不同，运行时需要据此调整。README

深入看架构。 其 Codex microkernel 文档描述了面向 GPT 系列的工具接口组织：终端、补丁、图像以及可编程调用能力分别承担不同职责。这里的“微内核”是一种架构比喻，并不是说它变成了操作系统内核。QuickJS 中的脚本没有直接获得 Node、进程和网络能力，但它调用到的宿主工具仍然需要权限管理；尤其不能把“JavaScript 被隔离”误读为“终端命令也被系统沙箱隔离”。架构说明、工具注册

长任务怎么保留状态。 当前设计包含跨会话记忆、检索和检查点文件，试图把目标、进展、约束保存成下一次可重新装载的材料。相较只留一句“之前我们讨论了登录功能”，这种方式更适合恢复“测试失败在哪里、哪些文件已经改过、下一步是什么”。但能恢复多少仍取决于写入内容和检索命中，不能保证毫无遗漏。README、压缩实现

怎样上手。 按官方指引安装 @mimo-ai/cli 并运行 mimo。先熟悉 Build／Plan；Compose 具有独立的模式约束，不宜在不了解工具变化的情况下频繁切换。让它先列出计划和验收，再实施一个小任务；查看它写出的进度、记忆与检查点是否准确。

模型与适用方向。 原生优先 MiMo-V2.5 系列；较复杂代理任务可试 Pro。仓库也为 GPT 等模型做了专门适配，因此跨模型使用比单纯“兼容接口”更有研究价值，但本报告没有证明它在 GPT 上优于 Codex。MiMo-X 等受限预览与公开可用模型要分开看。适合愿意尝试模型特定工具配置、持久任务状态的开发者。难度：中；理解模式和适配细节：中高。模型发布说明

A07 DeepSeek Harness：把代理循环本身也做成可替换部件

身份与成熟度。 这是 DeepSeek 官方 deepseek-ai/deepseek-harness 项目，而非仅仅给第三方壳换一个名字。当前仍标为开发者预览。关注度高说明值得研究，不代表接口已经稳定，或适合立即承担所有生产任务。仓库、产品说明

设计理念。 DSH 的中心思想是“连引擎也可以替换”。借助插件系统，模型、工具、会话存储、沙箱、代理循环以及界面被组织为可组合服务。Profile 决定装配哪些部件，再由配置层叠加修改。它既能成为终端／Web 产品，也能作为开发者搭建新代理的基础。架构文档

状态是怎么保存的。 会话事件日志是核心依据，模型看到的历史由日志推导出来。这样可以区分模型输出、工具调用、工具结果和失败尝试，也方便重建界面、排查运行过程。但“能回放日志”不等于重新请求模型会得到一模一样的答案，更不等于自动撤销已经发送的邮件或修改过的外部数据库。默认循环

工具与子代理。 源码将必须独占的工具调用作为执行屏障，其他调用进入有界并行队列；即便工具并发执行，也要维持可理解的结果顺序。子代理又是一条可替换接缝，后端可采用内部会话、ACP 或其他代理系统；不具备的能力应明确拒绝，而不是假装实现。其开放性比“支持某个固定子代理按钮”更深，但集成测试负担也随之增加。工具执行、子代理后端

怎样上手。 官方入口之一是 npx @deepseek-ai/dsh web。先运行标准 Profile，再查看配置和已启用插件；需要理解装配结果时使用文档中的配置导出能力。只有标准模式跑稳后，再尝试 Code／Minimal／Creator 等模式或替换代理循环。预览项目应固定版本，保存可工作的配置。

模型与适用方向。 原生优先当前 DeepSeek API 模型，例如 deepseek-flash 对应的 V4.1 Flash 路线，以及适合更重任务的 Pro 路线；具体映射应当天核实。选型上更适合代理研发、需要可替换执行层的团队，以及愿意承担预览变动的高级用户。普通日常开发可以试，但不应仅凭 GitHub 星数取代成熟流程。难度：标准使用中；开发新 Harness 高。API 模型目录

A08 OpenCode：把模型和界面选择权留给使用者

定位与理念。 OpenCode 的重点是开放、多 Provider 和多入口。模型服务、终端／桌面界面、会话和工具执行并非全部绑在一个厂商订阅里。它适合已经有 API 账户、想比较不同模型，又不愿为每个模型重学一套工具的用户。README

源码结构。 当前代码包括独立核心包以及会话、模型、权限、插件和快照服务。会话处理器将模型流转成消息与工具事件；还会在适当阶段准备快照。源码专门处理“工具可能早于某个流事件开始执行”的顺序问题，这说明保存状态不能只靠界面上看到的输出顺序。会话处理器

上下文与分工。 压缩不仅生成摘要，还涉及保留近期内容的预算、模型限制和大型附件溢出处理。任务工具创建独立子会话，并派生权限和模型设置。当前后台子代理还存在实验开关与深度限制；不要把源码中存在一条路径写成所有版本默认可用。压缩、任务工具

怎样上手。 安装后在仓库运行 opencode，连接 Provider，选择模型，先用 Plan 分析，再用 Build 实施。将项目约定放入文档支持的指令文件，按需接 LSP、MCP 和插件。切换模型后做一次最小工具测试，确认读文件、改文件、命令执行、恢复历史都正常。

模型与适用方向。 选型建议：在当前 Provider 确认支持的前提下，以 Sonnet 5／GPT-5.6 Terra 作为日常候选，复杂任务上探 Sol／Astra 或更强 Claude；重视成本与中文服务时比较 DeepSeek、Qwen、Kimi。模型广泛可接入是自由度，不是全部组合都同样可靠的保证。适合跨模型比较、个人开发、开放工作流和自定义扩展。难度：中；插件多了以后是中高。

A09 Pi：保留一个可理解的核心，把特殊需求交给扩展

定位与理念。 Pi 当前仓库迁至 earendil-works/pi。它吸引人的地方是执行核心、模型接口、终端交互和扩展边界相对清晰。使用者既可以直接编码，也可以把它当成搭建自己代理的材料。README

源码里的循环。 agent-loop.ts 将代理上下文转换成模型输入，处理工具结果、用户中途追加的引导和后续消息；准备下一回合时可以调整上下文、模型和推理设置。会话管理器则保留分支、模型变更、压缩等事件。这种设计便于研究“模型到底收到了什么”，也方便把 UI 换掉。代理循环、会话管理

扩展不是只能追加几句提示：它可以注册工具、命令、事件处理、Provider 和界面元素。因此 Pi 的团队、计划或审批体验可能来自扩展，而不是所有安装都自带同一套行为。比较时应写“Pi＋哪些扩展”，否则不是同一个实验对象。扩展文档

一个必须知道的取舍。 Pi README 明确说明默认没有内置权限系统；运行进程拥有启动用户的系统权限。扩展也在 Pi 进程内执行。想把它放进可控边界，应主动选择容器、虚拟机或文档列出的隔离方案，不能把简洁误认为自动安全。README

怎样上手。 使用当前 README 的安装方式，而不要机械照搬旧包名。先运行原生配置，接一个确认支持工具调用的模型，只加入真正需要的扩展。若目标是代理开发，先读 pi-ai → agent-core → coding-agent 的责任分工，再改循环。

模型与适用方向。 选型建议是先选一个能力稳定的云端模型建立基线，再用相同任务比较 DeepSeek／Qwen／Kimi 或本地模型。Pi 的优势在于能控制实验条件，而不是天然让弱模型变强。适合熟练开发者、终端爱好者、代理研究和定制工具；不适合期待完整权限管理开箱即用的初学者。难度：日常中；定制高。

A10 Cline：把过程看得见、能审查作为主要体验

定位与理念。 Cline 重视逐步展示代理在读什么、改什么、运行什么，让用户在编辑器中持续参与。当前产品已有扩展、CLI 和 SDK 等入口，不能只依据早期 VS Code 插件判断整体能力。README

当前分层。 SDK 把代理循环、模型适配和会话／工具基础能力分开。运行时处理模型输出限额、瞬时错误和重试，上下文层处理压缩与预算。这类分工使代理逻辑可以被不同入口复用，但入口是否暴露同一个功能仍是产品问题。代理运行时、压缩管线

“多代理”尤其需要分清。 当前文档中的普通 Subagents 是独立上下文的只读研究代理，适合找文件、查代码并返回报告；不能据此说它们可以任意编辑、浏览器操作或继续嵌套。CLI／SDK／Kanban 的 Agent Teams 则有共享任务板、消息箱和持久任务状态，文档明确说这套团队功能当时还不适用于 VS Code 与 JetBrains 扩展。只读子代理、团队功能

怎样上手。 安装对应编辑器扩展，配置 Provider 和模型，保留重要操作审批；用 Plan 整理思路，再进入执行。若确实需要持续团队任务，另按 CLI 文档使用团队模式，而不要在扩展里找不存在的同等功能。

模型与适用方向。 多模型是其优势。建议先试当前支持的 Sonnet 或 GPT 日常档位；预算敏感时比较 DeepSeek／Qwen。模型必须能稳定处理工具调用和代码编辑。适合希望逐步审阅、学习代码库、修复中小问题的开发者；团队功能适合愿意使用 CLI 的进阶用户。难度：扩展低中；SDK／团队中高。

A11 Kilo Code：围绕开放执行核心提供更多产品化入口

定位与演化。 Kilo 不能只用早期的 Cline／Roo 血缘来说明当前架构。当前仓库中已经有明显的 OpenCode 核心结构以及 Kilo 自己的会话处理层，同时覆盖 CLI、编辑器和云端服务。README、Kilo 会话处理

值得关注的差别。 用户购买的不只是一个本地循环，也可能包括模型入口、远程任务和代码审查等产品能力。相同基础执行结构之上，账户、模型路由、错误恢复、任务管理和界面整合仍能带来明显体验差异。源码中的错误信息与溢出处理也体现了模型服务出错后如何向用户解释、何时先压缩再重试。压缩衔接

怎样上手。 在自己最常用的编辑器或 CLI 中选一个入口，明确使用 Kilo 托管模型还是自己的 Provider，再比较费用和可用模型。先跑一个任务，不必同时启用所有云端服务。需要迁移时，检查规则、凭据、会话历史和模式配置分别如何导出；同源代码不代表这些格式完全兼容。

模型与适用方向。 选型建议：优先从当前 Kilo 模型目录中选择已经完整支持的日常型号，再按复杂度升级；可比较 Claude、GPT、DeepSeek、Qwen 等家族。不要把“模型数量很多”直接当成编程质量证据。适合希望多入口、多模型，又愿意使用统一商业服务的开发者。难度：低中；复杂模型路由与云任务：中高。

A12 Goose：以工具扩展为中心，把编程代理拓展到其他工作

定位与理念。 Goose 源于 Block，当前仓库已转到 aaif-goose/goose。它把外部能力接入放在很重要的位置，适合让代理同时操作代码、数据和业务工具。MCP 扩展在这里不是装饰，而是能力组织的重要方式。README

架构与上下文。 Rust 核心处理模型、会话、工具、权限和子代理等状态。上下文管理采用分层思路：接近限制时先主动压缩；仍溢出时再走后备策略。文档还区分桌面端和 CLI 的可选策略，说明“支持清空、截断、摘要”并不意味着每个界面都提供全部选项。Agent 核心、上下文管理

它也能参与 ACP 集成。需要特别区分“让编辑器驱动 Goose”和“Goose 使用另一个代理作为后端”：前者换交互入口，后者可能连执行逻辑也换掉。评估时必须记录到底是哪一种组合。

怎样上手。 安装桌面端或 CLI，配置一个 Provider，再添加工作真正需要的扩展，例如文件、数据库只读查询或项目工具。先用低风险任务检查工具参数和权限，再扩大自动执行范围。

模型与适用方向。 建议用支持可靠工具调用的 Claude／GPT 建立基线，再比较其他 Provider；任务如果大多是短工具调用，可测试更经济的型号。适合开发加办公、跨系统查资料、团队已有 MCP 服务的工作。优势是扩展空间，代价是连接器和权限需要自己管理。难度：中；企业工具集成高。

A13 Crush：重视终端体验的开放编程伙伴

定位与理念。 Charm 的 Crush 把终端交互质量作为产品的一部分。对于长期使用终端的人，清晰的状态、对话和工具反馈，可能比再增加几十个开关更有价值。README

结构与取舍。 Go 实现的 Coordinator 管理当前代理、模型配置与运行衔接；Agent 层处理消息、工具、队列和自动摘要。源码还区分大模型和小模型配置。这里的小模型可以承担辅助工作，但不能假定主任务成本从此只有“小模型价格”。切换模型也要避免一次运行中状态被拆到两个不同实例。协调器、Agent

怎样上手。 安装 crush，配置 Provider，在项目内启动，逐步加入 LSP、MCP 和规则。以实际终端使用体验判断是否合适：长输出容易看吗、审批容易理解吗、中断和恢复顺手吗？这些问题不能由功能列表替代。

模型与适用方向。 建议为主要编辑任务选择已适配的强工具模型，为辅助任务配置经济模型。适合终端开发、远程 SSH 环境和偏好简洁交互的用户。若首要需求是成熟云端团队编排，需要另看 Factory、Devin 或 OpenHands。难度：中。

A14 Mistral Vibe：让 Mistral 模型进入可控的开发循环

定位与理念。 Vibe 是 Mistral 的官方编程代理。它为希望使用 Devstral 等 Mistral 模型、同时保留可读源码和本地开发体验的人提供原生路径。README

架构特色。 Python 核心通过模型、工具、权限、压缩和子代理接口组织执行；异步事件把执行状态交给不同客户端。这里值得关注的是业务逻辑与外部能力之间的接口边界，方便替换或测试某一部分，而不必重写整个界面。执行循环

怎样上手。 安装后运行 vibe，选择登录／API 配置，查看当前代理模式。Ask、Plan、Accept-edits 和更自动的模式表达的是不同授权策略；应先了解自己的默认模式，再运行会修改环境的任务。需要接子代理时，验证模型、工具与权限组合。

模型与适用方向。 原生优先 Devstral 系列，复杂任务比较 Devstral 2，资源与预算受限时看 Devstral Small 2 等官方可用型号。不要因为某个 Mistral 通用模型更新，就自动认定它是 Vibe 最佳编程后端。适合 Mistral 用户、开放模型部署试验，以及希望研究清晰 Python 代理结构的人。难度：中。Mistral 模型目录

A15 OpenHands：把代理和它的工作环境一起管理

先更新印象。 当前 OpenHands/OpenHands 主仓库主要是 Agent Canvas；实际代理、会话、工作空间和服务接口在独立 Software Agent SDK 中继续实现。只读主仓库前端，不能得出执行引擎的完整结论。Canvas、SDK

设计理念。 OpenHands 更接近“给代理配一台工作机”的路线。代理不仅要调用模型，还要有工作目录、依赖、命令环境、浏览器和会话服务。SDK／Agent Server 提供执行能力，Canvas 提供交互，自动化层再安排任务和环境生命周期。Canvas 也可接入 ACP 代理，因此“在 OpenHands 界面里运行”未必等于使用原生 OpenHands 循环。

关键取舍。 工作空间可以是本机，也可以是 Docker／Kubernetes 等临时环境。这使批量任务更容易复制和隔离，但会增加环境构建、镜像、凭据和资源清理工作。不能把“支持容器”写成“任何安装默认都在容器里”。SDK 工作空间说明

怎样上手。 单人先按当前 Canvas／CLI 文档运行一个本地任务；需要可重复执行或团队部署时，再使用 Agent Server 和独立工作空间。验证流程至少应包含：拉取仓库、安装依赖、运行测试、保存变更、回收环境。环境没有准备好时，换更强模型往往无济于事。

模型与适用方向。 以原生 SDK 文档支持的强编程模型为起点；若通过 ACP 使用 Claude Code／Codex，则遵循对应代理的模型建议，不能把它们算成同一种后端。适合批量 issue 修复、远程开发代理、组织内部代理平台和需要统一环境的实验。难度：本地中；规模化部署高。

A16 Grok Build：开放源码的 Grok 编程运行时

定位。 Grok Build 提供终端 TUI、无界面脚本和 ACP 接入。当前公开仓库包含 Rust CLI／TUI 与代理运行时，并从内部大仓定期同步；这与“仅有安装说明的公开仓库”不同，但公开快照与最新商业二进制也不能自动视为完全相同。README

架构与功能。 公开包按代理、工具、会话、终端和沙箱等职责拆分。官方文档支持项目指令、Skills、MCP、Hooks、子代理、工作树及后台任务。配置又区分用户、项目和组织管理层；项目配置并不是任意覆盖所有用户设置。需要理解的是：模型配置、工具权限和组织强制策略属于不同责任层。设置

怎样上手。 按官方渠道安装，在仓库执行 grok，完成登录；使用 grok inspect 确认当前实际装载了哪些配置、指令和工具。脚本模式使用 grok -p，需要程序消费结果时选择结构化输出。自定义模型填写 API 后端与服务地址，不要只改显示名称。入门

模型与适用方向。 官方配置示例将 grok-build 作为编程／代理会话的推荐默认，并提供 Grok 4.7 API 路径；其他模型通过自定义配置接入。原生组合值得 Grok 用户优先试用，跨模型组合仍应先做工具兼容测试。适合终端开发、CI 脚本和希望通过 ACP 使用 Grok 的人。难度：中。

03B｜编辑器与托管工作台：把代理放进完整的工作流程

这一类产品通常替用户整合了界面、项目上下文、账户、模型路由和任务管理。代价是：可替换的部件少一些，产品方案、套餐和管理策略的影响更大。

阅读边界： Zed、Neovim 插件与 VS Code 的相关部分有公开源码；本章多数商业产品没有公开完整运行时。以下架构是根据官方接口和功能还原的责任分工，不冒充内部源码审计。模型建议均以所在入口和账户实际可选为前提；“Auto／内置路由”本身也是一种合理组合，不必硬填一个产品没有开放选择的模型名。

B01 Cursor：把编辑器里的即时上下文变成代理的工作起点

理念与结构。 Cursor 的优势是人仍在编辑器中工作，代理却能持续获得文件、选择区域、诊断与项目线索，并直接提出和执行修改。Agent 的工具、指令与模型适配共同构成执行体验；代码索引是帮助它找到相关材料的一条路径，不意味着每轮把整个仓库全部塞给模型。Agent 文档

当前产品还扩展了子代理、项目协调和云端工作。应把本地交互式编辑、后台任务和自动化分别评估：它们接触的环境、凭据和可运行时长可能不同。子代理能够减少主对话被探索细节占满的问题，但最终仍要有人检查集成结果。子代理

使用方式。 打开仓库，先让 Agent 解释一个具体模块，再交付小功能。为常见任务保存规则，查看 diff 后接受修改。只需要补全一行或修改一个函数时，使用轻量编辑能力即可，没有必要启动漫长自治任务。

模型搭配与场景。 日常可以从内置 Auto／Composer 路线开始，需控制变量时固定当前目录中的 Claude 或 GPT 型号。当前 Auto 还区分成本、平衡、智能等路线，收费与路由不能用早期套餐规则代替。它适合前端迭代、跨文件小中型实现、边写边改；如果要求每个模型、每条系统提示都由自己掌控，开放 Harness 更合适。难度：低中。模型与计费

B02 GitHub Copilot：嵌入代码协作平台的一组代理入口

先拆开品牌。 Copilot 的补全、IDE Chat／Agent、CLI 和云端编码代理不是同一个执行环境。IDE 代理在开发者附近修改和验证；云端代理围绕 issue、分支、PR 等协作对象工作。选择 Copilot，往往也是选择 GitHub 的协作入口、组织账户和审查流程。官方功能文档

源码能看到什么。 旧 microsoft/vscode-copilot-chat 已归档，相关开发迁入 VS Code 主仓库。不能因旧仓库归档就断言 Copilot 停止开发，也不能因 VS Code 开源就声称 GitHub 托管代理的全部服务端已经开源。公开仓库用于核对编辑器侧实现，云端行为以服务文档为准。旧仓库、VS Code 当前源码

使用方式。 已经在 GitHub 团队中工作的人，可以先从 IDE 的限定任务开始，再把成熟的重复修复交给 issue／PR 流程。任务必须有测试命令与验收条件；PR 被创建不等于代码已经通过审查和合并。

模型搭配与场景。 当前支持目录包括多个 GPT、Claude、Gemini 和其他型号，但可用性按产品入口划分，不能把网页目录的并集当成某个按钮的选项。日常选择入口中可用的 Sonnet 5／GPT-5.6 Terra；复杂任务比较更强型号或内置路由。适合现有 GitHub 团队、代码审查、常规维护、从 issue 到 PR 的工作。难度：个人低中；组织治理中。模型支持矩阵

B03 Devin／Devin Desktop：从编辑器协作延伸到远程交付

命名变化。 旧 Windsurf 文档已迁入 Devin Desktop 文档体系，Cascade 仍是需要辨认的本地代理体验；它与 Devin 云端任务不能混为一谈。报告按产品家族合并说明，避免将迁移前后的名字重复计成两个完全独立竞品。Cascade 文档

理念与结构。 本地 Cascade 围绕编辑器上下文、规划、代码修改和检查点工作；远程 Devin 更强调把仓库、执行环境、任务和协作交付组织起来。需要企业自有基础设施时，还有 Outposts 路线。其架构差别主要在“工作机和任务生命周期由谁管理”，而不只在模型名字。Devin 入门、Outposts

使用方式。 本地边写边改选 Desktop；任务清晰、可以在独立环境重现时再交给远程代理。准备仓库说明、环境安装命令和验收步骤，比一句“帮我完成需求”更重要。可并行的任务应有清楚的文件或模块边界。

模型搭配与场景。 Desktop／CLI 以当前模型选择器为准，可比较其支持的 Claude、GPT、Gemini、Cognition 及开放模型；云端原生任务则优先使用产品调优的默认组合，不臆造无限 BYOK 能力。适合团队中长任务、异步修复、迁移和远程交付；即兴的小修改未必值得环境启动与任务交接成本。难度：本地低中；远程部署中高。CLI 模型说明

B04 Kiro：让需求、设计和任务清单成为持续上下文

理念。 Kiro 的辨识度在于 Spec 工作方式：先把需求、设计与实施任务写成可查看、可修改的材料，再让代理推进。它适合需求需要解释、多人需要对齐、实现时间跨度较长的项目。Spec 的价值是明确共识，不是生成文档越多越好。Specs

架构。 官方说明将其描述为跨 IDE、CLI、Web、移动入口的统一独立进程 Harness，通过 ACP 及相关扩展连接客户端。规则、Hooks、MCP、Skills 等围绕同一个核心配置，但功能在各入口仍有差异。“同一核心”意味着复用执行责任，不意味着所有界面功能完全相等。工作原理

使用方式。 从一个需要两三步实现的小需求开始，让它产生需求、设计与任务；删掉空泛内容，补入验收标准，再实施。需求很简单时直接对话即可，否则写规范的成本可能比修 bug 本身还高。

模型搭配与场景。 当前 Kiro 已提供多个 GPT、Claude 和其他模型，并非只支持某一个旧 Claude 版本。一般从 Auto 或可用的 Sonnet 5／GPT-5.6 Terra 开始；复杂规范与实现比较更强档位。预览模型受地区与组织治理约束。适合中型功能、正式需求开发、跨人协作、验收明确的长期改造。难度：低中；高质量 Spec 写作需要业务判断。模型矩阵

B05 JetBrains Junie：让代理使用 IDE 已经理解的代码结构

理念与架构。 Junie 的差异化在 JetBrains IDE 的代码理解能力：项目、符号、导航、诊断和运行配置已经存在，代理可以借此工作，而不必完全依赖文本搜索。当前产品还包含 CLI、CI 和远程监控等入口，已经不是只能在 IDE 中调用单一模型的小功能。官方产品页

工作方式。 计划阶段可以形成可编辑、可提交的需求／设计／交付材料；实施阶段可用另一档模型。其价值是让“为什么这样改”保存在项目中，同时使用 IDE 的已有工具验证结果。需要注意，宣传中的基准成绩属于厂商材料，本报告没有据此宣布它普遍优于其他代理。

使用方式。 如果日常在 IntelliJ IDEA、PyCharm、WebStorm 或 Android Studio 中工作，先在原有项目里启用 Junie。给出正确的运行配置、测试方法和项目指南；大型迁移先审核计划，再分批改动。

模型搭配与场景。 官方当前提供 BYOK 和本地模型支持。建议从可选的强编程云端模型开始，复杂规划用较强档位，简单实施再比较较快档位；具体型号以当前模型菜单验证。适合 JVM、复杂 IDE 项目、框架升级和已有 JetBrains 工作习惯的人。难度：低中。其优势依赖项目在 IDE 中被正确加载，项目配置损坏时不能靠模型补救。

B06 Zed：编辑器可以是代理的宿主，不必包办代理的全部能力

理念。 Zed 是开放的高性能编辑器，同时提供自有 Agent 和 ACP 外部代理接入。它最有启发性的设计是将编辑器与代理运行时分开：用户可以喜欢 Zed 的交互，却选择 Codex、Claude、OpenCode、Pi 等代理执行任务。项目、AI 概览

边界非常明确。 外部代理通常拥有自己的认证、模型选择、工具和配置；Zed 展示会话和交互。给 Zed 自有模型入口填了 API Key，并不自动意味着外部 Codex 或 Claude 也完成了相应认证。它们的费用、数据处理和权限仍要看各自运行时。外部代理文档

使用方式。 安装 Zed，打开项目，先选自有 Agent 或从 ACP Registry 安装外部代理。试用时固定其中一种；只有确认当前“谁在执行”后，再比较模型。否则很容易把编辑器变化、Harness 变化和模型变化一起归因。

模型搭配与场景。 “Zed＋Codex＋GPT”“Zed＋OpenCode＋Claude”是不同组合。前者遵循 Codex 的模型与权限配置，后者遵循 OpenCode。适合喜欢轻快编辑器、想在统一界面比较不同代理、重视开放协议的开发者。难度：中；跨代理配置中高。

B07 TRAE／SOLO：从编程界面走向可交付的完整工作

范围。 TRAE 产品、SOLO 工作方式，以及 GitHub 上的 trae-agent 研究代码不能互相替代。后者维护状态并不能证明商业产品当前活跃程度。本报告将 TRAE／SOLO 作为商业产品家族，研究仓库另列观察项。

理念与公开能力。 官方已将 SOLO 扩展到独立桌面和 Web 体验，并区分偏编程的工作与 More Than Coding 的资料、报告、数据任务。其方向是减少“模型回答完，用户再手工整理成品”的断层。但闭源运行时的调度、压缩和内部模型路由无法从公开网页完整还原。官方产品页、SOLO 说明

使用方式。 编程任务先提供代码仓库、运行方法和验收；资料任务先提供资料范围、输出文件格式和引用要求。国内／国际版本与不同入口应分开试用，不把一端的模型、额度和工具列表照搬到另一端。

模型搭配与场景。 推荐先使用产品实际提供的内置路由或当前模型选项。尚未核实每个版本都支持同等自由的 BYOK，因此不给出“任意 TRAE＋任意模型”的保证。适合希望减少配置、直接从需求得到原型或文档的用户。难度：低中；专业开发仍需会检查代码与部署结果。

B08 Augment／Auggie：先解决“找对代码和业务背景”

理念。 对大型代码库来说，模型不一定缺少编程知识，更常缺少“这家公司把事情放在哪里、为什么这样做”。Augment 的 Context Engine 围绕项目和相关仓库提供检索与上下文。Auggie 则把这种能力带入 CLI。Agent 文档、Auggie 入门

架构取舍。 索引和检索层位于模型之前，负责找材料；代理再决定怎样行动。索引需要维护，文件排除范围、更新延迟和访问权限会影响结果。它不保证一个名字相似的检索结果就是正确依赖。Context Engine 也能作为 MCP 服务给其他代理使用，这意味着团队可以只替换“找资料”这一层。Context Engine MCP

使用方式。 先导入一个真实项目，检查索引范围，再用几个已知答案的问题验证检索质量，例如“这个权限检查的所有入口在哪里”。之后再让代理修改代码。需要跨仓库背景时，显式配置相关工作空间，避免把整个组织随意纳入。

模型搭配与场景。 Auggie 内部选项按当前产品提供的路由选择；也可以采用“Codex／Claude Code＋Context Engine”的组合，此时模型仍由原代理决定。适合大型仓库、复杂内部业务、跨仓库改动和新成员熟悉项目。难度：中；索引与组织权限管理中高。

B09 Amp：把能力档位定义为一整套执行配置

理念。 Amp 当前的 low／medium／high／ultra 不只是更换模型。每档组合了模型、推理强度、系统提示、工具和 Oracle 等能力。它体现了一种产品判断：用户选“这个任务值得投入多少能力”，具体执行组合由产品组织。模式与模型

分工结构。 Search、Oracle、Librarian、Read Thread 等专门处理代码检索、难题推理、外部资料和历史任务。它们通常拥有独立上下文，主代理收到汇总；文档明确区分这种分工与可彼此随意沟通的团队。Orbs 则扩展到持久远程工作环境。工具、Orbs 入门

使用方式。 先从中等档位处理典型开发任务，困难时升级档位。保存任务与输出材料，观察升档究竟改善了什么。需要插件自定义代理时，再设计清楚输入、输出和可用工具。不要因为出现多个角色名就认为它们真的形成了一个可靠组织。

模型搭配与场景。 首选“任务档位＋当前官方路由”，并记录实际模型；需要固定模型或 BYOK 时按当前文档配置。其路由会更新，因此不能长期宣称 Amp 永久绑定某一家模型。适合希望减少自行调参、又需要专家分工的熟练开发者。难度：中；自定义编排中高。

B10 Factory Droid：把大任务组织成可验证的交付过程

理念。 Droid 提供通用代理执行，Missions 进一步安排规划、工作者和验证。与简单地“同时开五个聊天窗口”相比，其重点是任务交接、状态和完成标准。Missions

公开架构。 自定义 Droid 用项目级或用户级 Markdown 配置，指定职责、模型和工具；被调用时拥有独立上下文。官方还明确描述了工作者的限制，例如特定非交互式子任务不能像主代理那样随意向用户提问或继续套娃调用。限制能减少失控，也意味着主任务必须给出足够明确的输入。子代理

BYOK 也有入口范围：当前说明针对 CLI／Desktop 配置，不应扩展为所有托管 Web、移动入口自动支持相同自定义模型。权限和沙箱同样要分别配置。BYOK、沙箱

使用方式。 先用单个 Droid 完成小功能；再让 Mission 处理能拆分且能验收的任务，例如 API、前端、测试三部分。规划文件中写清共享接口，避免每个工作者各造一套约定。

模型搭配与场景。 官方当前目录提供 GPT-6 Astra、GPT-5.6、Claude 等多档选择。建议规划／疑难诊断用较强模型，可机械验收的实施用经济档，再由独立检查收尾。适合较完整的功能交付、重复开发流程和愿意为任务编排投入配置的团队。难度：中高。模型目录

B11 Warp／Automation Platform：从终端会话走向可触发的代理任务

理念。 Warp 原生终端会把命令、输出与上下文组织得更结构化。其代理在这样的工作环境中使用工具；同时也支持把 Claude Code、Codex、OpenCode 等第三方 CLI 放进 Warp。后者使用的代理核心仍属于第三方，而不是一律变成 Warp Agent。Agents 文档

架构分层。 Agent Profiles 配置模型、自治程度、工具与命令权限；Automation Platform 再提供远程环境、触发器、编排和观察能力。部分接口与应用仍使用 Oz 名称。比较时应区分“Warp 作为终端”“Warp 原生 Agent”和“平台上的远程执行”。CLI 文档

使用方式。 终端用户先从解释错误、整理日志、生成和执行可审查命令开始；重复任务稳定后再保存 Profile、配置触发器和远程环境。不要把第一次临时救火直接改成无人值守生产任务。

模型搭配与场景。 原生 Agent 使用当前 Profile 可选模型；第三方 CLI 遵循对应 Harness 的模型方案。适合日常终端操作、开发环境排障、运维脚本和周期性开发任务。难度：终端低中；平台自动化中高。涉及生产系统时，真正限制影响范围的是凭据和执行权限。

B12 Google Antigravity：让代码、浏览器和任务产物一起进入代理流程

理念。 Antigravity 把多步开发与可查看的产物结合，代理不仅输出代码，也通过计划、说明和浏览器结果帮助用户判断任务是否完成。其价值在于让开发验证进入同一工作过程。Agent 文档

能力边界。 对浏览器的操作、终端命令、项目修改和并行会话应分别看权限与环境。产物展示能提高可审查性，但截图好看不等于功能、无障碍和异常状态都正确。

使用方式。 导入项目，让代理写一份简短计划，实施后在浏览器中验证具体路径。例如不仅打开登录页，还测试错误密码、空输入和登录后跳转。要求保存验证结果，而不只是说“已经测试”。

模型搭配与场景。 当前官方列表以 Gemini 为主要路线，也列出部分 Claude 与 GPT-OSS 型号，并区分企业可用性。优先比较 Gemini 3.8 Flash 与可用的 3.1 Pro；不能因为别处发布了 GPT-6，就假定这里已经可选。适合前端、Web 应用、需要视觉验证的任务。难度：低中。模型列表

B13 Replit Agent：把从想法到可运行应用的环境准备一起包起来

理念。 Replit Agent 面向“我想做一个东西”的用户，把项目生成、运行环境、预览和发布串在一起。对初学者而言，省去安装依赖和配置服务往往比多一个模型选项更重要。Agent 介绍

架构取舍。 这是托管开发环境中的代理。平台控制环境与部分路由，因此起步快；迁出时需要确认代码、数据库、秘密配置、运行方式和部署依赖分别如何处理。一个可以下载的源码目录，不一定等于完整可迁移的线上系统。

使用方式。 先描述用户、核心流程和一个最小成品，不要一次要求完整商业平台。通过预览逐个验收，再决定是否增加数据库、认证和付费功能。部署前核对持续运行费用。

模型搭配与场景。 推荐使用产品提供的 Lite／Economy／Power 等能力档位与内置路由，而不承诺某个具体模型永远位于某个档位。小调整使用轻档，大改造再提高能力与预算。适合原型、内部小工具、演示应用和非开发者试验。难度：低；维护真实业务仍需要工程知识。使用与费用、预算管理

B14 Qoder：把项目知识和目标式执行放在同一个产品里

理念。 Qoder 同时强调代码理解、项目知识材料与较完整任务的推进。Quest 等工作方式希望把“告诉它目标”转成持续执行；Repo Wiki 则试图让项目背景成为可复用材料。产品概览、Quest

需要留意的产品边界。 当前桌面、IDE、CLI 等入口的历史和配置不应默认完全互通；文档对导入与独立空间有具体说明。自定义模型也不代表所有辅助能力都使用自己的 Key，例如 Repo Wiki 使用固定模型并单独消耗平台额度。自定义模型

使用方式。 先让它理解一个已有仓库，核对生成的知识说明有没有误解，再用 Quest 处理带明确输出的任务。模型切换前保存关键需求，防止只关注窗口长度而忽略任务状态。

模型搭配与场景。 当前 CLI 文档列出 Qwen3.8-Max、Kimi-K3、GLM-5.3、DeepSeek-V4 等选项，并支持若干 Provider 的自定义模型。可按同一任务比较中文项目理解、成本和工具稳定性。适合大型项目入门、中文开发、既要项目知识又要目标执行的用户。难度：低中。模型配置

B15 腾讯 CodeBuddy：面向中文开发生态的多入口代理

理念与公开能力。 CodeBuddy 覆盖 IDE、插件和 CLI；其上下文入口包括文件、代码片段、文档、Git 与终端。对微信小程序、腾讯云相关开发者，现成资料入口和中文工作流有实用价值，但这不等于其他项目不能用。上下文文档

CLI 的自定义子代理可以配置职责、工具和独立上下文，结果返回主代理；项目级与用户级配置承担不同作用。官方还提供团队、工作树、沙箱与 SDK 等文档入口。由于完整商业运行时未公开，本报告只确认文档所述行为，不推断它内部一定复用了某个竞品的实现。子代理、设置

使用方式。 选定国内／国际版本和一个入口，检查模型目录与权限。已有项目先精确引用相关文件、Git 变更和报错输出；可复用的研究职责再做成子代理。不要默认新建子代理就自动获得最小权限，应检查继承的工具集。

模型搭配与场景。 以当前版本实际提供的模型和自定义接入为准，优先产品默认路线；需要固定模型时先验证工具调用。适合中文团队、小程序、腾讯云相关开发以及希望兼顾插件和 CLI 的人。难度：低中。WorkBuddy 属于扩展到办公任务的相邻产品，不能用它的能力反推所有 CodeBuddy 入口。

B16 ZCode：把 GLM 的长任务能力放进目标管理流程

理念。 ZCode 官方明确围绕 GLM-5.3 适配，重点包括复杂项目理解、长任务、连续代码修改和恢复。Goal Mode 将目标、完成检查和状态恢复放在一个流程里，方向类似“任务尚未完成，就保留继续工作的依据”。Agent 文档

架构含义。 文件引用、工作空间、Git 分支、执行模式和推理档位共同决定代理的工作上下文。持久目标不等于模型拥有无限记忆，仍依赖任务状态被正确保存和重新装载。官方还特别说明 CLAUDE.md 在迁移时可作为一次性来源，后续使用 AGENTS.md；不能看到熟悉的文件名就假定运行时一直自动读取它。

使用方式。 导入仓库后先检查项目指令，明确当前目标与验收；从一个能在当天完成的任务测试暂停、继续和验证。较长任务将关键进度保存在项目文件中，再观察恢复是否准确。

模型搭配与场景。 原生优先 GLM-5.3。官方的性能描述属于厂商主张，本报告确认其适配方向，不将“长任务更强”当作已经独立验证的跨产品结论。适合 GLM 用户、中文开发、需要持续目标管理的任务。难度：低中；涉及其他 Provider 的完整兼容程度仍需按版本核实。模型介绍

B17 Avante.nvim：在 Neovim 里获得可直接应用的代理修改

理念。 Avante 希望让用户保留 Neovim 的键盘工作习惯，同时获得类似 AI IDE 的项目对话、修改与差异审查。当前已有多 Provider、项目指令、可选检索、工具和 ACP 接入，不只是代码补全插件。README

结构与边界。 Lua 模型层区分直接调用 Provider 与 ACP 路径，并处理流、工具和记忆摘要。所检查的 dispatch_agent 面向独立的只读搜索任务，不能因此理解为一套默认可写文件的团队。ACP 路线又可能把代理运行交给 Codex、Gemini 等外部进程。模型层、分派工具

使用与模型。 按当前 Neovim 版本要求安装插件和依赖，先配置一个 Provider，再练习选取文件、提出修改和接受 diff；项目规则可放在 avante.md。直接接模型时选择已适配的 Claude／GPT 或其他工具模型；接外部 ACP 代理则沿用对方模型方案。适合熟练 Neovim 用户和终端开发者。难度：已有 Neovim 配置者中；初学者高。

B18 CodeCompanion.nvim：把模型适配和完整代理接入明确分开

理念。 CodeCompanion 提供对话、局部转换、代码审查、工具和工作流，同时保留较强的编辑器配置自由。它适合希望在 Neovim 内按自己的习惯组合 AI 能力的人。README

一个清楚的架构边界。 HTTP Adapter 处理模型请求、响应和工具格式；ACP Connection 处理外部代理的会话、能力、权限请求和流式更新。前者是“自己组织对话并请求模型”，后者是“把完整任务交给另一个代理”。两者都出现在同一编辑器里，但负责执行的人不同。HTTP 适配、ACP 连接

使用与模型。 安装插件后，先在 HTTP 模型与 ACP 代理两条路线中选一条。局部变换可以使用较快模型；复杂任务可接 Codex／Claude Code 等原生代理。再按需添加 MCP、规则和 Skills，避免一次改变整个配置。适合 Neovim 用户、自定义提示与工作流爱好者；模型和多入口配置成本较高。难度：中高。

B19 Tabnine Agent：把企业模型选择与开发环境控制放在前面

理念。 Tabnine 当前不只有补全和 Chat，也有直接在开发环境中执行目标的 Agent。产品强调项目上下文、用户反馈和组织控制。对于已有企业部署约束的团队，模型治理和私有端点可能比追逐最新单一型号更重要。Agent 说明

公开能力与边界。 IDE 中的工具设置分别控制读取、命令和应用代码等能力；管理员可以决定组织可用的模型。完整商业核心未公开，因此本报告按公开配置描述其责任分工，不声称验证其内部调度算法。工具设置

使用与模型。 在组织批准的 IDE 与部署中启用 Agent，先确认读取和执行权限，再尝试一个范围明确的重构或测试任务。官方模型页列出 GPT、Claude、Gemini、Devstral 等选项，且并非所有型号都适用于所有入口；不能假定目录永远同步最新发布。适合企业代码助手、私有端点和统一模型策略。难度：个人低中；组织部署高。模型目录

B20 Google Jules：把仓库任务交给独立云端工作机

理念。 Jules 是异步编码代理：连接 GitHub，选择仓库和分支，在云端虚拟机中克隆代码、安装依赖、修改并验证。它与 Gemini CLI 的主要差别是环境和任务生命周期由服务管理。当前入门文档仍标记实验性质，应保留成熟度判断。入门

架构与使用。 官方 API 以 Source、Session 和 Activity 等对象管理仓库与任务。用户可以先检查计划，再让任务运行，随后审阅产物；CLI 主要提供与云端 Jules 交互的入口，不应误认为把同一引擎完全搬回本地。先接一个仓库，提供环境脚本和 AGENTS.md，从测试补齐或小修复开始。API

模型搭配与场景。 优先使用 Jules 原生模型路由；公开材料没有证明任意 BYOK 都受到同等支持，因此不指定一个可随意更换的后端。适合独立 issue、测试补齐、文档更新与批量维护。验收仍需看变更和实际测试，云端任务完成通知不等于应直接合并。难度：初次低中；环境配置中。

下一章转向个人助理、通用客户端与知识工作台。这些产品与编程代理越来越接近，但状态、连接器和长期记忆的设计重心仍然不同。

03C｜个人助理与知识工作台：围绕长期信息和日常工作组织代理

这类工具的起点通常不是一个 Git 仓库，而是人、资料、对话和外部应用。它们越来越多地加入代码执行、子代理、浏览器和定时任务，因此不能沿用“都是聊天皮肤”的旧判断。

这里更需要问三个问题：长期记忆存在哪里？谁能触发任务？代理操作的是哪个人的账户和工作空间？ 同样一次工具调用，放在一个临时编程会话中，与放在持续在线的聊天机器人里，管理难度很不一样。

C01 Hermes Agent：把一次任务的经验变成下一次可用的材料

理念。 Hermes 将长期使用放在中心：会话可以检索，经验可以写成记忆和 Skills，任务可以从 CLI、消息渠道或自动化入口到来。“会越用越懂你”在工程上主要意味着保存并重新使用材料，不是每聊一次就训练模型权重。README

源码结构。 Python 会话循环把模型请求、上下文准备、工具分派和结果处理拆成多个部分；模型协议经适配后进入统一执行逻辑。记忆管理又通过独立 Provider 接口工作。在压缩前保存必要信息，是避免长任务丢失关键进展的一条路径。循环、记忆管理

子代理并不是共享大脑。 委派工具为子任务建立独立代理，主代理通常只看见任务与摘要，而不是所有中间步骤。源码还为子任务处理模型覆盖、工作树、取消和预算。特别要注意，子代理可以有自己的运行预算，父任务上限不能直接当作整棵任务树的总成本上限。委派工具

怎样使用。 先只启用本地 CLI 与一个模型，完成资料整理或项目研究；确认会话检索和记忆内容有用后，再接消息渠道、定时任务和外部工具。把长期偏好、项目事实、临时任务进度分开保存，避免一次性的错误结论成为永久偏好。

模型与适用方向。 建议用可靠的 GPT／Claude 工具模型建立基线；中文任务与成本敏感场景比较当前适配的 Kimi、Qwen、DeepSeek。接本地模型时应检查真实上下文和工具调用能力，不能只看模型参数。适合持续研究助理、个人工作自动化、跨会话项目管理、从重复工作积累 Skills。难度：CLI 中；长期在线与多渠道运维高。

C02 OpenClaw：让个人代理持续在线，连接不同渠道与设备

理念。 OpenClaw 更像个人代理的接线与运行中心。Gateway 维持长连接、渠道、会话和设备关系；手机、桌面、消息平台可以成为交互入口。它不只是把同一聊天框复制到几个应用。架构文档

关键架构。 Gateway 管理连接与任务进入方式，具体代理运行时负责模型和工具循环。当前文档已经涉及不同运行时路径，因此不宜永久把它概括成某一版本 Pi 的简单包装。每个会话的任务通常串行化，持久化写入还需要确认当前运行是否仍拥有写入资格，防止被替代的旧任务把过时状态写回去。代理循环

长期记忆。 工作空间中的记忆材料、会话摘要、检索和后台整理共同服务持续使用。这里有一个实际取舍：记忆越多，维护和纠错越重要。能记住一句话不代表知道它何时过期，用户需要能够查看、修正和删除。记忆设计

怎样使用。 先部署一个 Gateway，完成设备／渠道配对，只接一个工作入口，验证谁能向代理发指令。随后配置工具权限和沙箱。默认宿主机执行与显式沙箱是不同状态，不能因为产品是自托管就假定工具已经隔离。最后再开放定时任务或更广的渠道。

模型与适用方向。 依据实际运行时选模型；原生多 Provider 路线可比较强工具模型，若接 Codex 等运行时则遵循其原生模型配置。适合跨设备个人助理、消息入口统一、长期自动化。单纯偶尔问答或修一个 bug，部署整个持续服务可能没有必要。难度：高，主要高在服务、账户与权限管理。

C03 Agent Zero：给代理一套可以动手操作的工作环境

理念。 Agent Zero 偏向通用任务代理：让模型在可操作的计算环境中使用工具、编写程序、处理资料和分派任务。提示、工具、扩展和工作空间可以被用户修改，因此它兼具产品与实验平台的性质。README

执行结构。 agent.py 的循环反复准备提示、调用模型、处理工具，并在多个节点触发扩展与用户干预。子代理通过上下级关系和独立配置组织，具体任务可以交给不同职责的下属。这套设计容易扩展，但扩展一多，排查行为变化也更费力。主循环、下属代理

怎样使用。 按官方方式准备容器或工作环境，先配置模型与文件范围。用“读取一批文件，生成索引与一份报告”这样的任务检验文件、浏览器和输出保存能力，再考虑更长任务。容器仍可能挂载宿主目录或持有外部凭据，边界应看实际挂载和授权。

模型与适用方向。 优先能稳定处理工具、多轮纠错和代码执行的模型，如当前适配的 Claude／GPT；成本方案再比较开放模型。复杂编排对小模型的稳定性要求高，不宜只按每百万 Token 单价选择。适合技术用户的资料处理、自动化、通用代理实验。难度：中高；无人值守部署高。

C04 Chatbox AI：低门槛客户端正在长出真正的工作模式

先纠正旧印象。 Chatbox 的经典价值是多模型聊天、文件与对话管理，但当前公开技术文档已经描述 Agent／Work 模式、工具、Skills 和记忆。因此它不应再被一概排除在 Harness 讨论之外。商业发行版与社区源码也有差别，功能判断必须标注版本。项目说明、功能页

一个具体设计。 当前 Agent 模式将身份、Soul、个人偏好、工作目录说明与工具信息组装成提示；会话首次启动时保存一份上下文快照。稳定前缀有助于缓存和一致性，但代价是中途修改某些规则，不一定立刻影响这段既有会话，需要新会话或相应重捕获条件。提示与记忆设计

Skills 则可以按需加载，避免把所有工作手册每次全塞进去。Provider 层区分模型配置和实际协议适配；“某服务兼容 OpenAI”并不意味着所有参数与推理行为一致。Skills、Provider 设计

怎样使用。 先用 Chat 模式连接一个模型，熟悉历史、文件和导出；确需写文件、执行任务时再启用 Work 模式。把长期写作偏好放在可查看的规则中，把某一份报告的事实留在项目材料里。修改全局人格后，要确认它对当前会话是否已生效。

模型与适用方向。 日常写作可比较当前接入的 Claude、GPT、Kimi／Qwen；工作模式更应优先可靠工具调用。适合一般用户、报告润色、翻译、资料讨论和轻量本地任务。复杂团队开发或持续在线服务不是其最自然的起点。难度：聊天低；Agent 中。

C05 Cherry Studio：多模型桌面工作台，也可以成为其他代理的宿主

理念。 Cherry 面向同时使用多个模型、资料和助手的人。当前架构已经从普通多模型对话扩展到独立 Agent Session 运行时，因此“多个模型各答一遍”和“多个代理分工执行”需要分别讨论。README

当前架构。 Electron 界面通过进程间通信交给主进程的 AI 服务；主进程负责流、持久化与不同消费者。Agent Session 又区分宿主服务与具体驱动：宿主管会话、排队、恢复标记和界面生命周期，驱动对接 Claude Code、Pi、DSH 等不同执行后端。这是“统一工作台＋不同引擎”的明确例子。核心架构、Agent Session

这也带来边界：统一界面不意味着各后端的工具、审批和恢复语义完全一致。切换后端时，应确认原来的任务状态与权限怎样处理，而不只是看聊天记录还在不在。

怎样使用。 普通知识工作先配置模型、助手和资料；需要任务执行时创建明确工作空间，并选择运行后端。别一次导入所有个人文件。用一份报告或一个小项目检验资料引用、生成文件与恢复任务。

模型与适用方向。 普通对话可自由比较 GPT／Claude／Kimi／Qwen；Agent 驱动则依其后端来选，例如 Claude 驱动优先 Claude、Pi／DSH 按对应适配。适合中文用户、多模型比较、知识整理、希望保留桌面统一入口的人。难度：基础低；多运行时管理中高。

C06 Open WebUI：自托管的共享 AI 门户，工具执行能力取决于部署

理念。 Open WebUI 常被用于为本地或远端模型提供统一网页入口。其能力已经延伸到用户权限、知识检索、工具、MCP／OpenAPI 接入以及终端执行相关能力。它既可能是一套聊天门户，也可能被配置成真正的代理工作台。README

架构与边界。 后端中间层组织消息、模型服务、检索与工具结果，工具模块再结合用户权限暴露能力。换句话说，模型本身未必知道你公司的全部数据，是后端决定哪些资料和工具能够进入这轮任务。中间层、工具处理

一旦接上 Open Terminal 等执行能力，就必须检查每个用户的文件、进程和凭据边界。模型服务“只在内网”不能替代用户间隔离。插件或自定义代码也可能访问服务进程本身能够访问的资源。

怎样使用。 单人部署先连接模型并关闭不需要的能力；多人使用再配置账户、知识库权限、备份和配额。先用已知答案测试资料检索，再考虑加工具。需要真正离线时，连嵌入、搜索、语音、遥测和工具出口一起检查。

模型与适用方向。 与 Ollama／兼容服务的本地模型组合适合内网问答；较难知识任务可接强云端模型，但数据会按配置流向相应服务。适合团队共享入口、内网知识库、本地模型试用。难度：单人中；多人服务高。

C07 LibreChat：以对话产品为入口，扩展到可配置的 Agent 运行

理念。 LibreChat 将多 Provider、用户系统、历史和工具放在熟悉的聊天界面中，同时提供 Agent Builder、子代理／多代理和代码执行等能力。它适合希望自行托管一个统一 AI 工作入口的团队。README

源码结构。 服务端创建运行时，将模型、消息、工具、摘要、子代理配置和追踪信息交给 Agent 执行包。它并非只转发一个 HTTP 请求；会话、工具发现和长期运行需要由服务端管理。但底层依赖的完整实现还在其他包里，本报告不把单个仓库的导入语句当作已经审计整个依赖树。运行创建、客户端衔接

怎样使用。 按官方部署文档配置数据库与模型入口，先建立一个只读研究 Agent，再逐步增加工具。团队使用时检查用户凭据与共享 Agent 的关系，确认谁能修改 Agent、谁能调用其工具、历史是否互相隔离。

模型与适用方向。 选型建议是针对每个 Agent 的职责固定模型：资料摘要可用经济档，代码执行与复杂工具链用更稳的档位。可选家族以当前适配目录为准。适合共享助理、团队研究、统一模型管理和自定义业务 Agent。难度：中高，尤其需要维护服务与数据库。

C08 LobeHub：从“助手集合”走向有状态的协作工作台

理念。 LobeHub 已不能只按早期 LobeChat 的界面理解。当前方向包括 Agent、工具与协作，其价值是让不同职责的助手与任务状态在同一工作台中组织起来。README

源码中的执行模型。 AgentRuntime 接收代理产生的指令，再执行调用模型、调用工具、请求人工审批或结束等动作。批量工具可从同一基础状态并行执行，再合并结果；服务端协调器负责更完整的运行生命周期。这样将“决定下一步”和“实际执行下一步”分开，便于扩展，但并行结果是否相互冲突仍需要上层语义处理。运行时、协调器

怎样使用。 先建立一个职责清楚的 Agent，例如“只根据团队资料回答产品问题”；确认工具和知识来源，再扩展为多个角色。不同人设不一定需要不同代理进程，只有确实需要独立状态、权限或执行时才增加角色。

模型与适用方向。 根据当前 Provider 支持选择 GPT、Claude 或中文模型；多角色可以各用不同档位，但应防止风格统一掩盖证据矛盾。适合希望把聊天、资料与多个工作角色集中管理的个人和团队。难度：托管使用低中；自托管与协作治理中高。

C09 AnythingLLM：围绕工作空间里的资料组织问答和流程

理念。 AnythingLLM 的自然起点是一个资料工作空间：导入文档、处理与建立索引、按问题检索，再由模型回答。Agent 与 Flow 在此基础上连接外部动作。因此它对“围绕一批固定资料反复工作”的任务很合适。README

架构。 文档处理、嵌入、向量检索、生成模型是不同部件，可以分开选择。执行层还有 Agent 对话管理与 Flow 执行器。当前所检查的 Flow 实现按步骤运行、传递变量，遇到错误或直接输出条件结束；这与让模型自由决定所有下一步的循环不同。Agent 管理、Flow

怎样使用。 先创建单一主题工作空间，导入经过整理的资料；用五到十个有标准答案的问题测试检索。确认引用的原文能支持回答，再做 Agent Flow。桌面版和多人服务的管理能力不同，应按实际部署选择。

模型与适用方向。 回答模型可以是云端 GPT／Claude／Kimi，也可以是本地模型；嵌入与检索设置同样影响结果。如果资料根本没检索到，升级生成模型通常只能得到更流畅的错误答案。适合个人文档库、内部手册问答、固定材料上的工作报告和可重复资料流程。难度：桌面低中；多人部署中高。

普通知识工作者还应认识的相邻产品

完全不想管理 Provider、运行环境和工具的人，也应比较原生托管工作产品，例如 ChatGPT Work、Claude Cowork。它们把模型、连接器和工作空间作为一套产品提供；与自由换模型的 Harness 相比，更接近整套办公服务。Claude Cowork 的官方说明强调围绕文件与应用执行工作；ChatGPT 的能力和模型则按具体产品与账户开放。Cowork、OpenAI 官方产品文档

Manus 的官方资料还描述了持续运行的云端计算环境，属于值得关注的相邻路线。Cloud Computer Genspark、Perplexity Computer、Kimi 的办公产品，以及各类 AI 应用生成器，也处于相邻市场。但本次没有对它们全部建立同等级源码／架构证据，因此不把它们混进“已深读的开放 Harness”数量。对于只想完成一份报告的用户，选择托管产品往往值得考虑；对于要研究和替换代理内部结构的人，开放 Harness 更合适。

同样，LM Studio、Ollama 主要帮助运行和服务模型；SillyTavern 等更偏创作／角色对话；LangGraph、AutoGen、CrewAI 等偏开发框架。它们可能进入一套完整方案，但不应与开箱即用的代理产品在同一张总分表里硬排高低。

03D｜相邻路线与维护观察：不要把旧印象当作当前产品

有些工具很重要，却不适合直接与一个桌面编码代理比较；另一些曾经流行，现在的维护状态需要重新判断。本章保留它们的研究价值，同时说明为什么不把它们全部作为新用户的默认推荐。

D01 Dify：把模型能力做成可复用的业务应用

理念与结构。 Dify 更接近 AI 应用与流程平台。用户组织输入、知识检索、模型、工具、分支和输出，再将流程交给其他人使用。代码中，Workflow Entry 负责图运行状态、节点与事件，Agent Runner 则在需要自治的步骤中循环调用模型和工具。确定流程与代理循环可以同时存在。README、工作流入口、工具调用代理

它的好处是：业务逻辑不必每次依靠模型重新猜。例如客户问题先分类，再检索对应知识库，证据不足转人工。代价是需要设计和维护流程、变量、权限与失败分支。

上手与模型。 从一个简单问答或资料提取流程开始，固定输入和输出格式；模型使用平台当前支持的 GPT、Claude、Qwen、DeepSeek 等。简单分类与复杂判断可以分配不同档位，但必须对整个流程验收。适合客服知识、文档处理、企业内部 AI 应用；临时修一个代码 bug 通常不是最简路径。难度：基础中；生产化高。许可证、企业能力和云服务与自托管差异应单独核对。

D02 n8n：让代理进入已有的业务自动化

理念与结构。 n8n 的起点是连接应用与触发流程，AI Agent 是其中可配置的节点。当前 Tools Agent 执行器建立模型、记忆、批处理等上下文，再将工具执行交还工作流引擎并接续结果，同时记录执行次数、失败类型和记忆读写等追踪信息。README、Tools Agent V3

这与终端代理最明显的差别在于“什么时候开始做事”：可以由表单、计划、Webhook 或应用事件触发；输入输出已经是业务数据。模型负责有不确定性的环节，外层流程负责顺序与交接。

上手与模型。 先做“读取数据→生成草稿→人工确认→保存”四步，再加自动触发。简单步骤试经济模型，复杂判断试更强模型；只有确认所用节点支持相应接口后才接入。适合每周报告、线索整理、工单分类、跨应用资料处理。难度：中；可靠生产流程高。官方称其为 fair-code，不应把可见源码直接解释成无条件的宽松开源许可。

D03 mini-SWE-agent：研究代理时，一个短循环有时比复杂平台更有用

理念。 mini-SWE-agent 强调小而可理解的执行核心，面向软件工程任务与评测。当前 v2 的 Agent 反复执行查询模型、执行动作、加入观察；它也有步数、成本、时间与格式错误终止条件，并保存运行轨迹。README、核心实现

少量代码更容易理解实验中到底改变了什么。代价是完整产品通常还需要的用户管理、丰富 UI、长期个人记忆和业务连接器不属于这个核心目标。

上手与模型。 使用官方教程，在隔离环境中跑一个 issue，固定模型、提示、环境和预算，再改变单一变量。适合模型／Harness 对照实验、课程教学、自动修复研究。模型应选择评测任务能稳定调用的接口；不因为 README 宣称某项基准领先，就推断它适合所有日常交互。难度：研究者中；非开发者高。

D04 SWE-agent：仍值得理解，但官方已把主力转向 mini

SWE-agent 对代理如何使用软件工程工具、怎样给模型设计可操作接口，有重要历史与研究价值。其执行器围绕模型、环境、工具、格式检查与重试推进任务。核心实现

但当前 README 明确表示主要开发精力转向 mini-SWE-agent，并建议新用户优先采用后者。即使仓库近期有推送，也不能把它当成与 mini 同等优先的新路线。适合复现实验、读旧配置或维护已有项目；不列为本报告的新用户首选。维护说明

D05 Oh My OpenAgent／OmO：叠加在执行核心之上的编排体系

不要只套用旧名。 当前仓库是 oh-my-openagent，文档已经覆盖 Pi 相关路线和新的编排配置，不能一直按早期 OpenCode 插件的固定角色表介绍它。README

理念与结构。 当前编排文档区分规划、执行、依赖图和团队模式。主代理保持任务所有权，通过任务工具委派；工作者可以按类别选择模型，探索与资料代理拥有受限职责。计划文件、进度状态与证据材料服务于继续执行和验证。编排说明

这类系统的收益在于把经验性的提示、任务拆分和复查做成可复用流程。代价是增加一层依赖：模型、底层 Harness、插件与配置都可能影响结果。升级任何一层都应做回归任务。

上手与模型。 先让底层 Harness 独立工作，再安装当前官方推荐的 OmO 路线；对一个具有独立子任务的项目试用，而不必让每个小改动都走完整编排。模型选择遵循角色配置和当前匹配文档，主代理用更强模型、机械任务用经济型号是一种待验证策略。难度：高。适合有能力维护配置的开发者，不适合作为完全不懂环境管理者的第一套工具。

  • Kimi：当前 kimi-code 与旧 kimi-cli 不应按同一套源码架构描述。
  • Copilot Chat：旧仓库归档后，编辑器侧开发迁入 VS Code；这不等于产品终止。

这也是为什么本报告同时检查仓库元数据、README、当前文档与实际源码入口。单看星数，或者单看最后一次推送时间，都可能得出错误结论。

04｜架构分类与取舍：真正的区别在于，谁保存状态、谁决定下一步

把这些产品分成“CLI、IDE、网页”很容易，却不足以指导选择。同一套代理可以同时有三种界面；一个网页工作台也可以承载完全不同的代理核心。

更有用的做法，是把每个产品放到几条独立坐标上：模型替换自由度、执行环境、上下文策略、任务组织方式、长期状态，以及治理能力。下面的分类是对第三章证据的分析，产品可以跨类，不是互斥名单。

4.1 先按设计重心分成六类

设计重心 代表 主要替你解决什么 为此付出的代价
模型与代理共同优化 Claude Code、Codex、Gemini CLI、Kimi Code、Vibe、Grok Build 原生模型、工具格式、提示与错误恢复更容易配套 换模型后原本的优势可能减弱；账户与供应商影响较大
开放执行核心与多模型 OpenCode、Pi、DSH；Qwen Code、MiMo Code 也跨入此类 自选模型、接口和扩展，方便研究和替换 配置组合多，兼容性与升级负担落到用户身上

这张表表达的是倾向，不是功能禁令。例如 Chatbox 可以执行任务，Codex 可以写报告，Hermes 也能写代码。分类的意义是判断“哪类工作是产品组织起来最顺手的”。

4.2 一套方案其实有六层，可以只换其中一层

这是阅读用的概念图，不是所有仓库都真的有六个同名模块。

几个组合能帮助理解：

  • Zed＋Codex＋GPT：编辑器来自 Zed，代理执行和模型配置来自 Codex。
  • Cherry＋Pi＋某个 Provider：Cherry 管理桌面会话，Pi 处理代理运行，Provider 提供模型。
  • Claude Code＋Augment Context Engine：保留代理，增加项目检索能力。
  • OpenHands Canvas＋ACP 代理：保留任务界面，却可以更换执行后端。
  • Warp 中运行 Claude Code：换了终端体验，并不意味着底层自动使用 Warp 原生代理。

这些都是官方公开支持路线的例子，但安装、认证和具体版本仍要逐一核对。Zed 外部代理、Cherry 运行时、Augment MCP、OpenHands、Warp

4.3 模型中立与原生适配：自由度为什么不是免费的

一个模型要在代理中表现好，需要做到的不只是答对问题。它还需要稳定输出工具参数，理解工具错误，遵守编辑格式，在长历史中继续工作，并知道什么时候需要验证。

层次 “兼容”实际意味着什么 还不能证明什么
网络可达 API 地址、Key、认证有效 工具调用是否正确
请求兼容 能按 Chat Completions、Responses 或 Messages 等协议交互 所有参数、推理状态、图片和缓存都可用
工具兼容 工具名称、参数与结果能来回传递 模型是否会选对工具、处理失败
代理适配 提示、编辑方式、截断、压缩、重试适合该模型 在你的项目里是否更可靠
任务验证 在真实任务中满足验收、成本和人工介入要求 对所有其他任务也最好

原生路线容易把第三、第四层一起调好；开放路线让使用者有机会自行组合。MiMo 的模型特定工具配置、Grok 的多协议后端、Pi 的 Provider 扩展都说明：真正可用的模型中立需要代码和测试，不是一个下拉框。MiMo 适配、Grok 配置、Pi 扩展

对普通使用者，先用原生组合建立成功基线，再试便宜或更开放的替代品，往往比一开始同时修改模型、提示、网关和插件更容易定位问题。对平台开发者，可替换性本身就是重要收益，值得承担更复杂的验证。

4.4 上下文管理：把工作记清楚，比把窗口做大更重要

设想请一个助理整理一份报告。桌面可以放下十本书，不代表他知道哪页支持哪个结论。上下文窗口是桌面大小；检索、摘要、状态文件和记忆，才决定桌面上放什么。

方法 通俗解释 优点 容易出的问题
直接装入近期历史 把最近聊天和工具结果带上 简单，近期细节完整 历史越来越长，重要规则可能被噪声淹没
工具输出精简 大日志写文件，只带相关片段 减少重复和无关内容 关键错误可能被截掉，需要能回读原文件
历史压缩 把旧过程写成摘要 延长任务连续性 摘要可能遗漏否定条件、失败尝试和未决问题
检索 需要时查文件或历史 大资料库不必全部装入 检索不命中，模型就看不到关键材料
任务检查点 明确保存目标、进度、决定、下一步 更容易中断后继续 检查点过期，可能重复执行旧步骤
长期记忆 保存跨任务有用的偏好和事实 降低重复解释 错误或临时信息可能长期污染后续工作
子代理隔离 把探索细节放在另一会话 主任务保持清晰 摘要交接丢细节，父代理可能误信结论

源码中的代表性选择各有侧重：Goose 分主动压缩与溢出后的后备策略；Kimi 注意不切断工具交换；MiMo 保存可恢复的任务材料；Hermes 在压缩前处理记忆；DSH 从事件日志推导模型历史。Goose、Kimi、MiMo、Hermes、DSH

写长篇小说的例子。 不能只在一个聊天窗口里连续写二十章。应单独保存人物设定、时间线、地点、已发生事件与伏笔；每章结束更新这些材料，下一章只装载相关部分。全局记忆可以保存作者偏好的文风，却不应混入某一本小说中虚构的人物事实。

修复杂 bug 的例子。 检查点最好写出：已重现的现象、已经排除的假设、改动文件、通过和失败的检查、下一步。仅写“正在解决登录问题”，恢复时几乎没有帮助。

4.5 三种“记住了”，其实是三回事

聊天记录用于查“曾经说过什么”；任务状态用于知道“现在进行到哪里”；长期记忆用于判断“以后也值得知道什么”。成熟方案往往同时需要三者。

假设代理昨天帮你做预算表：聊天记录包含讨论过程；任务状态写着“还有一列公式未验证”；长期记忆只应留下你长期采用的财年和格式偏好。若把昨天估算的数字直接当作永久记忆，未来报告可能反复引用一个过期值。

稳定提示也有取舍。Chatbox 当前的会话快照能避免每轮变化打乱前缀缓存，但中途改规则未必立即生效。相反，每轮动态重读规则更及时，却可能改变任务的一致性和缓存成本。没有一种策略对所有任务都最好。Chatbox 快照设计

4.6 多代理：先判断是否真的能够拆开

形式 结构 适用任务 主要成本
单代理 一份连续上下文做完 小修复、线性任务、需要紧密共享背景 长任务可能拥挤，但交接最少
只读研究子代理 主代理委派探索，收报告 找依赖、查资料、独立审查 摘要遗漏、重复研究
主从实施 主代理规划，多工作者实施 边界清楚的模块或文件改造 合并、接口不一致、验证成本
团队与共享任务板 多代理保存任务与消息 跨阶段大任务 协调状态、并发冲突、总预算
固定工作流中的代理节点 流程确定，部分步骤由模型决定 周报、分类、资料提取、审批流程 配置和维护流程，需要显式处理失败

当前 Cline 的只读子代理与 CLI Agent Teams 恰好展示了前两种协作差别；Factory 自定义 Droid、Hermes 委派和 DSH 可换后端又提供不同程度的组织能力。它们不是同一个“多代理：是”的复选框。Cline 团队、Factory、Hermes、DSH

如果后端接口还没有确定，前端马上并行实现可能反而更慢。若三个代理都改同一配置文件，又没有工作树或责任分区，就很容易互相覆盖。值得并行的标准是任务相对独立，而不是想让屏幕看起来更忙。

总耗时也不是简单除以代理数。粗略地说：并行时间由最慢子任务，加上拆分、交接、合并与检查组成。成本则通常把各个代理的模型调用都加起来。多代理更有机会节省等待时间，却未必节省费用。

4.7 权限审批、沙箱和回滚，各自解决不同问题

机制 真正解决的问题 不负责解决的问题
提示中要求谨慎 影响模型的选择 不能强制阻止进程访问文件
操作审批 决定某次或某类动作是否允许 用户误点后仍可能造成影响
工具参数限制 限制可调用的目录、接口、命令 绕过工具的其他执行通道仍要管
系统沙箱 由操作系统限制文件／网络／进程行为 不自动理解业务动作是否正确
容器／虚拟机 分离运行环境与依赖 挂载目录、外网和凭据仍可能扩大影响
Git／文件检查点 恢复受跟踪的文件状态 无法普遍撤销邮件、付款、数据库写入
审计日志 事后知道发生过什么 不会自动阻止问题发生

Pi 默认没有权限系统，是明确选择；Codex 将权限和执行边界纳入核心；Grok Build 的公开沙箱模块区分进程与子进程网络；OpenClaw 的 Gateway 又需要额外处理远程入口和宿主执行。它们都能完成任务，但默认风险边界并不相同。Pi、Codex、Grok 沙箱、OpenClaw

对一般用户，最实用的做法是让代理在任务目录工作，使用独立分支或副本；对可能影响外部系统的动作，只提供必要账户权限。不是每一步都要弹窗，而是让真正不可轻易撤销的步骤有清楚边界。

4.8 自由代理与固定工作流：业务稳定后，未必还需要处处自治

自由代理适合未知问题，例如“查清这个测试为什么偶尔失败”。下一步需要随证据变化，事先很难画出完整流程。

固定工作流适合已知业务，例如“每周读取三张表，计算指标，生成草稿，经过负责人确认后归档”。哪些数据来自哪里、怎样验证、失败后怎么办，最好显式定义。Dify、n8n、AnythingLLM Flow 属于值得比较的相邻路线。

两者可以嵌套：外层用确定流程控制触发、权限、格式和审批，内部某一步让代理自主研究。这通常比让一个通用代理每周重新猜一遍公司流程更容易维护。

4.9 本地、云端和自托管：必须拆成三条数据流

“桌面应用”只说明一部分界面或逻辑在电脑上；模型仍可能在云端，联网搜索和嵌入也可能经过第三方。真正的全本地方案，需要检查这几条路径都在哪里。

方案 收益 成本与限制
本地 Harness＋云模型 使用自己的文件和工具，模型能力选择多 选中的内容仍会发给模型服务
本地 Harness＋本地模型 更强的数据路径控制，可离线 硬件、速度、模型能力与服务维护
托管 Harness＋云环境 起步快，远程任务容易持续 对平台环境、账户和计费依赖更高
自托管服务＋云模型 可统一用户和流程 自托管不意味着推理数据不出网
自托管服务＋内网模型与工具 全链路控制空间较大 运维、权限隔离、备份和容量规划最复杂

4.10 开放源码、开放模型、开放协议，是三种不同的自由

开放源码让你有机会理解和修改 Harness；开放权重让你有机会自己部署模型；MCP／ACP 等协议让部件更容易互接。三者可以独立存在。

同样，“代码看得见”不代表任意商业使用都没有限制；“模型权重能下载”也不代表训练数据、训练过程与全部许可条件都开放。正式部署前应检查具体版本的许可证，而不要把产品统称为“开源”后就停止核对。

4.11 不应做一张总分榜，而应找出你的首要瓶颈

经常遇到的困难 优先改哪一层 先比较哪些方向
总找不到正确文件 检索、项目说明、索引 Augment、IDE 上下文、准确文件引用
模型会解释但改不对 工具适配、编辑方式、模型能力 原生 Claude Code／Codex 等组合
长任务跑着跑着忘事 检查点、压缩、状态恢复 MiMo、Hermes、任务型平台及明确进度文件
改好了但交付很麻烦 环境、测试、PR 与产物管理 Copilot 云端、Devin、OpenHands、Factory
资料库答案不准确 导入质量、切分、检索、引用 AnythingLLM、Open WebUI、LibreChat 的检索配置
每天重复解释偏好 可维护记忆与规则 Hermes、Chatbox／Cherry 的规则和工作空间
多人用起来互相干扰 账户、权限、环境隔离 有组织治理的托管方案或认真配置的自托管服务
成本高却不见收益 任务拆分、重试、缓存、人工介入 先测量，不急着换最便宜或最强模型

当你知道瓶颈在哪一层，选型会简单很多。接下来按细分使用场景寻找两三个候选即可，无需安装完整名单。

5.5 三个可以直接照着组织的工作方案

方案一：一个人做中型 Web 项目

选一套主力即可：Codex＋Terra／Sol，或 Claude Code＋Sonnet 5。仓库保存项目说明、运行命令与验收标准。先实现一条最小完整流程，再扩展其他功能。

遇到困难时，先让主代理说明卡点和证据，再提高模型能力；只有前后端接口稳定、任务真的独立时才引入子代理。浏览器验证可以来自原工具或额外连接器，但必须真正走过核心用户路径。

输出至少包含可运行代码、必要测试、启动说明和已知限制。接受代码之前看 diff，部署另作一个明确步骤。

方案二：持续写长篇中文小说

用 Cherry／Chatbox 管理对话与稿件，或者用 Hermes 管理跨会话工作。模型先通过小样盲评选定，再固定一段时间，不要每章都换。

建立四份材料：人物表、时间线、世界规则、章节与伏笔账本。每章输入包含本章目标、相关设定与上一章必要信息；生成后先做情节一致性检查，再润色语言。只将确认后的变化写回设定库，避免草稿想法被当成正史。

这里不需要代理任意访问邮件或执行系统命令。工具应围绕读取设定、写稿、对照和保存版本来配。

方案三：每月固定业务报告

第一次可以用 Codex／Cowork 等探索数据与报告格式；稳定以后，把数据来源、口径计算和模板沉淀下来。定期生产可用 n8n／Dify 组织，模型负责解释变化与组织语言。

用程序计算数字，用检索找支持材料，让模型解释；三者职责分清。缺数据时标记缺失，不允许模型补造。正式发出之前，人工核对关键指标与敏感表述。这样比每个月让通用代理从头猜流程更容易控制质量。

6.3 怎样判断模型适不适合某个 Harness

按这个顺序检查，比一次跑一个庞大任务更有效：

  1. 基础输入输出。 中文、代码、文件片段是否正常；需要图像时，实际请求有没有把图像发送给支持图像的模型。
  2. 工具往返。 能否正确调用一个只读工具，读取结果，再作下一步决定。
  3. 编辑与验证。 能否按该工具要求修改文件，并用正确命令验证。
  4. 错误恢复。 文件不存在、命令失败、工具参数不合法时，能否根据错误调整，而不是重复同一错误。
  5. 历史与压缩。 会话变长或恢复后，是否记得关键约束；工具调用与结果有没有失配。
  6. 控制与成本。 中断能否生效；子任务是否继续烧费；模型窗口、输出上限与 Harness 的估算是否一致。

某些模型需要保留推理状态、签名或特定响应字段。网关如果只转发文本，看起来仍能聊天，却可能破坏长任务。也有服务仅在协议表面兼容，实际不支持某些参数。遇到这种问题应先核对适配层，而不是立即认定模型“变笨”。

本地模型的主要收益是数据路径控制、可定制与不依赖外部推理服务。它并不天然更便宜或更快，尤其是在硬件已经不足、任务又需要很多重试时。

硬件的一个简单估算。 如果有 300 亿参数，粗略按每参数 4 bit 保存，仅权重理论下限约为 15 GB。实际还要加上量化元数据、运行缓冲、上下文缓存等，不能由此推出“16 GB 电脑一定能流畅运行”。不同架构和推理引擎也会改变实际需求。

MoE 模型每步只激活一部分参数，主要影响计算量；不能仅按活跃参数估计全部权重占用。上下文越长、并发越多，也可能越吃内存。先用短上下文测实际资源，再逐步扩展。

完全本地需要整条链都本地。 回答模型、嵌入模型、文档解析、搜索、语音、工具与日志都可能是独立服务。尤其知识库工具即使用本地回答模型，也可能仍把文档发给云端嵌入接口。

6.5 成本要按“完成一项可接受的任务”来算

同样一次“帮我修 bug”，背后可能调用几十次模型；子代理、摘要、标题生成、检索和重试都可能增加消耗。并行让等待缩短，不会自动让所有分支只收一份费用。

多代理完成得快 总调用量、重复调查与合并成本

Qoder 的 Repo Wiki 单独计费就是一个具体例子：主对话使用 BYOK，不代表产品里的所有模型能力都改走同一账户。Factory 文档又说明不同入口对 BYOK 的支持范围不同。因此应读到功能级别，不能只看产品首页的一个词。Qoder、Factory

缓存与压缩也有取舍

模型服务可能对重复输入提供缓存优惠。稳定的项目规则与工具列表有利于复用；频繁修改系统提示、切模型或更换工具集合，可能降低命中。另一方面，为了缓存而保留大量无关历史，也可能让任务更难理解。

压缩通常需要额外模型调用，且可能丢信息。合理目标是保留足够准确的任务状态，而不是让 Token 指示器始终最低。某次压缩少花了一点钱，却导致代理重做整个调查，整体并不划算。

6.6 订阅、API 与网关：使用前把钱和数据的路径画清楚

接入方式 谁提供模型 谁向你计费 需要确认什么
产品内置订阅／额度 平台选择或转售的模型 产品平台 包含哪些入口、模型、上限和额外费用
官方 API Key 模型厂商 模型厂商，可能另有平台费 模型权限、余额、地域和数据设置
第三方网关 网关路由到上游 网关，可能加价或另有规则 实际模型、日志、协议转换、失败处理
本地／内网服务 自己部署的模型 硬件与运维资源 模型格式、版本、许可、容量和出口

优先使用产品官方支持的认证方式。不要因为某个不明插件声称能共用订阅，就默认它受到模型厂商支持；也不要将账户凭据交给未经核实的中间服务。

6.7 一个简单的升级策略

先用中等档位完成普通任务；若失败，要求代理说明证据和卡点。只有确实需要更复杂推理、更长资料理解或更稳定工具使用时，才升级模型。机械批处理先用小样评估经济模型，达到标准后再放大。

对重要任务，可以让第二个模型或独立代理审查，但它必须查看原始材料与实际结果。只让另一个模型阅读第一份答案，容易变成互相认可，而不是独立验证。

模型升级是解决问题的一条路径；更好的输入、项目说明、工具、检索和验收，常常同样重要。

7.3 记录结果，而不只记录“感觉不错”

建议使用目录中的评估记录模板。每个任务至少记录：

  • 产品与版本、实际模型、Provider、关键参数。
  • 是否完成验收，出现了什么错误。
  • 人工干预次数，以及干预的内容。
  • 总费用、总等待时间、人工检查与返工时间。
  • 修改是否容易审查，能否解释依据。
  • 中断、恢复、导出和迁移是否正常。

“代理自己说完成了”不算通过。若没有独立检查，就将该任务记为未验证，而不是成功。

结果正确、达到验收 40% 35%

7.6 迁移时，哪些东西通常容易搬，哪些很难

资产 可迁移程度 建议
Markdown 项目规则 通常较高 保留一份核心规范，再按产品文件名适配
Skills 文档 内容通常可搬，元数据与触发语义可能不同 检查工具名称、路径和入口差异
MCP 工具连接 协议可复用，认证与权限未必相同 重新核对凭据和工具白名单
模型 API 配置 需按协议调整 不直接复制不明私有字段
对话导出 常能保留阅读记录 不等于能恢复原始代理状态
子代理配置 差异大 重新定义职责、权限、模型和交接
检查点与执行日志 往往与运行时耦合 保留面向人的进度文件和真实产物
云端项目环境 迁移成本较高 保存构建说明、数据导出和依赖清单

将长期知识保存在可读文件中，往往比把全部工作记忆只留在某个产品私有数据库里更容易迁移。但也不能认为复制一个 JSON 历史文件，就已经复制了凭据、进程、工具状态和远程环境。

7.7 新版本来了，应该重测什么

没有必要每次全面重做所有任务。优先复测发生变化的部分：模型别名更新后检查工具与长任务；压缩机制更新后检查恢复；权限默认值变化后检查受限动作；新增团队功能后检查取消、预算和共享文件冲突。

保留一个已知稳定的版本与配置，升级后若真实任务退化，可以有依据地回退。不要只记录“昨天好用、今天不好用”，尽量记录变化前后的具体组合。

08｜研究方法、证据与参考资料

8.1 本报告实际做了什么

本次研究以 2026 年 9 月 22 日 的公开材料为时间截面，先做候选发现和维护筛选，再采集公开仓库目录、文档与核心源文件，并围绕以下路径检查实现：

用户任务进入 → 组织上下文 → 请求模型 → 分派工具 → 权限与执行 → 保存结果 → 压缩／记忆／子代理 → 恢复、结束与验证。

本报告形成 45 个核心工具／产品家族档案、5 个相邻或转移重点项目、4 个维护观察条目和 40 个场景建议。41 个仓库快照包含支持性仓库，例如 OpenHands SDK、VS Code 和 Qwen 文档仓库，因此“仓库数”不是“独立产品数”。

对“通读代码库和所有文档”的诚实说明： 本次没有完成几十个项目全部文件的逐行阅读，也没有完整审计每一项依赖；闭源商业运行时本来就不可全部取得。实际深度是：对收集仓库做文件目录普查，保存广泛文档与按主题筛选的源码，对核心执行路径、架构文档和关键边界进行重点阅读。不能把下载过、检索到或自动摘录过，写成已经逐行读完。

报告也没有对所有工具安装运行、购买全部模型套餐或开展统一性能基准。故“适合”“优先试用”属于有来源约束的选型分析，不能解释为实测速度、成功率或安全保证。

如果要公平比较 Harness，理想方法是固定模型和任务，再改变运行外壳；如果要比较完整产品，就允许各自使用原生配置，但同时记录总费用、人工介入与功能限制。两种实验回答的问题不同，不应混在一张分数表中。

8.6 适合继续追踪的变化
