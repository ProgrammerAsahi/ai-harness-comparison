# 03C｜个人助理与知识工作台：围绕长期信息和日常工作组织代理

这类工具的起点通常不是一个 Git 仓库，而是人、资料、对话和外部应用。它们越来越多地加入代码执行、子代理、浏览器和定时任务，因此不能沿用“都是聊天皮肤”的旧判断。

这里更需要问三个问题：**长期记忆存在哪里？谁能触发任务？代理操作的是哪个人的账户和工作空间？** 同样一次工具调用，放在一个临时编程会话中，与放在持续在线的聊天机器人里，管理难度很不一样。

## C01 Hermes Agent：把一次任务的经验变成下一次可用的材料

**理念。** Hermes 将长期使用放在中心：会话可以检索，经验可以写成记忆和 Skills，任务可以从 CLI、消息渠道或自动化入口到来。“会越用越懂你”在工程上主要意味着保存并重新使用材料，不是每聊一次就训练模型权重。[README](https://github.com/NousResearch/hermes-agent/blob/42c1a93417fa588e735736a0740787ce37381ffd/README.md)

**源码结构。** Python 会话循环把模型请求、上下文准备、工具分派和结果处理拆成多个部分；模型协议经适配后进入统一执行逻辑。记忆管理又通过独立 Provider 接口工作。在压缩前保存必要信息，是避免长任务丢失关键进展的一条路径。[循环](https://github.com/NousResearch/hermes-agent/blob/42c1a93417fa588e735736a0740787ce37381ffd/agent/conversation_loop.py)、[记忆管理](https://github.com/NousResearch/hermes-agent/blob/42c1a93417fa588e735736a0740787ce37381ffd/agent/memory_manager.py)

**子代理并不是共享大脑。** 委派工具为子任务建立独立代理，主代理通常只看见任务与摘要，而不是所有中间步骤。源码还为子任务处理模型覆盖、工作树、取消和预算。特别要注意，子代理可以有自己的运行预算，父任务上限不能直接当作整棵任务树的总成本上限。[委派工具](https://github.com/NousResearch/hermes-agent/blob/42c1a93417fa588e735736a0740787ce37381ffd/tools/delegate_tool.py)

**怎样使用。** 先只启用本地 CLI 与一个模型，完成资料整理或项目研究；确认会话检索和记忆内容有用后，再接消息渠道、定时任务和外部工具。把长期偏好、项目事实、临时任务进度分开保存，避免一次性的错误结论成为永久偏好。

**模型与适用方向。** 建议用可靠的 GPT／Claude 工具模型建立基线；中文任务与成本敏感场景比较当前适配的 Kimi、Qwen、DeepSeek。接本地模型时应检查真实上下文和工具调用能力，不能只看模型参数。适合持续研究助理、个人工作自动化、跨会话项目管理、从重复工作积累 Skills。难度：CLI 中；长期在线与多渠道运维高。

## C02 OpenClaw：让个人代理持续在线，连接不同渠道与设备

**理念。** OpenClaw 更像个人代理的接线与运行中心。Gateway 维持长连接、渠道、会话和设备关系；手机、桌面、消息平台可以成为交互入口。它不只是把同一聊天框复制到几个应用。[架构文档](https://github.com/openclaw/openclaw/blob/b419a4add99ff917504ed26168babdbde6ac7ab6/docs/concepts/architecture.md)

**关键架构。** Gateway 管理连接与任务进入方式，具体代理运行时负责模型和工具循环。当前文档已经涉及不同运行时路径，因此不宜永久把它概括成某一版本 Pi 的简单包装。每个会话的任务通常串行化，持久化写入还需要确认当前运行是否仍拥有写入资格，防止被替代的旧任务把过时状态写回去。[代理循环](https://github.com/openclaw/openclaw/blob/b419a4add99ff917504ed26168babdbde6ac7ab6/docs/concepts/agent-loop.md)

**长期记忆。** 工作空间中的记忆材料、会话摘要、检索和后台整理共同服务持续使用。这里有一个实际取舍：记忆越多，维护和纠错越重要。能记住一句话不代表知道它何时过期，用户需要能够查看、修正和删除。[记忆设计](https://github.com/openclaw/openclaw/blob/b419a4add99ff917504ed26168babdbde6ac7ab6/docs/concepts/memory.md)

**怎样使用。** 先部署一个 Gateway，完成设备／渠道配对，只接一个工作入口，验证谁能向代理发指令。随后配置工具权限和沙箱。默认宿主机执行与显式沙箱是不同状态，不能因为产品是自托管就假定工具已经隔离。最后再开放定时任务或更广的渠道。

**模型与适用方向。** 依据实际运行时选模型；原生多 Provider 路线可比较强工具模型，若接 Codex 等运行时则遵循其原生模型配置。适合跨设备个人助理、消息入口统一、长期自动化。单纯偶尔问答或修一个 bug，部署整个持续服务可能没有必要。难度：高，主要高在服务、账户与权限管理。

## C03 Agent Zero：给代理一套可以动手操作的工作环境

**理念。** Agent Zero 偏向通用任务代理：让模型在可操作的计算环境中使用工具、编写程序、处理资料和分派任务。提示、工具、扩展和工作空间可以被用户修改，因此它兼具产品与实验平台的性质。[README](https://github.com/agent0ai/agent-zero/blob/b1cbd1f960a1a5c4482b324dcff4742aa67b7a51/README.md)

**执行结构。** `agent.py` 的循环反复准备提示、调用模型、处理工具，并在多个节点触发扩展与用户干预。子代理通过上下级关系和独立配置组织，具体任务可以交给不同职责的下属。这套设计容易扩展，但扩展一多，排查行为变化也更费力。[主循环](https://github.com/agent0ai/agent-zero/blob/b1cbd1f960a1a5c4482b324dcff4742aa67b7a51/agent.py)、[下属代理](https://github.com/agent0ai/agent-zero/blob/b1cbd1f960a1a5c4482b324dcff4742aa67b7a51/tools/call_subordinate.py)

**怎样使用。** 按官方方式准备容器或工作环境，先配置模型与文件范围。用“读取一批文件，生成索引与一份报告”这样的任务检验文件、浏览器和输出保存能力，再考虑更长任务。容器仍可能挂载宿主目录或持有外部凭据，边界应看实际挂载和授权。

**模型与适用方向。** 优先能稳定处理工具、多轮纠错和代码执行的模型，如当前适配的 Claude／GPT；成本方案再比较开放模型。复杂编排对小模型的稳定性要求高，不宜只按每百万 Token 单价选择。适合技术用户的资料处理、自动化、通用代理实验。难度：中高；无人值守部署高。

## C04 Chatbox AI：低门槛客户端正在长出真正的工作模式

**先纠正旧印象。** Chatbox 的经典价值是多模型聊天、文件与对话管理，但当前公开技术文档已经描述 Agent／Work 模式、工具、Skills 和记忆。因此它不应再被一概排除在 Harness 讨论之外。商业发行版与社区源码也有差别，功能判断必须标注版本。[项目说明](https://github.com/chatboxai/chatbox/blob/0cf406cbd93197a89487c740cb101bef36641d35/README.md)、[功能页](https://chatboxai.app/en)

**一个具体设计。** 当前 Agent 模式将身份、Soul、个人偏好、工作目录说明与工具信息组装成提示；会话首次启动时保存一份上下文快照。稳定前缀有助于缓存和一致性，但代价是中途修改某些规则，不一定立刻影响这段既有会话，需要新会话或相应重捕获条件。[提示与记忆设计](https://github.com/chatboxai/chatbox/blob/0cf406cbd93197a89487c740cb101bef36641d35/docs/technical/agent-soul-memories.md)

Skills 则可以按需加载，避免把所有工作手册每次全塞进去。Provider 层区分模型配置和实际协议适配；“某服务兼容 OpenAI”并不意味着所有参数与推理行为一致。[Skills](https://github.com/chatboxai/chatbox/blob/0cf406cbd93197a89487c740cb101bef36641d35/docs/technical/agent-skills.md)、[Provider 设计](https://github.com/chatboxai/chatbox/blob/0cf406cbd93197a89487c740cb101bef36641d35/docs/technical/ai-providers.md)

**怎样使用。** 先用 Chat 模式连接一个模型，熟悉历史、文件和导出；确需写文件、执行任务时再启用 Work 模式。把长期写作偏好放在可查看的规则中，把某一份报告的事实留在项目材料里。修改全局人格后，要确认它对当前会话是否已生效。

**模型与适用方向。** 日常写作可比较当前接入的 Claude、GPT、Kimi／Qwen；工作模式更应优先可靠工具调用。适合一般用户、报告润色、翻译、资料讨论和轻量本地任务。复杂团队开发或持续在线服务不是其最自然的起点。难度：聊天低；Agent 中。

## C05 Cherry Studio：多模型桌面工作台，也可以成为其他代理的宿主

**理念。** Cherry 面向同时使用多个模型、资料和助手的人。当前架构已经从普通多模型对话扩展到独立 Agent Session 运行时，因此“多个模型各答一遍”和“多个代理分工执行”需要分别讨论。[README](https://github.com/CherryHQ/cherry-studio/blob/633729727543cfe7ccab776cc08e3a24fa7a925d/README.md)

**当前架构。** Electron 界面通过进程间通信交给主进程的 AI 服务；主进程负责流、持久化与不同消费者。Agent Session 又区分宿主服务与具体驱动：宿主管会话、排队、恢复标记和界面生命周期，驱动对接 Claude Code、Pi、DSH 等不同执行后端。这是“统一工作台＋不同引擎”的明确例子。[核心架构](https://github.com/CherryHQ/cherry-studio/blob/633729727543cfe7ccab776cc08e3a24fa7a925d/docs/references/ai/core-architecture.md)、[Agent Session](https://github.com/CherryHQ/cherry-studio/blob/633729727543cfe7ccab776cc08e3a24fa7a925d/docs/references/ai/agent-session-runtime.md)

这也带来边界：统一界面不意味着各后端的工具、审批和恢复语义完全一致。切换后端时，应确认原来的任务状态与权限怎样处理，而不只是看聊天记录还在不在。

**怎样使用。** 普通知识工作先配置模型、助手和资料；需要任务执行时创建明确工作空间，并选择运行后端。别一次导入所有个人文件。用一份报告或一个小项目检验资料引用、生成文件与恢复任务。

**模型与适用方向。** 普通对话可自由比较 GPT／Claude／Kimi／Qwen；Agent 驱动则依其后端来选，例如 Claude 驱动优先 Claude、Pi／DSH 按对应适配。适合中文用户、多模型比较、知识整理、希望保留桌面统一入口的人。难度：基础低；多运行时管理中高。

## C06 Open WebUI：自托管的共享 AI 门户，工具执行能力取决于部署

**理念。** Open WebUI 常被用于为本地或远端模型提供统一网页入口。其能力已经延伸到用户权限、知识检索、工具、MCP／OpenAPI 接入以及终端执行相关能力。它既可能是一套聊天门户，也可能被配置成真正的代理工作台。[README](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/README.md)

**架构与边界。** 后端中间层组织消息、模型服务、检索与工具结果，工具模块再结合用户权限暴露能力。换句话说，模型本身未必知道你公司的全部数据，是后端决定哪些资料和工具能够进入这轮任务。[中间层](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/utils/middleware.py)、[工具处理](https://github.com/open-webui/open-webui/blob/8bd8b4fac5e059578ac0c74b3c18d11139f88b7d/backend/open_webui/utils/tools.py)

一旦接上 Open Terminal 等执行能力，就必须检查每个用户的文件、进程和凭据边界。模型服务“只在内网”不能替代用户间隔离。插件或自定义代码也可能访问服务进程本身能够访问的资源。

**怎样使用。** 单人部署先连接模型并关闭不需要的能力；多人使用再配置账户、知识库权限、备份和配额。先用已知答案测试资料检索，再考虑加工具。需要真正离线时，连嵌入、搜索、语音、遥测和工具出口一起检查。

**模型与适用方向。** 与 Ollama／兼容服务的本地模型组合适合内网问答；较难知识任务可接强云端模型，但数据会按配置流向相应服务。适合团队共享入口、内网知识库、本地模型试用。难度：单人中；多人服务高。

## C07 LibreChat：以对话产品为入口，扩展到可配置的 Agent 运行

**理念。** LibreChat 将多 Provider、用户系统、历史和工具放在熟悉的聊天界面中，同时提供 Agent Builder、子代理／多代理和代码执行等能力。它适合希望自行托管一个统一 AI 工作入口的团队。[README](https://github.com/danny-avila/LibreChat/blob/ef89fbd5b3840ef9b628ab0763a862623cdce18b/README.md)

**源码结构。** 服务端创建运行时，将模型、消息、工具、摘要、子代理配置和追踪信息交给 Agent 执行包。它并非只转发一个 HTTP 请求；会话、工具发现和长期运行需要由服务端管理。但底层依赖的完整实现还在其他包里，本报告不把单个仓库的导入语句当作已经审计整个依赖树。[运行创建](https://github.com/danny-avila/LibreChat/blob/ef89fbd5b3840ef9b628ab0763a862623cdce18b/packages/api/src/agents/run.ts)、[客户端衔接](https://github.com/danny-avila/LibreChat/blob/ef89fbd5b3840ef9b628ab0763a862623cdce18b/packages/api/src/agents/client.ts)

**怎样使用。** 按官方部署文档配置数据库与模型入口，先建立一个只读研究 Agent，再逐步增加工具。团队使用时检查用户凭据与共享 Agent 的关系，确认谁能修改 Agent、谁能调用其工具、历史是否互相隔离。

**模型与适用方向。** 选型建议是针对每个 Agent 的职责固定模型：资料摘要可用经济档，代码执行与复杂工具链用更稳的档位。可选家族以当前适配目录为准。适合共享助理、团队研究、统一模型管理和自定义业务 Agent。难度：中高，尤其需要维护服务与数据库。

## C08 LobeHub：从“助手集合”走向有状态的协作工作台

**理念。** LobeHub 已不能只按早期 LobeChat 的界面理解。当前方向包括 Agent、工具与协作，其价值是让不同职责的助手与任务状态在同一工作台中组织起来。[README](https://github.com/lobehub/lobehub/blob/035f1e7476eb8a3c66befb76f16ae25673d31e4a/README.md)

**源码中的执行模型。** AgentRuntime 接收代理产生的指令，再执行调用模型、调用工具、请求人工审批或结束等动作。批量工具可从同一基础状态并行执行，再合并结果；服务端协调器负责更完整的运行生命周期。这样将“决定下一步”和“实际执行下一步”分开，便于扩展，但并行结果是否相互冲突仍需要上层语义处理。[运行时](https://github.com/lobehub/lobehub/blob/035f1e7476eb8a3c66befb76f16ae25673d31e4a/packages/agent-runtime/src/core/runtime.ts)、[协调器](https://github.com/lobehub/lobehub/blob/035f1e7476eb8a3c66befb76f16ae25673d31e4a/apps/server/src/modules/AgentRuntime/AgentRuntimeCoordinator.ts)

**怎样使用。** 先建立一个职责清楚的 Agent，例如“只根据团队资料回答产品问题”；确认工具和知识来源，再扩展为多个角色。不同人设不一定需要不同代理进程，只有确实需要独立状态、权限或执行时才增加角色。

**模型与适用方向。** 根据当前 Provider 支持选择 GPT、Claude 或中文模型；多角色可以各用不同档位，但应防止风格统一掩盖证据矛盾。适合希望把聊天、资料与多个工作角色集中管理的个人和团队。难度：托管使用低中；自托管与协作治理中高。

## C09 AnythingLLM：围绕工作空间里的资料组织问答和流程

**理念。** AnythingLLM 的自然起点是一个资料工作空间：导入文档、处理与建立索引、按问题检索，再由模型回答。Agent 与 Flow 在此基础上连接外部动作。因此它对“围绕一批固定资料反复工作”的任务很合适。[README](https://github.com/Mintplex-Labs/anything-llm/blob/d401491d67ee88c40d04ab67d71b7360ca6627b4/README.md)

**架构。** 文档处理、嵌入、向量检索、生成模型是不同部件，可以分开选择。执行层还有 Agent 对话管理与 Flow 执行器。当前所检查的 Flow 实现按步骤运行、传递变量，遇到错误或直接输出条件结束；这与让模型自由决定所有下一步的循环不同。[Agent 管理](https://github.com/Mintplex-Labs/anything-llm/blob/d401491d67ee88c40d04ab67d71b7360ca6627b4/server/utils/agents/aibitat/index.js)、[Flow](https://github.com/Mintplex-Labs/anything-llm/blob/d401491d67ee88c40d04ab67d71b7360ca6627b4/server/utils/agentFlows/executor.js)

**怎样使用。** 先创建单一主题工作空间，导入经过整理的资料；用五到十个有标准答案的问题测试检索。确认引用的原文能支持回答，再做 Agent Flow。桌面版和多人服务的管理能力不同，应按实际部署选择。

**模型与适用方向。** 回答模型可以是云端 GPT／Claude／Kimi，也可以是本地模型；嵌入与检索设置同样影响结果。如果资料根本没检索到，升级生成模型通常只能得到更流畅的错误答案。适合个人文档库、内部手册问答、固定材料上的工作报告和可重复资料流程。难度：桌面低中；多人部署中高。

## 普通知识工作者还应认识的相邻产品

完全不想管理 Provider、运行环境和工具的人，也应比较原生托管工作产品，例如 **ChatGPT Work、Claude Cowork**。它们把模型、连接器和工作空间作为一套产品提供；与自由换模型的 Harness 相比，更接近整套办公服务。Claude Cowork 的官方说明强调围绕文件与应用执行工作；ChatGPT 的能力和模型则按具体产品与账户开放。[Cowork](https://claude.com/product/cowork)、[OpenAI 官方产品文档](https://learn.chatgpt.com/docs/llms.txt)

Manus 的官方资料还描述了持续运行的云端计算环境，属于值得关注的相邻路线。[Cloud Computer](https://help.manus.im/en/articles/15392111-what-is-the-cloud-computer) Genspark、Perplexity Computer、Kimi 的办公产品，以及各类 AI 应用生成器，也处于相邻市场。但本次没有对它们全部建立同等级源码／架构证据，因此不把它们混进“已深读的开放 Harness”数量。对于只想完成一份报告的用户，选择托管产品往往值得考虑；对于要研究和替换代理内部结构的人，开放 Harness 更合适。

同样，LM Studio、Ollama 主要帮助运行和服务模型；SillyTavern 等更偏创作／角色对话；LangGraph、AutoGen、CrewAI 等偏开发框架。它们可能进入一套完整方案，但不应与开箱即用的代理产品在同一张总分表里硬排高低。
