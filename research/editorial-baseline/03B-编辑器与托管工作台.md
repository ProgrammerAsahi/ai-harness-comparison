# 03B｜编辑器与托管工作台：把代理放进完整的工作流程

这一类产品通常替用户整合了界面、项目上下文、账户、模型路由和任务管理。代价是：可替换的部件少一些，产品方案、套餐和管理策略的影响更大。

**阅读边界：** Zed、Neovim 插件与 VS Code 的相关部分有公开源码；本章多数商业产品没有公开完整运行时。以下架构是根据官方接口和功能还原的责任分工，不冒充内部源码审计。模型建议均以所在入口和账户实际可选为前提；“Auto／内置路由”本身也是一种合理组合，不必硬填一个产品没有开放选择的模型名。

## B01 Cursor：把编辑器里的即时上下文变成代理的工作起点

**理念与结构。** Cursor 的优势是人仍在编辑器中工作，代理却能持续获得文件、选择区域、诊断与项目线索，并直接提出和执行修改。Agent 的工具、指令与模型适配共同构成执行体验；代码索引是帮助它找到相关材料的一条路径，不意味着每轮把整个仓库全部塞给模型。[Agent 文档](https://cursor.com/docs/agent/overview)

当前产品还扩展了子代理、项目协调和云端工作。应把本地交互式编辑、后台任务和自动化分别评估：它们接触的环境、凭据和可运行时长可能不同。子代理能够减少主对话被探索细节占满的问题，但最终仍要有人检查集成结果。[子代理](https://cursor.com/docs/subagents)

**使用方式。** 打开仓库，先让 Agent 解释一个具体模块，再交付小功能。为常见任务保存规则，查看 diff 后接受修改。只需要补全一行或修改一个函数时，使用轻量编辑能力即可，没有必要启动漫长自治任务。

**模型搭配与场景。** 日常可以从内置 Auto／Composer 路线开始，需控制变量时固定当前目录中的 Claude 或 GPT 型号。当前 Auto 还区分成本、平衡、智能等路线，收费与路由不能用早期套餐规则代替。它适合前端迭代、跨文件小中型实现、边写边改；如果要求每个模型、每条系统提示都由自己掌控，开放 Harness 更合适。难度：低中。[模型与计费](https://cursor.com/docs/models)

## B02 GitHub Copilot：嵌入代码协作平台的一组代理入口

**先拆开品牌。** Copilot 的补全、IDE Chat／Agent、CLI 和云端编码代理不是同一个执行环境。IDE 代理在开发者附近修改和验证；云端代理围绕 issue、分支、PR 等协作对象工作。选择 Copilot，往往也是选择 GitHub 的协作入口、组织账户和审查流程。[官方功能文档](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)

**源码能看到什么。** 旧 `microsoft/vscode-copilot-chat` 已归档，相关开发迁入 VS Code 主仓库。不能因旧仓库归档就断言 Copilot 停止开发，也不能因 VS Code 开源就声称 GitHub 托管代理的全部服务端已经开源。公开仓库用于核对编辑器侧实现，云端行为以服务文档为准。[旧仓库](https://github.com/microsoft/vscode-copilot-chat)、[VS Code 当前源码](https://github.com/microsoft/vscode)

**使用方式。** 已经在 GitHub 团队中工作的人，可以先从 IDE 的限定任务开始，再把成熟的重复修复交给 issue／PR 流程。任务必须有测试命令与验收条件；PR 被创建不等于代码已经通过审查和合并。

**模型搭配与场景。** 当前支持目录包括多个 GPT、Claude、Gemini 和其他型号，但可用性按产品入口划分，不能把网页目录的并集当成某个按钮的选项。日常选择入口中可用的 Sonnet 5／GPT-5.6 Terra；复杂任务比较更强型号或内置路由。适合现有 GitHub 团队、代码审查、常规维护、从 issue 到 PR 的工作。难度：个人低中；组织治理中。[模型支持矩阵](https://docs.github.com/en/copilot/reference/ai-models/supported-models)

## B03 Devin／Devin Desktop：从编辑器协作延伸到远程交付

**命名变化。** 旧 Windsurf 文档已迁入 Devin Desktop 文档体系，Cascade 仍是需要辨认的本地代理体验；它与 Devin 云端任务不能混为一谈。报告按产品家族合并说明，避免将迁移前后的名字重复计成两个完全独立竞品。[Cascade 文档](https://docs.devin.ai/desktop/cascade/cascade.md)

**理念与结构。** 本地 Cascade 围绕编辑器上下文、规划、代码修改和检查点工作；远程 Devin 更强调把仓库、执行环境、任务和协作交付组织起来。需要企业自有基础设施时，还有 Outposts 路线。其架构差别主要在“工作机和任务生命周期由谁管理”，而不只在模型名字。[Devin 入门](https://docs.devin.ai/get-started/first-run.md)、[Outposts](https://docs.devin.ai/cloud/outposts/overview.md)

**使用方式。** 本地边写边改选 Desktop；任务清晰、可以在独立环境重现时再交给远程代理。准备仓库说明、环境安装命令和验收步骤，比一句“帮我完成需求”更重要。可并行的任务应有清楚的文件或模块边界。

**模型搭配与场景。** Desktop／CLI 以当前模型选择器为准，可比较其支持的 Claude、GPT、Gemini、Cognition 及开放模型；云端原生任务则优先使用产品调优的默认组合，不臆造无限 BYOK 能力。适合团队中长任务、异步修复、迁移和远程交付；即兴的小修改未必值得环境启动与任务交接成本。难度：本地低中；远程部署中高。[CLI 模型说明](https://docs.devin.ai/cli/models.md)

## B04 Kiro：让需求、设计和任务清单成为持续上下文

**理念。** Kiro 的辨识度在于 Spec 工作方式：先把需求、设计与实施任务写成可查看、可修改的材料，再让代理推进。它适合需求需要解释、多人需要对齐、实现时间跨度较长的项目。Spec 的价值是明确共识，不是生成文档越多越好。[Specs](https://kiro.dev/docs/specs/)

**架构。** 官方说明将其描述为跨 IDE、CLI、Web、移动入口的统一独立进程 Harness，通过 ACP 及相关扩展连接客户端。规则、Hooks、MCP、Skills 等围绕同一个核心配置，但功能在各入口仍有差异。“同一核心”意味着复用执行责任，不意味着所有界面功能完全相等。[工作原理](https://kiro.dev/docs/how-kiro-works/)

**使用方式。** 从一个需要两三步实现的小需求开始，让它产生需求、设计与任务；删掉空泛内容，补入验收标准，再实施。需求很简单时直接对话即可，否则写规范的成本可能比修 bug 本身还高。

**模型搭配与场景。** 当前 Kiro 已提供多个 GPT、Claude 和其他模型，并非只支持某一个旧 Claude 版本。一般从 Auto 或可用的 Sonnet 5／GPT-5.6 Terra 开始；复杂规范与实现比较更强档位。预览模型受地区与组织治理约束。适合中型功能、正式需求开发、跨人协作、验收明确的长期改造。难度：低中；高质量 Spec 写作需要业务判断。[模型矩阵](https://kiro.dev/docs/models/)

## B05 JetBrains Junie：让代理使用 IDE 已经理解的代码结构

**理念与架构。** Junie 的差异化在 JetBrains IDE 的代码理解能力：项目、符号、导航、诊断和运行配置已经存在，代理可以借此工作，而不必完全依赖文本搜索。当前产品还包含 CLI、CI 和远程监控等入口，已经不是只能在 IDE 中调用单一模型的小功能。[官方产品页](https://junie.jetbrains.com/)

**工作方式。** 计划阶段可以形成可编辑、可提交的需求／设计／交付材料；实施阶段可用另一档模型。其价值是让“为什么这样改”保存在项目中，同时使用 IDE 的已有工具验证结果。需要注意，宣传中的基准成绩属于厂商材料，本报告没有据此宣布它普遍优于其他代理。

**使用方式。** 如果日常在 IntelliJ IDEA、PyCharm、WebStorm 或 Android Studio 中工作，先在原有项目里启用 Junie。给出正确的运行配置、测试方法和项目指南；大型迁移先审核计划，再分批改动。

**模型搭配与场景。** 官方当前提供 BYOK 和本地模型支持。建议从可选的强编程云端模型开始，复杂规划用较强档位，简单实施再比较较快档位；具体型号以当前模型菜单验证。适合 JVM、复杂 IDE 项目、框架升级和已有 JetBrains 工作习惯的人。难度：低中。其优势依赖项目在 IDE 中被正确加载，项目配置损坏时不能靠模型补救。

## B06 Zed：编辑器可以是代理的宿主，不必包办代理的全部能力

**理念。** Zed 是开放的高性能编辑器，同时提供自有 Agent 和 ACP 外部代理接入。它最有启发性的设计是将编辑器与代理运行时分开：用户可以喜欢 Zed 的交互，却选择 Codex、Claude、OpenCode、Pi 等代理执行任务。[项目](https://github.com/zed-industries/zed/blob/16c9aa7ea6d897a8044d9501cde1b295256722f2/README.md)、[AI 概览](https://zed.dev/docs/ai/overview)

**边界非常明确。** 外部代理通常拥有自己的认证、模型选择、工具和配置；Zed 展示会话和交互。给 Zed 自有模型入口填了 API Key，并不自动意味着外部 Codex 或 Claude 也完成了相应认证。它们的费用、数据处理和权限仍要看各自运行时。[外部代理文档](https://github.com/zed-industries/zed/blob/16c9aa7ea6d897a8044d9501cde1b295256722f2/docs/src/ai/external-agents.md)

**使用方式。** 安装 Zed，打开项目，先选自有 Agent 或从 ACP Registry 安装外部代理。试用时固定其中一种；只有确认当前“谁在执行”后，再比较模型。否则很容易把编辑器变化、Harness 变化和模型变化一起归因。

**模型搭配与场景。** “Zed＋Codex＋GPT”“Zed＋OpenCode＋Claude”是不同组合。前者遵循 Codex 的模型与权限配置，后者遵循 OpenCode。适合喜欢轻快编辑器、想在统一界面比较不同代理、重视开放协议的开发者。难度：中；跨代理配置中高。

## B07 TRAE／SOLO：从编程界面走向可交付的完整工作

**范围。** TRAE 产品、SOLO 工作方式，以及 GitHub 上的 `trae-agent` 研究代码不能互相替代。后者维护状态并不能证明商业产品当前活跃程度。本报告将 TRAE／SOLO 作为商业产品家族，研究仓库另列观察项。

**理念与公开能力。** 官方已将 SOLO 扩展到独立桌面和 Web 体验，并区分偏编程的工作与 More Than Coding 的资料、报告、数据任务。其方向是减少“模型回答完，用户再手工整理成品”的断层。但闭源运行时的调度、压缩和内部模型路由无法从公开网页完整还原。[官方产品页](https://www.trae.ai/)、[SOLO 说明](https://www.trae.ai/blog/new_solo_beta_0331)

**使用方式。** 编程任务先提供代码仓库、运行方法和验收；资料任务先提供资料范围、输出文件格式和引用要求。国内／国际版本与不同入口应分开试用，不把一端的模型、额度和工具列表照搬到另一端。

**模型搭配与场景。** 推荐先使用产品实际提供的内置路由或当前模型选项。尚未核实每个版本都支持同等自由的 BYOK，因此不给出“任意 TRAE＋任意模型”的保证。适合希望减少配置、直接从需求得到原型或文档的用户。难度：低中；专业开发仍需会检查代码与部署结果。

## B08 Augment／Auggie：先解决“找对代码和业务背景”

**理念。** 对大型代码库来说，模型不一定缺少编程知识，更常缺少“这家公司把事情放在哪里、为什么这样做”。Augment 的 Context Engine 围绕项目和相关仓库提供检索与上下文。Auggie 则把这种能力带入 CLI。[Agent 文档](https://docs.augmentcode.com/jetbrains/using-augment/agent.md)、[Auggie 入门](https://docs.augmentcode.com/cli/overview.md)

**架构取舍。** 索引和检索层位于模型之前，负责找材料；代理再决定怎样行动。索引需要维护，文件排除范围、更新延迟和访问权限会影响结果。它不保证一个名字相似的检索结果就是正确依赖。Context Engine 也能作为 MCP 服务给其他代理使用，这意味着团队可以只替换“找资料”这一层。[Context Engine MCP](https://docs.augmentcode.com/context-services/mcp/overview.md)

**使用方式。** 先导入一个真实项目，检查索引范围，再用几个已知答案的问题验证检索质量，例如“这个权限检查的所有入口在哪里”。之后再让代理修改代码。需要跨仓库背景时，显式配置相关工作空间，避免把整个组织随意纳入。

**模型搭配与场景。** Auggie 内部选项按当前产品提供的路由选择；也可以采用“Codex／Claude Code＋Context Engine”的组合，此时模型仍由原代理决定。适合大型仓库、复杂内部业务、跨仓库改动和新成员熟悉项目。难度：中；索引与组织权限管理中高。

## B09 Amp：把能力档位定义为一整套执行配置

**理念。** Amp 当前的 low／medium／high／ultra 不只是更换模型。每档组合了模型、推理强度、系统提示、工具和 Oracle 等能力。它体现了一种产品判断：用户选“这个任务值得投入多少能力”，具体执行组合由产品组织。[模式与模型](https://ampcode.com/docs/markdown/models-and-subagents)

**分工结构。** Search、Oracle、Librarian、Read Thread 等专门处理代码检索、难题推理、外部资料和历史任务。它们通常拥有独立上下文，主代理收到汇总；文档明确区分这种分工与可彼此随意沟通的团队。Orbs 则扩展到持久远程工作环境。[工具](https://ampcode.com/docs/markdown/tools)、[Orbs 入门](https://ampcode.com/docs/markdown/orbs/getting-started)

**使用方式。** 先从中等档位处理典型开发任务，困难时升级档位。保存任务与输出材料，观察升档究竟改善了什么。需要插件自定义代理时，再设计清楚输入、输出和可用工具。不要因为出现多个角色名就认为它们真的形成了一个可靠组织。

**模型搭配与场景。** 首选“任务档位＋当前官方路由”，并记录实际模型；需要固定模型或 BYOK 时按当前文档配置。其路由会更新，因此不能长期宣称 Amp 永久绑定某一家模型。适合希望减少自行调参、又需要专家分工的熟练开发者。难度：中；自定义编排中高。

## B10 Factory Droid：把大任务组织成可验证的交付过程

**理念。** Droid 提供通用代理执行，Missions 进一步安排规划、工作者和验证。与简单地“同时开五个聊天窗口”相比，其重点是任务交接、状态和完成标准。[Missions](https://docs.factory.ai/missions/overview.md)

**公开架构。** 自定义 Droid 用项目级或用户级 Markdown 配置，指定职责、模型和工具；被调用时拥有独立上下文。官方还明确描述了工作者的限制，例如特定非交互式子任务不能像主代理那样随意向用户提问或继续套娃调用。限制能减少失控，也意味着主任务必须给出足够明确的输入。[子代理](https://docs.factory.ai/harness/subagents.md)

BYOK 也有入口范围：当前说明针对 CLI／Desktop 配置，不应扩展为所有托管 Web、移动入口自动支持相同自定义模型。权限和沙箱同样要分别配置。[BYOK](https://docs.factory.ai/model-independence/byok.md)、[沙箱](https://docs.factory.ai/autonomy-and-safety/sandbox.md)

**使用方式。** 先用单个 Droid 完成小功能；再让 Mission 处理能拆分且能验收的任务，例如 API、前端、测试三部分。规划文件中写清共享接口，避免每个工作者各造一套约定。

**模型搭配与场景。** 官方当前目录提供 GPT-6 Astra、GPT-5.6、Claude 等多档选择。建议规划／疑难诊断用较强模型，可机械验收的实施用经济档，再由独立检查收尾。适合较完整的功能交付、重复开发流程和愿意为任务编排投入配置的团队。难度：中高。[模型目录](https://docs.factory.ai/models.md)

## B11 Warp／Automation Platform：从终端会话走向可触发的代理任务

**理念。** Warp 原生终端会把命令、输出与上下文组织得更结构化。其代理在这样的工作环境中使用工具；同时也支持把 Claude Code、Codex、OpenCode 等第三方 CLI 放进 Warp。后者使用的代理核心仍属于第三方，而不是一律变成 Warp Agent。[Agents 文档](https://docs.warp.dev/_llms-txt/agents.txt)

**架构分层。** Agent Profiles 配置模型、自治程度、工具与命令权限；Automation Platform 再提供远程环境、触发器、编排和观察能力。部分接口与应用仍使用 Oz 名称。比较时应区分“Warp 作为终端”“Warp 原生 Agent”和“平台上的远程执行”。[CLI 文档](https://docs.warp.dev/_llms-txt/warp-agent-cli.txt)

**使用方式。** 终端用户先从解释错误、整理日志、生成和执行可审查命令开始；重复任务稳定后再保存 Profile、配置触发器和远程环境。不要把第一次临时救火直接改成无人值守生产任务。

**模型搭配与场景。** 原生 Agent 使用当前 Profile 可选模型；第三方 CLI 遵循对应 Harness 的模型方案。适合日常终端操作、开发环境排障、运维脚本和周期性开发任务。难度：终端低中；平台自动化中高。涉及生产系统时，真正限制影响范围的是凭据和执行权限。

## B12 Google Antigravity：让代码、浏览器和任务产物一起进入代理流程

**理念。** Antigravity 把多步开发与可查看的产物结合，代理不仅输出代码，也通过计划、说明和浏览器结果帮助用户判断任务是否完成。其价值在于让开发验证进入同一工作过程。[Agent 文档](https://www.antigravity.google/docs/agent)

**能力边界。** 对浏览器的操作、终端命令、项目修改和并行会话应分别看权限与环境。产物展示能提高可审查性，但截图好看不等于功能、无障碍和异常状态都正确。

**使用方式。** 导入项目，让代理写一份简短计划，实施后在浏览器中验证具体路径。例如不仅打开登录页，还测试错误密码、空输入和登录后跳转。要求保存验证结果，而不只是说“已经测试”。

**模型搭配与场景。** 当前官方列表以 Gemini 为主要路线，也列出部分 Claude 与 GPT-OSS 型号，并区分企业可用性。优先比较 Gemini 3.8 Flash 与可用的 3.1 Pro；不能因为别处发布了 GPT-6，就假定这里已经可选。适合前端、Web 应用、需要视觉验证的任务。难度：低中。[模型列表](https://www.antigravity.google/docs/models/)

## B13 Replit Agent：把从想法到可运行应用的环境准备一起包起来

**理念。** Replit Agent 面向“我想做一个东西”的用户，把项目生成、运行环境、预览和发布串在一起。对初学者而言，省去安装依赖和配置服务往往比多一个模型选项更重要。[Agent 介绍](https://docs.replit.com/features/agent/overview.md)

**架构取舍。** 这是托管开发环境中的代理。平台控制环境与部分路由，因此起步快；迁出时需要确认代码、数据库、秘密配置、运行方式和部署依赖分别如何处理。一个可以下载的源码目录，不一定等于完整可迁移的线上系统。

**使用方式。** 先描述用户、核心流程和一个最小成品，不要一次要求完整商业平台。通过预览逐个验收，再决定是否增加数据库、认证和付费功能。部署前核对持续运行费用。

**模型搭配与场景。** 推荐使用产品提供的 Lite／Economy／Power 等能力档位与内置路由，而不承诺某个具体模型永远位于某个档位。小调整使用轻档，大改造再提高能力与预算。适合原型、内部小工具、演示应用和非开发者试验。难度：低；维护真实业务仍需要工程知识。[使用与费用](https://docs.replit.com/learn/build-with-agent.md)、[预算管理](https://docs.replit.com/billing/managing-spend.md)

## B14 Qoder：把项目知识和目标式执行放在同一个产品里

**理念。** Qoder 同时强调代码理解、项目知识材料与较完整任务的推进。Quest 等工作方式希望把“告诉它目标”转成持续执行；Repo Wiki 则试图让项目背景成为可复用材料。[产品概览](https://docs.qoder.com/qoder/overview.md)、[Quest](https://docs.qoder.com/user-guide/quest/overview.md)

**需要留意的产品边界。** 当前桌面、IDE、CLI 等入口的历史和配置不应默认完全互通；文档对导入与独立空间有具体说明。自定义模型也不代表所有辅助能力都使用自己的 Key，例如 Repo Wiki 使用固定模型并单独消耗平台额度。[自定义模型](https://docs.qoder.com/qoder/custom-models.md)

**使用方式。** 先让它理解一个已有仓库，核对生成的知识说明有没有误解，再用 Quest 处理带明确输出的任务。模型切换前保存关键需求，防止只关注窗口长度而忽略任务状态。

**模型搭配与场景。** 当前 CLI 文档列出 Qwen3.8-Max、Kimi-K3、GLM-5.3、DeepSeek-V4 等选项，并支持若干 Provider 的自定义模型。可按同一任务比较中文项目理解、成本和工具稳定性。适合大型项目入门、中文开发、既要项目知识又要目标执行的用户。难度：低中。[模型配置](https://docs.qoder.com/cli/model.md)

## B15 腾讯 CodeBuddy：面向中文开发生态的多入口代理

**理念与公开能力。** CodeBuddy 覆盖 IDE、插件和 CLI；其上下文入口包括文件、代码片段、文档、Git 与终端。对微信小程序、腾讯云相关开发者，现成资料入口和中文工作流有实用价值，但这不等于其他项目不能用。[上下文文档](https://www.codebuddy.ai/docs/ide/User-guide/Context)

CLI 的自定义子代理可以配置职责、工具和独立上下文，结果返回主代理；项目级与用户级配置承担不同作用。官方还提供团队、工作树、沙箱与 SDK 等文档入口。由于完整商业运行时未公开，本报告只确认文档所述行为，不推断它内部一定复用了某个竞品的实现。[子代理](https://www.codebuddy.cn/docs/cli/sub-agents)、[设置](https://www.codebuddy.cn/docs/cli/settings)

**使用方式。** 选定国内／国际版本和一个入口，检查模型目录与权限。已有项目先精确引用相关文件、Git 变更和报错输出；可复用的研究职责再做成子代理。不要默认新建子代理就自动获得最小权限，应检查继承的工具集。

**模型搭配与场景。** 以当前版本实际提供的模型和自定义接入为准，优先产品默认路线；需要固定模型时先验证工具调用。适合中文团队、小程序、腾讯云相关开发以及希望兼顾插件和 CLI 的人。难度：低中。WorkBuddy 属于扩展到办公任务的相邻产品，不能用它的能力反推所有 CodeBuddy 入口。

## B16 ZCode：把 GLM 的长任务能力放进目标管理流程

**理念。** ZCode 官方明确围绕 GLM-5.3 适配，重点包括复杂项目理解、长任务、连续代码修改和恢复。Goal Mode 将目标、完成检查和状态恢复放在一个流程里，方向类似“任务尚未完成，就保留继续工作的依据”。[Agent 文档](https://zcode.z.ai/en/docs/agents)

**架构含义。** 文件引用、工作空间、Git 分支、执行模式和推理档位共同决定代理的工作上下文。持久目标不等于模型拥有无限记忆，仍依赖任务状态被正确保存和重新装载。官方还特别说明 `CLAUDE.md` 在迁移时可作为一次性来源，后续使用 `AGENTS.md`；不能看到熟悉的文件名就假定运行时一直自动读取它。

**使用方式。** 导入仓库后先检查项目指令，明确当前目标与验收；从一个能在当天完成的任务测试暂停、继续和验证。较长任务将关键进度保存在项目文件中，再观察恢复是否准确。

**模型搭配与场景。** 原生优先 GLM-5.3。官方的性能描述属于厂商主张，本报告确认其适配方向，不将“长任务更强”当作已经独立验证的跨产品结论。适合 GLM 用户、中文开发、需要持续目标管理的任务。难度：低中；涉及其他 Provider 的完整兼容程度仍需按版本核实。[模型介绍](https://docs.z.ai/guides/llm/glm-5.3)

## B17 Avante.nvim：在 Neovim 里获得可直接应用的代理修改

**理念。** Avante 希望让用户保留 Neovim 的键盘工作习惯，同时获得类似 AI IDE 的项目对话、修改与差异审查。当前已有多 Provider、项目指令、可选检索、工具和 ACP 接入，不只是代码补全插件。[README](https://github.com/avante-corp/avante.nvim/blob/18316361891e59f3d18732fea0b1fe68c8be56e9/README.md)

**结构与边界。** Lua 模型层区分直接调用 Provider 与 ACP 路径，并处理流、工具和记忆摘要。所检查的 `dispatch_agent` 面向独立的只读搜索任务，不能因此理解为一套默认可写文件的团队。ACP 路线又可能把代理运行交给 Codex、Gemini 等外部进程。[模型层](https://github.com/avante-corp/avante.nvim/blob/18316361891e59f3d18732fea0b1fe68c8be56e9/lua/avante/llm.lua)、[分派工具](https://github.com/avante-corp/avante.nvim/blob/18316361891e59f3d18732fea0b1fe68c8be56e9/lua/avante/llm_tools/dispatch_agent.lua)

**使用与模型。** 按当前 Neovim 版本要求安装插件和依赖，先配置一个 Provider，再练习选取文件、提出修改和接受 diff；项目规则可放在 `avante.md`。直接接模型时选择已适配的 Claude／GPT 或其他工具模型；接外部 ACP 代理则沿用对方模型方案。适合熟练 Neovim 用户和终端开发者。难度：已有 Neovim 配置者中；初学者高。

## B18 CodeCompanion.nvim：把模型适配和完整代理接入明确分开

**理念。** CodeCompanion 提供对话、局部转换、代码审查、工具和工作流，同时保留较强的编辑器配置自由。它适合希望在 Neovim 内按自己的习惯组合 AI 能力的人。[README](https://github.com/olimorris/codecompanion.nvim/blob/3af636c9892c70c5a4e91604718bf902076aff26/README.md)

**一个清楚的架构边界。** HTTP Adapter 处理模型请求、响应和工具格式；ACP Connection 处理外部代理的会话、能力、权限请求和流式更新。前者是“自己组织对话并请求模型”，后者是“把完整任务交给另一个代理”。两者都出现在同一编辑器里，但负责执行的人不同。[HTTP 适配](https://github.com/olimorris/codecompanion.nvim/blob/3af636c9892c70c5a4e91604718bf902076aff26/lua/codecompanion/adapters/http/init.lua)、[ACP 连接](https://github.com/olimorris/codecompanion.nvim/blob/3af636c9892c70c5a4e91604718bf902076aff26/lua/codecompanion/acp/init.lua)

**使用与模型。** 安装插件后，先在 HTTP 模型与 ACP 代理两条路线中选一条。局部变换可以使用较快模型；复杂任务可接 Codex／Claude Code 等原生代理。再按需添加 MCP、规则和 Skills，避免一次改变整个配置。适合 Neovim 用户、自定义提示与工作流爱好者；模型和多入口配置成本较高。难度：中高。

## B19 Tabnine Agent：把企业模型选择与开发环境控制放在前面

**理念。** Tabnine 当前不只有补全和 Chat，也有直接在开发环境中执行目标的 Agent。产品强调项目上下文、用户反馈和组织控制。对于已有企业部署约束的团队，模型治理和私有端点可能比追逐最新单一型号更重要。[Agent 说明](https://docs.tabnine.com/main/getting-started/tabnine-agent)

**公开能力与边界。** IDE 中的工具设置分别控制读取、命令和应用代码等能力；管理员可以决定组织可用的模型。完整商业核心未公开，因此本报告按公开配置描述其责任分工，不声称验证其内部调度算法。[工具设置](https://docs.tabnine.com/main/getting-started/tabnine-agent/agent-settings)

**使用与模型。** 在组织批准的 IDE 与部署中启用 Agent，先确认读取和执行权限，再尝试一个范围明确的重构或测试任务。官方模型页列出 GPT、Claude、Gemini、Devstral 等选项，且并非所有型号都适用于所有入口；不能假定目录永远同步最新发布。适合企业代码助手、私有端点和统一模型策略。难度：个人低中；组织部署高。[模型目录](https://docs.tabnine.com/main/welcome/readme/ai-models)

## B20 Google Jules：把仓库任务交给独立云端工作机

**理念。** Jules 是异步编码代理：连接 GitHub，选择仓库和分支，在云端虚拟机中克隆代码、安装依赖、修改并验证。它与 Gemini CLI 的主要差别是环境和任务生命周期由服务管理。当前入门文档仍标记实验性质，应保留成熟度判断。[入门](https://jules.google/docs)

**架构与使用。** 官方 API 以 Source、Session 和 Activity 等对象管理仓库与任务。用户可以先检查计划，再让任务运行，随后审阅产物；CLI 主要提供与云端 Jules 交互的入口，不应误认为把同一引擎完全搬回本地。先接一个仓库，提供环境脚本和 `AGENTS.md`，从测试补齐或小修复开始。[API](https://jules.google/docs/api/reference/)

**模型搭配与场景。** 优先使用 Jules 原生模型路由；公开材料没有证明任意 BYOK 都受到同等支持，因此不指定一个可随意更换的后端。适合独立 issue、测试补齐、文档更新与批量维护。验收仍需看变更和实际测试，云端任务完成通知不等于应直接合并。难度：初次低中；环境配置中。
