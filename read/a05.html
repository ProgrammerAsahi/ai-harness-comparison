A05 Kimi Code：围绕 Kimi 的长任务体验重新组织执行核心

定位与设计理念

本报告使用的是 MoonshotAI/kimi-code。旧 kimi-cli 的架构介绍不能直接套到新代码。当前仓库是 TypeScript 多包结构，agent-core-v2 是需要重点看的执行核心；发布的独立程序也不意味着用户必须先搭建 Node 开发环境。当前仓库

它更关心长任务中的连续性：当前目标、已经读到的文件、未完成的工具交换和接下来要做的事，都必须在多轮调用中正确衔接。大窗口有帮助，但不能替代运行时维护状态。对读很多资料、再推进多文件修改的开发任务，这种连续性通常比第一轮回答写得多长更有意义。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

Kimi Code 将终端任务、编辑器连接、工具和独立子任务组合起来。ACP 让编辑器可以接入同一类代理会话，插件与 Hooks 扩展行为，不同子代理承担探索、规划和实现。它更接近一套完整开发助手，而不是模型 API 的薄转发层。

历史压缩根据上下文预算触发，并为下一步留出空间；压缩边界还要避开没有完成的工具交换。为什么要这样做？如果只留下“调用工具”的消息，却丢掉对应结果，下一轮模型会看到一段断裂的对话。长上下文管理首先是状态正确性问题，然后才是节省 Token。压缩策略、模型请求层

可以把工具调用看成一封请求与一封回信。压缩时若只留下请求，模型可能以为动作还没完成；若只留下回信，也可能不知道结果对应哪个动作。Kimi 的压缩策略对这种边界做处理，目的是给下一轮留下可解释的历史。ACP 解决的则是界面连接问题：编辑器可以展示会话，但实际循环仍由 Kimi 负责。换编辑器不等于换了模型协议或执行权限。

深入一层：请求适配与上下文压缩是两条独立职责

Kimi Code 的请求层把代理内部信息转换为具体 Provider 接口能接受的请求；压缩策略则负责在历史变长时重新组织可用材料。两者都影响模型看到什么，但解决的问题不同：接口适配处理格式，压缩处理容量。换一个兼容接口，不能据此保证原有长任务行为也完全一致。

模块／交接点 怎样工作 状态与边界
LLM Requester 准备请求并处理服务端响应 认证成功只证明一层可用。
Full Compaction 在有限窗口中维持后续任务所需信息 旧细节可能不再逐字存在，关键约束要有稳定载体。
执行反馈 工具观察继续参与模型判断 摘要与聊天记录不能代替仓库里的实际补丁。

沿着一次任务看数据怎样走。 在大规模重命名中，前几轮找到调用点，后几轮修改并检查。发生压缩后，仍需知道哪些目录已完成、哪些测试失败、哪些公开接口不能变。若漏掉一个范围限制，应先检查输入和摘要，再断言模型理解能力不足。

与相近工具的实质差别。 与单轮聊天客户端相比，Kimi Code 的关键是持续的请求—观察过程。与其他编码代理比较，应固定任务长度，并观察压缩前后约束是否保留，而非只比较第一次回答。

本节细图与机制依据：llmRequester.ts、strategy.ts、providers.md。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
项目身份 当前 kimi-code 多包实现 阅读旧 kimi-cli 教程前先核对版本和命令
长任务 上下文预算与完整工具交换共同决定压缩 用阶段性检查点补充摘要，不把窗口长度当记忆保证
多入口 CLI 与 ACP 等连接方式 外部编辑器需要单独配置代理与认证
分工与扩展 子任务、插件和 Hooks 先验证单代理循环，再增加独立调查职责
模型别名 账户目录与别名映射可以变化 试用记录保存实际 ID，不能只写 Kimi
兼容服务 Provider 文档提供配置路径 不同协议的工具、流和推理语义要重新验收

把机制放进实际工作。

上下文压缩首先需要保留一段合法的对话。工具调用和工具结果必须能对应，压缩边界不能随意切在两者中间。之后才是摘要质量：目标、约束、已改文件、失败方案和下一步应能支持继续工作。只留下漂亮的项目概述，往往不足以恢复真正的工程进度。

长窗口减少了部分切片需求，却不会自动告诉模型哪些资料最关键。迁移文档、旧接口和最新代码同时存在时，需要说明时效与优先级，否则模型可能把互相矛盾的版本混用。每阶段交付一个小而可验证的成果，有助于及时发现理解偏差，也能让恢复材料更准确。

ACP 连接失败时，应分别检查客户端配置、Kimi 进程启动和模型认证。客户端能显示历史，不代表当前模型账户可继续请求；命令能在终端运行，也不代表编辑器传入了同一个目录。把入口与环境分开核对，有助于避免把连接问题误认为长任务能力不足。

从安装到完成第一个任务

  1. 从当前 kimi-code 的 README 安装发行版，在项目目录启动 kimi；不要混用旧项目的配置说明。

  2. 在交互界面用 /login 完成认证，用 /model 查看本账户实际可用模型。核对订阅别名和 API 型号是否相同。

  3. 先让它整理项目入口、测试命令和已有约束；提交一个需要读多个文件、但修改范围明确的任务，观察文件引用是否准确。

  4. 长任务每完成一个阶段，要求记录已修改文件、验证结果和下一步；恢复后抽查这些事实，再继续实施。

  5. 需要编辑器入口再配置 kimi acp；需要跨模型再按 Provider 文档增加一项配置，并重复同一组工具与恢复测试。

下面是启动命令或操作路线；路径、认证与功能入口请按自己的版本调整。

cd /path/to/project
kimi
# 在支持 ACP 的客户端中，按文档将代理启动命令设为：
kimi acp

模型搭配、适用方向与取舍

原生优先 Kimi。当前文档区分 K3 的不同上下文档位；kimi-for-coding 别名目前指向 K2.8 Preview，不能把这个别名永久当作某个固定旧版本。复杂、资料量大的任务可先试可用的 K3，日常工作比较 K2.8 路线。适合中文项目沟通、长资料辅助开发和 Kimi 订阅用户。上手难度：中。模型说明、更新记录

选择路线 候选组合 怎样决定
原生日常 Kimi 账户实际提供的型号 核对 kimi-for-coding 别名，不把套餐名当固定权重版本。
长资料与复杂实现 可用 K3 档位 先确认窗口和配额，再测试关键约束在长任务中是否保留。
成本对照 K2.8 Preview 等当前服务路线 同任务比较输入、重试与人工检查；不因窗口更大就自动选最高档。

适合 Kimi 用户、中文交流和材料较多的工程任务。长上下文能少做一些切片，但仍需承担输入成本、摘要偏差和恢复核验。与 Hermes 比较时，前者偏开发任务，后者更强调长期个人经验与多入口持续工作。
