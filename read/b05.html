B05 JetBrains Junie：让代理使用 IDE 已经理解的代码结构

定位与设计理念

Junie 的差异化在 JetBrains IDE 的代码理解能力：项目、符号、导航、诊断和运行配置已经存在，代理可以借此工作，而不必完全依赖文本搜索。当前产品还包含 CLI、CI 和远程监控等入口，已经不是只能在 IDE 中调用单一模型的小功能。官方产品页

Junie 利用 JetBrains IDE 已经建立的项目理解：符号、引用、诊断与运行配置能为代理提供比纯文本更有结构的入口。对于依赖 IDE 的大型 Java、Kotlin 或 Python 项目，沿用这些能力可以减少重新建立工作环境的成本。前提是项目本身已经正确加载；错误的 SDK 或构建配置不会因为加了模型就自动消失。

工作原理与架构图

下图依据官方公开接口整理，表示责任分工，不代表已审计闭源内部实现。

计划阶段可以形成可编辑、可提交的需求／设计／交付材料；实施阶段可用另一档模型。其价值是让“为什么这样改”保存在项目中，同时使用 IDE 的已有工具验证结果。需要注意，宣传中的基准成绩属于厂商材料，本报告没有据此宣布它普遍优于其他代理。

文本搜索擅长找字符串，IDE 的语义能力则可以帮助区分同名符号、调用与类型关系。代理因此有机会做更精确的定位，但是否正确仍要看实际操作与补丁。规划和实施可以使用不同模型，是把成本投入与职责分开的一种方法；如果规划中的接口约定没有进入实施上下文，再强的规划模型也无法保证最终一致。

深入一层：计划、IDE 项目理解与开发者检查点

Junie 的公开产品流程强调先整理需求、设计和交付阶段，再进行代码工作。理解它时要把 IDE 提供的项目现场、代理的任务判断以及用户检查点分开：代码分析帮助代理定位，计划帮助人确认方向，实际正确性仍由修改和验证结果决定。闭源内部如何建立索引与安排模型请求并未在此得到源码证明。

模块／交接点 怎样工作 状态与边界
计划材料 把目标转为可检查的实施路径 计划合理不代表生成代码已经正确。
IDE 现场 项目结构、编辑和运行工具提供执行背景 能力与具体 IDE、版本和配置有关。
用户接续 审阅与反馈影响后续任务 按任务影响安排必要的审阅与反馈。

沿着一次任务看数据怎样走。 例如给服务增加字段校验：先确认校验位置与兼容要求，再在 IDE 中定位实现，修改并运行相关测试。若计划与现有项目结构不符，应在实施前纠正背景；若测试配置失败，则需要单独处理环境。

与相近工具的实质差别。 与终端代理相比，Junie 直接服务于现有 IDE 工作方式；与规格文件驱动的路线相比，是否把计划长期保存为项目资产，需要依具体产品功能判断。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
项目理解 IDE 的导航、符号、诊断与运行配置 先确认项目索引与构建正确
规划材料 可编辑、可保留的设计与交付说明 计划需要具体到接口和兼容要求
实施 在既有开发环境修改并验证 代理用的运行配置应与人工一致
入口 IDE 之外还有 CLI／CI 等路线 逐个入口确认可用的代码理解能力
模型 当前产品提供 BYOK／本地等配置路线 部署路线和具体型号仍需账户与版本核对
成本 规划和实施可分配不同能力 以整项任务及返工衡量，不能只看实施模型便宜

把机制放进实际工作。

IDE 语义能力只有在项目正确加载时才有价值。错误 SDK、缺失模块或未解析依赖会使导航与诊断不完整，代理可能误判引用关系。开始试用前人工跑通基础检查，能够把环境缺陷与代理能力分开。

大型重构应先比较符号关系，再做小批修改。纯字符串替换可能误伤同名变量，语义导航则有助于区分不同对象；但代理是否真正采用正确工具仍要看实际结果。要求它列出受影响调用方和兼容条件，比笼统说“使用 IDE 能力”更容易验收。

规划与实施用不同模型时，交接材料必须可独立理解。架构理由、接口、异常条件与不可改变行为都应进入实施任务，不能只留一句“按计划做”。如果更便宜的实施模型因上下文不足反复返工，分工并未真正节约。模型组合应根据最终可审查补丁与总时间决定。

从安装到完成第一个任务

  1. 在日常使用的 JetBrains 项目中启用 Junie，先修好 SDK、依赖和运行配置；人工运行一次原有测试建立基线。

  2. 给出一个模块级任务，让它说明将使用哪些项目线索与检查；补入隐藏业务约定和不可变接口。

  3. 较大任务先审阅计划材料，特别检查类职责、调用方和迁移顺序。选择当前支持的规划与实施模型组合。

  4. 实施后在 IDE 查看真实 diff、诊断和测试；确认不是通过削弱断言、跳过测试或改运行配置掩盖问题。

  5. 同类任务稳定后再考虑 CLI／CI 或本地模型路线；重新验证环境与模型能力，而不把 IDE 试用结论直接照搬。

模型搭配、适用方向与取舍

官方当前提供 BYOK 和本地模型支持。建议从可选的强编程云端模型开始，复杂规划用较强档位，简单实施再比较较快档位；具体型号以当前模型菜单验证。适合 JVM、复杂 IDE 项目、框架升级和已有 JetBrains 工作习惯的人。难度：低中。其优势依赖项目在 IDE 中被正确加载，项目配置损坏时不能靠模型补救。

选择路线 候选组合 怎样决定
IDE 基线 当前菜单中的强编程云模型 优先检验语义导航、修改与运行配置协同。
规划／实施分工 规划较强、实施经济档 检查接口交接及总返工，不能只节省实施调用。
BYOK／本地 当前版本明确支持的路线 独立验收服务端模板、延迟和多轮工具能力。

适合已有 JetBrains 工作习惯和复杂 IDE 项目的团队。优势来自环境整合，换成不熟悉或不支持的项目体系后未必同样明显。与 Cline、Cursor 比较时，先评估是否值得迁移编辑器；与 CLI 比较时，看语义工具带来的收益能否抵消环境依赖。
