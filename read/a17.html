A17 Step Code：在 Pi 核心上，围绕 Step 模型组织完整工作流程

定位与设计理念

Step Code 是在本机终端运行的编程代理，围绕读代码、修改、运行验证和交付产物组织工作。官方着重强调长任务、Token 效率和原生模型协同。这些是产品目标；“完成同样任务一定更省”仍需要在相同验收条件下测量。产品说明

其许可文件明确说明：Step Code 派生自 Pi，第一方代码默认采用 MIT 许可，派生部分继续保留上游声明。它的区别主要体现在如何把已有核心组合成产品：Step 认证与模型目录、工具接口、权限、多代理、任务目标、定时触发及插件。公开仓库含产品源码和构建材料，正式发布凭据、部分私有服务与观测实现不在其中。许可与来源、公开仓库边界

可以把它理解为在可扩展代理底座上做出一组明确产品选择：优先采用 Step 服务、提供现成任务控制，并为静态成果交付增加入口。底层血缘解释了为什么有熟悉的会话与扩展结构，产品层则解释了默认权限、认证、工具和编排为何与原版 Pi 不同。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

图中 Step 产品接口把输入、插话、中断和模型选择交给会话运行时；它没有再建立一套平行的状态机。底层循环根据模型结果分派工具，保存反馈，再决定是否继续。模型看到的 read_file、edit_file、run_command 等名称，由 Step 工具层映射到具体执行能力。这样既能保留 Pi 的扩展基础，也能调整模型熟悉的工具格式。产品接口、执行循环、工具接口

一条正常任务仍是“组装上下文→请求模型→检查并执行工具→保存结果→继续或结束”。子代理、goal、cron 和 workflow 是叠加在这条主线上、解决不同问题的能力。使用时应先把基本循环跑通，再按需要增加一种控制方式，才能判断问题出在模型、会话还是高级编排。

深入一层：会话宿主、工具档案与有限编排

Step Code 在代理循环之上增加了产品宿主与编排语义：AgentSession 管理运行、压缩和取消，工具档案决定模型可见能力，workflow 在独立 VM 中组织子调用。子进程虽然有自己的代理轨迹，却继承父任务工作目录和项目信任，因此“进程分开”并不等于“文件天然隔离”。

模块／交接点 怎样工作 状态与边界
工具档案 按模型和运行方式选择暴露能力 模型能调用的工具受具体档案约束。
有限扇出 宿主启动的子代理禁止再次启动子代理、workflow、cron 或 goal 限制递归与后台任务逃逸；不等于禁止对子任务继续发消息。
目标与预算 宿主在一轮落定后决定是否安排续轮 预算阻止新调用，已在运行的一批仍可能超出剩余额度。

沿着一次任务看数据怎样走。 例如主任务用 workflow 并行调查三个模块：每个子调用先进入进度记录，再等待并发槽位；结果回到当前编排。用户取消时必须沿宿主取消路径传播，而不是只关闭 UI。需要持续目标时由宿主管理下一轮，不能让子代理自行留下无人接管的定时任务。

与相近工具的实质差别。 与 Pi 的差异落在宿主、模型工具档案和编排生命周期。与 MiMo 的 exec 相比，workflow 会管理子代理任务；二者虽然都执行脚本，却不是相同职责的脚本工具。

本节细图与机制依据：agent-session.ts、tool-profile.ts、orchestration-lifecycle.md、goal-lifecycle.md。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

局部放大：一轮结束之后：目标、编排与日历触发

workflow 管当前编排中的子调用，goal 管同一会话是否继续推进显式目标，cron 管何时触发工作。三者不能用一个“自动执行”开关概括。取消或清除目标必须影响宿主后续调度，不能只修改显示文字；如果持久化失败，就不能声称目标已经清除。图中的续轮只有在目标状态、预算和取消条件允许时发生，子代理没有自行注册这些持续调度能力。

本图依据同节列出的固定源码与官方文档，表示所选子系统的主要路径。

能力、状态与边界

上下文、记录与长期工作。

机制 实际作用 使用时怎样理解
本地会话记录、恢复与导出 保存对话和工具过程，可继续或复制会话 能恢复聊天，不代表命令进程或外部动作也被恢复
/tree、/fork、/clone 从历史节点尝试另一条思路，或复制当前分支 对话分支不会撤销磁盘改动；代码实验仍需 Git 分支／工作树
自动压缩与 /compact 总结早期过程，保留近期消息 摘要包含目标、文件、验证、失败方案和下一步；要检查约束是否保留
AGENTS.md、CLAUDE.md、Skills 保存可反复使用的项目规则和方法 不等于自动筛选、纠错并检索的长期个人记忆

会话层会在工具批次结束等合适时点检查上下文，接近容量时生成交接摘要；文件操作也参与摘要组织。源码另有“发送请求前精简内容”的可选路径，只改变发给模型的材料，不重写完整记录，当前默认关闭。因此不能把所有实验性节省机制都写成默认生效。会话文档、压缩实现、请求前精简开关

子代理、workflow、goal 和 cron 各自负责什么。

这四个名字很相近，职责却不同：子代理负责分工，workflow 负责组织分工，goal 负责持续推进目标，cron 负责到了时间再触发。

能力 当前实现与特色 主要边界
子代理 内置 general、explore、review、planner；支持单个、并行、顺序串联及后台任务 独立上下文与用量；默认可共享目录；review／planner 有命令工具，不能理解成系统级只读
workflow／ultraloop 用受限 JavaScript 脚本编排并行、阶段和迭代，保存运行记录 依赖原生 isolated-vm；当前代码对不能承载它的 Bun 单文件运行环境停用注册
/goal 保存目标与预算，当前轮结束后继续；支持暂停、恢复、清除 完成状态由工作代理提交，没有独立的完成评判代理；仍需外部验收
/cron 以时间表触发任务；可将任务持久保存到项目 CLI 必须持续运行；保存到磁盘不等于关机后云端继续执行

子进程明确禁用再次派生、workflow、goal 和 cron，避免一层层放大代理数量或留下脱离父任务的定时工作。需要并行改代码时，可选择工作树，但独立目录与系统沙箱是两件事。目标预算和 workflow 预算的计数口径也有差别；正在生成的请求可能超过剩余额度，不能把 Token 限额当作绝对费用封顶。子代理文档、生命周期约束、目标控制

高级编排要按安装方式验收。 普通子代理和 workflow 是不同能力，前者可用不代表后者可用。源码的注册门控会因原生模块缺失或运行环境不支持而关闭 workflow；因此文档介绍的 /ultraloop 不能视为每个发布包的保证。它的使用授权主要通过提示约定和日志表达，缺少授权的调用会被记录，并非由这个约定本身强制拒绝。注册门控、脚本运行环境

权限、隔离与数据路径。

Step Code 提供 Ask、Read Only、Bypass、Autopilot 四档。本次源码及交互文档中的默认值是 Bypass：普通工具不逐次询问。Ask 会对写入和执行等操作询问；Read Only 阻止相关工具；Autopilot 还包含自动继续机制。被规则识别的危险命令，以及无法充分分析的命令，需要单独处理；没有交互审批通道时会拒绝相应操作。这种规则检查不能分析所有程序内容，也不是操作系统沙箱。权限源码、命令分析边界

安全文档明确把本地用户权限作为执行边界。工具命令可获得启动账户的系统权限，扩展与受信任项目也进入这一边界。工作流脚本受限、子代理上下文独立，都不能据此推出宿主文件和网络已被隔离。会话与配置在本地保存，选中的代码和资料仍会发往所配置的模型服务；联网工具和 StepPage 发布则增加各自的数据出口。安全说明、本地数据目录

扩展、迁移与静态网页交付。

MCP、Skills 和插件可增加工具与工作方法。迁移界面能导入部分 Claude Code／Codex MCP 配置，并复用已有 CLAUDE.md。但服务授权要重新核对；不是所有传输方式、项目配置和插件机制都自动迁移。文档明确说明没有文件式 Hooks，需要用扩展事件实现相应逻辑。“大多数插件兼容”不能写成行为完全等价。迁移说明、插件边界

StepPage 是很实用的产品差异：安装并启用 steppage 插件后，可以把本地静态输出目录发布成可访问网站，再管理版本、上线和回滚。它适合原型、产品介绍页、研究报告和数据展示页；后端程序与数据库需要另行部署。发布需要凭据和可用 MCP 服务，网站托管额度也不等于模型订阅额度。StepPage 指南

把机制放进实际工作。

这些机制应分别验收：权限决定能否执行，目标状态决定是否继续，调度决定何时触发，发布插件决定产物怎样交付。某一项可用不能替另一项作保证；特别是可恢复的任务记录与仍在运行的进程，需要分别检查。

从安装到完成第一个任务

  1. 按官方 README 为当前平台安装，确认 step --version；Windows 原生路线仍需核对 beta 限制，必要时采用官方推荐的 WSL。

  2. 进入项目运行 step，用 /login 选择地区及订阅／API 渠道，再用 /model 和 /status 核对可用模型与账户。

  3. 首次任务主动查看 /permissions，选择适合试用的 Ask 或 Read Only；用 /init 整理项目说明，先验证读取、修改和检查这条基础链。

  4. 完成一个可重现的小修复后，查看文件变更与测试结果；使用 step -c 继续，并抽查目标、约束及已完成动作是否正确保留。

  5. 再分别试子代理、目标预算与插件。高级 workflow 按安装包确认可用性；无界面 step -p 则要另行核对审批条件和退出状态。

模型搭配、适用方向与取舍

原生首选是 Step-5-Preview。 源码默认模型 ID 为 step-5-preview，但登录后仍从当前服务发现实际可用模型；目录读取失败不等于账户已拥有默认型号。普通摘要、小修改可以比较同服务中的 Step-3.7-Flash；纯文本高频任务再考虑 Step-3.5-Flash。具体角色建议及价格见第六章的模型与成本比较。默认模型、模型发现

跨厂商使用有一处文档冲突。 网站“Platforms and models”仍描述多厂商登录和多种云平台；当前 README 与源码则明确：默认产品只内置 Step，其他模型可通过 models.json 等自定义路径接入。源码保留 OpenAI Chat Completions／Responses 与 Anthropic Messages 适配代码，并不等于文档列出的每种原生登录、云平台和协议都已在此发行版验证。本报告将“Step 原生”作为可靠的起点，把 Claude、GPT、DeepSeek、Qwen 或本地服务归入需要单独验证的自定义组合，不给出“只填 Key 就全部可用”的承诺。网站模型文档、内置目录边界、协议兼容层

适用方向与难度。 适合愿意使用终端、主要采用 Step 模型的开发者：中小功能、跨文件修复、测试与技术文档、可拆分的仓库调查，以及需要发布静态成果的任务。基础使用难度中等；跨模型定制、长任务预算和高级编排为中高。对于要求完整 IDE 调试体验、全天候云端任务，或已验证企业隔离治理的场景，应继续比较对应专门产品。当前推荐等级是“值得纳入试用的新候选”，尚未经过本报告的统一运行测试。

选择路线 候选组合 怎样决定
原生旗舰 Step-5-Preview 复杂修改、长材料和多步工具任务先建立基线，核对地区与渠道。
日常成本对照 Step-3.7-Flash／3.5-Flash 摘要、局部修改和重复提取可先试；角色分配属于建议而非实测结论。
自定义后端 models.json 支持的协议路线 分别验证工具、推理字段、窗口与审批；源码适配存在不等于原生登录可用。

它适合希望采用 Step 模型，又需要现成任务与静态交付流程的终端用户。偏自由扩展可比较 Pi，偏 IDE 交互可比较 Cline，偏全天候远程工作可比较云端代理。新项目的版本稳定性与实际使用规模仍应继续观察。
