A17 Step Code：在 Pi 核心上，围绕 Step 模型组织完整工作流程

简档：保留定位、总体结构和能力边界；上手命令、试用任务和模型路线不再随事实刷新维护，选型请参考第 05 章的场景表与第 06 章的集中表。

定位与设计理念

Step Code 是在本机终端运行的编程代理，围绕读代码、修改、运行验证和交付产物组织工作。官方着重强调长任务、Token 效率和原生模型协同。这些是产品目标；“完成同样任务一定更省”仍需要在相同验收条件下测量。产品说明

其许可文件明确说明：Step Code 派生自 Pi，第一方代码默认采用 MIT 许可，派生部分继续保留上游声明。它的区别主要体现在如何把已有核心组合成产品：Step 认证与模型目录、工具接口、权限、多代理、任务目标、定时触发及插件。公开仓库含产品源码和构建材料，正式发布凭据、部分私有服务与观测实现不在其中。许可与来源、公开仓库边界

可以把它理解为在可扩展代理底座上做出一组明确产品选择：优先采用 Step 服务、提供现成任务控制，并为静态成果交付增加入口。底层血缘解释了为什么有熟悉的会话与扩展结构，产品层则解释了默认权限、认证、工具和编排为何与原版 Pi 不同。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

图中 Step 产品接口把输入、插话、中断和模型选择交给会话运行时；它没有再建立一套平行的状态机。底层循环根据模型结果分派工具，保存反馈，再决定是否继续。模型看到的 read_file、edit_file、run_command 等名称，由 Step 工具层映射到具体执行能力。这样既能保留 Pi 的扩展基础，也能调整模型熟悉的工具格式。产品接口、执行循环、工具接口

一条正常任务仍是“组装上下文→请求模型→检查并执行工具→保存结果→继续或结束”。子代理、goal、cron 和 workflow 是叠加在这条主线上的能力，名字相近，职责不同：**子代理负责分工，workflow 负责组织分工，goal 负责持续推进目标，cron 负责到了时间再触发。**子代理里明确禁止再次派生，也不能启动 workflow、goal 和 cron，避免代理数量一层层放大，或留下脱离父任务的定时工作。使用时应先把基本循环跑通，再按需要增加一种控制方式，才能判断问题出在模型、会话还是高级编排。编排生命周期、目标控制

权限档位、脚本沙箱和子代理的独立上下文，都不能等同于系统隔离。安全文档把启动账户的本地权限作为执行边界：工具命令拥有这个账户的系统权限，扩展与受信任项目也在这一边界之内。会话与配置保存在本机，选中的代码和资料会发往所配置的模型服务，联网工具和静态网站发布又各自增加数据出口。权限实现、安全说明

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
会话与上下文 本地保存会话，可恢复、分支和导出；接近容量时先由模型修剪较早的工作上下文，不够再做摘要压缩 能恢复对话，不代表命令进程或外部动作也被恢复；修剪本身也计入用量
子代理 内置通用、探索、审阅、规划等角色，可单个、并行、串联或在后台运行 上下文与用量独立，但默认共享目录；审阅类角色也能运行命令，不是系统级只读
workflow 用受限 JavaScript 脚本编排并行、阶段和迭代；脚本在 WebAssembly 版 QuickJS 中运行，默认注册，按会话或单轮显式开启 脚本受限不等于宿主隔离；与普通子代理分开验收
goal 与 cron goal 保存目标与预算，本轮结束后继续；cron 按时间表触发，可保存到项目 完成状态由工作代理自己提交，仍需外部验收；定时任务要求 CLI 一直运行
权限 Ask、Approve for Me、Full Access 三档；交互界面默认 Approve for Me，无界面运行须明确指定 规则检查分析不了所有程序内容，也不是操作系统沙箱
扩展与交付 MCP、Skills 与插件；可导入部分 Claude Code／Codex 配置；StepPage 把本地静态目录发布为网站 迁移后重新核对授权，没有文件式 Hooks；网站托管额度不等于模型订阅额度
