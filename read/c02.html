C02 OpenClaw：让个人代理持续在线，连接不同渠道与设备

定位与设计理念

OpenClaw 更像个人代理的接线与运行中心。Gateway 维持长连接、渠道、会话和设备关系；手机、桌面、消息平台可以成为交互入口。它不只是把同一聊天框复制到几个应用。架构文档

OpenClaw 把个人代理做成持续在线的连接中心。来自手机、桌面与消息渠道的任务需要进入正确会话，再交给运行时执行。它解决的是“无论从哪里发起，怎样找到自己的工作状态”，而不是单纯多开几个聊天界面。持续连接带来便利，也要求清楚识别用户、设备和触发权限。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

Gateway 管理连接与任务进入方式，具体代理运行时负责模型和工具循环。当前文档已经涉及不同运行时路径，因此不宜永久把它概括成某一版本 Pi 的简单包装。每个会话的任务通常串行化，持久化写入还需要确认当前运行是否仍拥有写入资格，防止被替代的旧任务把过时状态写回去。代理循环

工作空间中的记忆材料、会话摘要、检索和后台整理共同服务持续使用。这里有一个实际取舍：记忆越多，维护和纠错越重要。能记住一句话不代表知道它何时过期，用户需要能够查看、修正和删除。记忆设计

Gateway 类似接线台，负责把输入放进正确会话；代理运行时才决定下一步动作。同一会话通常需要串行处理，避免两次任务同时修改同一份状态。旧任务被替换后，持久化写入还要确认它是否仍有资格写回，否则可能覆盖新任务的正确结果。记忆文件、检索和整理提供长期连续性，但过时信息仍需要用户纠正。

深入一层：常驻网关、控制客户端与设备节点

OpenClaw 的中心是常驻 Gateway，而不是某一个聊天页面。消息渠道、控制客户端和设备节点都是连接方，但职责不同：客户端管理与查看，节点声明设备能力，代理循环负责具体推理与工具往返。官方说明要求同一宿主的消息连接由网关统一拥有，避免多个进程争抢同一个渠道会话。

模块／交接点 怎样工作 状态与边界
控制平面 客户端通过 WebSocket 与 Gateway 通信 关闭一个客户端不等于网关和代理已停止。
设备节点 以 node 角色连接并声明能力 能连上设备不代表任何任务都可无条件使用全部能力。
会话与记忆 路由、排队、转录和持久材料各有职责 多个消息入口需要避免同时写坏同一任务状态。

沿着一次任务看数据怎样走。 例如从手机发来任务，网关识别渠道和会话，安排代理运行；需要设备能力时通过对应节点执行，结果再回到原消息入口。排错应先定位连接、路由、代理还是设备执行出了问题，而非一概重启模型。

与相近工具的实质差别。 与 Hermes 的持续个人助理目标有交集，但网关所有权、连接与设备能力是 OpenClaw 特别值得理解的一层；它也不等同于给 CLI 加一个定时器。

局部放大：从一条渠道消息到一次有归属的运行

入口统一之后仍要解决归属：这条消息属于哪个会话、由谁推进、结果发回哪里。会话队列帮助同一任务按秩序运行；设备节点连接说明能力在哪里，并不直接决定消息属于哪个任务。若多个入口同时更新一个目标，首先应检查路由与排队，再检查代理逻辑。这里只展示正常消息路径，渠道配对、断线重连及各类授权细节仍以相应文档为准。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
连接中心 Gateway 管渠道、设备与会话 先验证谁能发指令，再开放更多入口
执行后端 多种运行时路径 后端决定模型、工具及部分权限行为
并发状态 会话串行与写入资格控制 避免旧任务覆盖新状态，关注取消后的行为
记忆 工作空间材料、摘要、检索与整理 要能查看、更正和删除，而非只积累
工具环境 宿主执行与显式沙箱分开 自托管不等于工具天然隔离
持续运行 多渠道和自动化依赖服务在线 备份、升级、失败恢复也是使用成本

把机制放进实际工作。

多个渠道进入同一个个人代理，会同时提出身份与顺序问题。必须知道输入来自谁、应该进入哪个会话、能调用哪些工具；同一任务的补充要求也应与原任务正确关联。配对成功只是连接起点，后续权限与结果归属仍需验证。

串行化可以减少同一会话的争写，但跨会话、后台任务和外部系统还可能共享资源。旧任务被取消后是否仍有资格保存状态，关系到新结果会不会被覆盖。试用时故意修改目标或取消任务，检查实际文件和记忆，比只测试一问一答更能说明可靠性。

长期服务需要备份和恢复，而记忆内容也要能修订。把服务搬到另一台机器，除了聊天记录，还可能涉及工作空间、凭据、设备连接和工具环境。迁移时逐项验证；即使选用相同模型，运行位置和状态缺失也会使行为不同。

从安装到完成第一个任务

  1. 准备一个可维护的运行环境，按官方指南部署 Gateway；先只配一个设备或渠道，完成身份与连接检查。

  2. 选择代理后端和模型，确认工作空间、工具范围与执行环境。先做只读资料任务，核对结果回到正确会话。

  3. 连续发送两条有顺序的任务，观察队列、取消与状态保存；不要假定多个渠道意味着任务可以随意并发修改同一文件。

  4. 配置长期记忆后测试事实更新与删除，保留重要项目材料的备份；确认新会话使用的是最新信息。

  5. 再增加渠道或定时触发，逐项检查触发者、凭据、运行位置和失败恢复。服务升级后重复基本配对与工具测试。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

从消息渠道提交一份资料摘要任务，随后补充修订要求；代理应在同一项目中更新报告，并把新版本返回原会话，保留资料来源。

观察后发的修订是否被正确纳入、旧任务是否覆盖新文件，以及结果是否发到正确对象。单次聊天成功无法验证持续服务；中断恢复和跨渠道状态才是这条路线的重要试用点。

模型搭配、适用方向与取舍

依据实际运行时选模型；原生多 Provider 路线可比较强工具模型，若接 Codex 等运行时则遵循其原生模型配置。适合跨设备个人助理、消息入口统一、长期自动化。单纯偶尔问答或修一个 bug，部署整个持续服务可能没有必要。难度：高，主要高在服务、账户与权限管理。

选择路线 候选组合 怎样决定
内置多 Provider 当前运行时适配的强工具模型 先验证身份、会话和工具，再比较型号。
外部运行时 相应代理的原生模型路线 选择 Codex 等后端时，遵循其自身模型及认证。
长期成本 稳定任务使用已验收的经济档 持续服务须统计定时任务、失败和子任务总消费。

适合愿意维护个人服务、需要跨设备和消息入口的人。代价是部署、身份、权限与状态管理。若只是本地写报告，Chatbox／Cherry 更轻；若重点在可重复业务流程，n8n 的显式流程可能更容易观察和管理。
