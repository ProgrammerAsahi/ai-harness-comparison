B10 Factory Droid：把大任务组织成可验证的交付过程

定位与设计理念

Droid 提供通用代理执行，Missions 进一步安排规划、工作者和验证。与简单地“同时开五个聊天窗口”相比，其重点是任务交接、状态和完成标准。Missions

Factory Droid 把大任务看成一组需要交接和验证的工作。Missions 的价值不在于能开多少代理，而在于规划者、工作者与验证之间有可查看的材料和完成条件。只有接口明确、各部分能检验时，拆分才可能提高吞吐；需求模糊时增加工作者，往往只是更快地产生彼此不一致的代码。

工作原理与架构图

自定义 Droid 用项目级或用户级 Markdown 配置，指定职责、模型和工具；被调用时拥有独立上下文。官方还明确描述了工作者的限制，例如特定非交互式子任务不能像主代理那样随意向用户提问或继续套娃调用。限制能减少失控，也意味着主任务必须给出足够明确的输入。子代理

BYOK 也有入口范围：当前说明针对 CLI／Desktop 配置，不应扩展为所有托管 Web、移动入口自动支持相同自定义模型。权限和沙箱同样要分别配置。BYOK、沙箱

自定义 Droid 文件为一类任务定义职责、模型和工具，被调用后拥有自己的上下文。这让主任务可以把大量实现细节交出去，但也失去对子任务隐含假设的直接掌握。非交互工作者无法随时追问用户，因此规划阶段要把必要信息给足。验证者应依据代码与运行结果判断，不能只是重新读取工作者的成功总结。

深入一层：主 Droid、专用子任务与较长任务的组织

Factory 的 Droid 路线把执行代理与可配置的专门角色组合起来。公开资料中的子代理、模型选择与 Missions 等任务组织方式应分层理解：角色配置回答“谁擅长哪一段”，长任务组织回答“怎样推进和验收整个目标”。图只表达这些可见职责，不推断其商业调度服务内部。

模块／交接点 怎样工作 状态与边界
主任务 保留目标、范围与最终交付责任 不能因为子任务完成就跳过集成验证。
子 Droid 以专用说明、工具和模型承担一段工作 角色名称应落实为输入输出与工具边界。
模型渠道 产品支持的模型或 BYOK 路线 渠道可用不等于所有任务功能完全等价。

沿着一次任务看数据怎样走。 例如把一个旧模块迁到新接口：先建立整体验收条件，再分别调查依赖、修改实现与检查回归，主任务汇总差异。对于长任务，保留计划、完成状态与失败证据，比不断扩充角色数量更有价值。

与相近工具的实质差别。 与 Amp 相比，两者都有角色分工，但可配置维度和任务组织契约应分别查证。与固定工作流相比，Droid 的具体执行仍有较多代理动态决策。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
任务层次 普通 Droid 与 Missions 小任务不一定需要完整编排
角色配置 Markdown 定义职责、模型和工具 角色描述要能转化为明确的交付件
上下文 子代理拥有独立任务上下文 接口与共享事实需要显式传递
工作者限制 某些非交互路径限制提问和继续派生 不确定信息应在任务下发前解决
模型独立 CLI／Desktop 等入口有 BYOK 路线 不把该能力扩展到所有托管入口
完成控制 计划、实施和验证组成交付过程 证据需独立可查，避免代理自评替代验收

把机制放进实际工作。

复杂任务最容易在交接处丢信息。规划者知道整体目标，工作者只看到分配给自己的部分；如果共享接口、错误行为和测试要求没写清，各自完成后可能无法组合。Mission 的任务材料应围绕这些交接点设计，而不只是把大目标拆成很多标题。

非交互工作者不能随时问人，使“输入是否充分”成为重要条件。可以先让主任务解决业务疑问，再把稳定部分交出去；尚未确定接口的前后端不宜同时自主设计。并行的收益应来自真正独立的工作，而非同时修改同一个高耦合模块。

验证应看实际产物和环境，不只看工作者总结。一个独立检查角色若仍只阅读成功声明，并没有形成独立验收。模型成本应合计规划、所有工作者、验证和返工；当集成成为主要负担时，减少代理或缩小批次往往比继续增加并行更有效。

从安装到完成第一个任务

  1. 从单个 Droid 开始，完成一个小功能，确认模型、权限、沙箱和测试都能工作；先选边界清楚的小任务试用 Mission。

  2. 挑选能拆分的需求，定义共享接口、目录责任和验收方式。例如先统一 API 契约，再分配前后端实现。

  3. 按职责配置工作者的模型和工具，给非交互子任务完整输入；预算中同时计入规划、实施与验证。

  4. 检查中间产物是否符合接口，再集成修改；冲突交给有完整上下文的主任务处理，不让工作者相互猜测。

  5. 用独立检查核对真实运行结果，记录遗漏与返工。重复成功后再扩大任务规模或引入自定义模型。

模型搭配、适用方向与取舍

官方当前目录提供 GPT-6 Astra、GPT-5.6、Claude 等多档选择。建议规划／疑难诊断用较强模型，可机械验收的实施用经济档，再由独立检查收尾。适合较完整的功能交付、重复开发流程和愿意为任务编排投入配置的团队。难度：中高。模型目录

适合完整功能、重复开发流程和愿意维护角色配置的团队。代价是前期拆分、调用成本与集成负担。高度耦合的小修复通常交给单代理更直接；多代理收益可结合总交付时间、集成成本和返工量判断。
