A11 Kilo Code：围绕开放执行核心提供更多产品化入口

定位与设计理念

Kilo 不能只用早期的 Cline／Roo 血缘来说明当前架构。当前仓库中已经有明显的 OpenCode 核心结构以及 Kilo 自己的会话处理层，同时覆盖 CLI、编辑器和云端服务。README、Kilo 会话处理

Kilo 的产品选择是把开放执行核心与统一服务入口结合：用户既能享受多模型选择，也能使用账户、托管任务和审查等整合功能。它适合不想为每个模型重新准备界面的人。判断其价值时应把代理本身、模型转发和云服务分别列出来，才能看清自己实际购买了什么。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

用户购买的不只是一个本地循环，也可能包括模型入口、远程任务和代码审查等产品能力。相同基础执行结构之上，账户、模型路由、错误恢复、任务管理和界面整合仍能带来明显体验差异。源码中的错误信息与溢出处理也体现了模型服务出错后如何向用户解释、何时先压缩再重试。压缩衔接

相同核心血缘不意味着相同产品。会话出错时怎样解释、是否先压缩后重试、模型目录怎样更新，都可能改变实际完成率。另一方面，云端任务多了环境与账户服务，本地可用的凭据未必在远端存在。迁移时应拆开四类东西：代码文件、项目规则、会话状态与服务授权；只有代码能打开，不能证明完整流程已经迁移。

深入一层：产品配置怎样进入会话处理与压缩

Kilo 的当前固定快照含有自身目录下的 SessionProcessor 与 compaction 实现。对使用者来说，这意味着不能只拿早期编辑器扩展的印象理解所有入口；应该追踪当前入口究竟把任务交给哪条运行路径。模型渠道决定如何调用模型，会话处理决定工具和消息怎样延续，两者分别影响任务结果。

模块／交接点 怎样工作 状态与边界
入口到运行时 产品可能有多个交互入口 此图聚焦所引 Session 实现，不声明覆盖全部商业后端。
流事件处理 消息和工具状态随响应推进 工具完成与文本完成应分别观察。
压缩策略 持续任务需要裁剪或概括历史 换模型后要重新验收窗口与工具结果兼容。

沿着一次任务看数据怎样走。 当一项修复跨越多轮时，检查会话中是否保留最后一次失败测试、已修改文件和待办；若某工具执行成功却没有进入后续上下文，模型就可能重复操作。这类问题应沿会话处理链排查，定位工具结果是否进入后续输入。

与相近工具的实质差别。 与 OpenCode 比较时，看当前固定快照的差异；与 Roo 比较时，还要考虑维护状态与入口演变。这里保留实现血缘作为解释线索，不把它当作能力等价证明。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
入口 CLI、编辑器与云端服务 分别确认运行目录、授权和功能范围
模型 托管路由与自有 Provider 选择 BYOK 不代表其他平台能力也不收费
执行核心 当前包含 OpenCode 结构及 Kilo 会话层 旧 Roo／Cline 教程不能自动代表现版
恢复 错误信息、上下文溢出和压缩衔接 检查重试是否保留任务约束与有效工具结果
协作 按当前产品提供远程任务和审查等能力 分别核对本地扩展与云服务的职责
迁移 规则、模型、历史与权限分别处理 先迁一条完整任务，再迁全部配置

把机制放进实际工作。

比较 Kilo 与上游结构时，应观察产品行为的接缝：同样发生上下文溢出，是否压缩重试、怎样展示错误、哪些模型信息被记录，都可能改变实际体验。账户提供的模型目录与开放核心支持的协议，也不一定是同一范围。了解这两层能帮助解释为什么共享部分代码的产品仍然不同。

BYOK 主要说明主模型请求使用自己的凭据，并不自动说明云任务、知识服务或其他辅助能力免费。一次完整试用应同时检查 Provider 账单与产品消费，记录失败重试；否则很容易拿单次模型请求价格代表整套产品成本。

迁移旧 Roo 或 Cline 配置时，先核对当前字段含义与生效方式。逐项检查模式、项目指令、MCP、历史与权限的实际格式；先迁一条可验收流程，再迁其他内容。跨本地和云端时还要重新准备环境，因为本机能读取的文件、密钥和正在运行的服务不会自动出现在远端。

从安装到完成第一个任务

  1. 先选一个常用入口完成安装，决定使用 Kilo 模型服务还是自己的 Provider；记录模型账单和平台账单的边界。

  2. 导入一个小项目，确认当前模式、项目规则和执行权限。让它先说明运行方法，再实施一个易验收的修复。

  3. 查看 diff 与执行证据，记录调用成本和等待时间；失败时区分路由、限流、上下文溢出与代码问题。

  4. 需要远程任务时，另配置仓库访问与环境。用不依赖本机特殊文件的小任务验证，再把其他工作交出去。

  5. 迁移旧配置时逐项核对规则、模式、MCP 和认证，不直接复制全部目录；升级后重复同一条基础任务。

模型搭配、适用方向与取舍

选型建议：优先从当前 Kilo 模型目录中选择已经完整支持的日常型号，再按复杂度升级；可比较 Claude、GPT、DeepSeek、Qwen 等家族。用实际编程任务比较候选模型的完成质量与返工成本。适合希望多入口、多模型，又愿意使用统一商业服务的开发者。难度：低中；复杂模型路由与云任务：中高。

选择路线 候选组合 怎样决定
日常基线 已适配 Sonnet 5／GPT-5.6 Terra 优先稳定工具调用，先验证读、改、测与恢复。
较难任务 可用 Sol／Astra／较强 Claude 只在证据显示推理或实现能力不足时提升，环境错误先单独解决。
成本与中文对照 DeepSeek／Qwen／Kimi；Step 兼容路线 以当前 Provider 与官方接入说明为准；比较总重试和人工修正。

更适合既重视模型选择，又愿意使用整合服务的开发者。与 OpenCode 的差别不应只看共同源码，而应看账户、远程能力、错误恢复和费用；与单厂商原生代理相比，则更需要自己验收模型组合。
