A14 Mistral Vibe：让 Mistral 模型进入可控的开发循环

简档：保留定位、总体结构和能力边界；上手命令、试用任务和模型路线不再随事实刷新维护，选型请参考第 05 章的场景表与第 06 章的集中表。

定位与设计理念

Vibe 是 Mistral 的官方编程代理。它为希望使用 Mistral 模型、同时保留可读源码和本地开发体验的人提供原生路径。README

Vibe 是围绕 Mistral 编程模型组织的原生工具链，同时保留开放实现。它把模型、工具、权限与客户端通过清楚的接口衔接，适合既想直接开发，又希望读懂运行逻辑的人。官方原生适配可以减少部分工具格式摩擦，但某个型号是否最划算，仍取决于任务、服务端部署和失败重试。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

2026-10-15 发布的 3.0.0 版重组了运行结构：旧的 Python 执行运行时和 Python 终端界面被移除，vibe 命令现在总是启动 Rust 编写的终端界面。这个界面是一个轻客户端，背后连接需要 Python 3.14 以上的 vibe-app-server；真正执行和保存会话的 Unified Harness Core 与 Runtime 作为外部依赖引入，不在本仓库里。本段引用的执行循环属于 3.0.0 之前的固定提交，可以帮助理解模型、工具、权限、压缩和子代理怎样通过接口衔接、异步事件怎样把执行状态交给客户端，但它已经不是现行版本的代码位置。旧版执行循环、3.0.0 更新记录、现行结构说明

执行循环通过事件报告进度，让客户端知道代理是在等待模型、执行工具还是完成任务。对调用者而言，这比把所有输出当作一段普通文字更容易处理取消和审批。不同模式表达不同工作权限：逐项询问、自动接受文件编辑和全部自动批准不是同一件事。开放模型部署时还多一层约束，服务端的工具模板、上下文长度与吞吐会影响整个循环。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
原生模型 围绕 Mistral 模型适配，默认托管路线见集中表 通用新品不自动等于最佳编程后端
运行实现 3.0.0 起由外部依赖 Unified Harness 执行，Rust 界面经 Python app-server 连接 旧版源码只用于理解接口；研究现版要连同外部依赖一起看
交互状态 异步事件传递执行进度 客户端要正确区分等待、错误与完成
权限模式 ask、accept-edits（默认）、auto-approve 等内置代理；plan 模式已在 3.0.0 移除 启动前确认实际模式及工具范围
上下文与分工 压缩、工具和子代理接口 子代理数量增加后核对总成本与结果集成
开放部署 可研究适配的开放模型服务 硬件、模板和服务参数同样属于方案
