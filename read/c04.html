C04 Chatbox AI：低门槛客户端正在长出真正的工作模式

定位与设计理念

Chatbox 的经典价值是多模型聊天、文件与对话管理，但当前公开技术文档已经描述 Agent／Work 模式、工具、Skills 和记忆。因此它不应再被一概排除在 Harness 讨论之外。商业发行版与社区源码也有差别，功能判断必须标注版本。项目说明、功能页

Chatbox 从熟悉的多模型聊天入口出发，逐渐加入真正会操作工作目录的模式。对于报告、翻译和资料讨论，用户可以先不理解复杂代理配置就开始；需要生成文件或执行任务时，再进入 Work／Agent 路线。把两种模式区分清楚，能避免用普通聊天的预期理解具有实际操作能力的工作会话。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

当前 Agent 模式将身份、Soul、个人偏好、工作目录说明与工具信息组装成提示；会话首次启动时保存一份上下文快照。稳定前缀有助于缓存和一致性，但代价是中途修改某些规则，不一定立刻影响这段既有会话，需要新会话或相应重捕获条件。提示与记忆设计

Skills 则可以按需加载，避免把所有工作手册每次全塞进去。Provider 层区分模型配置和实际协议适配；“某服务兼容 OpenAI”并不意味着所有参数与推理行为一致。Skills、Provider 设计

稳定的上下文前缀有利于缓存和行为一致，代价是某些全局修改不会自动刷新旧会话。比如你修改报告语气偏好，既有任务仍可能沿用启动时的快照；应检查生效条件，而不是不断强调同一句要求。Skills 按需加载帮助减少提示长度，但文件中的一次性事实应留在项目材料，不能全部塞进长期人格。

深入一层：Provider、技能和个人资料怎样进入桌面会话

Chatbox 的技术资料将模型 Provider、Agent Skills 与 Soul／Memories 分开说明。Provider 解决“请求发给谁”，技能提供“怎样做这类任务”，个人资料与记忆提供“跨会话要知道什么”。把这些都塞进一个系统提示虽然表面相似，却失去了按需加载和独立维护的边界。

模块／交接点 怎样工作 状态与边界
Provider 统一不同模型渠道的接入 模型回复正常不等于所有工具调用能力都适配。
Skills 可复用工作方法参与当前任务 技能是说明材料，不自动带来新的执行权限。
Soul／Memories 保留个人背景与持续性资料 需要避免把临时假设固化为长期事实。

沿着一次任务看数据怎样走。 例如写月度工作报告：会话接收本月材料，技能提供报告方法，个人资料约束语气与岗位背景，模型通过所配 Provider 生成。验收时分别检查数据来源、方法是否适用以及旧偏好是否仍有效。

与相近工具的实质差别。 与纯粹多模型聊天器相比，技能和记忆增加了代理持续性；与面向代码执行的 CLI 相比，桌面交互和资料管理仍是主要入口。

本节细图与机制依据：ai-providers.md、agent-skills.md、agent-soul-memories.md。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
入口难度 Chat 与 Work／Agent 路线 先按任务选择是否需要实际工具执行
多模型 Provider 与协议适配分层 兼容接口仍需核对参数及工具能力
上下文 首轮保存一定的上下文快照 改变规则后检查当前会话是否刷新
工作方法 Skills 按需加载 常用写法与一次性事实分开管理
发行边界 社区源码与商业版本有差别 功能判断应记录实际版本
成果管理 对话、文件和目录任务 打开最终文件检查结构，而不只看聊天预览

把机制放进实际工作。

聊天、文件讨论和工作模式的验收不同。聊天主要看内容，资料任务要看引用是否支持结论，Work 还要看文件是否正确保存、工具有没有完成操作。选择最轻而足够的模式，可以减少普通写作被复杂执行流程打断。

上下文快照使会话拥有较稳定的起点。修改全局偏好后旧任务仍沿用原语气，可能是快照生效范围问题；重新确认当前上下文比不断追加同一句要求更直接。项目事实也不应全放进人格，因为其他项目未必适用，而且事实可能过期。

多模型比较时，将事实准确与文风偏好分开。先用原文核对遗漏、数字和否定，再评价自然程度；两个模型都说了同一件事，也不能替代来源。需要长期写小说时，人物与事件应落在可编辑文件中；需要工作报告时，保留材料和口径比持续增长的聊天历史更好查阅。

从安装到完成第一个任务

  1. 安装适合平台的发行版，在 Chat 中配置一个模型，先验证普通对话、文件输入和历史保存；确认版本所含能力。

  2. 用一份短材料试写报告，明确读者、语气、篇幅和引用要求，检查内容是否遵循原文。

  3. 把反复使用的风格偏好保存到可查看的规则中；改动后用新会话或文档规定的方法确认生效。

  4. 确需读写本地文件或执行步骤时才使用 Work，选择专门工作目录，先做小范围资料整理。

  5. 最终打开导出的文件检查标题、表格和引用，保存事实来源；再把稳定的方法提炼为 Skill，而不是把整段历史当作长期记忆。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

根据三份周会记录写一份管理层周报，突出进展、风险和需要决定的事项。不得把计划写成已完成，保留可追溯的来源。

核对时态、责任人和完成状态，尤其检查模型是否为了行文顺畅补造信息。切换模型时用同一材料比较结构和事实忠实度；启用 Work 后再增加文件保存和格式验证。

模型搭配、适用方向与取舍

日常写作可比较当前接入的 Claude、GPT、Kimi／Qwen；工作模式更应优先可靠工具调用。适合一般用户、报告润色、翻译、资料讨论和轻量本地任务。复杂团队开发或持续在线服务不是其最自然的起点。难度：聊天低；Agent 中。

选择路线 候选组合 怎样决定
日常文字 已接入 Claude／GPT／Kimi／Qwen 同材料比较事实忠实、语气和编辑负担。
Work 任务 工具调用稳定的已支持型号 写文件与执行能力单独验收，聊天好不代表工具好。
轻量或本地 经济文本模型／兼容本地服务 短摘要先试；需要图像时确认实际输入链路。

适合低门槛多模型写作、翻译和轻量目录任务。大量并行工程、持续在线或多人服务不是最自然的起点。与 Cherry 比较工作台和后端需求，与 AnythingLLM 比较是否需要长期资料库，选择自己实际要用的最小复杂度。
