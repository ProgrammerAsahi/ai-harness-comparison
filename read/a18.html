A18 Muse Code：模型与代理一起训练，用独立工作树并行分工

简档：保留定位、总体结构和能力边界；上手命令、试用任务和模型路线不再随事实刷新维护，选型请参考第 05 章的场景表与第 06 章的集中表。

定位与设计理念

Muse Code 是 Meta 为自家 Muse 模型推出的终端编码代理，面向多文件重构、长时间调试这类要连续推进很多步的工程任务。它在 2026 年 8 月 5 日以早期 beta 发布，发布博客说明代理从训练阶段就参与了模型调整，希望减少工具调用失败和重试；8 月 31 日官方宣布结束 beta，同时加入会话间消息、workflow、对话回退和 SDK 开发者预览。结束 beta 的公告它是闭源的订阅产品，按月分档计费，公开页面列出的型号都属于 Muse 系列。产品页

这条路线与 Claude Code、Grok Build 相近：模型厂商同时提供模型和代理，工具格式、规划方式与模型行为可以一起打磨。代价也很直接：选 Muse Code 基本就等于选 Muse 模型，公开材料没有说明能否接入其他厂商的模型。它适合已经打算试用 Muse 模型、手上又有能拆成几块独立工作的任务的人；对闭源、发布时间短和数据条款敏感的团队，应先小范围试点。

工作原理与架构图

下图依据官方公开接口整理，表示责任分工，不代表已审计闭源内部实现。

发布博客重点介绍了两项机制。第一项是并行分工：一项大工作拆成几个子任务后，父代理为每个子任务派出能写文件的子代理，每个子代理在 .muse/worktrees/ 下拿到自己的 Git 工作树和分支，彼此不会改到同一份文件，用户自己的工作副本也保持原样；同时运行的子代理超过上限时，其余任务排队等待。第二项是事件日志：每个会话把派生子代理、工具调用、中途插话和取消写成本地 JSONL 文件，muse resume 读取这份日志，从最后记录的一步继续。发布博客

产品页还写到后台审阅代理、能操作浏览器与桌面应用的电脑操作能力，以及 /plan、/grilling 等内置技能；博客说明这些技能只在用户显式调用时加载，/plan 写好计划后停下等待批准。这些能力目前只见于官方描述，本报告没有运行验证。

工作树隔离解决的是几个代理同时改文件会互相覆盖的问题，它不会替用户合并结果：各子代理的提交留在各自分支上，父代理或用户要逐个审阅和合并，冲突也在合并时处理。事件日志让“哪个子代理在什么时候做了什么”可以用 jq 之类的工具查出来，对审计和崩溃后续跑都有用；但日志记录的是代理的动作，测试是否通过、改动是否正确，还要看仓库里的实际结果。图中父代理与子代理之间的调度关系依据博客的公开描述整理，属于职责示意。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
运行位置 本机终端运行 muse，推理请求发往 Meta Model API 代码留在本机，但提示与上下文会发往 Meta 服务；零数据保留需另向销售申请
模型与计费 公开页面只列 Muse 系列型号，文档写明默认是 Muse Spark 1.2；按型号 ID 区分订阅额度档与按量计费档 订阅默认处于 Contributor 模式，提示、代码和回答可能用于训练 Meta 模型，可在设置中关闭；处理敏感代码前先看数据条款
并行子任务 父代理为每个子任务派可写子代理，各自位于独立工作树和分支 文件互不覆盖，合并与冲突处理仍需审阅
事件日志与续跑 每个会话写本地 JSONL 日志，muse resume 从最后一步继续 日志可用于审计动作，不能代替测试与代码审查
内置技能 /plan、/grilling、/taste 等只在显式调用时加载 规划类技能停在批准点，确认后才改代码
成熟度与平台 已结束 beta；文档称支持 macOS、Linux 与 Windows，命令行与 CI 均可用（产品页措辞较窄，只列 macOS 与 Windows） 闭源，功能、型号和价格变化快；workflow 并非每个构建和平台都有，以官方最新页面为准
