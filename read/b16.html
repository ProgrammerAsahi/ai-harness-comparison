B16 ZCode：把 GLM 的长任务能力放进目标管理流程

定位与设计理念

ZCode 官方明确围绕 GLM-5.3 适配，重点包括复杂项目理解、长任务、连续代码修改和恢复。Goal Mode 将目标、完成检查和状态恢复放在一个流程里，方向类似“任务尚未完成，就保留继续工作的依据”。Agent 文档

ZCode 将长任务与目标管理结合，希望代理不仅处理当前一句话，还能保留继续工作的依据。对跨多次会话的改造，这比单纯增加窗口长度更有意义。但目标保存只解决“回来时知道要做什么”，完成判断仍需要测试、文件和需求证据，不能由一句自我报告决定。

工作原理与架构图

下图依据官方公开接口整理，表示责任分工，不代表已审计闭源内部实现。

文件引用、工作空间、Git 分支、执行模式和推理档位共同决定代理的工作上下文。持久目标不等于模型拥有无限记忆，仍依赖任务状态被正确保存和重新装载。官方还特别说明 CLAUDE.md 在迁移时可作为一次性来源，后续使用 AGENTS.md；不能看到熟悉的文件名就假定运行时一直自动读取它。

持续目标可以在一轮结束后帮助决定是否继续，也能在暂停后装载当前进度。真正关键的是恢复材料包含哪些事实：已经改过的文件、验证结果、仍未解决的问题和下一步。若只是重复初始需求，模型仍可能重做工作。项目指令迁移同样需要明确：将旧 CLAUDE.md 导入一次，与每次运行持续读取该文件，是不同机制。

深入一层：主会话、侧边讨论与分叉历史的不同语义

ZCode 的会话分叉有明确的产品语义：从干净完成的助手消息处分出历史，而不是复制所有后台运行状态；排队输入、在途工作和后台任务不会一并复制。更重要的是，分叉不回滚磁盘文件，两个会话仍面对同一个工作区。侧边讨论也应和分叉分别理解，不要仅凭多个聊天面板推断隔离。

模块／交接点 怎样工作 状态与边界
分叉起点 已完成的助手消息才可作为起点 失败的半条回复或工具结果不能随意当恢复点。
共享文件 两条会话操作相同工作区 同时实施不同方案可能互相覆盖。
接续状态 队列与后台工作不随历史复制 新会话需要重新确认正在运行的操作。

沿着一次任务看数据怎样走。 例如在方案 A 后分叉讨论方案 B：新对话有继承的历史，但文件仍含当前改动。应先查看 diff，再决定只讨论、创建代码分支或实施；不能以为“新分支”已经自动给你一份干净仓库。

与相近工具的实质差别。 与 Qoder 编辑旧消息触发的回滚不同，ZCode 明确把对话分叉和文件回滚分开。与 Pi 的树状历史相似之处在于上下文分支，具体宿主状态仍各自管理。

本节细图与机制依据：zcode-agent。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
原生适配 围绕 GLM-5.3 的官方路线 产品适配主张与跨产品胜负分开理解
目标管理 Goal Mode、状态及恢复 完成标准需外部可查，不能只凭目标状态
项目上下文 工作空间、文件引用与指令 让关键约束进入实际读取的文件
迁移规则 旧指令可作迁移来源，后续使用 AGENTS.md 修改旧文件后不要假定当前任务自动更新
执行设置 模式、分支与推理档位 目录隔离、权限和模型能力分别核对
兼容性 其他 Provider 按实际版本确认 不把原生模型表现推及任意自定义后端

把机制放进实际工作。

持续目标需要明确结束条件。比如“完成配置迁移”应包含哪些调用方必须替换、哪些兼容测试必须通过，而不是只凭模型觉得工作差不多。目标越抽象，自动继续越可能变成无止境扩展；设置阶段成果与验收有助于让任务及时停下。

暂停恢复是检查状态质量的好方法。让代理指出已完成文件、实际验证和下一步，再与磁盘核对；若只复述最初目标，说明恢复材料不够。人手修改过文件后尤其要重新核对，避免旧检查点覆盖最新进展。

项目指令迁移也需区分一次导入与持续读取。修改旧规则文件后行为没有变化，可能是当前运行时已经使用另一份文件，而非模型故意不遵守。先核对真实来源与生效范围，再调整提示或推理档位。原生模型适配能改善部分执行，不能替代任务状态和项目配置正确性。

从安装到完成第一个任务

  1. 导入一个已有仓库，确认模型、项目目录和执行模式；核对当前项目指令实际来自哪里。

  2. 用一个当天可以完成的需求试 Goal Mode，写清完成条件和改动范围，不使用“尽可能完善”这类无终点目标。

  3. 要求在阶段结束保存文件、检查和待办，主动暂停一次，再恢复并核对这些事实。

  4. 实施过程中遇到目标变化，明确更新目标与验收，而不是继续沿用旧任务清单。

  5. 交付后查看 diff 和真实测试，记录恢复是否减少重复工作；稳定后再扩大任务长度或尝试其他模型路线。

模型搭配、适用方向与取舍

原生优先 GLM-5.3。官方的性能描述属于厂商主张，本报告确认其适配方向，不将“长任务更强”当作已经独立验证的跨产品结论。适合 GLM 用户、中文开发、需要持续目标管理的任务。难度：低中；涉及其他 Provider 的完整兼容程度仍需按版本核实。模型介绍

选择路线 候选组合 怎样决定
原生基线 GLM-5.3 优先验证长任务与目标恢复，而非只看单轮生成。
较难任务 原生模型的合适推理档位 先检查目标与材料是否充分，再提高投入。
跨模型对照 实际版本确认支持的 Provider 无充分兼容证据时不当默认推荐，先跑基础工具测试。

适合 GLM 用户、中文工程沟通和持续目标改造。若需求经常变化，应先建立规范或任务边界；若只修一个小问题，目标模式可能没有额外收益。与 Step Code 比较时看持续控制，与 Kiro 比较时看前期规范，三者不必互相替代。
