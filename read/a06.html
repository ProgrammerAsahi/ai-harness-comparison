A06 MiMo Code：按模型家族调整工具，而非假定所有模型用同一套手势

定位与设计理念

MiMo Code 继承了可辨认的 OpenCode 结构，同时加入自己的模型适配、记忆和任务模式。最值得关注的不是支持多少模型，而是承认：不同模型训练时学会的工具习惯可能不同，运行时需要据此调整。README

MiMo Code 的一个重要判断是：工具不是中性的插座。模型在训练和使用中形成了不同的调用习惯，有的更适合补丁，有的更适合命令或可编程工具组合。因此，同一个任务可以保留外层会话结构，却为不同模型配置不同工具接口。这让模型适配深入到行为层，也增加了维护多条执行路径的成本。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

其 Codex microkernel 文档描述了面向 GPT 系列的工具接口组织：终端、补丁、图像以及可编程调用能力分别承担不同职责。这里的“微内核”是一种架构比喻，并不是说它变成了操作系统内核。QuickJS 中的脚本没有直接获得 Node、进程和网络能力，但它调用到的宿主工具仍然需要权限管理；尤其不能把“JavaScript 被隔离”误读为“终端命令也被系统沙箱隔离”。架构说明、工具注册

当前设计包含跨会话记忆、检索和检查点文件，试图把目标、进展、约束保存成下一次可重新装载的材料。相较只留一句“之前我们讨论了登录功能”，这种方式更适合恢复“测试失败在哪里、哪些文件已经改过、下一步是什么”。但能恢复多少仍取决于写入内容和检索命中，不能保证毫无遗漏。README、压缩实现

在可编程调用路线中，脚本可以把多次工具调用组织成一次小流程，减少来回解释。但脚本虚拟机没有直接的文件或网络访问，只能说明脚本自身的能力受限；它转而调用的宿主终端仍可能执行有影响的命令。另一个设计重心是把进度写成可装载材料：检查点应说明已经做了什么、为什么失败和怎样继续，而不只是重复最初需求。两条机制分别解决调用效率与任务连续性。

深入一层：同一 Session 内，模型工具表与脚本执行怎样分层

MiMo Code 的公开架构文档把 GPT 路线称为“Codex microkernel runtime”，这里的微内核是工具组织方式的比喻，并非操作系统内核，也不是另启一套 Codex 引擎。它仍使用统一 Session，只按模型调整提示和可见工具，并用 QuickJS 执行组合工具的脚本。真正读文件、启动进程和访问 MCP 的仍是宿主工具。

模块／交接点 怎样工作 状态与边界
工具表 ToolRegistry 决定模型看到的能力 提示路由与工具路由是两套规则，不能只核对模型名字。
脚本隔离 QuickJS 限制脚本本身的执行环境 脚本沙箱不等于 bash 运行在容器里。
副作用控制 直接调用和脚本子调用都回到宿主权限 批量组合不应扩大原有授权；多文件写入也不等于数据库事务。

沿着一次任务看数据怎样走。 例如一轮读取三个文件并比较：模型可用 exec 组合已允许的工具，把整理后的结果回传，减少冗长往返。但调用写入工具仍须通过原来的权限和路径检查；脚本失败后应检查已执行的动作，不能假定全部自动回滚。

与相近工具的实质差别。 与 DeepSeek Harness 的全插件能力接缝相比，这里的重点是统一 Session 上的模型工具契约。与 Pi 相比，模型专属工具组合和脚本宿主承担了更多产品策略。

模型适配 不同家族可采用专门工具配置 兼容结论要精确到模型、协议和工具模式
任务模式 Plan／Build／Compose 等有各自约束 切模式前确认是否改变可写能力和工具集

把机制放进实际工作。

模型特定工具层意味着“同一份提示＋同一个模型”也不一定是同一次实验：工具名称、参数、补丁方式和调用组织改变后，模型看到的任务接口已经不同。比较 microkernel 路线时，应记录实际启用了哪些工具，不能只记录界面上的型号。

脚本可以把独立查询合并处理，减少模型与工具之间的来回。但脚本编排一旦包含依赖关系、错误分支和有副作用的操作，仍需明确何时停止、哪些结果已经生效。脚本引擎限制只能保证其直接可用能力；调用宿主命令之后的资源边界，需要另外看权限和执行环境。

检查点的价值在恢复时最容易检验：故意在一个阶段完成后停止，再让任务说明实际文件、已通过检查及下一步。若检查点与磁盘不一致，应先核对事实再继续，不能让模型依据旧记录覆盖新改动。持久记忆、当前任务检查点与自动摘要应各有职责，避免同一条错误在多个位置被反复保存。

从安装到完成第一个任务

  1. 按当前 README 安装 CLI，在项目目录启动 mimo；先选官方原生模型路线，建立一条能完成修改与测试的基线。

  2. 用 Plan 讨论任务和验收，用 Build 实施一个范围明确的改动；切换前查看实际工具与权限，不把模式名当成唯一保障。

  3. 要求将阶段成果写进项目中可查看的记录，包含文件、检查结果、失败原因和下一步。重新开启任务后验证恢复准确性。

  4. 确需使用其他模型时，核对其适配路径和工具配置；先运行相同小任务，观察调用格式、补丁应用和错误处理是否稳定。

  5. 再尝试可编程工具或 Compose。单独记录它节约的是往返次数、输入量还是人工干预，避免用更复杂的流程掩盖任务返工。

模型搭配、适用方向与取舍

原生优先 MiMo-V2.5 系列；较复杂代理任务可试 Pro。仓库也为 GPT 等模型做了专门适配，因此跨模型使用比单纯“兼容接口”更有研究价值，但本报告没有证明它在 GPT 上优于 Codex。MiMo-X 等受限预览与公开可用模型要分开看。适合愿意尝试模型特定工具配置、持久任务状态的开发者。难度：中；理解模式和适配细节：中高。模型发布说明

选择路线 候选组合 怎样决定
原生起点 MiMo-V2.5 系列 先验证标准模式下的工具与恢复，再调高级功能。
复杂任务 MiMo-V2.5-Pro 对跨文件实现和困难诊断作对照，检查总调用与返工。
适配研究 有专门工具路径的 GPT 等 属于需验证的组合；确认实际启用的工具层，不等同于原生 Harness。

适合愿意研究模型与工具协同、希望任务进度可恢复的开发者。优势越依赖特殊适配，跨型号升级就越需要回归。若只需要简单多 Provider 终端工作，先比较 OpenCode；若重点是原生 MiMo 服务，MiMo Code 更值得先试。
