06｜模型搭配与成本：选对组合，而不是背一张永久排名

模型目录变化很快。以下型号依据已收集的官方资料，采集时间见来源记录；它们用于说明候选，不是永久有效的安装清单。产品界面、地区、账户和 Provider 都可能限制可用型号。

本报告没有购买各家 API 跑统一基准，因此推荐的准确含义是“依据公开适配和任务特征，值得优先试用”。厂商自报成绩只用于了解定位，不用于证明跨产品冠军。

6.1 三种搭配证据，强度不同

标记 依据 怎样理解
原生组合 模型厂商自己的 Harness，或明确的专门适配 通常是最容易建立可工作基线的起点
官方支持 产品文档明确列出 Provider／模型／协议 证明有支持路径，不证明每个任务质量相同
选型推断 根据任务、工具与上下文特征提出 必须以自己的任务验证，不能冒充实测结论

例如 Claude Code＋Claude、Codex＋GPT、Kimi Code＋Kimi 属于原生路线；OpenCode／Cline＋某个目录内模型属于官方支持路线；“用经济型号做摘要，用强型号判断架构”则是工作分配建议。

型号名为什么容易误导

sonnet、opus、kimi-for-coding、deepseek-flash 可能是别名。别名让用户自动获得新版本，但降低了实验可重复性。当前 Claude Code 文档甚至按 Provider 列出不同映射；DeepSeek 文档说明部分旧型号名称仍被接受，实际已路由到新模型。

因此在调试或比较时，应保存四项：Harness 版本、Provider、实际模型 ID／版本、请求参数。只写“用了 GPT”或“用了 Claude”几乎没有比较价值。Claude 映射、DeepSeek 别名

6.3 怎样判断模型适不适合某个 Harness

按这个顺序检查，比一次跑一个庞大任务更有效：

  1. 基础输入输出。 中文、代码、文件片段是否正常；需要图像时，实际请求有没有把图像发送给支持图像的模型。
  2. 工具往返。 能否正确调用一个只读工具，读取结果，再作下一步决定。
  3. 编辑与验证。 能否按该工具要求修改文件，并用正确命令验证。
  4. 错误恢复。 文件不存在、命令失败、工具参数不合法时，能否根据错误调整，而不是重复同一错误。
  5. 历史与压缩。 会话变长或恢复后，是否记得关键约束；工具调用与结果有没有失配。
  6. 控制与成本。 中断能否生效；子任务是否继续烧费；模型窗口、输出上限与 Harness 的估算是否一致。

某些模型需要保留推理状态、签名或特定响应字段。网关如果只转发文本，看起来仍能聊天，却可能破坏长任务。也有服务仅在协议表面兼容，实际不支持某些参数。遇到这种问题应先核对适配层，而不是立即认定模型“变笨”。

6.4 开放权重与本地模型：适合什么，不适合什么

本地模型的主要收益是数据路径控制、可定制与不依赖外部推理服务。它并不天然更便宜或更快，尤其是在硬件已经不足、任务又需要很多重试时。

已有官方模型卡的候选 可搭配的路线 本报告建议的初始任务 验证重点
Qwen3-Coder-30B-A3B-Instruct Qwen Code／OpenCode／Pi＋正确配置的本地服务 局部代码问答、小修复、可验收脚本 工具模板、上下文、格式和修改正确性
Qwen3.5-27B Open WebUI／AnythingLLM／Chatbox／Cherry＋本地服务 中文资料整理、短报告、检索后的问答 中文事实准确性、量化损失、检索质量与速度
gpt-oss-20b 支持对应格式的本地推理服务＋兼容 Harness 结构化推理、短工具任务、对照实验 服务端格式与工具适配，中文任务另测
更大型开放模型 具备资源的组织推理平台 经过容量规划的团队任务 权重许可、显存、并发、上下文缓存和运维

来源：Qwen Coder 模型卡、Qwen3.5-27B、gpt-oss 模型卡。这些是可检验的候选，不是本地模型完整排行榜，也不意味着它们是截至当日最新的所有开放模型。

硬件的一个简单估算。 如果有 300 亿参数，粗略按每参数 4 bit 保存，仅权重理论下限约为 15 GB。实际还要加上量化元数据、运行缓冲、上下文缓存等，不能由此推出“16 GB 电脑一定能流畅运行”。不同架构和推理引擎也会改变实际需求。

MoE 模型每步只激活一部分参数，主要影响计算量；不能仅按活跃参数估计全部权重占用。上下文越长、并发越多，也可能越吃内存。先用短上下文测实际资源，再逐步扩展。

完全本地需要整条链都本地。 回答模型、嵌入模型、文档解析、搜索、语音、工具与日志都可能是独立服务。尤其知识库工具即使用本地回答模型，也可能仍把文档发给云端嵌入接口。

开放状态要按型号核对。 Qwen3-Coder、gpt-oss 等已有官方模型卡的候选，与仅提供云端服务或仍在计划开放的型号不能混为一类。Step-5-Preview 的官方发布页说明产品与 API 已提供，权重计划于 2026 年 10 月 15 日开放；所收集资料没有证明官方完整权重和最终许可已可获得。第三方同名上传不替代官方发布证据。Harness 的 MIT 许可也不能自动转移给其调用的模型。模型发布与开放计划

大型 MoE 尤其不能只按活跃参数买硬件。例如 Step-5-Preview 公布约 600B 总参数、每 Token 激活 27B；全部参数按 16 bit 保存的理论原始权重约 1.2 TB，理想化 4 bit 约 300 GB，还没有算额外数据和上下文缓存。它与几十 B 的本地候选是不同的容量级别。这只是算术下限，不是实际发行包或部署承诺。参数来源

6.5 成本要按“完成一项可接受的任务”来算

一个实用的成本拆解是：

总开销 ≈ 订阅与平台费用＋模型输入输出费用＋缓存相关费用＋工具调用费用＋执行环境费用＋人工检查和返工。

同样一次“帮我修 bug”，背后可能调用几十次模型；子代理、摘要、标题生成、检索和重试都可能增加消耗。并行让等待缩短，不会自动让所有分支只收一份费用。

表面上很便宜 可能遗漏的开销
模型 Token 单价低 失败重试、上下文重复传输、需要更长输出
Harness 免费或源码开放 模型 API、机器、网关、连接器和维护时间
已有某家聊天订阅 API 未必包含在订阅里；第三方接入资格也可能不同
BYOK 平台部分能力可能仍另外收费，辅助模型可能不走自己的 Key
本地模型不要 API 费 硬件、能源、部署与速度损失
多代理完成得快 总调用量、重复调查与合并成本

Qoder 的 Repo Wiki 单独计费就是一个具体例子：主对话使用 BYOK，不代表产品里的所有模型能力都改走同一账户。Factory 文档又说明不同入口对 BYOK 的支持范围不同。因此应读到功能级别，不能只看产品首页的一个词。Qoder、Factory

缓存与压缩也有取舍

模型服务可能对重复输入提供缓存优惠。稳定的项目规则与工具列表有利于复用；频繁修改系统提示、切模型或更换工具集合，可能降低命中。另一方面，为了缓存而保留大量无关历史，也可能让任务更难理解。

压缩通常需要额外模型调用，且可能丢信息。合理目标是保留足够准确的任务状态，而不是让 Token 指示器始终最低。某次压缩少花了一点钱，却导致代理重做整个调查，整体并不划算。

把标价换算成任务费用

按量服务至少分未缓存输入、缓存命中输入和输出三项；订阅的 Credits 则可能另有换算规则。地区价格应分别读取，不能拿一个地区的人民币价格按汇率猜另一个地区。下面用公开价目提供一个可复算示例，用量是演算假设，不是实测任务，也不是跨厂商价格排名。

计费形态 例子 应比较什么 常见误读

上述不同形态的来源与入口边界见 Cursor 模型、Amp 档位、Replit 预算、Qoder 自定义模型、Factory BYOK。模型服务与网页托管、远程工作机、发布服务又可能分开收费，最终应画出整套方案的账单路径。

6.6 订阅、API 与网关：使用前把钱和数据的路径画清楚

接入方式 谁提供模型 谁向你计费 需要确认什么
产品内置订阅／额度 平台选择或转售的模型 产品平台 包含哪些入口、模型、上限和额外费用
官方 API Key 模型厂商 模型厂商，可能另有平台费 模型权限、余额、地域和数据设置
第三方网关 网关路由到上游 网关，可能加价或另有规则 实际模型、日志、协议转换、失败处理
本地／内网服务 自己部署的模型 硬件与运维资源 模型格式、版本、许可、容量和出口

优先使用产品官方支持的认证方式。不要因为某个不明插件声称能共用订阅，就默认它受到模型厂商支持；也不要将账户凭据交给未经核实的中间服务。

6.7 一个简单的升级策略

先用中等档位完成普通任务；若失败，要求代理说明证据和卡点。只有确实需要更复杂推理、更长资料理解或更稳定工具使用时，才升级模型。机械批处理先用小样评估经济模型，达到标准后再放大。

对重要任务，可以让第二个模型或独立代理审查，但它必须查看原始材料与实际结果。只让另一个模型阅读第一份答案，容易变成互相认可，而不是独立验证。

模型升级是解决问题的一条路径；更好的输入、项目说明、工具、检索和验收，常常同样重要。

6.8 从规格表到可用能力：用同一套问题读所有模型

型号不同，真正要核对的问题相同。先区分模型本身、服务端点、Harness 适配和当前账户这四层。任何一层不支持，宣传页上的能力都未必能进入你的任务。

规格或能力 通俗解释 如何核对 不同路线中的例子
实际 ID 与版本 请求究竟交给哪个模型 保存服务返回、别名映射和版本 Claude 别名、kimi-for-coding、deepseek-flash 都可能变化
上下文与最大输出 一次可读多少、一次最多生成多少 模型上限、服务配置、客户端元数据分别看 Kimi 的档位、本地服务设置、Step 的百万窗口都需入口配合
输入模态 能接文字、图像还是视频 检查实际消息与上传路径 Gemini／GPT／Step 的模型能力不等于每个 CLI 都有同样附件入口
推理设置 允许为困难问题投入多少思考 查该服务支持的字段、档位和计费 某家的 low／medium／high 不能直接替换为别家的 max
工具调用 模型能否生成工具请求并利用结果 至少跑一次成功、失败、纠错和多轮往返 原生适配、兼容网关、本地模板的效果可能不同
结构化输出 能否按规定的数据形状返回 区分 JSON Mode 与 JSON Schema 支持范围 正常聊天成功不能证明严格字段与工具参数可用
缓存 重复输入是否按优惠规则计费 查看实际命中量与服务计费说明 稳定规则和工具前缀有帮助；摘要和路由变化会影响复用
开放与部署 能否取得权重、怎样合法运行 官方权重、许可、资源和推理服务 可下载的 Qwen／gpt-oss 与计划开放的型号要分开

以一个规格较齐全的型号示范：Step-5-Preview 的模型 ID 是 step-5-preview，官方列出 1M Token 上下文、64k 最大输出，支持文本／图像／视频输入与文本输出，以及工具调用、流、JSON Mode／Schema、缓存和 low／medium／high 推理档位。这些字段共同描述模型服务；其中任何一项都不能直接推导出 Step Code 或第三方客户端已完整支持。模型规格、推理参数

同样的核对方式也适用于其他家族：Gemini 要看具体 Flash／Pro 以及服务渠道；Claude 要看直连与云供应商的模型映射；GPT 要看实际产品目录而非另一入口的选项；本地 Qwen 要看推理服务实际启动的窗口和工具模板。这些都不能只靠模型名字判断。Gemini 目录、Claude 配置、OpenAI 产品模型、Qwen 模型卡

客户端元数据可能成为实际瓶颈。 例如 Step 的服务模型页写百万窗口，但 Step Code 获取元数据失败时有 256,000 的后备值；成本也有零值后备。于是“模型有大窗口”“当前会话按大窗口管理”“界面费用估算准确”是三种不同结论。自定义 Provider 和本地模型同样应核对上下文、最大输出和价格元数据。模型发现与后备值

视觉能力尤其需要端到端检查。Step 模型页列出的图片数量与视频上传方式属于服务接口限制；当前 Step Code 可确认文本与图像路径，不能因此声称所有视频都能直接送入。其他模型也有同样问题：先确认客户端确实发出了附件，再讨论模型有没有读懂。输入限制、客户端工具

6.9 接入路径与兼容性：模型地址、协议、账户分别配置

路线 配置责任 适合的起点 必须单独验证
厂商原生组合 产品处理主要适配与账户流程 Claude Code＋Claude、Codex＋GPT、Kimi Code＋Kimi、Step Code＋Step 实际账户开放、权限、版本与费用
多 Provider Harness 用户选择服务、协议和模型 OpenCode、Cline、Kilo、Pi、Hermes 等 工具、推理字段、窗口、压缩与附件
兼容 API／网关 服务声明兼容某协议，客户端配置端点 OpenAI 风格或 Messages 兼容服务 支持的是哪个协议版本和功能子集
ACP 外部代理 编辑器连接一个完整代理 Zed、Neovim 插件、其他宿主 外部代理自己的认证、模型、工具与恢复

“官方支持”还应写明是谁的官方。以 StepFun 的接入材料为例，它列出 OpenCode、Cline、Kilo、Hermes、Cherry、DSH 和 Claude Code 等路线，证明模型提供方给出了配置办法，不等于所有客户端团队共同担保全部版本兼容。Claude Code 的 Messages 路线还注明客户端版本与窗口设置，说明仅改模型名不一定获得完整能力。OpenCode、Cline、Kilo、Hermes、Cherry、DSH、Messages 接入

地址会决定账单渠道。 例如海外 Step 标准 API 使用 https://api.stepfun.ai/v1，Step Plan 使用 https://api.stepfun.ai/step_plan/v1；Messages 的相应基地址规则又不同，不能机械加 /v1。中国区使用对应 .com 服务与账户。其他模型服务同样要区分产品订阅、API 与网关，凭据和额度不能想当然通用。渠道说明、Messages 接口

下面是 OpenAI 风格 Chat Completions 兼容端点的文本连通示例，不是跨协议通用客户端，也不包含 Agent 循环。需要安装 SDK、配置环境变量和开通相应服务；本报告没有实际付费运行此示例。

import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["MODEL_API_KEY"],
    base_url=os.environ["MODEL_BASE_URL"],
)
reply = client.chat.completions.create(
    model=os.environ["MODEL_ID"],
    messages=[{"role": "user", "content": "说明这段代码的输入、输出与边界：……"}],
    max_tokens=4096,  # 仅适用于支持此字段的目标端点
)
print(reply.choices[0].message.content)

例如用 Step 海外标准 API 时，地址与 ID 分别为上述标准地址和 step-5-preview；其推理设置可按文档另外传入 reasoning_effort="medium"。换服务时必须重新核对字段；有的模型或协议并不接受同一套参数。连接成功以后，还要继续测试工具失败、纠错、附件和压缩恢复，不能停在能说一句话。接口示例与字段、推理字段

6.10 模型分数怎样还原成一套完整系统

要问的问题 为什么影响结论
用了哪个 Harness、提示与工具？ 同模型换工具接口，可能改变任务完成率
任务是什么版本，环境怎样准备？ 数据集、依赖与评测器会影响成功定义
单次尝试还是多次尝试统计？ 成功率与成本需要按相同尝试次数比较
推理、步数、时间和重试预算是多少？ 额外计算可能带来提升，不能忽略代价
成绩由谁发布，能否独立复现？ 厂商自报、内部基准与独立评测证据强度不同
与自己的任务相似吗？ 修复软件的分数不能直接代表中文小说或管理报告质量

例如 Step 官方发布页给出的 DeepSWE v1.1 为 67.7%，注明采用 SWE-agent；内部 StepCodeBench 为 49.0%（avg@4），FrontierFinance 为 66.4%。这些数字能帮助理解厂商定位，却不能直接当作 Step Code 外壳胜过其他工具的证明，也不能把不同统计口径拼成总排名。官方成绩与设置

同理，mini-SWE-agent 的基准主张、IDE 厂商的任务分数和模型厂商的发布图，都需要还原为模型、工具、环境与预算组合。读者真正要选的是日常可用系统，应再用第七章的任务集验证结果、成本和人工负担。mini 项目说明、试用与验收
