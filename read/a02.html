A02 Codex：把任务、执行环境和审查组织成一套系统

定位与设计理念

Codex 的关键不只是生成补丁，而是让代理在明确工作空间中持续执行任务，留下可审查的变更。CLI、编辑器和桌面入口可以提供不同交互方式；不能因为名称相同，就假定每个入口拥有完全一样的功能、模型和权限设置。CLI、工作树

它更强调任务的持续执行和结果审查：代理先获得一个明确的工作空间，再围绕文件、命令与验证推进。对于开发者，这意味着一次对话可以形成一组可检查的改动；对于界面开发者，同一核心又能通过协议被不同客户端使用。桌面上的任务管理方便组织工作，但真正决定任务能做什么的是运行位置、权限和所选模型。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

当前公开核心以 Rust 为主。codex-rs/core 放可复用业务逻辑，app-server 通过结构化协议把任务、回合和输出事件交给界面。通俗地说，界面负责“怎样看和怎样点”，核心负责“任务到底跑到了哪里”。这使桌面交互、自动化客户端和执行逻辑可以分开演进。核心说明、app-server

权限也不是一串提示词。源码将沙箱策略选择、命令转换和执行请求衔接起来；子代理创建时处理父级与请求权限的有效边界，并管理运行容量。其含义是：一个子代理不该因为“另起了会话”就自动获得比父任务更大的权限。具体平台使用的沙箱实现有所不同，部署时要看对应系统说明。沙箱适配、子代理创建

AGENTS.md、Skills、记忆与历史压缩分别解决项目规则、可复用方法、跨任务信息和当前窗口容量问题。压缩有本地／远端处理路径，不等于原始文件消失。工作树能够减少并行改代码时的文件冲突，但最后仍要集成、检查测试和审阅变更。压缩实现、自定义、子代理文档

app-server 的意义可以用远程控制来理解：界面发送结构化请求，核心把一轮中的消息、工具进度和完成状态回传。界面刷新不应让客户端重新猜任务有没有执行过。工作树则解决另一个问题：两个任务各自在不同目录改代码，减少争写文件；它不提供网络隔离，也不会自动解决两个补丁在业务逻辑上的冲突。源码中的子代理控制把容量和权限继承放进创建流程，说明分工需要运行时管理，而非只在提示里写几个角色名。

深入一层：客户端、会话协议与执行边界

Codex 要把同一任务呈现给不同客户端，因此“界面”与“运行中的会话”分开理解更清楚。App Server 用请求和通知传递线程、轮次与条目；一次 turn 内可产生多个工具条目。core 负责实际代理逻辑，界面消费进度，并在协议要求时处理审批。图中的两条入口是接入关系，不表示 App Server 之外又有一套不同模型。

模块／交接点 怎样工作 状态与边界
协议层 客户端发起请求，服务端持续报告条目状态 一次请求返回不代表整个任务已经完成。
执行层 工具请求经过策略与具体沙箱后端 macOS、Linux、Windows 的实现不同，不能拿一种平台的隔离承诺套用全部。
历史与分工 会话历史、压缩和子代理控制是不同职责 恢复聊天不等于恢复文件系统；并行任务仍需管理工作目录。

沿着一次任务看数据怎样走。 例如改 API：客户端创建轮次，core 组织上下文并请求模型；命令需要审批时，客户端收到请求并返回决定。允许后才进入相应执行路径，输出再作为工具条目回到会话。用户看到的“正在运行”是生命周期事件，不是模型一直输出文字。

与相近工具的实质差别。 与仅把 HTTP 模型接口包在聊天窗口里的工具相比，Codex 的客户端协议还要承载工具、审批和持续会话。与云端远程工作机相比，本地 core 的边界不自动等于云产品全部实现。

本节细图与机制依据：README.md、README.md、mod.rs、compact.rs。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

局部放大：一次命令：策略判断、审批与操作系统限制

这幅图单独拆开命令出口。策略判断决定该走哪条路径；需要审批时，用户或配置中的审批机制给出决定；获准动作再按实际配置进入执行后端。具体策略可能无需交互，也可能拒绝执行。审批回答的是“是否准许”，沙箱回答的是“运行时能碰到什么”，两者不能互相替代。恢复会话后，仍要检查命令是否已经执行及其退出状态，避免把缺少结果的调用直接重复一次。

本图依据同节列出的固定源码与官方文档，表示所选子系统的主要路径。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
项目规则 AGENTS.md、Skills 与产品支持的记忆 固定规范进入规则，当前进度进入任务记录，职责不要混用
状态与界面 任务／回合／事件通过 app-server 协议交互 自建客户端需要正确处理审批、流式事件和任务结束
上下文容量 保留历史并按路径进行压缩 压缩后抽查目标、文件和失败原因，必要时重新读原文
并行工作 子代理与 Git 工作树承担不同职责 前者分工，后者隔开文件；完成后都需要集成
执行环境 本地及其他产品入口的环境与沙箱不同 先确认当前目录、可写范围和网络访问策略
交付 文件变更、命令输出与审阅流程 最终要检查实际 diff；任务完成标签不是业务验收

把机制放进实际工作。

事件接口的价值在于让客户端区分“正在请求模型”“工具已开始”“需要审批”和“回合结束”。如果只把它们拼成一段文字，重新连接时就容易误判操作是否做过。开发自有客户端时，应该按协议管理任务状态；普通用户则应查看实际命令和文件，确认成功提示对应真实结果。

并行任务有三种不同的分离：子代理分开上下文，工作树分开代码目录，沙箱限制系统资源。可以只拥有其中一种，也可以组合。两个工作树仍可能使用同一个数据库或相同端口；两个子代理在共享目录里也可能争改同一文件。因此，分工应写明文件与外部资源责任，集成测试仍由整体任务承担。

恢复时至少核对四件事：当前任务目标、实际分支与文件、上次验证结果、仍在运行或已结束的外部操作。摘要里写“服务已启动”，不表示进程重启后服务还在。让代理先核对环境再继续，通常比直接说“接着做”更稳。模型升级适合解决推理瓶颈，不能替代这些状态检查。

从安装到完成第一个任务

  1. 选择 CLI、编辑器或桌面入口，打开目标仓库。确认当前分支和已有未提交修改，避免把用户原有工作误当作代理产物。

  2. 检查实际工作目录、模型、权限与执行环境，让它解释项目运行方法；把长期有效的约定放进适用范围内的 AGENTS.md。

  3. 提交完整任务，包括复现、改动边界、可运行的测试和完成标准。复杂需求先要求简短计划，确认关键接口后实施。

  4. 检查执行证据：命令是否真的运行、返回状态如何、验证覆盖了哪些行为。没有运行条件时，明确区分静态检查与真实运行验证。

  5. 确有独立改动再创建工作树或子任务；集成时重新做相关检查。需要开发自己的客户端时，再读 app-server 协议及事件生命周期。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

为现有服务增加分页查询，保留旧接口行为。先梳理调用方和测试，再实现参数校验、分页逻辑与测试。完成后解释兼容性，并列出未验证的部署条件。

分页任务要检查空结果、边界页和非法参数，不能只看返回了十条数据。若并行实现前后端，还要确认参数名称、排序规则和错误码一致。这个例子用来检验任务管理是否真正改善交付，而不是检验界面能否同时显示多个任务。

模型搭配、适用方向与取舍

原生优先当前官方 GPT 系列：日常先试 GPT-5.6 Terra，重复且容易验收的任务试 Luna，较深推理和成品质量需求试 Sol，最复杂的长任务试 GPT-6 Astra。选择必须以所在产品实际开放的模型为准。自定义 Provider 可以接入其他服务，但“接口能调用”不等于工具格式、推理状态和长任务行为已经同等优化。适合完整功能实现、迁移、复杂调试、需要反复运行验证的任务。上手难度：中；工作树和自动化管理：中高。模型说明、配置

选择路线 候选组合 怎样决定
原生日常 GPT-6 Sol；仍可用的 GPT-5.6 Terra 优先核对当前入口的模型目录，以同一小任务建立开发基线。
困难任务 GPT-6 Astra／Sol 深推理、复杂迁移和长任务候选；比较提升是否抵消额外时间与成本。
可机械验收 GPT-6 Luna；仍可用的 GPT-5.6 Luna 用于清楚、重复的小任务；失败应有明确升级条件。

它适合把实现、验证和审查作为一件连续工作的用户。原生模型路线通常省去协议适配负担；自定义 Provider 仍需确认工具参数、推理状态和上下文处理。与 Kiro 比较时看是否需要先形成规范；与轻量 Pi 比较时看是否更重视现成任务与权限管理。
