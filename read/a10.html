A10 Cline：把过程看得见、能审查作为主要体验

简档：保留定位、总体结构和能力边界；上手命令、试用任务和模型路线不再随事实刷新维护，选型请参考第 05 章的场景表与第 06 章的集中表。

定位与设计理念

Cline 重视逐步展示代理在读什么、改什么、运行什么，让用户在编辑器中持续参与。当前产品已有扩展、CLI 和 SDK 等入口，不能只依据早期 VS Code 插件判断整体能力。README

Cline 的起点是让用户看见过程并参与决定。它适合希望知道代理为什么读这个文件、为什么执行这条命令的人。Plan 与执行阶段帮助用户先对齐思路，再让代理动手。随着 CLI 和 SDK 发展，同一品牌的用途已经更广；选型时仍要把编辑器中的透明交互与命令行中的团队编排分别判断。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

SDK 把代理循环、模型适配和会话／工具基础能力分开。运行时处理模型输出限额、瞬时错误和重试，上下文层处理压缩与预算。这类分工使代理逻辑可以被不同入口复用，但入口是否暴露同一个功能仍是产品问题。代理运行时、压缩管线

现行文档中的子代理由 spawn_agent 工具启动，只在 Cline CLI 与桌面应用中可用，VS Code 和 JetBrains 扩展不使用它。每个子代理有独立上下文，可用的内置工具跟随当前模式：Act 模式下能读写文件、运行命令，还能再启动自己的子代理；Plan 模式下没有编辑工具，rm、git commit 这类通常会改文件的命令会被拒绝，但其他命令照常运行，其中 python -c 之类仍可能写入文件。子代理拿不到 MCP 工具。批准一次 spawn_agent，就等于批准了这个子代理之后的全部操作，审批设置在子代理内部不生效，所以批准前应先读清它要执行的任务。CLI／SDK／Kanban 的 Agent Teams 则有共享任务板、消息箱和持久任务状态，文档明确说这套团队功能当时还不适用于 VS Code 与 JetBrains 扩展。子代理文档、团队功能

把调查交给子代理的好处是减少主会话噪声：它在自己的上下文里阅读相关文件，再返回路径和发现，主代理不必接收每一次搜索输出。子代理能做什么取决于当前模式：Plan 模式下接近只读研究，Act 模式下也能修改文件和运行命令，而且批准一次就覆盖它之后的全部操作。团队任务则多出共享任务板、消息和长期状态，需要处理工作交接。两者解决的问题不一样：临时子代理不能替代有持久状态的团队；有团队状态也不能免去最终集成检查。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
交互 操作过程与审批可见 根据具体风险授权，避免机械地全部点同意
规划 Plan 与执行工作方式 计划中要有改动边界和验收，不只是步骤数量
子代理 CLI 与桌面应用中的 spawn_agent，独立上下文，可用工具随 Plan／Act 模式变化 批准一次即放行子代理之后的全部操作；VS Code 与 JetBrains 扩展不使用它
团队 CLI／SDK 等有独立团队机制 所核验文档未把同等能力开放给所有 IDE 扩展
模型与错误 多 Provider、重试和输出限制处理 协议错误、限流和真正推理失败要区分
上下文 独立压缩管线与预算管理 长任务要保存关键约束并抽查交接摘要
