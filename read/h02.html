H02 Roo Code：保留多模式工作经验，重新选择维护中的执行入口

定位与设计理念

Roo 的历史产品重心是编辑器内的多模式代理，README 列出 Code、Architect、Ask、Debug 和自定义模式，以及 MCP 等能力。当前仓库已归档，README 说明扩展关闭。它仍可用于理解旧工作流，但不能据此推荐新用户继续依赖旧服务。README 与模式说明

多模式将工作意图显式区分：规划、提问、调试和实施各有关注点，用户可按任务切换。它能帮助组织工作，但模式名称本身并不构成权限保障，真正的执行边界还取决于配置与工具。项目关闭后，这些方法仍可带到其他工具，旧服务和旧插件则需要单独评估。

工作原理与架构图

模式可以改变提示与允许使用的能力，让同一个代理先分析再实施；这与启动多个独立工作者并不一样。迁移自定义模式时，把原来的用途落实为新工具的规则、权限和任务说明。某些模式允许命令时，即便名字叫 Architect，也不能默认它没有写入能力。

深入一层：工作模式、工具范围与迁移后的权限重建

Roo 的模式首先是工作职责与配置的组合，不自动代表一个独立进程或一台隔离机器。同一个代理从规划切换到实施，与生成多个并行工作者是不同机制。项目关闭之后，细化这层边界的实际用途，是把旧模式的真实意图迁移到新工具，而非机械复制名称。

模块／交接点 怎样工作 状态与边界
模式提示 改变角色与工作方法 叫 Architect 不能证明没有写入能力。
工具范围 配置决定允许哪些具体操作 迁移后要重新核对权限，不能沿用旧印象。
资产导出 保存规则和代表性任务 旧服务状态与新工具维护状态须分开判断。

沿着一次任务看数据怎样走。 例如迁移先规划后编码模式：把规划阶段的输入、输出和允许工具写清，再在新工具重建，检查其是否真的限制写入。随后验证实施阶段能否读取计划，并将其用于实际修改。

与相近工具的实质差别。 与 Cline 当前子代理／团队能力相比，历史模式切换不是同一层协作机制；共同代码历史也不保证当前权限或可用性相同。

从安装到完成第一个任务

  1. 确认旧环境是否仍可用，保存必要项目资产；阅读关闭说明，不依据陈旧安装教程启动新的长期依赖。

  2. 整理每个自定义模式的真正职责、输入、输出和工具，不只记录角色名称。

  3. 选择维护中的候选，如 Cline、Kilo 或其他适合入口，重新设计规则和权限。

  4. 迁移 MCP 时重新确认服务、认证和工具范围；用只读任务先验收，再开放写入。

  5. 在相同代码任务上比较计划、实施与验证，检查新模式是否保留了原工作方法，并删除已无意义的旧配置。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

将一个先规划后实施的 Roo 工作流迁移到新工具。保留项目约束和检查步骤，分别验证规划阶段的工具范围与实施后的结果。

查看新工具是否按预期限制动作，以及规划是否真正指导实施。旧模式名相同却权限不同，应视为迁移差异；以当前生效的配置和实际操作结果核对权限。

模型搭配、适用方向与取舍

选择路线 候选组合 怎样决定
已有部署 仍受支持且已验证的旧配置 维护状态限制新投入，不把历史推荐当当前最佳。
迁移对照 新工具明确支持的相同模型 先迁工作流再升模型，尽量减少比较变量。
新用户 维护活跃产品的原生或正式支持路线 不为复刻旧入口而绑定不可用服务。

模型应随新工具当前适配重新选择，不能沿用旧排行榜中的最优组合断言。历史 Roo 适合研究多模式方法，活跃生产使用应比较维护中的产品。迁移的目标是保留有用的工作习惯，并在新工具中找到合适的实现方式。
