A08 OpenCode：把模型和界面选择权留给使用者

定位与设计理念

OpenCode 的重点是开放、多 Provider 和多入口。模型服务、终端／桌面界面、会话和工具执行并非全部绑在一个厂商订阅里。它适合已经有 API 账户、想比较不同模型，又不愿为每个模型重学一套工具的用户。README

OpenCode 把选择权放在模型和入口上：同一套会话与工具机制可以接不同 Provider，也能由不同界面使用。它对已有多个模型账户的用户很有吸引力。自由度带来的责任是明确记录究竟使用了哪个服务、哪套权限和哪些插件；“我用的是 OpenCode”本身并不足以复现一次任务。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

当前代码包括独立核心包以及会话、模型、权限、插件和快照服务。会话处理器将模型流转成消息与工具事件；还会在适当阶段准备快照。源码专门处理“工具可能早于某个流事件开始执行”的顺序问题，这说明保存状态不能只靠界面上看到的输出顺序。会话处理器

压缩不仅生成摘要，还涉及保留近期内容的预算、模型限制和大型附件溢出处理。任务工具创建独立子会话，并派生权限和模型设置。当前后台子代理还存在实验开关与深度限制；不要把源码中存在一条路径写成所有版本默认可用。压缩、任务工具

会话处理器把流式模型回复转为可保存的消息和工具事件；某些事件先后顺序并不直观，因此不能只按终端文字出现顺序理解内部状态。快照、历史和压缩共同服务恢复，但分别处理文件状态、对话过程和窗口容量。任务工具创建的子会话可以带着派生模型与权限工作：这能分开探索细节，也可能让总账单包含多个模型。

深入一层：流式处理、压缩与子会话的连接点

OpenCode 的 SessionProcessor 处理的不只是完整回复，而是模型流中的不同事件，并据此更新消息部件和工具状态。压缩模块单独管理历史整理；task 工具则把工作放进子会话。于是一个可恢复的任务至少涉及三类信息：对话内容、工具调用状态，以及仍然存在于工作目录中的文件。

模块／交接点 怎样工作 状态与边界
Processor 消费流事件并推进工具状态 流中断可能留下未完成调用，不能按普通答复处理。
Compaction 清理或摘要较早上下文 减少输入体积不等于删除真实文件。
task 通过子会话完成委派 子会话 ID 与结果是交接线索，不自动隔离工作目录。

沿着一次任务看数据怎样走。 例如主任务改后端，同时委派调查前端调用点：task 返回调查结论，主任务继续处理。排查断线问题时，先看调用是否已执行、结果是否已记录，再决定续跑或重试，避免重复执行有副作用的命令。

与相近工具的实质差别。 与源自同一代码路线的产品比较，要分别看工具注册、模型适配、压缩和持久化改动。同样的 Session 名称不代表这些策略继续保持一致。

本节细图与机制依据：processor.ts、compaction.ts、task.ts。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
模型自由 多个 Provider 与协议适配 模型列表多不代表所有组合都通过同等级测试
任务方式 Plan 分析与 Build 实施 核对实际工具策略，不能只看模式名称
历史与文件 会话记录、快照及压缩各有职责 继续对话与恢复文件应分别验证
子任务 独立子会话、模型与权限派生 后台等能力需确认版本和实验开关
扩展 插件、LSP、MCP 等能力 一次增加一类能力，才能定位行为变化
迁移 模型与界面解耦降低部分绑定 账户授权、工具格式与历史结构仍有迁移成本

把机制放进实际工作。

开放 Provider 解决的是接入选择，不会消除模型在工具描述、推理状态与输出格式上的差异。发现模型开始重复调用或丢失工具结果时，应检查适配和历史，而不是首先增加更长提示。网关若只保留可见文本，可能使表面正常的聊天在多轮执行中失去必要信息。

会话记录、压缩摘要和文件快照分别回答不同问题：之前说过什么、下一轮需要记住什么、某时文件是什么样。恢复对话后应核对实际目录，特别是在人工已经改过文件或从其他分支带入变更时。不要让过时摘要成为覆盖现状的依据。

子会话通过派生模型与权限开展局部工作，主任务则承担汇总和验收。给子任务限定文件范围与输出形式，可以减少无关修改和主上下文噪声。启用后台或实验功能时，应把版本、开关和取消行为一并记录；“支持子代理”不足以描述这个组合是否适合长任务。

从安装到完成第一个任务

  1. 安装并进入仓库运行 opencode，连接一个 Provider；优先选择已经明确支持工具调用的模型，记录实际 ID。

  2. 先用 Plan 让它解释修改范围、依赖和测试，再切换 Build 实施；将不变的项目约定写入文档支持的指令文件。

  3. 做一次完整的小任务，包括读取、修改、运行检查和展示 diff。工具调用失败时先看协议与参数，再怀疑模型能力。

  4. 保存任务的材料与验收条件，切换第二个模型重做同等任务；不要同时更换插件和模式，否则难以判断差异来源。

  5. 长任务再试压缩与子会话。检查摘要是否保留约束、子任务是否只修改分配范围，以及合并结果能否通过统一检查。

模型搭配、适用方向与取舍

选型建议：在当前 Provider 确认支持的前提下，以 Sonnet 5／GPT-5.6 Terra 作为日常候选，复杂任务上探 Sol／Astra 或更强 Claude；重视成本与中文服务时比较 DeepSeek、Qwen、Kimi。模型广泛可接入是自由度，不是全部组合都同样可靠的保证。适合跨模型比较、个人开发、开放工作流和自定义扩展。难度：中；插件多了以后是中高。

选择路线 候选组合 怎样决定
日常基线 已适配 Sonnet 5／GPT-5.6 Terra 优先稳定工具调用，先验证读、改、测与恢复。
较难任务 可用 Sol／Astra／较强 Claude 只在证据显示推理或实现能力不足时提升，环境错误先单独解决。
成本与中文对照 DeepSeek／Qwen／Kimi；Step 兼容路线 以当前 Provider 与官方接入说明为准；比较总重试和人工修正。

适合希望长期保留模型选择权的人。它让替换服务更容易，但没有消除服务差异。与 Kilo 比较时，关注是否需要账户与托管任务整合；与原生 Claude Code／Codex 比较时，关注模型适配成熟度及你愿意承担多少配置工作。
