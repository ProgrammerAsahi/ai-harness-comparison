A08 OpenCode：把模型和界面选择权留给使用者

定位与设计理念

OpenCode 的重点是开放、多 Provider 和多入口。模型服务、终端／桌面界面、会话和工具执行并非全部绑在一个厂商订阅里。它适合已经有 API 账户、想比较不同模型，又不愿为每个模型重学一套工具的用户。README

OpenCode 把选择权放在模型和入口上：同一套会话与工具机制可以接不同 Provider，也能由不同界面使用。它对已有多个模型账户的用户很有吸引力。自由度带来的责任是明确记录究竟使用了哪个服务、哪套权限和哪些插件；“我用的是 OpenCode”本身并不足以复现一次任务。

版本口径先说清：官方默认安装已经换成 OpenCode 2（当前 2.2.7），它重写了源码目录和会话层。下面“工作原理与架构图”里的深层模块图已按 2.2.7 的源码重写，依据是读源码，没有运行验证。档案里标着 1.19.0 的段落和较早的源码链接说的仍是旧结构；模块名和文件路径请以自己安装的版本为准。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

按 1.19.0 的源码，代码包括独立核心包以及会话、模型、权限、插件和快照服务，会话处理器将模型流转成消息与工具事件（2.x 把这一层重写成收件箱、逐步执行器和事件投影，见下文的深层模块图）；还会在适当阶段准备快照。源码专门处理“工具可能早于某个流事件开始执行”的顺序问题，这说明保存状态不能只靠界面上看到的输出顺序。会话处理器

压缩不仅生成摘要，还涉及保留近期内容的预算、模型限制和大型附件溢出处理。任务工具创建独立子会话，并派生权限和模型设置。OpenCode 2 把它改称 subagent 工具，子代理可以前台跑完，也可以放到后台运行；按 2.2.7 的源码，嵌套深度默认 1，子代理不能再派子代理，可用 experimental.subagent_depth 调大。试用时需核对安装版本和实际配置。压缩、任务工具

模型的回复分段到达，后台服务在每一段结束时把完整内容存成消息和工具事件；工具参数一到齐就开始执行，不等整段回复结束，因此不能只按终端文字出现顺序理解内部状态。快照、历史和压缩共同服务恢复，但分别处理文件状态、对话过程和窗口容量。任务工具（OpenCode 2 改称 subagent 工具）创建的子会话可以带着派生模型与权限工作：这能分开探索细节，也可能让总账单包含多个模型。

还要分清界面和服务。按 2.2.7 的源码，终端界面是一个客户端，默认连接本机的后台服务，由这个服务运行会话；加 --standalone 改用一个私有的服务进程，加 --server 则连接指定地址的服务。会话状态归属于服务一侧，所以排查任务进度、从别的入口继续会话之前，先确认终端连的是哪个服务。

深入一层：终端界面、后台服务与逐步执行的分工

OpenCode 2 把“显示界面”和“真正干活”分给两个进程。在终端输入 opencode 后，前台只运行终端界面（TUI）；它先找本机已经在运行、版本相符的后台服务，找不到或版本不符时，另起一个脱离终端的 opencode serve --service（默认入口、服务启动）。服务默认只监听本机地址 127.0.0.1，模型请求、工具执行和会话记录都归它管；界面用 HTTP 提交输入，再从 SSE 事件流接收进度。服务会一直运行，直到被停止、重启或被新版本替换，关掉界面不会顺带停掉它（服务进程）。

一次输入进了服务，先由 Session.prompt 记入这个会话的收件箱，再唤醒执行（会话入口）。执行器 SessionRunner 一步一步推进：每一步先估算要发给模型的内容有多大，快到上限就先压缩，再把历史重新整理成模型能读的消息发出去（逐步循环）。模型的回复以流的形式分段到达，文字、推理和工具调用各成一段；某个工具调用的参数一到齐，对应工具就开始执行，不等整段回复结束（单步执行）。这一步只要执行过本地工具，下一步就带着工具结果再请求一次模型；模型直接作答、又没有新的输入时，会话回到空闲。

写进磁盘的内容有明确分界。流式的文字片段只推给界面，大约每 100 毫秒合并发送一次，不写库；一段文字或一组工具参数结束时，带完整内容的结束事件才经投影写进本机 SQLite 文件 opencode.db 的会话、消息和收件箱表（事件定义、合批发布、投影、表结构）。所以重新打开会话时看到的，是已经结束并写入的内容；进程在一段文字结束前意外退出，屏幕上出现过的半段话不保证留在记录里。以上依据固定提交 fedc6f2 的源码阅读，没有运行验证。

模块／交接点 怎样工作 状态与边界
后台服务与中断恢复 一轮执行开始时，服务在数据库里留下一条“执行中”的记录，执行结束才清掉；服务重启后会找出没清掉的会话，提醒模型“从中断处继续、不要重复已完成的工作”，自动续跑，同一轮默认最多续 10 次（重启恢复）。 源码注释说明这种恢复是“至少一次”：能防止同一会话被两处同时执行，防不住崩溃后外部副作用重复发生。命令或改动在中途被打断后，先查它是否已经执行、结果是否已记录，再决定续跑还是重试。
上下文压缩 默认自动开启。每一步请求模型前估算输入量，超过“模型窗口减去预留量”就先压缩，预留量取窗口的 15%，窗口够大时至少 16000 token；模型报告上下文超长时也会触发。普通压缩由模型写一份结构化摘要，并原样保留最近约 15000 token 的内容；支持原生压缩的模型改用供应商自己的方式（压缩）。 压缩只改变之后发给模型的内容：模型从最近一次压缩开始读历史，数据库里的旧消息还在（历史读取）。单个工具输出超过 2000 行或 50 KiB 时会当场截断，全文另存为文件并在结果里给出路径（输出截断），这一步和压缩是两回事。
subagent 子会话 模型调用 subagent 工具时，服务新建一个记着父会话 ID 的子会话，把任务说明当作它的第一条输入，走和普通输入相同的 Session.prompt 流程；父会话的聊天记录不会复制过去。默认前台等待，把子会话 ID 和它最后的回答作为工具结果交回；设了 background 就立即返回，子会话完成后再通知父会话（subagent 工具）。 子会话继承父会话的工作位置、元数据和会话级权限（建会话），不会另开工作目录，并行的子会话可能改到同一批文件。默认只允许一层子代理，子会话里不能再开子会话。

沿着一次任务看数据怎样走。 例如让它“修复登录接口的报错，并让子代理查一下前端哪里调用了这个接口”。界面把这句话交给后台服务，服务记入收件箱并唤醒执行。第一步模型决定先读代码、跑测试，工具参数一到齐就开始执行，结果写进消息，下一步连同历史再发给模型。模型调用 subagent 后，服务新建子会话；子会话自己完成查找，把结论作为工具结果交回，主会话接着修改后端。中途关掉终端，后台服务仍在执行；再次运行 opencode 会连上同一个服务，界面向服务取回会话和消息，再接上实时事件。服务本身意外中断时，重启后会自动续跑这一轮，这时先核对测试命令和改动是否已经做过，避免重复执行有副作用的操作。

与相近工具的实质差别。 OpenCode 1.x 以 SessionProcessor 处理模型流、以 task 工具委派子会话；2.x 换成收件箱、逐步执行器和事件投影这一套，源码里没有逐个模块的迁移对照，两者不能按名称一一对应。比较不同版本或从 OpenCode 衍生的产品时，要分别看进程划分、工具注册、压缩策略和存储方式。和界面、执行同在一个进程里的命令行代理相比，OpenCode 2 关掉界面后任务还能继续跑，代价是多了一个要管版本和端口的常驻进程，排查问题时也要分清界面、服务和数据库三处状态。

本节细图与机制依据：opencode2-cli-default、opencode2-session-prompt、opencode2-runner-llm、opencode2-runner-step、opencode2-projector、opencode2-compaction、opencode2-subagent。图中选取主要模块与交接路径，完整结构及并行条件请结合所引材料阅读。

把机制放进实际工作。

开放 Provider 解决的是接入选择，不会消除模型在工具描述、推理状态与输出格式上的差异。发现模型开始重复调用或丢失工具结果时，优先检查适配和历史记录，定位信息在哪一步丢失。网关若只保留可见文本，可能使表面正常的聊天在多轮执行中失去必要信息。

会话记录、压缩摘要和文件快照分别回答不同问题：之前说过什么、下一轮需要记住什么、某时文件是什么样。恢复对话后应核对实际目录，特别是在人工已经改过文件或从其他分支带入变更时。继续执行前，先根据当前文件更新摘要中的过时信息。

子会话通过派生模型与权限开展局部工作，主任务则承担汇总和验收。给子任务限定文件范围与输出形式，可以减少无关修改和主上下文噪声。让子会话在后台运行或调大嵌套深度时，应把版本、配置和取消行为一并记录；“支持子代理”不足以描述这个组合是否适合长任务。

从安装到完成第一个任务

  1. 安装 OpenCode 2：官方文档和 README的默认命令是 curl -fsSL https://opencode.ai/v2/install | bash，也可用 npm 包 @opencode/cli；旧地址 opencode.ai/install 和 npm 包 opencode-ai 装的仍是 1.x。macOS 和 Linux 可直接用这条脚本；Windows 上文档写明不支持 Windows 包管理器，可下载官方独立二进制。随后进入仓库运行 opencode，用 /connect 连接一个 Provider；优先选择已经明确支持工具调用的模型，记录实际 ID 和 OpenCode 版本。

  2. 先用 Plan 让它解释修改范围、依赖和测试，再按 Shift+Tab 切换到 Build 实施；将不变的项目约定写入文档支持的指令文件。

  3. 做一次完整的小任务，包括读取、修改、运行检查和展示 diff。工具调用失败时先看协议与参数，再怀疑模型能力。

  4. 保存任务的材料与验收条件，切换第二个模型重做同等任务；保持插件和模式一致，便于辨认模型切换带来的差异。

  5. 长任务再试压缩与子会话。检查摘要是否保留约束、子任务是否只修改分配范围，以及合并结果能否通过统一检查。

模型搭配、适用方向与取舍

选型建议：在当前 Provider 确认支持的前提下，以目录内的 Claude Sonnet／GPT 日常档作为日常候选，复杂任务上探 GPT-6 Astra 或更强 Claude；重视成本与中文服务时比较 DeepSeek、Qwen、Kimi。模型广泛可接入是自由度，不是全部组合都同样可靠的保证。适合跨模型比较、个人开发、开放工作流和自定义扩展。难度：中；插件多了以后是中高。

选择路线 候选组合 怎样决定
日常基线 目录内当前的 Claude Sonnet／GPT 日常档 以该工具当前目录为准，优先稳定工具调用，先验证读、改、测与恢复。
较难任务 可用的较强 GPT／Claude 只在证据显示推理或实现能力不足时提升，环境错误先单独解决。
成本与中文对照 DeepSeek／Qwen／Kimi；Step 兼容路线 以当前 Provider 与官方接入说明为准；比较总重试和人工修正。

适合希望长期保留模型选择权的人。它让替换服务更容易，但没有消除服务差异。与 Kilo 比较时，关注是否需要账户与托管任务整合；与原生 Claude Code／Codex 比较时，关注模型适配成熟度及你愿意承担多少配置工作。
