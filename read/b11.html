B11 Warp／Automation Platform：从终端会话走向可触发的代理任务

定位与设计理念

Warp 原生终端会把命令、输出与上下文组织得更结构化。其代理在这样的工作环境中使用工具；同时也支持把 Claude Code、Codex、OpenCode 等第三方 CLI 放进 Warp。后者使用的代理核心仍属于第三方，而不是一律变成 Warp Agent。Agents 文档

Warp 从终端出发，把命令及其输出组织成容易理解的工作单元；原生 Agent 在此基础上完成多步操作，Automation Platform 再把稳定工作转成可触发任务。这条路线适合本来就在终端处理构建、日志和环境的人。需要先分清自己是在 Warp 里运行第三方 CLI，还是使用 Warp 自己的代理，因为两者的模型和执行逻辑不同。

工作原理与架构图

下图依据官方公开接口整理，表示责任分工，不代表已审计闭源内部实现。

Agent Profiles 配置模型、自治程度、工具与命令权限；Automation Platform 再提供远程环境、触发器、编排和观察能力。部分接口与应用仍使用 Oz 名称。比较时应区分“Warp 作为终端”“Warp 原生 Agent”和“平台上的远程执行”。CLI 文档

终端保留命令与输出，有助于模型把错误和具体操作对应起来。Profile 将模型、工具和自治程度保存为一组配置，让重复任务少一些临时设置；触发器只负责何时开始，远程环境负责在哪里执行。一个本机排障任务变成定时自动化时，输入、凭据、重复执行和失败通知都需要重新设计，不能只给同一句提示加一个时间表。

深入一层：真实终端、代理会话与云端自动化

Warp 的终端不是只用来显示文本的窗口。代理可以在真实终端中运行命令并读取动态输出，这与一次性执行命令后收集字符串的工具有区别。App、CLI 与云端自动化提供不同入口；规则、技能和上下文可以共享，但本地与云端的进程、凭据及环境仍然不同。

模块／交接点 怎样工作 状态与边界
终端状态 交互程序可能等待输入而非已经退出 提示符、退出状态和实时输出都影响后续动作。
代理入口 App 与 CLI 承载同一产品路线 终端模拟器和代理运行时仍是不同概念。
云自动化 触发、环境与运行观察由平台承担 计划触发不等于当前本地会话一直在线。

沿着一次任务看数据怎样走。 例如在数据库 Shell 中排查问题，代理需要理解当前程序状态再发送下一步输入。若改为云端定时任务，应重新准备连接和运行环境；复制聊天记录不能搬走仍在本机运行的进程。

与相近工具的实质差别。 与纯聊天终端界面相比，Warp 的差异在真实终端交互；与 n8n 相比，其自动化更围绕代理运行环境，而非首先围绕显式业务节点图。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
终端宿主 可运行第三方编码 CLI 第三方核心与账单仍按其自身规则
原生 Agent 结合终端上下文与工具执行 核对读取到的命令输出与实际运行环境
Profiles 模型、工具、自治与命令权限 配置保存后仍需按任务限制能力
自动化平台 触发、远程环境、编排与观察 启动成功不代表业务任务完成
生命周期 本机会话与远程任务分开 退出终端后是否继续取决于运行路线
权限 执行凭据与命令权限共同限制影响 产品界面的确认不能替代系统账户边界

把机制放进实际工作。

终端背景有助于定位问题，但输入范围仍需选择。一个失败命令后可能产生很多连锁报错，先找到首个相关原因，有助于集中解决根因。保留原命令、目录、退出状态和关键输出，可以帮助区分环境错误与代码错误。

将临时操作保存成 Profile，只是固定了一组能力与设置；把它变成自动化还需定义输入、触发、失败和结果保存。一次救火中临时扩大过的权限，不应不加判断地成为日常任务默认。对于会修改外部状态的任务，重跑前还要检查上一次是否已经生效。

Warp 中运行第三方 CLI 时，代理模型和会话仍由对方管理。原生 Agent、第三方代理和远程平台可能同时出现在同一个终端体验中，但账单和权限不一定合并。排错时先确定实际执行者与主机，再查看对应配置，可以避免在错误产品里寻找模型设置。

从安装到完成第一个任务

  1. 先把 Warp 当作日常终端使用，确认项目命令、输出和路径；选择原生 Agent 或第三方 CLI，明确当前执行者。

  2. 给原生 Agent 一个解释错误或整理日志的任务，先保留审查，核对它是否读到了正确命令的输出。

  3. 重复任务稳定后保存 Profile，写清可用工具、命令范围、模型和预期产物；排障完成后，将权限收回到日常任务所需范围。

  4. 需要自动运行再准备独立环境与触发条件，设置不会重复产生副作用的任务边界，并明确失败后如何检查。

  5. 在测试环境触发一次完整运行，核对日志、产物与费用。相同输入重跑时检查是否重复写入，再决定上线频率。

排障阶段看是否抓住第一个根因，避免被后续连锁错误带偏；自动化阶段看任务输入、结果和重复执行是否可控。只有自然语言总结，没有保存实际日志或报告，就难以长期维护。

模型搭配、适用方向与取舍

原生 Agent 使用当前 Profile 可选模型；第三方 CLI 遵循对应 Harness 的模型方案。适合日常终端操作、开发环境排障、运维脚本和周期性开发任务。难度：终端低中；平台自动化中高。涉及生产系统时，真正限制影响范围的是凭据和执行权限。

选择路线 候选组合 怎样决定
Warp 原生 Agent Profile 实际可选模型 按终端任务和工具稳定性选择。
第三方 CLI 对应 Harness 的原生组合 如 Codex＋GPT；Warp 在此主要是终端宿主。
周期任务 通过固定样本的经济档 将失败重跑和外部操作纳入成本，先稳定流程再降档。

适合终端排障、开发环境和周期性工程任务。相比通用自动化平台，它更贴近开发环境；相比单纯 CLI，它提供更完整的终端与远程组织。成本是 Profile、执行环境与触发流程的维护，特别是在涉及共享系统时。
