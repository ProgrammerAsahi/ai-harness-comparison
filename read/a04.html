A04 Qwen Code：在熟悉的终端代理结构上扩大模型与渠道覆盖

定位与设计理念

Qwen Code 既服务 Qwen 生态，也重视多协议接入。当前版本已不宜只用“Gemini CLI 的中文分支”概括：历史来源解释了部分结构，但现有模型配置、团队功能和入口已经继续演化。README

Qwen Code 把熟悉的终端代理形式与更宽的模型接入结合。它允许用户在保留一套工作习惯的同时调整模型服务，但这个自由度也要求用户了解地址、协议、认证和模型能力是四件事。最适合的用户不是只想填一个模型名字的人，而是希望围绕中文服务或自己的推理环境形成稳定流程的人。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

模型客户端中可以看到压缩、上下文精简和目标预算相关逻辑；代理工具则把子任务的生命周期、权限、会话和工作目录纳入管理。它不是简单将请求中的模型名替换成 Qwen。客户端

一个有代表性的源码细节是：某些 shell 沙箱环境只允许在同一工作空间内运行子代理，工作树、另选工作目录和队友功能会受到限制；前台子代理也需要处理父任务取消的向下传播。由此可见，宣传页上的“支持子代理”“支持沙箱”，并不保证两者在每一种组合中完全可用。代理工具

同一个子任务能否放进工作树，取决于运行环境是否允许它访问那个目录。源码对这类限制做了明确判断，所以不能孤立地比较功能勾选项。上下文预算也是如此：客户端可以精简和压缩材料，但服务端真实可容纳多少内容，还取决于模型部署参数。特别是在本地服务中，模型卡写着很长的窗口，并不意味着推理服务已经按相同长度启动。

深入一层：主会话与专用 Agent 工具如何分工

Qwen Code 不只是替换了模型名称。主会话客户端组织持续交互，Agent 工具把一个范围较明确的任务交给另外的代理执行，再把结果作为主任务的观察。这里最关键的是输入输出边界：子任务需要哪些文件、可用哪些工具、交付什么证据，应在委派时说清。图中并列分支表示不同职责，不承诺每条都会同时运行。

模块／交接点 怎样工作 状态与边界
会话客户端 管理请求与会话继续 模型渠道和认证配置仍须单独核对。
Agent 工具 把任务包装为可委派的调用 委派结果是结论和证据，不自动合并所有思考历史。
项目状态 工具最终作用于实际工作环境 多个任务修改相同文件时需要明确所有权。

沿着一次任务看数据怎样走。 例如排查构建失败：主会话保留用户目标，一条专用调查分析依赖错误，主任务检查构建配置；返回结果后再决定修改。验收应检查导致失败的命令是否恢复，而不只检查子代理是否返回“已找到原因”。

与相近工具的实质差别。 与 Gemini CLI 的差异需要落到各自的工具实现与适配，而不是仅看两者终端界面。与重型团队编排器相比，单个 Agent 工具也不自动具备共享任务板和全队调度。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
模型接入 多协议与多个 Provider 逐个确认 Base URL、认证、模型 ID 与协议
项目上下文 规则、当前历史和压缩／精简 保留关键约束，验证长任务恢复时是否仍然有效
目标控制 客户端处理目标与预算相关状态 预算应连同子任务用量一起观察
分工 子任务、会话、目录与权限共同管理 沙箱条件可能限制工作树和团队模式
本地模型 可按文档接入自建兼容服务 先通过工具调用与多轮测试，再讨论长任务
迁移 可复用项目文件与任务描述 认证、规则优先级和插件配置仍需重新核对

把机制放进实际工作。

多协议配置至少包含服务地址、认证、模型 ID 与请求格式。地址正确而协议错误时，普通文本可能勉强可用，工具、多模态或推理参数却失败；模型 ID 是别名时，还可能在不改配置的情况下切到新版本。完成一次聊天连接后，应继续测试工具往返和恢复，而不是立即迁移全部工作。

子任务创建既涉及上下文，也涉及工作目录和父任务的生命周期。若当前沙箱限制了可访问目录，独立工作树可能无法运行；若取消只结束父任务，子任务还在改文件，就会留下状态问题。源码中对此做约束的意义，是承认这些能力需要共同设计，不能分别打开几个开关就假定全部兼容。

本地模型方案还需核对推理服务的真实窗口、输出限制与工具模板。硬件不足导致截断、服务模板改变调用格式，与模型自身不会解决问题是不同情况。先用短任务排除部署问题，再增加上下文和任务复杂度；这样得到的成本与质量判断才有意义。

从安装到完成第一个任务

  1. 安装当前发行版并运行 qwen。先使用文档推荐的认证路线，避免第一步就同时自建模型、修改工具和启用团队。

  2. 让它解释仓库入口与测试方法，补充项目指令；确认中文需求中的业务术语与代码名的对应关系。

  3. 选择一个明确模型，用读取、单文件修改、运行检查三个动作验证基础工具链；记录返回的实际模型 ID。

  4. 接入本地服务时，再检查服务的上下文参数、工具模板和是否支持所需多模态能力。先测两三轮纠错，不能只以首轮能回答作为验收。

  5. 基础稳定后试一个独立子任务，确认目录、权限继承和取消行为。需要工作树时先检查当前沙箱是否允许，完成后由主任务统一验证。

模型搭配、适用方向与取舍

原生优先 Qwen 的编程／推理模型，当前服务目录包括 Qwen3.8 系列；跨厂商接入以文档支持的协议为准。若重视开放权重和本地试验，可测试 Qwen3-Coder-30B-A3B-Instruct 这类有官方模型卡的模型，但不要期待小模型承担和最大云端模型一样的长链条任务。适合中文开发协作、多协议部署、国内服务接入和本地模型探索。难度：中；自建推理服务：高。Qwen 模型目录、本地候选模型卡

选择路线 候选组合 怎样决定
原生云端 Qwen 当前编程／推理服务 中文开发先建立基线，记录实际 Qwen3.8 等服务 ID。
开放部署 Qwen3-Coder-30B-A3B-Instruct 等 仅在服务端格式、硬件和工具模板合适时试小修复，不直接承担最长任务。
跨厂商对照 当前明确支持的 Provider 保持相同工具、任务和预算，比较格式稳定性与返工。

跨协议和中文生态选择丰富，代价是配置组合更复杂。纯原生 Gemini 工作可选 Gemini CLI，偏模型无关插件生态可比较 OpenCode，极简研究可比较 Pi。比较时固定相同模型和任务，才能判断差异来自工具设计还是模型能力。
