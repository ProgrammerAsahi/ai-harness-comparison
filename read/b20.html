B20 Google Jules：把仓库任务交给独立云端工作机

简档：保留定位、总体结构和能力边界；上手命令、试用任务和模型路线不再随事实刷新维护，选型请参考第 05 章的场景表与第 06 章的集中表。

定位与设计理念

Jules 是异步编码代理：连接 GitHub，选择仓库和分支，在云端虚拟机中克隆代码、安装依赖、修改并验证。它与 Gemini CLI 的主要差别是环境和任务生命周期由服务管理。官方各页对它的成熟度说法不一（见下方表格），REST API 也仍是 v1alpha 预览版本，选型时按尚在演进的产品对待。入门、API 参考

它要解决的问题是：把一件说得清楚的仓库任务交出去，人可以先去做别的事，回来再审阅结果。与在本机终端里边看边改的 A 类代理不同，Jules 的计划、执行和记录都发生在服务端和临时虚拟机里；与 Devin 等其他托管工作机相比，它把“先出计划、再动代码”放在流程中心，交付物固定落到 GitHub 分支或 PR。代价是本机的即时环境帮不上忙，任务说明和环境准备要事先写清楚。

一次任务大致这样走完。用户在网页上选定仓库和起始分支，写下任务；也可以给 GitHub issue 加上 jules 标签，或通过 API 创建会话。Jules 随即启动一台短时虚拟机：克隆代码，运行用户提供的设置脚本，或者参考 README 与 AGENTS.md 自行准备依赖，然后给出分步计划。在网页上，计划要经用户批准才开始写代码；但用户离开页面后，计划会在计时结束时自动批准。通过 API 创建的会话默认自动批准计划，需要人工把关时要显式要求。执行中，活动记录逐步列出做了什么和每个文件的差异，用户可以随时插话、暂停或让它重新规划。结束时得到一份任务摘要，用户点击发布分支或发布 PR，改动才进入 GitHub，提交作者显示为 Jules。运行任务、计划审阅、审阅与发布、API 参考

状态分在三处。会话、计划、活动记录和对话保存在 Jules 服务端，API 把它们分别表示为 Session 与 Activity，仓库来源表示为 Source。虚拟机是短时的；设置脚本运行成功后保存的环境快照，会用于同一仓库以后的任务。代码只以 GitHub 分支或 PR 的形式回到用户手里。所以本机正在运行的服务、未提交的文件和个人环境变量都不会出现在云端，需要的依赖和测试步骤要写进设置脚本或仓库说明。Jules Tools（CLI）是连接这套云端服务的另一个入口，执行仍在云端。环境设置

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
发起方式 网页、GitHub issue 标签和 v1alpha 版 REST API API 会话默认不自动建 PR，也默认自动批准计划，按需要显式设置
计划确认 先出分步计划；网页上离开后会计时自动批准 需要人工把关的任务要留在页面上审阅计划
运行环境 短时 Ubuntu 虚拟机；设置脚本成功后保存环境快照 把安装与测试步骤写进设置脚本；依赖变动后重新运行并检查
状态归属 会话、计划与活动在服务端；代码以分支或 PR 交回 审阅以 GitHub 上的差异和测试为准，不只看完成通知
项目规则 仓库根目录的 AGENTS.md 与 README 未写进仓库的背景要补进任务说明
模型 原生模型路由 公开材料不支持任意 BYOK 的普遍承诺
成熟度 入门页称实验性，常见问题称 Public Beta，2025-08-06 更新记录称已结束测试 说法不一致时按试点对待，保持小范围试点与正常人工审查
