C05 Cherry Studio：多模型桌面工作台，也可以成为其他代理的宿主

定位与设计理念

Cherry 面向同时使用多个模型、资料和助手的人。当前架构已经从普通多模型对话扩展到独立 Agent Session 运行时，因此“多个模型各答一遍”和“多个代理分工执行”需要分别讨论。README

Cherry Studio 希望把多模型、多资料与不同工作角色集中在一个桌面入口。用户可以比较回答，也可以选择实际执行任务的代理后端。二者不能混同：让三个模型各写一篇文章只是多份答案，真正分工还需要共同目标、状态交接与结果整合。统一工作台的便利主要在组织和切换，而不意味着底层能力完全一致。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

Electron 界面通过进程间通信交给主进程的 AI 服务；主进程负责流、持久化与不同消费者。Agent Session 又区分宿主服务与具体驱动：宿主管会话、排队、恢复标记和界面生命周期，驱动对接 Claude Code、Pi、DSH 等不同执行后端。这是“统一工作台＋不同引擎”的明确例子。核心架构、Agent Session

这也带来边界：统一界面不意味着各后端的工具、审批和恢复语义完全一致。切换后端时，应确认原来的任务状态与权限怎样处理，而不只是看聊天记录还在不在。

界面通过进程间通信请求主进程服务，主进程管理输出与持久状态。Agent Session 的宿主负责排队、生命周期和恢复标记，具体驱动负责连接执行后端。这就像同一工作台可以接不同发动机：工作台能统一显示进度，却不能凭空让所有发动机获得相同工具和恢复语义。切换后端时，除模型外还要核对认证、目录和权限。

深入一层：稳定会话宿主与可替换运行时驱动

Cherry Studio 的 AgentSessionRuntimeService 管 UI 轮次、队列、持久化和恢复令牌；Driver 管具体代理如何运行。Claude Code、Pi 与 DSH 的传输、工具、审批和恢复格式被藏在各自驱动后面。统一提示材料由宿主组织，再映射到各运行时，因此一致的个人背景不意味着底层机制完全相同。

模块／交接点 怎样工作 状态与边界
宿主所有权 会话入口、UI 队列与恢复信息由 Runtime Service 管理 界面刷新不应被理解成重新创建底层任务。
驱动所有权 send、reconcile、close 等接口映射原生运行时 同一个按钮背后可能是长进程、流或 SDK 调用。
统一政策材料 身份、工作区、记忆和语言等由共同入口生成 原生工具与具体审批仍取决于 Driver。

沿着一次任务看数据怎样走。 例如从 Pi 驱动切到 DSH：用户希望保留同样的角色与工作区约束，但恢复令牌、工具表和运行事件不能简单照搬。验收应分别检查宿主资料是否一致、驱动是否能正常继续以及权限请求是否正确呈现。

与相近工具的实质差别。 与普通 Provider 切换相比，这里替换的是代理运行时；与 Zed 的外部代理宿主类似，但 Cherry 还拥有更明确的统一个人资料与桌面会话层。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
桌面组织 模型、助手、资料与任务集中管理 方便整理，但要明确资料属于哪项任务
普通对话 可比较多个模型的回答 多个答案不自动构成协作或相互验证
Agent 宿主 排队、持久化与会话生命周期 界面有历史不代表执行后端已恢复全部状态
代理驱动 连接 Claude、Pi、DSH 等后端 模型、工具和权限依驱动分别核对
数据路径 桌面、模型服务及工具后端 本地界面不能证明全部资料留在本机
迁移 资料、会话与代理配置分层 迁出前检查文件与历史是否真正可复用

把机制放进实际工作。

桌面宿主管理会话生命周期，驱动管理具体执行，这有助于统一入口，却也形成两层状态。界面保留了任务记录，后端可能已经退出或改变配置；恢复时要确认驱动、模型、目录和工具仍然匹配。恢复后，同时检查聊天记录、工具状态、工作区和待办是否衔接。

多模型同时回答适合比较观点与文风，但事实判断需要原始证据。若模型读取同一份错误摘要，它们的共识没有独立验证价值。分工时应明确各自职责与交付件，例如研究交付来源表、写作交付正文，最后核对两者。

后端切换时也应分别处理权限与费用。Claude、Pi、DSH 的工具、认证和恢复行为并非由桌面壳统一消除。对普通用户，先稳定一条常用路线更省事；只有明确需要另一种执行方式时再增加驱动，避免把管理所有后端变成新的日常工作。

从安装到完成第一个任务

  1. 安装桌面端，先配置一个模型与一个资料主题，验证对话、引用和导出；不必一次导入所有个人文件。

  2. 为常见工作建立职责明确的助手，说明输出要求；用同一材料比较模型时，保持提示和验收一致。

  3. 需要执行任务时创建明确工作空间，选择 Agent 驱动，完成该后端的认证和模型配置。

  4. 让它生成一个真实文件，检查工具、权限和保存位置；中断后恢复一次，确认宿主记录与后端状态衔接正确。

  5. 再尝试第二个驱动，记录能力差异。把不能自动迁移的规则、历史和授权列出来，避免只凭统一界面判断兼容。

模型搭配、适用方向与取舍

普通对话可自由比较 GPT／Claude／Kimi／Qwen；Agent 驱动则依其后端来选，例如 Claude 驱动优先 Claude、Pi／DSH 按对应适配。适合中文用户、多模型比较、知识整理、希望保留桌面统一入口的人。难度：基础低；多运行时管理中高。

选择路线 候选组合 怎样决定
多模型文字 GPT／Claude／Kimi／Qwen／Step 等已接入路线 同材料对照，关键事实回原文，不按多数票决定。
Agent 驱动 Claude 驱动用原生模型；Pi／DSH 按适配 完整记录驱动和工具，不只记录桌面客户端。
成本优化 摘要轻档、困难工具任务较强档 两种模式分开验收，保留真实服务账单。

适合中文多模型用户、资料整理和希望统一桌面入口的人。优势是集中管理，代价是后端组合仍需要理解。只需简单写作可以选 Chatbox；需要多人门户可以看 Open WebUI／LibreChat；想直接控制执行循环则更适合原生代理。
