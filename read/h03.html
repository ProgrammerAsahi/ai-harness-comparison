H03 Aider：项目地图、编辑协议与 Git 紧密结合

定位与设计理念

Aider 将代码地图、模型适合的编辑格式与 Git 工作流结合。仓库快照未归档，但推送间隔值得继续观察；这不足以断言不可用，也不足以证明当前所有新模型已适配。仓库

Aider 的鲜明路线是把有限上下文用在重要代码结构上，并采用适合模型的编辑协议。它不需要为每项改动建立复杂团队，也能通过明确输入、编辑和 Git 审查完成工作。项目地图帮助模型了解仓库，但它是压缩表示，无法替代必要时阅读实际实现。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

RepoMap 用有限预算表示仓库中的重要结构；编辑核心负责把模型输出变成代码修改。Architect 路线将提出方案与具体编辑分开，说明不依赖复杂团队编排也能形成清楚分工。项目地图、编辑核心

项目地图从代码结构中挑选重要信息，帮助模型知道相关文件和符号在哪里；编辑核心再将模型回复解析为实际修改。若模型频繁生成无法应用的编辑，问题可能在协议匹配而非理解能力。Architect 分工则让强模型先描述方案、另一模型具体编辑，节省与否要看交接遗漏和重试成本。

深入一层：RepoMap、编辑协议与 Git 的完整链条

Aider 的 RepoMap 在预算内选取重要的仓库结构，帮助模型定位相关代码。真正编辑还需要实际文件内容与适合模型的编辑协议。Architect 路线可以让一个模型提出方案，另一个负责按协议实施；节省多少要连同交接和补丁失败一起算。

模块／交接点 怎样工作 状态与边界
结构地图 提供符号和文件关系线索 地图帮助找位置，不替代关键代码阅读。
编辑协议 解析模型返回的修改格式并应用 模型理解正确也可能因格式不匹配而编辑失败。
Git 与验证 保存和审查实际差异 格式应用成功不等于语义正确。

沿着一次任务看数据怎样走。 例如提取重复校验：地图帮助定位调用方，模型读取相关文件后给出修改，编辑核心尝试应用，最后通过 diff 和测试核查。若补丁应用失败，应先检查格式与目标文件状态，再决定是否需要更强的规划模型。

与相近工具的实质差别。 与检索知识库的路线相比，RepoMap 更偏代码结构与预算；与多代理编排相比，Aider 说明上下文选择和编辑契约本身也能构成重要架构差异。

本节细图与机制依据：repomap.py、base_coder.py。图中选取主要模块与交接路径，完整结构及并行条件请结合所引材料阅读。

从安装到完成第一个任务

  1. 先核实当前维护与模型兼容说明，在项目副本或独立分支准备一项小任务，保存原有改动。

  2. 选择官方说明支持的模型与编辑格式，明确相关文件，先让它解释影响范围。

  3. 完成一项修改并检查 diff；遇到编辑格式失败时核对模型与协议，不只重复同一提示。

  4. 再试 Architect 分工，对照同一任务的完成质量、总调用与交接成本。

  5. 若迁移到新工具，保留项目资料、测试与版本习惯；不要求新工具必须复刻 RepoMap 才能取得相同结果。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

将一个模块中的重复校验提取成共享函数，保持所有调用方行为。用直接编辑和 Architect 分工各做一次对照，检查补丁和测试。

先看语义是否保留，再看编辑是否顺利。若分工减少规划错误却增加补丁失败，应将规划、补丁应用和返工合并计算，比较整项任务的成本。

模型搭配、适用方向与取舍

模型必须适配具体编辑协议；Architect 与编辑角色可采用不同能力。先以当前官方模型说明核对支持，再用相同改动验收。已有用户按实际稳定性决定是否继续，新用户先核实维护与兼容情况。官方模型说明

选择路线 候选组合 怎样决定
直接编辑 官方说明支持的模型与编辑格式 以补丁能否应用、行为正确与测试通过验收。
Architect 规划模型＋编辑模型分开 统计交接遗漏与编辑重试，不只看规划回答质量。
维护与迁移 核对当前适配后再接新型号 旧排行榜和包名不能保证现有服务仍可用。

适合喜欢终端与 Git、任务范围较清楚的既有用户。新选型先核对当前维护及模型适配；需要持续个人记忆、浏览器工作台或云端团队时应另选方向。它提醒我们，上下文与编辑协议也能形成重要差异。
