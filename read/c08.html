C08 LobeHub：从“助手集合”走向有状态的协作工作台

定位与设计理念

LobeHub 已不能只按早期 LobeChat 的界面理解。当前方向包括 Agent、工具与协作，其价值是让不同职责的助手与任务状态在同一工作台中组织起来。README

LobeHub 将助手、资料与有状态任务放在协作工作台中。一个角色可以负责研究，另一个负责写作，但真正的协作需要共享目标、可查证据和明确交接；不同名字与头像并不会自动形成分工。它适合希望把多种工作职责集中管理的人，同时要求用户避免过度创建角色造成信息分散。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

AgentRuntime 接收代理产生的指令，再执行调用模型、调用工具、请求人工审批或结束等动作。批量工具可从同一基础状态并行执行，再合并结果；服务端协调器负责更完整的运行生命周期。这样将“决定下一步”和“实际执行下一步”分开，便于扩展，但并行结果是否相互冲突仍需要上层语义处理。运行时、协调器

运行时把代理产生的指令转成具体动作，例如调用模型、使用工具、请求人工审批或结束。批量工具可以从同一份基础上下文出发再合并结果，这提高独立查询的效率；如果两项动作都要修改同一业务对象，仅有并发机制无法保证语义一致。角色设计应从任务边界出发：是否真的需要不同状态、工具和权限，还是只需换一个提示模板。

深入一层：代理运行核心与服务端状态协调

LobeHub 把运行核心与服务端协调器分开：Runtime 推进代理步骤，Coordinator 保存状态并发布流事件。源码中特别区分可见输出结束与权威的运行结束事件，这说明“文字停止增长”不等于整个代理任务已经终结。前端需要依赖完整生命周期来清理队列和对齐最终状态。

模块／交接点 怎样工作 状态与边界
运行步骤 模型和工具动作产生 StepResult 单步完成后仍可能有后续工作。
状态保存 Coordinator 与 State Manager 协调运行事实 存储暂时失败与模型失败属于不同故障层。
流事件 进度与终态通知供界面更新 以服务端保存的最终运行状态核对界面提示。

沿着一次任务看数据怎样走。 例如一次多工具调查：每步返回结果并更新运行状态，界面收到阶段进度，最终再收到结束事件。若输出已经停止而任务仍显示运行，可以沿状态保存与事件发布链检查，确认任务停在哪一步。

与相近工具的实质差别。 与仅在单机内维护循环的工具相比，服务端状态和 UI 流的一致性是额外难点；与其他多用户工作台比较，也应关注断线后的接续与状态对齐。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
角色组织 Agent 与协作工作台 角色要有职责和交付件，不只换人设
有状态运行 指令与实际执行分开 完成状态要能对应真实产物
批量工具 从基础状态执行并汇总结果 独立查询可并行，冲突写入需额外设计
人工参与 运行时支持审批动作 明确何时需要人的判断及判断材料
模型 按 Provider 与角色配置 多模型结论一致也可能源自同一错误材料
部署 托管与自托管路线 多人权限和数据保存按实际部署核对

把机制放进实际工作。

运行时将“决定动作”与“执行动作”分开，便于增加工具、审批和结束处理。用户看到任务完成时，仍应能找到对应文件或结果；状态标签不能脱离真实产物。这种有状态设计的收益，主要在任务可追踪和可接续。

从同一基础状态并行执行工具，适合多个独立查询；如果两项动作都要更新同一对象，结果合并需要业务规则。例如两个角色同时修订同一段报告，应先确定归属或交由统一编辑者整合。底层可以收齐结果，不代表语义冲突自动解决。

角色设计可以从最小职责开始：研究负责事实，写作负责表达，核验负责回原文。若只是改变语气，一份提示模板可能已经足够。只有需要不同状态、工具或权限时才增加独立 Agent，这样既减少调用成本，也让读者知道每项结论由谁依据什么产生。

从安装到完成第一个任务

  1. 先用一个职责明确的 Agent，例如仅基于团队资料回答问题，配置模型、知识来源和必要工具。

  2. 用已知答案检查材料引用和结果；记录任务状态与输出在哪里保存，确认以后能够追溯。

  3. 任务确实有不同职责时再增加角色，给出输入、输出和交接规则。例如研究交回证据表，写作根据证据表成文。

  4. 并行工具只用于真正独立的动作；涉及写入同一对象时安排顺序或统一负责人，避免冲突后靠语言总结掩盖。

  5. 多人使用时检查角色配置修改权、资料范围及产物归属；模型或服务升级后重做一条完整工作流。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

把一组市场材料整理成产品简报。先由研究职责形成证据表，再按该表写正文；最后检查观点、数据和来源是否一一对应。

检查两个角色之间的证据交接，确认后续工作使用了前一步的材料。不同模型若用了同一份错误摘要，不能算独立复核；应回到原材料抽查关键数据和冲突观点。

模型搭配、适用方向与取舍

根据当前 Provider 支持选择 GPT、Claude 或中文模型；多角色可以各用不同档位，但应防止风格统一掩盖证据矛盾。适合希望把聊天、资料与多个工作角色集中管理的个人和团队。难度：托管使用低中；自托管与协作治理中高。

选择路线 候选组合 怎样决定
单 Agent 基线 当前 Provider 支持的强工具模型 用受限职责建立可检查结果，再扩展角色。
分工方案 研究／执行用强档，摘要用经济档 交接必须保留来源和约束；角色多不等于更准确。
组织方案 批准的云端或私有端点 同时验证账户、资料与工具身份，模型不能补齐治理。

适合希望集中管理资料、角色与协作任务的个人和团队。代价是角色、共享状态和权限设计。简单任务保留一个 Agent 往往更清楚；固定业务流程可以比较 Dify，需要随时从消息渠道工作则可比较 OpenClaw。
