A09 Pi：保留一个可理解的核心，把特殊需求交给扩展

定位与设计理念

Pi 当前仓库迁至 earendil-works/pi。它吸引人的地方是执行核心、模型接口、终端交互和扩展边界相对清晰。使用者既可以直接编码，也可以把它当成搭建自己代理的材料。README

Pi 的设计可以理解为一套可理解、可改造的工作底座。模型接口、代理循环和编码产品分层，让使用者能在某一层定制，而不必把整个项目复制后全面修改。它把许多产品偏好留给扩展，因此同名 Pi 安装之间也可能有很大差异。简洁的价值在于职责清楚，使用者更容易理解和调整工作流程。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

agent-loop.ts 将代理上下文转换成模型输入，处理工具结果、用户中途追加的引导和后续消息；准备下一回合时可以调整上下文、模型和推理设置。会话管理器则保留分支、模型变更、压缩等事件。这种设计便于研究“模型到底收到了什么”，也方便把 UI 换掉。代理循环、会话管理

扩展可以注册工具、命令、事件处理、Provider 和界面元素，参与多个层面的工作。因此 Pi 的团队、计划或审批体验会随所装扩展而变化。比较时应写“Pi＋哪些扩展”，否则不是同一个实验对象。扩展文档

Pi README 明确说明默认没有内置权限系统；运行进程拥有启动用户的系统权限。扩展也在 Pi 进程内执行。想把它放进可控边界，应主动选择容器、虚拟机或文档列出的隔离方案，不能把简洁误认为自动安全。README

模型适配包负责把不同服务的消息与流接到统一接口；代理核心处理下一轮、工具和中途引导；编码产品再加入会话树、终端 UI 与扩展。扩展既可以增加一个工具，也能在关键事件中调整行为，所以比较 Pi 的实验应记录扩展清单。会话树帮助你从某个思路重新开始，但此前写入磁盘的文件还在原处；想同时保留两套代码实验，仍需要独立目录或 Git 工作树。

深入一层：小型代理循环与树状会话如何组合

Pi 在代理内部使用 AgentMessage，到调用模型时才转换成模型接口消息。循环内层处理工具与插入的指令，外层接续排队的后续任务；会话管理器则用带父子关系的条目表达历史分支。这样“继续当前工作”“在旧节点另开一条思路”“扩展工具”不必全部硬编码进一个庞大工作流。

模块／交接点 怎样工作 状态与边界
循环边界 核心发出 agent、turn、message 等事件 界面可订阅事件，不能把显示层当成执行引擎。
消息转换 调用模型前才转成 Provider 可接受格式 自定义消息不是天然都能直接发送给模型。
历史树 当前节点决定选取哪条祖先路径 切换分支改变对话上下文，不自动回滚项目文件。

沿着一次任务看数据怎样走。 试想你在修复方案 A 的一半返回旧节点，尝试方案 B。Pi 可以从历史树取出新的上下文路径，但文件仍可能含有方案 A 的改动。因此要配合 Git 或独立工作目录验证，而不是把对话分叉当成代码分支。

与相近工具的实质差别。 与 Step Code 相比，Pi 展示了更小的核心和可扩展的会话底座；调度、目标追踪等上层产品语义应以各自实际实现为准，不能从共同血缘反推。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
分层 pi-ai、agent-core、coding-agent 改模型接口与改产品交互不必落在同一层
历史 分支、模型变更和压缩等会话事件 对话树不是文件系统快照
扩展 工具、命令、事件、Provider、UI 说明所装扩展与版本，才能复现工作方式
分工与计划 可由扩展补充具体编排体验 记录具体扩展及其配置，说明能力来自哪里
权限 默认没有内置系统权限限制 工具和扩展按启动进程的权限运行
隔离 可采用容器或文档中的隔离方案 核对宿主挂载、网络和凭据，不能只看容器名称

把机制放进实际工作。

最小核心让行为来源更容易辨认，但前提是扩展数量受控。一个扩展可能注册新工具，另一个监听同一事件并改变上下文；两者各自正常，也可能在组合后产生顺序或状态问题。出现异常时从最小配置重现，逐个恢复扩展，比直接修改代理核心更容易定位。

会话树保留的是讨论与运行事件的分支。回到较早节点可以换一种思路，却不会让外部数据库、命令进程和文件自动倒退。需要比较两套实现时，应同时安排代码版本和对话分支；否则模型沿旧思路继续时，看到的可能已经是另一方案修改后的文件。

默认缺少内置权限系统，使运行边界尤其依赖启动方式。隔离方案不只是给程序套一个名字，还应检查目录挂载、网络和凭据。对研究者，这让实验条件可以明确控制；对普通用户，这意味着还需自行安排权限、隔离和维护。自由扩展与维护责任是一组相连的取舍。

从安装到完成第一个任务

  1. 使用当前官方包名与安装说明，先运行最小配置。配置一个稳定的工具模型，确认终端中能看到文件操作和结果。

  2. 在一次性测试项目中完成小修改；先了解启动进程可访问什么，再决定是否用容器或其他隔离环境。

  3. 观察会话历史和分支功能。尝试从较早节点改变方案，然后检查磁盘，理解聊天状态与文件状态的区别。

  4. 只安装一个有明确用途的扩展，例如固定检查或任务分工。查看它注册了什么工具、监听哪些事件，再重复基础任务。

  5. 要开发自己的 Harness 时，先选需要复用的层；尽量在公开扩展接口内实现需求，确需改变核心语义再修改循环。

模型搭配、适用方向与取舍

选型建议是先选一个能力稳定的云端模型建立基线，再用相同任务比较 DeepSeek／Qwen／Kimi 或本地模型。Pi 的优势在于能控制实验条件，便于辨认模型、工具和扩展各自的作用。适合熟练开发者、终端爱好者、代理研究和定制工具；不适合期待完整权限管理开箱即用的初学者。难度：日常中；定制高。

选择路线 候选组合 怎样决定
可控基线 Pi 当前适配的强 GPT／Claude 固定扩展、工具和任务，再评价核心与交互。
成本对照 当前适配的 DeepSeek／Qwen／Kimi 逐一验证多轮工具调用、编辑和纠错。
本地研究 正确服务的开放编程模型 从局部任务起步，记录量化、上下文与工具模板，保持实验可解释。

它尤其适合终端熟手、研究者和想写自己工作方式的人。代价是权限、团队流程和扩展质量需要更主动地管理。若希望这些产品决策已经替你做好，可以比较 Step Code、Cline 或完整 IDE；如果乐于自己决定，Pi 的分层更有价值。
