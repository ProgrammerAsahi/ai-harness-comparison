B04 Kiro：让需求、设计和任务清单成为持续上下文

定位与设计理念

Kiro 的辨识度在于 Spec 工作方式：先把需求、设计与实施任务写成可查看、可修改的材料，再让代理推进。它适合需求需要解释、多人需要对齐、实现时间跨度较长的项目。Spec 的价值在于明确需求、设计与验收共识。Specs

Kiro 将需求、设计和任务列表视为开发过程中持续使用的材料。模型围绕可持续修订的规范推进工作。对业务规则多、需要跨人交接的功能，这可以减少来回解释；对已经完全明确的一行修复，则可能增加不必要的文档成本。规范是否有用，要看它能否帮助澄清分歧、指导实施和检查结果。

工作原理与架构图

下图依据官方公开接口整理，表示责任分工，不代表已审计闭源内部实现。

官方说明将其描述为跨 IDE、CLI、Web、移动入口的统一独立进程 Harness，通过 ACP 及相关扩展连接客户端。规则、Hooks、MCP、Skills 等围绕同一个核心配置，但功能在各入口仍有差异。“同一核心”意味着复用执行责任，不意味着所有界面功能完全相等。工作原理

需求说明应回答用户要什么，设计说明回答准备用什么结构实现，任务列表回答当前先做哪一小步。三者形成可查看的交接材料，但它们也可能过时：代码改了、业务条件变了，就需要同步修订。统一进程 Harness 和 ACP 解决跨入口复用；Spec 解决工作方法，两者是不同层面的设计，不能把用了同一核心理解成所有客户端功能完全一样。

深入一层：共享 Harness、界面工具与配置作用域

Kiro 官方把多入口描述为共享同一 Harness，但执行地点随入口变化。IDE 还可以用编辑器自身 API 替代部分内置文件操作，说明界面并非完全没有执行职责。项目级配置跟随仓库，用户级配置跟随本机账户，工作区信任另存于机器侧；三者分开，是为了避免仓库自行给自己授予信任。

模块／交接点 怎样工作 状态与边界
项目配置 规则、规格、代理和 Hooks 可随仓库分发 团队共享行为材料，不等于共享每个人的授权。
客户端工具 IDE 可贡献编辑器原生能力 同一循环在不同入口可能调用不同工具实现。
本地与云端 相同逻辑在不同机器执行 依赖、凭据、网络与交付方式需要重新确认。

沿着一次任务看数据怎样走。 例如按规格增加一个接口：项目中的规格与设计约束引导实施；本地会话改当前工作区，云端会话则在克隆环境中完成并交付。迁移入口时，同时核对对话、项目配置和所需依赖。

与相近工具的实质差别。 与以自由聊天为中心的工具相比，Kiro 把规格与共享配置放在显眼位置；与 ACP 宿主相比，它公开强调的是共享自身 Harness，而非任意外部代理都由界面统一接管。

本节细图与机制依据：kiro-how、kiro-specs。图中选取主要模块与交接路径，完整结构及并行条件请结合所引材料阅读。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
需求材料 Spec 将需求、设计与任务显式保存 用户需删掉空话，补上例外和验收
长期规则 Steering 等持续背景 区分全项目约定与一次任务进度
跨入口 统一核心与 ACP 等连接方式 逐入口确认支持程度和可见功能
扩展 Hooks、MCP、Skills 等 确定性触发与模型判断的方法要分清
模型 Auto 及当前可选型号 档位变化后用同一规范测试结果
维护 规范与代码需要共同演进 完成后清除过时任务，记录真实设计差异

把机制放进实际工作。

规范可以减少歧义，也可能把模型猜测固化成看似正式的文档。审核时先找无法由已有材料确定的业务决定，如取消条件、权限与默认值，把它们交给真正了解业务的人确认。用规范约束实施的前提，是规范本身值得信任。

需求、设计和任务应保持对应关系。某项需求没有实施任务，容易被遗漏；某项任务找不到需求依据，可能是无关扩展。完成后将实际实现和设计对照，记录合理偏差，让这些材料在交付后仍能用于维护。

Hooks 适合在确定时机执行检查，Skills 适合复用需理解的方法，MCP 适合连接外部能力。这些扩展不能替代需求判断。简单修复可以直接完成；只有协调和返工成本值得时，再使用完整 Spec 流程。评价 Kiro 时，应把规范节约的沟通和维护规范的时间一起计算。

从安装到完成第一个任务

  1. 打开一个已有项目，确认构建和测试能运行；选择一个真正需要业务说明的小功能，从当前产品入口创建相应任务。

  2. 让代理形成需求材料，逐条检查对象、输入、输出、边界和异常；不懂的业务点由人决定，不让模型默默补成假设。

  3. 审阅设计，确认数据结构、接口和依赖符合现有项目。将大任务拆成能独立验证的小步，避免一项任务涵盖整个系统。

  4. 逐步实施并核对产物；需求发生变化时先更新规范，再继续改代码，减少前后解释不一致。

  5. 收尾时对照验收标准检查，更新实际采用的设计和遗留事项。简单后续修复直接对话即可，不必强迫所有任务重走完整规范流程。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

增加订单撤销功能。先整理需求与异常场景，明确库存回补和幂等规则，再设计接口与状态变化；逐步实现并对照规范验收。

最有辨识度的指标是规范能否减少返工。检查“重复撤销不能重复回补库存”这类关键规则是否同时出现在需求、实现和测试里。文档很完整但代码漏了约束，说明流程尚未闭合。

模型搭配、适用方向与取舍

当前 Kiro 已提供多个 GPT、Claude 和其他模型，并非只支持某一个旧 Claude 版本。一般从 Auto 或可用的 Sonnet 5／GPT-5.6 Terra 开始；复杂规范与实现比较更强档位。预览模型受地区与组织治理约束。适合中型功能、正式需求开发、跨人协作、验收明确的长期改造。难度：低中；高质量 Spec 写作需要业务判断。模型矩阵

选择路线 候选组合 怎样决定
规范与日常实现 Auto／可用 Sonnet 5 或 Terra 用需求、设计与实现一致性验收。
复杂设计 当前可用较强 GPT／Claude 先补全业务决策，再比较架构与边界推理。
简单后续任务 较快档位或直接对话 保持既有规范，避免每次重建长文档和全套流程。

适合需求需要讨论、多人需要共识、中等以上复杂度的功能。代价是规范维护与前期思考，过度使用会拖慢简单任务。与直接执行型 CLI 比较时，应同时计入代码生成、文档整理和返工时间。
