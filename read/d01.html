D01 Dify：把模型能力做成可复用的业务应用

定位与设计理念

Dify 更接近 AI 应用与流程平台。用户组织输入、知识检索、模型、工具、分支和输出，再将流程交给其他人使用。代码中，Workflow Entry 负责图运行状态、节点与事件，Agent Runner 则在需要自治的步骤中循环调用模型和工具。确定流程与代理循环可以同时存在。README、工作流入口、工具调用代理

Dify 的目标是把 AI 能力做成别人也能反复使用的应用。用户先设计输入、知识、模型、工具与分支，再让使用者提交数据。它不要求每次都让模型从头决定所有步骤，因此适合业务规则较稳定的任务。代理节点保留局部灵活性，外层流程则明确顺序与交接。

工作原理与架构图

下图结合所引源码与文档，画出本工具的主要责任分工；为便于理解，省略次要模块与错误分支。

它的好处是：业务逻辑不必每次依靠模型重新猜。例如客户问题先分类，再检索对应知识库，证据不足转人工。代价是需要设计和维护流程、变量、权限与失败分支。

假设客服问题先分类，再检索对应资料，最后生成回答：这三个步骤可以写进流程，不必每轮重新猜。某个节点需要灵活调查时，再使用 Agent Runner 循环调用工具。变量是步骤之间的交接单，字段写错会让下游拿不到输入；失败分支决定资料不足或工具报错时如何退出。图画得通并不代表业务规则已经正确，仍需代表性输入测试。

深入一层：外层工作流图与内层 Agent 循环

Dify 的外层工作流决定节点顺序与分支，Agent 节点内部再根据模型响应灵活调用工具。Workflow Entry 准备图、变量池和运行状态，并把引擎事件变为应用可消费的输出。因此要区分“整个流程下一步去哪里”和“某个 Agent 节点下一次用什么工具”，两个决定由不同层承担。

模块／交接点 怎样工作 状态与边界
外层图 显式节点和连线组织业务顺序 连错分支时，换强模型不能修复流程。
变量池 保存系统和节点产生的数据 字段名称、类型与空值决定交接是否正确。
内层 Agent 在节点范围内反复请求模型和工具 应配置预算、工具范围与可观察的退出条件。

沿着一次任务看数据怎样走。 例如政策问答先分类，再检索，再判断证据是否充分。只有需要开放式调查的那一步用 Agent；最终回答节点读取确定的证据字段。排查错误时先看分类和变量，再看检索，最后看生成，避免把所有问题归给模型。

与相近工具的实质差别。 与自主编码代理相比，Dify 把可预设部分交给图；与 n8n 相比，AI 应用、知识和节点内部模型运行更居于中心。

本节细图与机制依据：workflow_entry.py、fc_agent_runner.py。箭头表示主要信息或控制交接，不表示所有分支必然并行；省略的模块不能视为不存在。

局部放大：放大一个 Agent 节点：循环与流程的出口

外层工作流进入 Agent 节点后，不一定马上得到一个结果：Runner 可能多次请求模型和工具。只有节点形成输出或结束状态，外层流程才能按自己的规则继续。Agent 内部思路再灵活，也必须遵守节点输入输出契约。比如调查节点最终必须返回 evidence 字段，后续回答节点才知道哪些是已取得的证据；仅输出一段“我查好了”的说明可能无法完成结构化交接。

本图依据同节列出的固定源码与官方文档，表示所选子系统的主要路径。

能力、状态与边界

观察项 实际机制／公开能力 对使用者意味着什么
流程 显式节点、分支与变量 适合重复任务，变更时需维护流程
Agent 节点 局部多轮模型与工具循环 自治范围应限制在确有不确定性的环节
知识 检索材料参与应用回答 引用和缺失资料需要单独验收
模型 可按节点选择支持的 Provider 不同节点的错误会累积到最终结果
发布 应用供其他用户或系统调用 测试版本与对外使用版本需区分
部署与许可 云服务、自托管与企业能力 按实际许可证和服务条款确认范围

把机制放进实际工作。

流程图适合表达可确定的业务顺序，但模型仍会引入不确定输出。每个节点应有明确输入与输出约定，必要时增加结构检查；上游字段缺失时，下游不能默默以常识补齐。调试从节点数据开始，通常比直接修改整条提示更有效。

Agent 节点应放在真正需要探索的环节。若只是固定分类或提取，让模型自由调用许多工具可能增加成本与失败路径；若资料明显不足，流程应返回缺口或人工处理，而不是一直要求更长推理。外层流程和局部自治各用在适合的位置，才能发挥组合价值。

应用发布后，模型、知识源和提示的变化都可能改变结果。保留代表性样本与可工作的流程版本，变更后重点回归受到影响的分支。多人业务应用还要区分终端使用者与流程管理者的权限，不能因为作者能访问某项资料，就把它暴露给所有应用用户。

从安装到完成第一个任务

  1. 选择云服务或按官方文档自托管，先配置一个模型与测试资料；明确最终应用面对谁、接收什么输入。

  2. 建立最小流程，只保留输入、必要检索、生成与输出。固定输出字段，便于检查与后续系统使用。

  3. 加入分类和分支时，为每类准备正常、边界与无法判断的样本；证据不足应有明确返回，而非继续编造。

  4. 只有某一步不能预先固定时再用 Agent 节点，为其指定工具、预算和退出条件。工具报错要回到可观察的失败分支。

  5. 用代表性样本验收整条流程，再发布给实际用户；修改模型、提示或知识源后重新验证，并保存可工作的流程版本。

典型任务与验收方法

下面是一份可直接改写使用的试用任务，属于本报告设计的验收示例，并非已完成的运行测试。

建立内部政策问答应用，按问题类型检索不同手册；答案要引用来源，无法确认时返回待人工处理的原因和需要补充的资料。

逐节点检查输入输出，再检查最终用户结果。分类错会检索错库，字段丢失会让后续模型凭空猜；强模型只能改善部分判断，无法修复错误的流程连线或权限设计。

模型搭配、适用方向与取舍

从一个简单问答或资料提取流程开始，固定输入和输出格式；模型使用平台当前支持的 GPT、Claude、Qwen、DeepSeek 等。简单分类与复杂判断可以分配不同档位，但必须对整个流程验收。适合客服知识、文档处理、企业内部 AI 应用；临时修一个代码 bug 通常不是最简路径。难度：基础中；生产化高。许可证、企业能力和云服务与自托管差异应单独核对。

选择路线 候选组合 怎样决定
简单节点 支持接口的经济模型 分类和固定提取先用样本验收，并设计无法判断分支。
复杂判断 支持的较强 GPT／Claude／中文模型 按节点升级，避免整条流程无差别使用最高档。
本地或组织 对应插件／节点支持的内部服务 检查结构化输出、工具参数、失败重试与总成本。

适合可重复资料处理、客服与内部 AI 应用。它把临时任务变成需要维护的流程产品，因此改一个本地 bug 通常不值得先建应用。与 n8n 比较时看 AI 应用与业务连接器的重心；与自主代理比较时看可预设流程有多少。
