# 第二轮试编码记录（码本 fields-0.3）

这一页记录按修订后的码本重新编码的做法、两位编码者的一致程度，以及结果能说明什么、不能说明什么。逐字段的分歧随时可以复算：

```bash
python3 studies/harness-quantification/compare_codings.py
```

`data/codings/` 里现在放的就是这一轮的结果。它们仍是两位编码者各自独立的初稿，没有对过分歧，也没有人工裁决；用来检验码本，不是对任何工具的评分，也不进入方法报告正文。第一轮的经过见 [`round1.md`](round1.md)。

## 怎样做的

- 对象：和第一轮相同的 10 个配置记录（`data/configs/`），版本和提交钉在 2026-11-10。
- 码本：`data/schema/fields.json` 的 `fields-0.3`，36 个字段。相对第一轮，多了九条跨字段总则（R1–R9），每个字段都有定义和判定标准，集合字段多了可选的“疑似成员”（`unresolved`），配置记录多了一组钉住的环境前提。
- 任务卡：两位编码者都用 `coding-card-v4`。
- 编码者 `opus`：Claude Opus 5.5。编码者 `gpt`：GPT-6.1 Sol，型号按派活时请求的型号记录，运行环境没有回报实际型号。
- 材料：两位编码者都不联网，只读同一份按配置记录钉的提交取下的源码快照（Claude Code、Codex 另附官方文档导出）。第一轮里一位在线读、一位读快照的不对等，这一轮没有了。
- 两位编码者互不可见。每个配置分三段（字段组 ABC、DEF、GHI），一段一次独立运行，共 60 次；每段交回后由 `pilot/parts.py check` 检查，再合并。
- 都只读公开资料，不安装、不运行被研究的工具。

## 编码期间改过的环境前提

环境前提里有三处由研究负责人在 2026-11-10 重新选定，时间落在这一轮编码中途：

| 配置 | 改动 | 对这一轮的影响 |
|---|---|---|
| Pi | 凭据从一家接口密钥改为 ChatGPT 订阅登录，默认型号随之改变 | 两位编码者按新前提重新编码了全部三段，旧结果没有合并 |
| MiMo Code | 计费方式定为 Token Plan | 编码在改动之前完成。客户端源码里没有随计费方式变化的分支，所以结果保留，没有重编 |
| OpenClaw | 一度改为复用本机的 Codex CLI 登录，查证后退回接口密钥 | 两位编码者都按接口密钥这条路线编码 |

改动的理由记在码本的决定记录里；决定记录不交给编码者。

## 一致率

一致率是“两位编码者状态和取值都相同的字段数 ÷ 36”，没有做随机一致的校正；每个配置只有一对编码者。

| 配置 | 第一轮一致 | 第二轮一致 | 取值不同 | 状态不同 |
|---|---|---|---|---|
| A01 Claude Code | 53% | 89% | 4 | 0 |
| A02 Codex | 61% | 86% | 5 | 0 |
| A05 Kimi Code | 64% | 86% | 5 | 0 |
| A06 MiMo Code | 72% | 89% | 4 | 0 |
| A07 DeepSeek Harness | 61% | 81% | 7 | 0 |
| A08 OpenCode | 58% | 89% | 4 | 0 |
| A09 Pi | 75% | 97% | 1 | 0 |
| A10 Cline | 83% | 89% | 4 | 0 |
| A17 Step Code | 67% | 86% | 5 | 0 |
| C02 OpenClaw | 56% | 69% | 11 | 0 |

合计 360 个“字段 × 配置”里 310 个一致（86%，第一轮 65%），50 个取值不同，没有状态不同的。

**按字段看。** 10 个配置上全部一致的有 9 个字段：F01（主取值）、F05、F07、F08、F15、F18、F25、F26、F29。一致最少的是 F36（50%）、F17 和 F20（各 60%）、F04 和 F32（各 70%）。第一轮垫底的几个字段都有回升：F32 从 0% 到 70%，F29 从 20% 到 100%，F10 和 F31 从 30% 到 80%，F14 从 40% 到 90%，F17 从 40% 到 60%。

**分歧的形状。** 50 处取值不同里，44 处在集合字段上，其中 42 处是一方比另一方多记了成员、其余成员相同，2 处是互有出入；6 处在单选字段上（F02、F09 两处、F13、F34、F35）。有 9 处，一方确认的那个成员正好写在另一方的“疑似成员”里，也就是两人看到了同一样东西，只是一方认为证据够、一方认为不够。

**状态。** 两位编码者都没有写“未知”：各自是 345 个已知、9 个已知不存在、6 个不适用，分布相同。第一轮 11 处状态不同全部来自材料不对等，这一轮读的是同一份快照。

**把握程度。** `opus` 记高 196、中 122、低 36；`gpt` 记高 265、中 53、低 36。两边的 36 个“低”都是 Claude Code：它是闭源产品，按总则只能从官方文档推断。`opus` 有 20 处用了“疑似成员”，`gpt` 有 11 处。

**子维度。** 两人都已知取值时才比较子维度，一共比较 291 个，72 个不一致，其中 17 个是一方留空（未知）。不一致集中在 F31（30 个里 13 个）、F11（10 个里 7 个）、F01（10 个里 6 个）和 F29（20 个里 6 个）；F21 的 40 个和 F34 的 10 个全部一致。留空的都在 `gpt` 一侧。

两位编码者这一轮只提了 2 条词表补充建议（F19、F29 各一条，都来自 `opus`），第一轮是 15 条。

## 能说明什么

- 修订后的码本让两位编码者在更多字段上得出了同样的答案，剩下的分歧多数是集合里多一项少一项。
- 这个提升有一部分是“照着答案改题”：码本正是根据这 10 个配置上的第一轮分歧修订的，再拿同样的 10 个配置检验，会比换一批新配置好看。码本够不够用，要在没参与修订的配置上再试才知道。
- 一致不等于正确：两位编码者可能错在同一处。不一致也不说明哪一方错。这一轮没有裁决，也没有逐条回查源码。
- 没有人写“未知”，不等于证据都充分。总则收窄了“未知”的适用范围，拿不准口径的地方改为按码本判再写疑问；证据薄不薄要看把握程度和疑似成员，两位编码者在这两项上的用法差别不小。
- 样本只有 10 个配置、一对编码者，没有做随机一致校正，不足以给单个字段的可靠性下结论。

## 编码者提出的口径疑问

下面的问题来自两位编码者的说明和这一轮的分歧，留给下一次码本修订，这里不作裁决。

| 字段 | 疑问 |
|---|---|
| 总则 R3 | 文档写“默认关闭”或“实验功能”、代码里却按默认型号自动生效的功能，按哪一边记；只靠提示词约束、代码不拦的开关算哪一档 |
| 总则 R5 | 一个提交同时发布几条产品线（编辑器扩展、命令行、SDK）时，“同一发行版的全部入口”包括哪些 |
| F03、F12 | 按“每次模型尝试”计的时长上限覆盖整轮多步运行时，算不算任务级的时间预算 |
| F04 | 框架替模型修正输入（补全、改写参数）与普通重试的界线 |
| F09 | 自带多家适配器、默认只走一家官方 SDK 时，记适配层还是厂商 SDK |
| F13 | “每轮”指每次模型请求还是每个用户回合；压缩后把摘要和近几轮原文放回消息列表，算不算另一种组织方式 |
| F17 | 一份会话记录里既有消息、又有模型切换和压缩等带类型的条目时，记消息还是事件日志；写在临时目录的溢出内容算不算外部引用 |
| F20 | 防止重复执行的持久标识不按工具调用分配时，算不算幂等键；回退时原会话只是停掉、没有删除，算不算会话分支 |
| F21 | 文档里还写着、代码已不再读取的规则字段怎样处理；工具加载名单算不算允许／拒绝规则 |
| F23 | 代码检查自己承认拦不全时，算不算“只靠提示词” |
| F28 | 取消范围随取消方式不同（显式停止会传到整棵子代理树，正常结束和超时不会），选哪一项 |
| F29、F31 | “默认在用”怎样判：注册了但默认不激活的工具和钩子算不算；一个事件既是旧会话结束又是新会话开始时归哪一项；“只能观察”的界线 |
| F30 | 工作流文件记作工作流定义还是提示模板；“可执行条目”包括哪些 |
| F32、F33 | 服务接口、外部事件这类入口，一方确认、一方只记作疑似：证据到什么程度才计入取值 |
| F36 | 消息通知、可恢复待办、结构化交接三项的界线；通知功能默认只对审批类开启、而本配置默认不弹审批时怎样记。这是一致率最低的字段 |

## 这一轮之后改过的配置记录

OpenClaw 的两位编码者在 F34（生命周期由谁维持）上相反：一位按配置记录的入口记“本地服务”，一位按环境前提里的 Quick start 记“前台进程”。对照钉住的提交核对：引导选 Quick start 时不安装守护进程，网关留在终端前台；官方快速开始的下一步让用户停掉前台网关、运行 `openclaw gateway install` 装成系统服务。原记录的入口写“经 onboarding 安装为常驻守护进程”，前提又写 Quick start，两处指向不同的状态。

记录已改：入口写明“引导完成后按官方快速开始用 `openclaw gateway install` 装成常驻系统服务”，环境前提补上这一步和两条证据。这一轮的编码是照改之前的记录做的，F34 的分歧来自记录，不来自码本。

两位编码者说法相反或各执一词的事实另有 39 件，都对照钉住的提交回查了一遍（Claude Code 只有官方文档和更新日志可查）。据此又改了六份配置记录，各补了证据卡：

| 配置 | 改了什么 |
|---|---|
| Codex | 默认型号在内置型号目录里声明第二版多代理工具，实际启用的是第二版；ChatGPT 登录后服务端下发的目录会整份替换内置目录，实际值由服务端决定。另补三句：默认型号的工具调用经受限的代码单元发出；命令行默认的线程历史模式和它记录哪些审批结果；目标工具默认开放给模型 |
| Kimi Code | 目标工具默认注册给主代理、模型可直接调用；开始目标时所选的档位会改变之后的审批方式 |
| OpenCode | 待办工具受实验开关控制，正式版默认关闭、不注册给模型 |
| Cline | 扩展会话默认会从工作区和用户目录发现并加载插件（默认环境下目录为空）；两页官方文档称插件不适用于 VS Code 扩展，与代码和 4.0.0 发布说明不一致 |
| Step Code | 工作流工具的 `/ultracode` 同意在代码里是软闸：未同意的调用只记录、不拦截 |
| OpenClaw | 环境前提补上：接口密钥这条路线把默认型号钉到内置运行时，官方 codex 插件不随安装启用；Code Mode 在默认型号下默认生效（有一页文档称默认关闭，与代码不一致）。默认扩展补上：电脑控制插件在本环境没有可用目标 |

39 件里有 3 件没能完全查清：Claude Code 的内置探索、规划子代理是否单独带搜索工具（文档没有明文）；DeepSeek Harness 崩溃后收件箱里的消息是否自动重发；OpenClaw 默认是否给单次请求设输出上限（代码和文档不一致，调用链没有追完）。回查只读源码和文档，没有安装或运行这些工具；其中 DeepSeek 两个型号名是否指同一模型，依据的是 2026-11-11 在线读到的官方价格页，没有固定版本。
