# 第三轮试编码记录（码本 fields-0.4，十个新配置）

这一页记录码本修订后换一批新配置编码的做法、两位编码者的一致程度、随后的交叉核对，以及结果能说明什么、不能说明什么。逐字段的分歧随时可以复算：

```bash
python3 studies/harness-quantification/compare_codings.py
```

这一轮的编码文件归档在 [`round3/`](round3/)。它们是两位编码者各自独立的初稿，没有人工裁决；用来检验码本，不是对任何工具的评分，也不进入方法报告正文。前两轮的经过见 [`round1.md`](round1.md)、[`round2.md`](round2.md)。

## 怎样做的

- 对象：10 个没参与过码本修订的配置（`data/rounds/pilot-2.json`，角色 `holdout`）：A04 Qwen Code、A12 Goose、A13 Crush、A14 Mistral Vibe、A15 OpenHands、A16 Grok Build、B06 Zed、B10 Factory Droid、C01 Hermes Agent、D03 mini-SWE-agent。版本和提交钉在 2026-11-11；入口、登录方式和环境前提在编码前由研究负责人逐项确认，编码期间没有改过配置记录。
- 码本：当时的 `fields-0.4`（现存 [`round3/fields-0.4.json`](round3/fields-0.4.json)），36 个字段，十条跨字段总则（R1–R10）。
- 任务卡：两位编码者都用 `coding-card-v6`。
- 编码者 `opus`：Claude Opus 5.5。编码者 `gpt`：GPT-6.1 Sol，型号按派活时请求的型号记录，运行环境没有回报实际型号。
- 材料：两位编码者都不联网，只读同一份按配置记录钉的提交取下的源码快照，文档在仓库外的另附官方文档导出。三处要说明：
  - Factory Droid 闭源，只有官方文档导出和发布说明。
  - OpenHands 的界面和执行端在两个仓库，快照两个都有；配置记录还钉了自动化服务的仓库，这一份没有取到快照里。
  - Grok Build 的配置钉的是当前正式版 1.0.77，公开仓库最后一次同步停在 1.0.45，源码快照是后者，文档导出是现行文档。
- Goose 的源码归档有 316 MB，超过 `gpt` 一侧运行环境的输入上限。给 `gpt` 的是同一份归档去掉图片和视频文件后的副本（3091 个条目里去掉 336 个，源码和文字文档没有改动）；`opus` 读的是完整归档。
- 两位编码者互不可见。每个配置分三段（字段组 ABC、DEF、GHI），一段一次独立运行，共 60 次；每段交回后由 `pilot/parts.py check` 检查，再合并。`gpt` 有一段（Hermes Agent 的 ABC）写到了运行目录里约定之外的位置，原样取回后通过了同样的检查。
- 都只读公开资料，不安装、不运行被研究的工具。

## 一致率

一致率是“两位编码者状态和取值都相同的字段数 ÷ 36”，没有做随机一致的校正；每个配置只有一对编码者。

| 配置 | 一致 | 取值不同 | 状态不同 |
|---|---|---|---|
| A04 Qwen Code | 86% | 5 | 0 |
| A12 Goose | 69% | 11 | 0 |
| A13 Crush | 94% | 2 | 0 |
| A14 Mistral Vibe | 89% | 4 | 0 |
| A15 OpenHands | 75% | 8 | 1 |
| A16 Grok Build | 89% | 3 | 1 |
| B06 Zed | 81% | 6 | 1 |
| B10 Factory Droid | 69% | 9 | 2 |
| C01 Hermes Agent | 89% | 4 | 0 |
| D03 mini-SWE-agent | 94% | 2 | 0 |

合计 360 个“字段 × 配置”里 301 个一致（83.6%），54 个取值不同，5 个状态不同。一致的 301 个里，292 个是取值相同，6 个是两人都记“不适用”，3 个是两人都记“未知”（都在 Factory Droid 上）；都记未知没有共同的证据，单列出来。

第二轮在参与过修订的 10 个配置上是 86%。两轮的配置不同，这一轮还多了闭源产品和版本对不上的情形，两个数字只能粗略对照。

**按字段看。** 10 个配置上主取值全部一致的有 11 个字段：F01、F05、F06、F08、F09、F10、F11、F16、F25、F27、F34。一致最少的是 F20（40%）、F12 和 F19（各 50%），其次是 F26、F28、F29、F30、F32（各 70%）。

**分歧的形状。** 54 处取值不同里，49 处在集合字段上：31 处是 `gpt` 比 `opus` 多记了成员，13 处是 `opus` 多记，5 处互有出入；3 处在单选字段上（F13 两处、F18 一处）；2 处是一方记“已知不存在”、另一方给了取值。有 12 处，一方确认的成员正好写在另一方的“疑似成员”里。

**状态。** `opus` 记已知 328、已知不存在 23、不适用 6、未知 3；`gpt` 记已知 327、已知不存在 19、不适用 6、未知 8。5 处状态不同都是 `gpt` 记未知而 `opus` 给了判断：Factory Droid 的 F07、F17（闭源），Grok Build 的 F12（版本对不上），Zed 的 F12 和 OpenHands 的 F35（没找到）。

**把握程度。** `opus` 记高 180、中 135、低 36；`gpt` 记高 241、中 74、低 31。“低”几乎都在 Factory Droid 上（`opus` 33 个、`gpt` 31 个），按总则只能从官方文档推断。`opus` 有 19 处用了“疑似成员”，`gpt` 有 6 处。

**子维度。** 两人都已知取值时才比较子维度，一共比较 286 个，77 个不一致，其中 19 个是一方留空（`gpt` 14 个、`opus` 5 个）。不一致较多的是 F28（17 个里 8 个）、F12（25 个里 7 个）、F31（30 个里 7 个）、F32（22 个里 7 个），以及 F01、F11、F23、F33（各 5 个）；F21 的 41 个里只有 1 个不一致。

**词表补充建议。** 一共 4 条：两位编码者都在 OpenHands 的 F11 上提出“主模型自己调用工具切换主循环的型号”；`gpt` 另提了两条，一条是 mini-SWE-agent 上“一次审批同一条回复里的整批工具调用”，一条是 Goose 上“在隔离的浏览器窗口里执行模型生成的页面脚本”。

## 交叉核对

第二轮之后定过一步：算完一致率，再核对“一方找到、另一方没提”的机制，因为这一类分歧改码本解决不了。原先设想让两位编码者各看对方的说明。这一轮改由第三位读者来做，原因有两个：`gpt` 一侧的编码运行环境在编码文件收齐后已经关闭；让编码者核对自己的分歧，也容易各自维护原判。

做法：

- 每个配置一位读者（Claude Opus 5.5），一次独立运行，共 10 次。读者只拿到两人判得不同的字段，两位编码者写成“甲”“乙”，不知道谁是谁。
- 读者同样不联网，读同一份快照、配置记录和码本里相关字段的定义，不重新编码。
- 一个字段里差了几项就分几条，每条归入一类：一方没提这个机制；两人看到同一机制、归法不同；所取前提不同；材料不足；其他。
- 只对“一方没提”的条目回到快照里核对两件事：这个机制在钉住的版本里在不在；按配置记录的入口和环境前提，它在不在用户不改设置就生效的路径上。

任务卡和逐条结果在 [`round3/`](round3/)。

59 个有分歧的字段拆成 75 条：

| 类别 | 条数 |
|---|---|
| 两人看到同一机制，按码本归到了不同地方 | 35 |
| 一方记入，另一方完全没提 | 26 |
| 材料不足，一方记未知或疑似，另一方做了推断 | 9 |
| 所取前提不同（版本、入口、系统，或对配置记录的读法） | 2 |
| 其他（一方没核完而留空 2 条，恢复后能否续接子代理 1 条） | 3 |

“一方没提”的 26 条里，`opus` 记入、`gpt` 没提的 13 条，反过来也是 13 条。回查结果：

| 回查结果 | 条数 |
|---|---|
| 在钉住的版本里，并且在默认路径上 | 18 |
| 在钉住的版本里，但要用户另行操作才生效 | 5 |
| 在钉住的版本里，是否默认生效查不到 | 1 |
| 在不在查不到（一条卡在 Grok Build 的版本差，一条只有 Factory Droid 的旧发布说明） | 2 |

按配置：

| 配置 | 一方没提 | 归法不同 | 材料不足 | 前提不同 | 其他 |
|---|---|---|---|---|---|
| A04 Qwen Code | 5 | 3 | 0 | 0 | 0 |
| A12 Goose | 6 | 7 | 0 | 0 | 2 |
| A13 Crush | 1 | 1 | 0 | 0 | 0 |
| A14 Mistral Vibe | 1 | 2 | 0 | 1 | 0 |
| A15 OpenHands | 2 | 9 | 3 | 0 | 0 |
| A16 Grok Build | 1 | 2 | 1 | 0 | 0 |
| B06 Zed | 2 | 4 | 1 | 0 | 1 |
| B10 Factory Droid | 5 | 4 | 4 | 1 | 0 |
| C01 Hermes Agent | 3 | 1 | 0 | 0 | 0 |
| D03 mini-SWE-agent | 0 | 2 | 0 | 0 | 0 |

按字段，两类分歧落在不同的地方：

- 归法不同集中在 F20（6 条，另有 1 条前提不同）、F13 和 F32（各 3 条）。F20 的 7 条里没有一条是漏看。
- 漏看集中在 F26（5 条，全部是漏看）和 F04（3 条）。F26 漏掉的是框架内部起的代理和用户命令起的代理，比如每个回合结束后自动起的记忆整理代理、分叉会话的命令。
- 材料不足的 9 条里，Factory Droid 占 4 条，OpenHands 占 3 条（都指向没取进快照的材料）。

这一步的局限：读者和编码者 `opus` 是同一型号；每条只有一位读者判，没有复核；只看了两人有分歧的字段，两人一致的 301 个没有回查。

## 能说明什么

- 码本在没见过的工具上基本站得住：十个新配置的一致率是 83.6%，和上一轮在旧配置上的 86% 相差不大；十个配置里六个在 86% 以上。
- 剩下的分歧大致对半：35 条出在码本的句子能读出两种意思，下一次修订可以处理；26 条是一方漏看，改码本改不掉。
- 漏看是对称的，两位编码者各漏 13 条，漏掉的机制多数（18 条）确实在默认路径上。两人各有对方找到而自己没找到的东西，可以推想还有两人都没找到的；一致的字段没有回查，这一点没有证据。
- 一致不等于正确，不一致也不说明哪一方错。交叉核对只给分歧分了类、回查了漏看的事实，没有裁决取值。
- 闭源产品上“未知”和推断并存：Factory Droid 的一致率是 69%，5 处状态不同里它占 2 处，材料不足的 9 条里占 4 条。只靠文档时，证据到什么程度可以下判断，两位编码者的尺度不同。
- Goose 也是 69%，分歧里 6 条漏看、7 条归法不同。两位编码者读的归档差在图片和视频文件上，没有迹象显示这影响了结果。
- 样本只有 10 个配置、一对编码者，没有做随机一致校正，不足以给单个字段的可靠性下结论。

## 编码者和读者提出的口径疑问

下面的问题来自两位编码者的说明和交叉核对里“归法不同”的条目，留给下一次码本修订，这里不作裁决。

| 字段 | 疑问 |
|---|---|
| 总则 R3 | 工具默认注册、模型可以直接调用，但只能“提议”，要用户在不能跳过的对话框里批准才生效（目标续跑一类）：算第一档还是第二档。同一位编码者在同一配置的两段里判得不一样，牵动 F03、F12、F35、F36 |
| 总则 R10 | 发行版落不到确切提交、实现和文档属于不同版本时怎样判；“实现”看所选入口实际用到的，还是后端具备的能力 |
| 环境前提 | `host_os` 写了两种系统、而某个机制只在其中一种上出现时，按哪一种判 |
| F01 | 模型自己调用默认注册的工作流工具去跑当场写的脚本，记不记次要控制方式；让模型用定时工具排后续提示的命令归 F01 还是 F33 |
| F02 | 模板要求每一轮回复都先写分析和计划，算“明确要求先产出计划”还是泛泛鼓励 |
| F03 | 有上限的单次重试（校验不合格让再答一次，第二次放行）算不算验证条件 |
| F04 | 上下文超长时框架先压缩再续跑，词表里没有对应项；框架修整输入的范围（补调用编号、丢弃无名调用） |
| F05 | 前端拉起后端子进程、两者经本机回环端口通信：记子进程协议还是本地服务接口 |
| F12 | 客户端照服务端下发的型号列表填的输出上限，算“按型号查的表”还是“完全来自服务端”；版本对不上时，总则 R10 和本字段的未知规则指向不同结果 |
| F13、F17 | 标记写在消息的字段或行上（可见性、摘要标志、中断类型），却会改变回放时取哪些内容，算不算控制条目。现行界线“消息自身的字段不算”在 5 个配置上被问到。另有：每轮把新增事件增量折叠进缓存视图，归哪一层；控制条目在发出前被换成固定文字或摘要，算修整还是逐类解释 |
| F18 | 恢复时待批的审批被带回、运行到一半的调用标为中断：记检查点恢复还是重建后重跑 |
| F19 | 恢复后只补投已完成子代理的结果，或只能按旧编号另起一次运行，算不算“关联”；只在内存里的待办清单 |
| F20 | 一致率最低的字段。按文件记下修改前原文、可以逐个改回的机制，是工作区快照还是补偿操作；不另设键库、恢复时从会话历史重建去重表，算不算持久的幂等键；有持久编号和执行前检查、但默认路径上没有重试场景触发它，算不算；以摘要另开新会话算不算会话分支 |
| F21 | 自动审核器算不算“批准者”；环境变量、只经工具参数传入的范围算不算用户写的规则；“本会话允许”时框架自动带上的目录范围算不算路径规则；只决定工具在不在的名单 |
| F22 | 抓取网页时每一跳重定向单独授权、脚本里每次终端调用单独审批，算不算比“工具调用”更细的一档 |
| F23 | 委派入口对工作目录范围的校验算应用层检查还是参数校验；工具说明里写成只读的委派用途算内置角色还是一般建议 |
| F24 | 默认没有人工审批、记录里只有自动放行的策略名，算不算“分得出人工批准和自动放行” |
| F26 | 框架内部起的代理（记忆整理、定时器到点起的运行）和用户命令起的分叉、并列代理，算不算、记在哪一项 |
| F28 | 委派调用立刻返回、等待由框架在下一次推理前接管，算不算同步返回；子会话被卸载但之后可恢复，算不算取消；用户在弹窗里选择停掉子代理，算不算框架完成的取消 |
| F29、F32 | 用官方构件库组装新代理，算不算“嵌入本核心”；嵌入方的工具经 SDK 起的本机回环工具服务接入，记嵌入方声明还是外部协议服务；有公开门面但没有使用文档的包算不算“公开发布”；模型接口兼容协议算不算公共协议；“改设置”算不算直接开放 |
| F30 | 配方、技能组合、按名选用的人格提示、整份可执行的命令文件各归哪一项；带重试段的配方是一个机制还是两个 |
| F31 | 写文件工具完成后的事件归“保存”还是“工具前后”；一个通知事件横跨两个阶段怎样拆；订阅整条事件流、按类型认出压缩事件，算不算一个事件点；新建工作树时触发的处理器算不算会话开始 |
| F34 | “关掉界面”指退出键、关窗口还是关终端；退出界面后是否存活，看进程还是看执行核心 |
| F35、F36 | 工作项写了盘、重启后不自动执行，记持久还是内存；代理不等待的“向人索取材料”请求卡算不算待办；回合数到上限时框架询问是否继续 |

码本 0.4 起草时由维护者补定、当时没有逐条请负责人过目的几条界线里，F13、F17 那一条（只标记流程的分片和消息自身的字段不算控制条目）在这一轮被问得最多。

## 这一轮之后改过的配置记录

编码期间没有改过配置记录。两位编码者和交叉核对的读者指出，六份记录里有句子和钉住提交的源码对不上。编码结束后逐条对照快照核实，属实的改了记录、补了证据卡。这一轮的编码是照改之前的记录做的。

| 配置 | 改了什么 |
|---|---|
| A04 Qwen Code | 定时工具（建立、列出、删除定时任务和循环唤醒）默认开启并注册给模型，原记录把它列在“默认关闭”里；待办工具默认不注册，原记录把它列在默认工具里 |
| A14 Mistral Vibe | 这一版的会话都走统一运行时，内置的 grep、task 两个工具在这条路径上不起作用：按内容搜索靠在命令行里跑搜索命令；派子代理经脚本工具里的代理接口，不经审批，内置的探索子代理不向模型公布；联网搜索和打开网页走厂商托管的连接器，不是内置的两个联网工具 |
| A15 OpenHands | `subagents_enabled` 由否改为是：界面默认给主代理挂一个能另开独立会话的客户端工具，子会话的结果不交回父代理；执行端自带的委派工具默认不挂。另补一条：自动化服务随整套本机服务默认启动，用户建好定时或事件自动化后由它起独立运行（它自身的源码不在快照内） |
| A16 Grok Build | “默认工具是否都注册未逐一核实”一句换成按快照（1.0.45）列出的确切清单：定时和监视工具无条件默认注册，另分列本地可关、本地和远程设置都能关、默认关闭的三组 |
| B06 Zed | 列出代理和型号的工具不受功能开关控制，默认提供给模型，原记录把它和被开关挡下的工具写在一起；那个开关的说明注释与代码不一致，以代码为准 |
| C01 Hermes Agent | 入口补上执行位置：终端进程只是前端，启动时拉起或接上本机的网关守护进程，回合在网关里执行，没有回退到进程内执行的分支。权限补上两条例外：写受保护的指令文件要逐次人工审批，写 SSH 客户端配置走和终端命令相同的审批；“命中即报错、没有审批提示”只适用于硬黑名单 |

这些出入对这一轮结果的影响：

- OpenHands 的 F25（有没有多代理）两位编码者都记“已知不存在”，并且都在说明里指出记录的 `subagents_enabled` 和实际不符；任务卡规定记录写“否”时 F25 不能记“有”。这一格算作一致，但它是照着有误的记录得出的。结果不交回父代理的子会话、自动化服务起的独立运行算不算多代理，码本没有写，留给下一次修订。
- Mistral Vibe 的 F15 上“前提不同”的那一条，来自记录把 grep 列为默认工具。
- Qwen Code、Hermes Agent、Zed、Grok Build 的出入，在交叉核对的 75 条里没有对应的分歧。两人在这些地方是否都按源码判，没有逐格回查。

没有改的两处：环境前提的 `host_os` 在十份记录里都写“macOS 或 Linux”，某个机制只在一种系统上出现时按哪一种判，是配置约定的问题，留到修订时一并定；Zed 的默认型号由服务端下发，离线查不到，F12、F14 上各有一处分歧和它有关。

## 快照里缺的材料

- OpenHands：配置记录钉了自动化服务仓库的提交，取快照时漏了这个仓库；执行端按型号查输出上限用的第三方型号表、默认加载的公共技能和插件所在的扩展仓库也不在快照里。F12、F31、F35 上的 3 条“材料不足”都出在这里。
- Grok Build：源码快照（1.0.45）比配置钉的正式版（1.0.77）旧，中间只有官方更新日志可查。F12、F20、F26 各有一处分歧和它有关。
- Crush：模型调用的重试在一个外部库里，重试次数和退避策略在快照里看不到。
- Factory Droid：闭源，执行位置、会话记录的格式都只能从文档和发布说明推断。
