# 码本 fields-0.5 的决定记录

这份记录说明 `fields.json` 从 `fields-0.4` 改到 `fields-0.5` 时定了什么、为什么、哪些备选没有采纳。它只作记录，**不发给编码者**：里面点名了配置，也写了第三次编码时两位编码者各自怎样判。

- 依据：第三次试编码（`pilot/round3.md`）的一致率、交叉核对和分歧归因。这一次换了十个没参与过修订的配置；算完一致率后，第三位读者不看是谁编的，对照快照核对了 75 条分歧；三位分析者再按字段组只读两位编码者的并排记录，逐处判断分歧的主因。修订提案的初稿请两位读者独立审过，一位核对数字和描述是否对得上归因材料，一位看照着写进码本会不会互相矛盾。
- 决定：下面第一、二、八节共 26 条，每条都列了推荐和另一案，项目负责人 2026-11-11 答复“都按推荐”，即全部取“推荐”或“推荐甲案”，每条下面的“同时删改”一并照做。第三、四节是定下以上各条后照做的事，第五节是不动码本的流程对策。
- 落实：总则由维护者写成 R1–R10 和子维度总则；三位起草者按字段组把决定写进字段定义，再由三位没看过起草材料的审阅者各读一组合并稿。起草和审阅时为了让规则能用在具体字段上而补的界线，列在第六节，这些没有逐条请负责人过目。

下文的甲、乙指第三次编码的两位编码者：甲是 Claude Opus 5.5，乙是 GPT-6.1 Sol。配置编号对应的工具见 `data/rounds/pilot-2.json`。

## 分歧出在哪

两人不一致的字段×配置共 102 个：59 个取值或状态不同，43 个取值相同、只差子维度或只有词表提议。一个字段×配置里可能有几处互不相干的分歧，分析者拆成 118 条，每条按主因计一次：

| 主因 | 条数 | 说明 |
|---|---|---|
| 定义缺口 | 45 | 判定标准没覆盖这种情况，两人都说得通 |
| 一方漏看 | 23 | 机制在默认路径上，一方记了，另一方没提 |
| 子维度留空 | 12 | 一方逐项判过就填，另一方有一项拿不准或没查完就整层写“未知” |
| 范围口径 | 10 | 争的是算不算默认、算不算所选入口直接开放 |
| 材料不足 | 10 | 闭源、快照缺仓库，或快照版本比钉住的版本旧 |
| 要回原始材料核对 | 9 | 两人对同一事实说法相反 |
| 确认门槛 | 4 | 看到同一样东西，一方认为证据够，一方列为疑似 |
| 词表缺项 | 3 | |
| 配置记录的问题、疑似没照码本做 | 各 1 | |

和第二轮比，有三点不同：

- 定义缺口多数只在一个配置上出现。新配置带来的是新的边角；老问题（目标续跑、默认在用、入口范围）在 0.4 里写过的地方基本没有再分歧。
- 漏看的 23 条，机制藏的地方比较集中：回合结束后、到达上限时、失败或中止时框架自己做的事（约十条）；用户命令设立的状态或直接起的代理（四条）；工具执行中途才弹出的授权，以及某个设置项、参数取值或另装的官方包下才有的入口（六条）。
- 有两个配置的分歧和证据本身有关：A16 Grok Build 的快照（1.0.45）比钉住的版本（1.0.77）旧；B10 Factory Droid 闭源，两人对哪些文档能借口径不一。这两类在总则第 3、5 条处理。

F20（怎样处理回退与重复执行）一致率最低，十个配置里六个取值不同；其次是 F12（怎样管理调用预算）和 F19（恢复会覆盖哪些状态），各五个。

每条推荐后面的“同时删改”，列的是现行码本里和新句子相反、必须一起改掉的旧句。负责人定的是方向；合并稿照这些清单逐句核对。

## 一、总则的修订

**1. R3：模型只能“提议”、用户批准后才启动的路径归第几档。**
- 现在：R3 第一档写“工具默认注册、模型不经用户操作就能调用的，算默认”。没说另一种情形：工具默认注册，模型可以直接调用，但调用的结果只是弹出一个不能跳过的对话框，用户批准后这条路径（目标续跑一类）才启动。
- 问题：A04 上同一位编码者在两个字段组里判得不一样，牵动 F03（通过什么结束或暂停）、F12、F35、F36。
- 推荐甲案：算第一档。R3 第一档末尾加一句：“模型不经用户命令就能用默认工具提出、用户只在对话框里批准或拒绝的路径，算第一档，路径里的机制计入取值，value_note 写明‘需用户批准’。这次批准按 F22 的判定记（只放行这一次启动的记调用层，批准时一并决定后续放行方式的记任务层），不记 F36。用户要先主动输入命令或按快捷键才会出现的，才算第二档。”F03、F04、F12 三处只引用这句，不各写一遍。理由：R3 的判断点是“模型能不能不经用户操作走到”，用户只回答是或否，不算主动进入；F01 已经写了“审批停顿不改变类别”。
- 乙案：归第二档，写“可选：”。取值更保守，但和 F01、F22 对审批的口径不一致。
- 同时删改：F03、F04、F12 范围规则里各自写的“目标工具默认注册、模型能直接调用的”一句，改成引用 R3。

**2. R2：机制默认开着，但只在失败、超限、重入时才走到，或者能否触发取决于没钉住的参数。**
- 现在：R2 写“机制不改任何开关就开放，就记入取值”，没说要不要默认路径上真会走到。
- 问题：直接争这一点的有两处。A12 的 F20：执行前按存储里的调用编号查有没有结果，一人记入，一人认为默认路径上没有重试会触发它，放进了疑似成员。B06 的 F14（超长内容如何缩减）：自动摘要默认开，但只在型号窗口不小于某个门槛时运行，而默认型号由服务端决定，一人记入，一人放进疑似成员。另外，漏看的 23 条里不少正是这类很少走到的分支（F14 的大小处理、F22 的跳转授权、F36 到达上限时的询问）；写明这条以后，编码者看到这类分支不必犹豫算不算。
- 推荐甲案：R2 加两句。“机制不改开关就会起作用的，计入取值，不要求默认路径上一定会走到；只在某种失败、超限或重入时才走到的分支也算，触发条件写 value_note。”“机制默认开着、能否触发取决于环境前提没钉住的参数（例如服务端下发的默认型号、窗口大小）的，照样计入，confidence 不高于 medium，value_note 写明门槛，不写进 unresolved；环境前提已经钉住、钉住的值达不到门槛的，按 R1 写‘其他环境：’，不计入。”理由：本研究量的是结构，不是某次任务里会不会碰到；“真会遇到”要靠运行才能判，静态材料判不了。
- 代价：开源配置读得到这些很少走到的分支，闭源配置的文档很少写。按甲案，开源配置的集合会比闭源的大一些，两类之间的距离会因为证据面不同而偏大。方法报告已经要求结构距离同时报告证据覆盖，闭源字段的 confidence 也都是 low，到距离阶段要把这一点单独写出来。
- 乙案：要求材料显示默认路径上会走到，否则写进 unresolved。更保守，但只在失败、超限、重入时走到的分支大多会变成疑似成员。
- 同时删改：新句不改变 R2 里“在用”的判法（“在用”仍指模型真能调到、钩子真会被触发），合并时注明。

**3. R10：快照比钉住的版本旧，按哪个编；“实现”指哪条路径。**
- 现在：R10 只管“文档和固定版本的实现说法相反”和“发行版开关查不到”。A16 的快照是 1.0.45，配置钉的是 1.0.77，中间只有官方更新日志。
- 问题：A16 上因版本差造成分歧的是 F12、F20、F26 和 F11 的子维度（同一位编码者在取值上按源码默认记，在子维度上又因版本对不上留空；F12 上两人分别按 R10 和“版本对不上写未知”判）。F19、F22、F24 上两人也都在说明里写了“近似提交”。F20 上还有一处：后端支持某种回退模式，所选入口却不会发出这种请求，一人按后端能力记入。
- 推荐甲案：R10 加一段。“配置记录写明以某个提交的快照代替所选版本时，按快照编码，confidence 不高于 medium，value_note 写明两个版本号。钉住版本的官方文档或更新日志明确写了和快照不同的行为的，这一项按文档记，confidence 同样不高于 medium，value_note 写明依据的是哪一版更新日志和快照里的实现。文档改了说法、又看不出改成什么的，集合字段把这一项写进 unresolved，单选字段写 unknown（version_unclear）。”“‘实现’指所选入口实际走到的代码路径：后端支持、所选入口不会发出的模式，不计入，写进 value_note。”流程上同步改：取快照时先找和钉住版本一致的提交；找不到的，配置记录的环境前提里写明“以某提交代替”。A16 的记录要补这句。
- 代价：这个配置所有字段的 confidence 都被压到 medium，包括和版本差无关的字段；编码者还要对着更新日志逐项看有没有改过。
- 乙案：把这类配置改钉到快照对应的版本，一律按快照编。判法最简单，confidence 可以写到 high；代价是编出来的是一个旧版本，和主报告写的现行版本对不上。版本差很大、更新日志又粗的配置，可以个案用乙案，由维护者提出。
- 同时删改：R10 原句“官方文档和固定版本的实现说法相反时，以实现为准”，限定为实现和钉住版本一致的情形。R7 的“其他版本……不算迹象”，写明“其他版本”指钉住版本以外、也不是配置记录写明用作替身的版本。

**4. R10：数值、型号或开关由服务端下发，客户端看不到。**
- 现在：R10 只说了发行版的构建开关。F11（模型在任务中如何分配）的范围规则写“看解析后的型号名”，它的辅助调用子维度写“型号由服务端决定、客户端看不到的，不计入”。
- 问题：三种情形各有分歧。B06 的标题和摘要固定取提供方的“快速型号”槽位（槽位，指客户端只写“用快速的那个型号”，具体是哪个型号由服务端的列表决定）；A16 有一个本地默认关、服务端可以为账户打开的开关；A15 的输出上限取自快照之外一个依赖库的型号表。一人按客户端看得到的规则记，另一人写未知、留空或放进疑似成员。
- 推荐甲案：R10 再加一段，把三种情形分开写。
  - 开关：“开关的值由服务端下发、本配置查不到的，按源码里的本地默认值判。本地默认关、只有服务端能为账户打开的，不进取值，value_note 写‘服务端可改：’；本地默认开、服务端可以关掉的，计入，confidence 不高于 medium。都不写进 unresolved。”
  - 数值和型号名：“机制在客户端代码里、看不到的只是具体数值或型号名的，机制照记，数值写进 value_note，不因此写 unknown 或整层 null。快照之外的依赖库里的表同样处理。”
  - F11 的槽位：“客户端自己按角色固定取另一个型号槽位、槽位里的具体型号由服务端决定的，是框架的分配，记 per_role（按角色），value_note 写‘型号由服务端决定’；能确认两个槽位解析到同一型号时不记。调用一个托管服务、服务内部用什么型号客户端无从选择的，不算框架的分配，照旧不计入。”
  - 字段另有规定的照字段。F12 对服务端下发的输出上限另有规定，见第 21 条。
- 理由：分配规则写在客户端，看得到；记成未知会丢掉这层信息，而且每个远程开关都会变成疑似成员。
- 代价：服务端把两个槽位解析成同一个型号的情况并不少见。按甲案，这类配置会被记成“按角色”，实际却是同一型号；value_note 里那句“型号由服务端决定”是唯一的提示。
- 乙案：看不到具体值就写未知或留空。和 F11 现在的字面一致，但由服务端配置的产品会大面积变成未知。
- 同时删改：F11 辅助调用子维度里“型号由服务端决定、客户端看不到的，不计入”一句，拆成上面两种情形。F11 按角色一项的“框架按角色默认解析到不同型号”和范围规则的“看解析后的型号名”，各加上槽位这个例外。

**5. R6：闭源产品能借哪些文档，旧的发布说明能不能推到当前版本。**
- 现在：R6 写“可以按官方对本配置的说明推断”“不从同一产品的其他形态借证据”。
- 问题：B10 的分歧里，F04、F07、F17、F18、F20、F24、F28、F33、F34 九个字段卡在四件事上：官方 SDK 文档算不算“对本配置的说明”；同一份发布说明里标了桌面版的条目能不能用；几个版本以前的发布说明写过的行为，当前版本还算不算有；文档只描述了外部表现时，能推断到哪一步。
- 推荐甲案：R6 加三句，另给三个字段各补一个推断默认。
  - “官方 SDK 文档明说它驱动的就是本配置这个程序（或同一个执行核心）的，可以作推断依据，confidence 为 low。标明属于其他形态（桌面版、网页版）的条目不借，即使出现在同一份发布说明里。”
  - “用同一形态的发布说明推断当前版本时：后来的说明改写了同一行为的，以后者为准。当前版本有覆盖这一方面的文档（命令表、工具清单）、里面却没有它的，写进 unresolved。当前文档根本不涉及这一方面的（例如取消时的内部行为），可以按旧说明推断延续，value_note 写明版本。”照这句，B10 上 F28 记取消传播，F33 的定时写进疑似成员，F04 的宽松解析按后来的说明不计。两位分析者对这句的写法略有不同，这里用的是 F25–F36 组的写法，它多分了“当前文档有没有覆盖这一方面”一层。
  - “文档描述了机制的外部表现（存在哪里、谁来恢复、何时询问用户），足以按判定标准归类的，就按本条推断；只有文档完全没涉及时才写 unknown。”
  - 三个推断默认，confidence 都是 low：F07（会话状态的权威副本归谁）在文档写明“由程序本身存成本机文件、由同一程序恢复”时记执行核心，云端默认镜像一份、关掉同步照常工作的不算独立状态服务。F17（运行记录以什么形式持久化）在文档只说保存了对话、没说条目类型时记消息；文档明说记录里有压缩边界、审批决定这类独立条目的，记事件日志。F34（生命周期由谁维持）在文档写明是前台进程时，“退出界面后任务是否继续”记“停止”，value_note 写“推断：随前台进程”。
- 代价：F17 的默认会让闭源产品偏向“消息”，因为带压缩的产品记录里往往有压缩边界，只是文档不写。
- 乙案：只认针对本配置这种形态、当前版本的文档；SDK 文档和旧发布说明只进 value_note 或 unresolved。更保守，闭源产品的未知会更多。
- 同时删改：F17 未知规则里“只知道会保存会话、不知道存成什么形式时写 unknown”；F34 子维度里“查不到写 null”；R7 的“其他版本……不算迹象”，给“同一形态的旧发布说明”开一个例外，指向 R6。

**6. 子维度：怎样算“判过”，汇总性的取值拿不准时怎么写。**
- 现在：子维度总则写“写 [] 或判‘没有’要查全：照清单逐项判过就填，判断写进 coder_note；个别项拿不准的也写进 coder_note，不因此整层写 null；清单里有项根本没查的，写 null”。但 F11 的辅助调用又写“各项都用主执行链同一型号时才记 single_fixed”，F23（约束由什么机制执行）的“只靠提示落实的限制”写“每一项都有代码检查才记 absent”。
- 问题：12 条子维度留空里，F11 和 F23 占 7 条，多数是有一项拿不准时，这两句和总则指向不同的写法；另外 5 条（F01、F28、F31）是没查完就留空。两人对“查到什么程度算判过”也不一样。
- 推荐甲案：统一照总则，并把“判过”说清楚。子维度总则加：“清单上一项算判过：能就这一项回答本子维度的问题。答‘有’的，指出一处代码或文档；答‘没有’的，写明查了哪里（命令表、工具注册处、相关模块），不要求审计全部代码。汇总性的取值（‘各项都用同一型号’‘交代了的限制都有代码检查’）也照此：各项都判过、个别项拿不准的，照记，confidence 不高于 medium，coder_note 写明是哪一项、缺什么。清单里有项根本没查的才写 null，coder_note 写明哪一项没查、为什么；源码在快照里的，查完再交。”理由：这是 0.4 定下的方向，分歧出在字段里的句子没跟上；拿不准的那一项记在 coder_note 里，裁决时可以单独核。这两个子维度都不进距离计算，判错的代价有限。
- 乙案：汇总性的取值从严，有一项拿不准就写 null。断言更稳，但主执行链清楚、只差服务端一项信息的配置都会变成未知。
- 说明：F13–F24 这组的分析者建议只对 F23 的“无”从严，理由是判“无”等于断言没有只靠提示的限制，拿不准时这个断言太强。提案没有采纳，因为 F11 的“全用主型号”是同一种断言，两处判法应当一致。
- 同时删改：F11、F23 里上面引的两句，改成引用总则。

**7. R5：“所选入口直接开放”的边界。**
- 现在：R5 说 F29、F31、F32、F33 的取值收全部有文档的入口，默认能不能用由 via_default_entry（所选入口直接开放）区分；它只排除了加启动参数、换子命令、另装官方包、另配凭据四种。
- 问题：F29（新工具以什么边界加入）、F32（核心可以怎样嵌入其他程序）、F33（任务从哪里触发）上有 8 处分歧，卡在三件没说的事上。
- 推荐（三件分开定，每件都写了另一种做法）：
  - 改设置：不算直接开放。分界按“加进去的这一项是否自带定义”：带服务地址或命令、文件内容的（在配置里加一条外部工具服务，往目录里放一个脚本），算添加内容，可以直接开放；只用名字启用一个已经装好的东西（把插件名加进启用名单）、打开开关、给一个只能填一个值的设置项填值的，算改设置，不算。另一种做法是只排除原来那四种，改设置也算直接开放；这和 R2、R3 第三档不一致，不推荐。
  - 管道输入：算直接开放。加一句“同一个命令不加参数，只因输入来自管道、不是终端，就进入有文档的非交互模式的，算直接开放”。宿主程序确实不需要任何额外步骤。另一种做法是算离开了所选的交互入口。
  - 入口自动拉起的本机服务：加一句“外部程序不另配凭据、按文档就能连上的，才算直接开放；靠每次启动随机生成、只交给自家前端的密钥或票据保护的，不算”。另一种做法是自动拉起就算。
- 同时删改：F29、F31、F32、F33 的 via_default_entry 子维度各自抄了原来的四项排除，四处都改成引用 R5。

**8. R5：官方单独发布、供人组装自己代理的构件库，算不算本核心的嵌入面和扩展面。**
- 现在：R5 的“同一发行版”指同一个源码提交随附的官方程序和包，没说构件库开放的东西在各字段怎样记。
- 问题：A12 上同一个包，F32 两人都记成了库，F29 一人记入、一人放进疑似成员，F31（生命周期允许在哪干预）一人记入、一人没提。
- 推荐甲案：R5 加一句。“官方构件库和所选程序出自同一个源码提交，或官方文档明说它运行的是本产品的同一套代理循环时，F32 记库，F29、F31 里它开放的工具声明和回调按对应取值记入，三个字段判法一致，都不进 via_default_entry。两个前提都不满足的，写 value_note，不记。”理由：三个字段对同一个包应当判法一致；满足前提时它跑的就是本核心，F32 上两人也已这样记。
- 乙案：构件库只是零件，不算嵌入本核心，三个字段都不记。要回头改 F32 的现有判法。

**9. R8：“一个机制”指什么；字段里的特别规定和词表先后谁优先。**
- 现在：R8 写“同一字段内，一个机制只归一项，按词表的先后取第一项命中的，字段另有说明的除外”。
- 问题：两处按 R8 套出了谁都不认的结果。F30（可复用指导如何装载）里，同一种文件既能只展开成一条提示，又能带框架推进的步骤和重试，一人按“一个机制”只记工作流定义，一人按用法分开记；严格按词表先后还会先命中角色模板。F29 里，嵌入方经 SDK 声明的工具，SDK 内部用一个只在本机通信的外部协议服务把调用交回嵌入方，一人按词表先后记外部协议服务，一人记嵌入方声明的工具。
- 推荐甲案：R8 加一句。“一个机制指同一条装载、注册或执行路径，不指同一种文件格式或同一种传输方式。字段判定里写明‘记本项，不记某项’的，优先于词表先后。”落到两个字段上：F30 同一种文件有两种用法的，分别按定义记；F29 嵌入方经嵌入接口为会话声明的工具一律记“嵌入方声明的工具”，即使内部走本机通信的协议服务。理由：F30 问的是用户能写下哪几类指导，F29 问的是嵌入方面对的边界；文件格式和传输方式只是实现细节。
- 乙案：维持按词表先后只记一项。有斜杠命令模板的工具会显得没有提示模板；同一种嵌入能力会随 SDK 的内部实现换归属。
- 同时删改：R2 的“按它实际经过的边界记”，写明“边界指声明工具的一方使用的接口，不指内部传输方式”。（归因记录里 F30 这一处的甲、乙编号和这里相反，内容一致，对应见第九节 F30 一条。）

**10. R1：配置记录和所选入口的代码对不上时，按哪个编。**
- 现在：R1 写“配置记录的入口描述和环境前提推出的路径对不上时，按入口描述编码，在 coder_note 写明矛盾，交主控改配置记录”。它没说记录里的事实陈述（默认工具清单、默认开关、默认型号）和代码对不上时怎么办。
- 问题：这一轮六份配置记录在编码之后才发现和源码对不上。A14 的记录把内容搜索工具列成默认内置，一人照记录记了 F15 的关键词检索，另一人发现所选入口并不运行这个工具，没记。
- 推荐甲案：R1 加一句。“配置记录决定编哪个版本、哪个入口、什么环境；它对默认工具、默认开关、默认型号的陈述不是证据。这些陈述和所选入口的代码对不上时，按代码记，coder_note 写明，交主控改配置记录。入口描述和环境前提互相矛盾时，仍按入口描述编码。”理由：编码要描述的是程序实际的样子；两位编码者都读代码，按代码判也更容易一致。
- 乙案：一律按配置记录编，发现对不上只写 coder_note。两人前提一致，但编出来的是记录写错的样子，改完记录要重编。
- 配套的流程改动见第五节第 5 项：编码前先由另一位读者核一遍配置记录。

## 二、字段级决定

**11. F13、F17：写在消息行或消息字段上的标志，算不算控制条目。**
- 现在：两个字段共用一段界线，里面两句话指向不同方向。一句是“消息自身的字段属于元数据，控制条目要有自己的条目类型或分片类型”，一句是“会改变回放时取哪些内容的，算控制条目”。这是 0.4 起草时由维护者补定、负责人当时没有逐条过目的一条。
- 问题：这一轮被问得最多的一条。A12、A13、C01 三个配置的消息行上有“可见”“已压缩”“摘要”一类标志，恢复时会按它跳过某些行；两位编码者都照前一句判成了消息，判法一致，但说明里写了拿不准。D03 的审批拒绝存成普通用户消息、附加字段里标了中断类别，两人判反了。
- 推荐甲案：两个条件都要满足。“控制条目要同时满足两条：（1）有自己的条目类型或分片类型；（2）属于压缩边界、检查点、型号或配置切换、分支、重置、审批这一类，或者会改变回放时取哪些内容。写在消息行或消息附加字段上的标志（可见性、已压缩、摘要标志、中断类别），不论会不会改变回放，都不满足第（1）条，算消息元数据，写进 value_note。只标记流程的独立分片（步骤开始结束、重试）不满足第（2）条，照旧按元数据处理。”理由：有没有独立的条目类型，看存储结构就能核对，三个配置上两人已经这样判；压缩几乎每个工具都有，带压缩标志的都算事件日志的话，“消息”和“事件日志”就分不开了。
- 代价：功能相同的两种存法会得到不同的取值。把压缩边界存成一条独立条目的记事件日志，存成消息行上一个标志的记消息。
- 乙案：按作用判，标志只要会改变回放时取哪些内容，就算控制条目。更贴近功能，但 A12、A13、C01 的 F17 会从消息改成事件日志，A12 的 F13 会改成类型化事件重建，而且“会不会改变回放”要读回放代码才能判。
- 说明：F13–F24 组的分析者只看到 D03 这一处分歧，建议写“只在附加字段里标一个类别、回放时仍当普通消息发出的，算元数据”，沿用的是“看回放时改不改变取哪些内容”这条原则。D03 在甲、乙两案下结果相同，都记消息。两案的差别只落在“标志会让回放跳过某些行”的那三个配置上；分析者的材料里没有这三处（两人取值相同，只在说明里提了疑问），甲案是维护者在他的建议之上多走的一步。
- 同时删改：两个字段范围规则里“会改变回放时取哪些内容的，算控制条目”和“标题、标签这类不影响回放的元数据不算”两句，改成和上面两个条件一致的说法；“挂在消息下也算”写明只指挂在消息下的独立分片。

**12. F13：类型化事件重建收多窄。**
- 现在：判定只区分“每轮遍历一份含多种条目类型的记录、逐类解释”和“直接取维护中的消息列表”。
- 问题：两种中间情形没写，两位编码者都在说明里问了。一种是运行中维护一份现成的列表，每来一个新事件就按类型转换后并进去，每轮请求直接取这份列表，不重读整份记录（A15）。一种是内存消息列表里的控制条目在发出前被换成一条固定文字或摘要文字（B06）。
- 推荐甲案：在“含多种条目类型”之上再加一个条件：每轮从存储重读，或每轮把整份记录从头转换一遍。加四句：
  - 只处理新增部分、每轮直接取现成列表的，记顺序消息，转换那一层记进“请求构造经过的各层”。
  - 控制条目被一对一换成固定文字或它自带的摘要、其余照原样发出的，算修整，记顺序消息。
  - 控制条目决定其他条目发不发（删去中间若干段、按类型跳过一部分）的，才算逐类解释；从某个边界往后取、边界之前一概不发的，属于定位起点，不算。
  - 每轮从存储重读、但记录里只有消息（含带标志的消息行）的，记顺序消息。
  - “各层”子维度另加一句：每轮现转出来、不跨轮保留的消息列表不另算一层。
- 乙案：只要构造请求时按条目类型分别转换、列表里有控制条目，就记类型化事件重建。带压缩标记的终端工具几乎都会落进来，这一项就分不出“按事件流回放的引擎”了。

**13. F19：子代理关联怎样算“重新连上”。**
- 现在：判定写“恢复后父会话能继续指挥原子代理，或能收到它的结果”。
- 问题：五个配置取值不同，其中两处卡在这里。C01：只把已完成、没交付的结果补送回原会话，运行中的子代理不续跑；而且补送靠一个后台进程，所选入口退出后它还在不在，也没说按哪条前提判。A16：模型可以按旧编号从磁盘重建一个已结束的子代理。
- 推荐甲案：改写成两条，满足任一条即计。“（1）父会话能用默认工具按原编号给原子代理发新指令，子代理带着原有的上下文接着做，不论它原来已结束还是被中断；（2）原子代理在中断前后产生、还没交付的结果，恢复后由框架自动送回父会话。按旧编号新开一个不带原上下文的子代理，或只保留了可追溯的编号的，不计。第（2）条依赖所选入口之外的常驻进程的，按总则 R1 写‘其他环境：’。”照这句，A16 归哪边取决于重建时是否载入原记录，回查结果见第七节。
- 乙案：只计第（1）条，补送结果写 value_note。等于收紧现行定义，第二轮的编码也要跟着重判。
- 这个字段另有两处随本条照做：时刻写明是“进程重启后执行恢复命令、代理接着工作之前”；只按时间间隔重发同一提示、没有完成条件的定时循环，属调度，不算持续目标。

**14. F20：幂等标识要不要专门的记录，要不要默认路径上真会重试。**
- 现在：判定写“持久的标识，在重试或恢复重跑时不会再执行”；0.4 补过“持久指标识和执行状态写进存储”。
- 问题：三个配置各卡一处。A15：没有专门存放“哪些调用做过了”的记录，恢复时按会话记录里的调用编号，把已有结果的调用排除出待执行列表；一人算执行前查重，一人认为不算。A12：执行前按存储里的调用编号查有没有结果，两人都看到了，争的是默认路径上没有重试时算不算（总则第 2 条）。A04：恢复时用历史现建一张“已处理”表，两人对它在执行前有没有被查说法相反（已列入回查）。
- 推荐甲案：改写。“框架在一条会重新发出已记录调用的路径上（重试、恢复重跑、重入的步骤），执行之前用存储里的标识判断这次调用是否已执行过，已执行的跳过、取旧结果或拒绝。标识可以是专门的记录，也可以是会话记录里调用编号和结果的配对，包括恢复时由它们现建的表。这条路径默认开着即可，不要求常走到（总则第 2 条）。恢复时只是修补历史（对没有结果的调用补一条错误或合成结果、不再执行）的，不是查重，写 value_note。”
- 乙案：要求有专门的幂等记录，而且默认路径上有会触发它的重试或恢复重跑。“每步从存储重读、按编号配对”的设计会落空，而它正是这一项想分出来的。

**15. F20：按文件留原文、可以逐个改回的机制，算工作区快照还是补偿操作。**
- 现在：两条判定都套得上。
- 问题：B06 上一人记工作区快照，一人记补偿操作。A15 上两人都记成了快照，但都问“备份放在临时目录、不跨进程，算不算”。
- 推荐甲案：按副作用在哪分。工作区快照加：“代理改文件前留下原文、有内置入口（用户按钮或模型可调的工具）把文件改回的，记这一项，不论按整个工作区还是按被改的文件，存在磁盘还是内存；范围和生命周期写 value_note。这和 F17 状态快照要求的‘持久副本’无关，两个字段各判各的。”补偿操作加：“只收对工作区以外的副作用（发出的请求、写入的外部系统、部署）登记的反向步骤。”
- 乙案：快照要求能回到某一时点的整体状态，逐文件改回归补偿。补偿这一项就混进了本地文件，“对外部副作用做补偿”这层意思会变淡。
- 另有一处随本条照做：以摘要而不是原有历史作种子另开的新会话，不算会话分支。

**16. F21：什么算“用户能写的规则”。**
- 现在：范围规则写“由用户或管理员设定，写进配置、在界面里选定或在会话中切换都算”。
- 问题：三种情形有分歧。A13：用户在询问里点“本会话允许”，框架自动按工具和所在目录记下临时授权，一人据此记了文件路径。A15：某个工具的构造参数里有域名限制，默认为空，文档和界面都没交代，一人据此记了网络目标；另一个模式专用编辑器的参数把可写文件限定为一个固定文件，一人记了文件路径，另一人没提。A14 还有一处争的是某条授权路径在不在所选入口里，已列入回查。
- 推荐甲案：加三句。“批准时选‘本会话允许’生成的临时授权，按用户能选择的东西计维度：用户只选了允许、范围由框架自动记下的，算工具类别；用户能自己指定或修改路径范围的，才计文件路径。”“用户能写的规则，指官方文档、设置界面或配置文件格式（源码里配置文件的模式定义也算）交代了的配置项；用户经配置文件到达不了、只能在代码里构造工具时传入的参数，写 value_note，不计。”“只指定一个工具写到哪个固定文件、而不是给出允许或禁止的范围的参数，按写死的名单处理，不增加取值。”另补：从代理的工具清单里去掉某个工具，算按工具类别拒绝。
- 乙案：凡是用户能经配置文件或接口传进去的都算。编码者要翻遍所有工具的构造函数才能判“没有”。

**17. F22：比“工具调用”更细的审批，哪些算操作层。**
- 现在：操作层的例子一栏写着“暂无合适的例子”。
- 问题：两种情形一人记了操作层、另一人没提，记入的一方自己也拿不准。一种是抓取网页时跟随跳转，每到一个未授权的新主机单独询问（B06）；一种是模型写的脚本运行时，脚本里每次调用终端命中危险模式就单独询问（C01）。
- 推荐甲案：两种分开归。跳转逐跳授权记操作层，并拿它当例子：一次工具调用里的具体效果被单独放行。脚本内层的调用记调用层：“模型写的脚本经框架再调起的工具调用，每次单独审批的，算对这次内层调用的审批；操作层只收不经工具调用发生的具体效果（联网、写某个路径）。”理由：按“一次批准能放行的范围”判，内层那一次批准放行的正是一整次调用。
- 乙案：两种都记操作层，理由是外层调用已经开始执行。
- 另有一处随本条照做：模型可以不经用户操作发起的计划审核，界面上呈现整份计划、但不改变后续动作放行方式的，只在“审批界面所在层”记任务层。

**18. F24：默认模式下没有逐次的批准决定时，“审批”计不计。**
- 现在：判定写“记下了批准或拒绝的决定，或者至少能分出人工批准和自动放行”。
- 问题：定义上的分歧在 A15：默认不审批，记录里按动作编号存了风险等级和“从不确认”的策略名；一人认为这就分得出自动放行，记入，一人认为没有审批记录，不记。A12 是另一回事：默认自动放行时，放行结果以一个标记写进工具请求的元数据，一人记了，另一人没提这个标记（漏看）；它算不算，取决于同一条界线。
- 推荐甲案：不计。加一句：“默认模式下没有任何一次逐次的批准或拒绝决定（人工的或自动审核器的）时，本项不计：只记下放行策略名或一个统一的放行标记，不等于有审批记录，写 value_note。默认模式下有逐次决定的自动审核器、并记下其决定的，计入。”A12 的询问路径上另有带同一编号的确认事件，它默认模式下有没有逐次决定，写 0.5 时一并核对。
- 乙案：能从记录分出“这次是自动放行”就计。默认全放行、又在记录里写了模式名的工具都会得到这一项，和 F22 的结论对不上。
- 另有一处随本条照做：“对得上”指两条记录共享调用编号，或在同一份按顺序写入的记录里相邻、能唯一对上；只有工具名和时间的不算。

**19. F25、F26：另开出来的会话，什么时候算框架管理的代理。**
- 现在：F25（是否存在框架管理的多个代理）的问法要求框架“创建这些代理、跟踪它们运行，并把结果交回上层”，不计“用户自己开多个会话”。
- 问题：三种情形没写。前两种出在 F26（代理由谁发起）的分歧里：用户命令把当前对话分叉成新会话，或为几个型号各起一个并列的代理（A04、B10，一人记了、另一人没提）。第三种不在归因材料里，来自这一轮之后改过的配置记录：模型用默认工具另开一个子会话，框架跟踪它，但结果不交回父代理（A15；记录改成了“能派出子代理”，两份编码是照旧记录记的）。
- 推荐甲案：F25 加两句。“模型用默认工具另开的对话，由框架创建并跟踪运行的，算框架派出的代理，结果不交回父代理也算；等不等、交不交回记在 F28，两种等待方式都不成立时 F28 不记等待方式，没有其他取值的写空集合。”“用户用命令让框架新开的对话，框架跟踪它的运行，并把结果交回发起它的会话或一个汇总界面的，算框架派出的代理；只是复制当前历史另开一个独立会话、结果不回到原处的，算用户自己开多个会话，不计。”F26 的“用户”一项相应写明：按这条算代理时才记。理由：模型能派出别的代理去做事，就是多代理结构，汇总方式的差别由 F28 表达；用户分叉出的独立会话和手工新开一个会话没有区别。
- 代价：F25 是门控字段。采纳后 A15 会从“无”变成“有”，F26–F28 要跟着编。
- 乙案：一律要求结果交回发起方才算。判法更简单，但“派出去、不收回”的设计会被记成没有多代理。
- 同时删改：F25 问法里的“并把结果交回上层”和“有”一项判定里的“收回”。

**20. F28：同步返回按什么判；卸载子会话算不算取消。**
- 现在：同步返回的判定里有“看发出委派或续派的那一次调用本身”和“不管内部用什么异步实现”两句。
- 问题：A12 的委派工具调用先立即返回，框架在下一次推理前运行子代理，等结果交回后才让父代理接着推理；两人按这两句各判一边。A14 父会话关闭时把子会话卸载（记录留着、以后能恢复），一人算取消传播，一人拿不准。A16 用户打断回合时框架先弹窗问要不要停子代理。
- 推荐甲案：
  - 同步返回看父代理：“从发出委派到拿到子代理结果之间，父代理不能再推理、也不能再发起新的工具调用的，记同步返回；委派调用本身先返回一个编号、由框架在下一次推理前接管等待的，也记这一项。同一次回复里和委派并列发出的调用不算‘新的工具调用’。父代理在这段时间能继续推理或发起新调用的，记异步等待。”
  - 取消传播加：“父会话关闭或释放时，框架把子代理的运行关掉（关闭、卸载、释放），即使记录留着、以后能恢复，也算取消；只是断开显示、子代理仍在运行的，不算。”
  - “哪些取消方式会连带”加：“取消时框架先问用户要不要一并停下子代理的，这种方式算不连带：连带要由框架自动完成。”
- 乙案：同步返回只看委派工具调用本身是否阻塞，先返回就记异步等待。结果会随一个实现细节翻转。
- 同时删改：同步返回判定里“看发出委派或续派的那一次调用本身”一句。

**21. F12：服务端下发的输出上限算不算；输出限制计入后算不算强制截止。**
- 现在：输出限制的判定里并列着两句，“按型号查的表”算，“阈值完全来自服务端的”不算。“强制截止”子维度列了“截断输出”。
- 问题：B06 的客户端把服务端型号列表里的输出上限填进请求，截断后只结束、不续写。一人读成“按型号查的表”，因为不知道默认型号写了未知；一人读成“完全来自服务端”，记不存在。B10 上两人都记了输出限制，一人放进强制截止，一人因为“截断恢复用完后会不会停下不清楚”放进了“软硬未明”。
- 推荐甲案：
  - “上限值由服务端下发（包括服务端下发的型号列表），客户端只照填、截断后没有专门续写或重试的，不算；截断后有专门续写或重试处理的，照常记。”这是总则第 4 条的一处例外：那里说机制在客户端就照记，这里客户端只是转发，没有自己的预算机制。本字段的范围规则本来就排除服务商的限额。
  - “输出限制计入取值的，默认写进强制截止：单次输出到上限即被截断；截断后的续写只是恢复处理，不改变这一点。”强制截止这个子维度进距离计算，这一句会影响距离。
- 乙案：服务端的型号列表也算“按型号查的表”，凡是客户端转发了上限的都记。等于把服务端限额算进 Harness 自己的预算。强制截止一项的乙案是：有截断恢复时写进“软硬未明”。
- 这个字段另有两处随本条照做：框架里有按型号查表取默认上限的分支、默认开着的，计入，查不到钉住型号的数值就写 value_note；同一段代码既按次数停止又做重复检测的，只有按次数停止的部分记调用次数。

**22. F23：写在参数校验里的范围检查算不算应用检查；“只读”的角色还能用命令行时怎么记。**
- 现在：应用检查的判定有“按路径限制在执行前拒绝”和“只核对参数格式的不算”两句。“只靠提示落实的限制”写：交代的限制有代码检查、但常用路径没有管到的，记“有”并写“部分兜底”；只凭推测、没有材料承认的绕过不算。
- 问题：A12 的委派工具拒绝工作目录越出父目录的子代理。一人算应用检查，一人算参数校验、不计，整个字段记成了不存在。A04 默认会调用的内置只读子代理只靠提示和工具清单落实只读，却仍有不受只读检查的命令行工具；一人记“有”，一人认为“仅凭有命令行就推断能绕过”不成立，留了空。
- 推荐甲案：
  - 应用检查改为：“检查的是动作的作用范围（路径、目录、主机、命令）的，即使写在参数校验里，也算；只核对参数类型、必填项或工具存不存在的，不算。只管某一个工具入口的，范围写 value_note（总则 R2）。”采纳后 A12 的 F23 会从不存在变成有取值。
  - “只靠提示”加：“某个模式或角色被说成只读，却仍能用不受只读检查的命令行工具的，算常用路径没管到，记‘有’，写‘部分兜底’，不需要材料承认能绕过。‘只凭推测的绕过不算’只适用于按命令名单检查的情形。”这比现行写法判得宽一点。
- 乙案：派生子代理时的目录校验不限制子代理之后的动作，不算应用检查；只读角色有命令行的，要材料承认能绕过才记“有”。前一句和总则 R2“只覆盖一个工具的机制也计入”不一致。
- 另有两处随本条照做：工具说明里把某种委派用途描述为只读、但没有具名角色的，以及系统提示里成段的通用安全守则，都按一般建议处理。

**23. F30：随指导装载、事后才由框架执行的代码，算不算“可执行项”。**
- 现在：“以可执行代码装载的项”只写了“展开或装载时”执行的嵌入命令片段。
- 问题：A04 的技能可以带框架执行的钩子，一人据此把技能目录记进可执行项，一人没提。A12 的配方文件带框架执行的检查和重试，也卡在执行时刻上。
- 推荐甲案：不限时刻。“随指导一并装载、由框架执行的代码，不论在展开时、装载时还是之后某个事件点（回合结束、检查失败）执行，都把它所在的取值记进本子维度，如技能自带的钩子、配置里写的检查命令。模型读到后自己决定去运行的，仍不算。”理由：这个子维度要分的是“交给模型读的文字”和“框架会执行的代码”，执行时刻不影响这个区分。
- 乙案：维持“展开或装载时”。
- 这个字段另有两处随本条照做：命令目录里的可执行文件由框架运行一次、把输出交给模型的，记提示模板并记进可执行项，不算工作流定义；按名切换、改写系统提示的输出风格或人格叠加，用户能自己新增的，记角色模板。

**24. F32：模型接口兼容的端点，算公共协议还是服务 API。**
- 现在：公共协议服务端只举了编辑器代理协议和工具协议。
- 问题：A15 的本机服务开放了模型接口兼容的对话补全端点，每个请求在背后跑完整代理。一人记公共协议，一人记服务 API。C01 上类似的端点两人都归进了服务 API，前后不一致。
- 推荐甲案：算公共协议。加一句：“对外表现为一个模型接口兼容的对话补全或响应接口、每个请求在背后跑完整代理循环的，记本项；只转发模型请求、不跑代理循环的不记。”理由：这类端点让现成的客户端不读厂商文档就能驱动核心，正是这一项要量的东西。采纳后 C01 按同一口径复查。
- 乙案：公共协议只收代理协议和工具协议，这类端点记服务 API。

## 三、定了以上各条后照做的

下面都是给判定补一句界线或一个例子。归因里列过另一种做法的，括号里写了为什么不采纳。负责人对这一节没有提出异议。

**总则和格式**
- R1：`host_os` 以后只钉一种系统。记录里已经写了两种的，按列在前面的那种判，只在另一种上出现的机制写“其他环境：”。
- R2：官方自带的前端经嵌入接口为会话声明的工具，按“嵌入方声明的工具”在用记，不算内置。（另一种做法是官方自带的都算内置；那样同一条边界会因为声明方是不是官方而换归属，和 0.4 已定的“按实际经过的边界记”相反。）
- R7：写进 unresolved 的迹象，要指向该取值判定里的关键条件（例如“批准和拒绝都落盘”）；只说明相关状态存在的不算。
- 子维度：只在状态为 known 时填写的子维度，状态不是 known 时保留键、写 null；校验脚本把缺键和 null 视同。
- “默认已有内容在用”（F29、F31）：配置记录写明默认安装没有预置内容的，照它写 []；记录没写、默认加载的扩展又不在快照里的，写 null 并写明缺哪份材料。

**F01–F12**
- F01：推进下一步的编排者本身是模型的（一个代理按计划派子代理、能改计划），仍记模型循环，计划的约束记 F02；只有由框架代码按事先写好或由程序确定性生成的脚本、节点推进下一步时，才记显式工作流。用户分别建任务、调度器只决定何时启动哪一个的，属任务发起（F33），不记事件调度。核对清单把子命令和源码里的内置命令表包括进去；随包命令在说明里写着会开启另一种运行时的，看到这一层即可判。
- F02：每次回复都要求附带“分析和打算”的推理文字、但不要求先给出覆盖整个任务的计划的，记“无独立计划”。（另一种做法是算“仅提示文本”；那样只要求“先思考再行动”的提示都会被拉进来。）
- F03：验证条件补一个例子：派生子代理时要求按固定结构交回结果，不合格就不让它结束。
- F04：认证失效后暂停、等用户重新登录、再从原请求接着走的，算升级人工。解析不了的参数换成空值后照常执行工具的，才算框架修正输入；替换只用于存档、工具不执行的，记模型自修。重发前只做压缩或截短的，仍记调用重试。
- F11：只在某一家提供方或网关上才走到的换型号分支，按钉住环境实际用的提供方判。

**F13–F24**
- F14：工具结果在进入上下文时没有先截短、整条换成占位或文件引用的，记工具结果替换。
- F15：读文件工具在文件过大时自动改给符号提纲，属于对已选定文件的缩减，记 F14，不算结构索引。（另一种做法是也算结构索引；那样同一机制在两个字段各计一次，而这里模型已经自己选定了文件，没有发生“取回”。）
- F16：只在提示里要求模型“需要时更新说明文件”、靠通用编辑工具写入的，不算自动摘要。（另一种做法是按 R3 第一档计入；很多工具的提示里都有这么一句，会不会真写取决于模型，静态材料判不了。）
- F18：检查点继续要求中断点上那一步不经模型重新决定就能接着执行；只把待批或待答的请求重新呈现、运行中的调用作废的，记重建对话再运行。（另一种做法是有一类待执行动作能接着执行就算检查点；待批请求被带回，多数只是一条未答的请求重新显示出来。这条决定 B10 的取值。）

**F25–F36**
- F26：每个回合结束后框架自动起、能多步调用工具的后台代理（如整理记忆），记框架内部，不论它是否服务于当前任务。定时器到点直接起的代理运行，按现行定义记事件调度。
- F27：新开一个子代理、把已完成子代理的记录带进去的，仍算每次新开，不记消息。
- F28：“哪些取消方式会连带”逐项判三种方式（打断当前回合、取消等待中的调用、取消父运行），每种写连带、不连带或默认路径上没有。同一次委派先在前台、超时后转后台的，只看前台阶段。默认委派路径上有一种方式会连带，两个子维度就按默认路径填，不换路径。默认工具在内部起子代理完成工作的，按 R4 计入。
- F29：用户在设置里给出一条发现命令、框架按它的输出注册工具的，记用户脚本。
- F31：“保存”只收框架自己把会话记录、检查点或工作区快照写盘前后的事件；某个工具改写文件之后触发的事件归工具前后。（另一种做法是两项都记，违反 R8。）订阅整条类型化事件流的接口，事件流里有某一阶段专属的事件类型时，按该阶段记一个事件点。靠抛错算阻断，要框架把这个错误当作拒绝或中止来处理才算。提供方接口里框架按阶段调用、并使用返回值的方法，算这个阶段的处理器。
- F32：官方文档明确称为公开接口、给出入口类或函数名的，算公开发布的库，即使没有完整用法指南、没有单独打包；文档提到了、但没说是否供外部使用的，写进疑似成员。官方 SDK 文档写明可以连接本机某个服务、而这个服务没有线协议文档的，记库，不写进疑似成员。
- F33：api 进不进“所选入口直接开放”，照 F32。
- F35：工作项写进了记录、但进程重启后要人重新发起的，记内存队列。定时任务的定义存盘、重启后按计划继续触发的算持久，但要有材料写明会继续触发。运行中提交的消息按它被执行之前存放在哪里判。
- F36：框架到达回合数、步数或费用上限时停下来问人的，记阻塞审批；阻塞类型里，要人提供信息或选择怎么继续的记“非审批提问”，由模型发出还是由框架发出都算。

**口径疑问表里这次不处理的**

第三轮记录的口径疑问表里，下面几处在归因里没有对应的分歧条目（两人判法一致，只在说明里提了疑问），这次先不动，记进后续清单，等再有配置在这里分歧时一并定：

- F01：让模型用定时工具排后续提示的命令，归 F01 还是 F33。
- F03：有上限的单次重试（校验不合格让再答一次、第二次放行）算不算验证条件。
- F04：框架修整输入的范围（补调用编号、丢弃没有名字的调用）。
- F05：前端拉起后端子进程、两者经本机端口通信，记子进程协议还是本地服务 API。
- F21：自动审核器算不算“批准者”；环境变量传入的范围算不算用户写的规则。
- F31：一个通知事件横跨两个阶段怎样拆；新建工作树时触发的处理器算不算会话开始。
- F34：“关掉界面”指退出键、关窗口还是关终端；看进程还是看执行核心。

## 四、词表提议的处理

这一轮有三个正式提议、两个写在说明里的非正式提议，都建议并入现有取值，词表不加项。其中 F11 和 F36 两处要改现有取值的判定：

| 提议 | 处理 | 理由 |
|---|---|---|
| F11 `model_selected_switch`（主模型用默认工具把自己后续的调用切到另一个型号；两人各提一次） | 并入 `model_selected_delegation`。id 不变，免得前几轮的数据要迁移；中文名改成“模型自选型号”，判定扩成“主模型在任务中自行为子代理、子任务或主循环自己后续的调用指定型号或推理强度”。钉住环境里只有一个可选型号、切不到别处的不记，写进 value_note | 两者都是“模型决定用哪个型号”，算距离时不该分开。代价是 id 里的 delegation 和新含义不完全对应 |
| F22 `tool_call_batch`（一次确认放行同一回复里的全部命令） | 并入调用层，value_note 写明批量 | 差别只在一次放行几条，批准不延续到后续回复 |
| F23 `browser_sandbox`（生成的网页在隔离浏览器里打开） | 不采纳，写 value_note | 限制的是页面本身，不是代理的动作 |
| F36 “非阻塞的向人请求”（代理发出、等人填写的请求卡） | 持久保存、重启后仍在的并入可恢复待办，即使发出它的那次调用已经立即返回；不持久的写 value_note | 这一项问的就是“留下等人处理的待办”；为一个配置加新取值会让词表更难判 |
| F30 “输出风格” | 并入角色模板（见第 23 条末尾） | 按名切换、改写系统提示，就是一份可复用的角色定义 |

## 五、防漏看的流程对策

交叉核对里“一方找到、另一方没提”的有 26 条，两人各 13 条；回查后 18 条确实在默认路径上，5 条要用户另行操作才有。分析者归为主因的是 23 条。这类分歧改定义消不掉，下面几项都落在编码任务卡和维护者的准备工作上，不动码本。前五项直接照做；第六项随第八节第 25 条一起定。

1. **任务卡加一条通用提示。** “每个字段都按三个时刻再查一遍：回合结束后框架自己做了什么；到达上限时；超时、失败或中止时。”漏看的 23 条里约十条落在这三个时刻。
2. **任务卡按字段加查找提示。** 三位分析者为 F03、F04、F12、F14、F19、F21、F22、F24、F26、F28、F29、F30、F31、F32、F36 各写了一两句，都不带产品名，可以直接放进卡里。例如 F12：“找到某一维的硬上限后，在同一处再找有没有提前给模型或用户的提醒；框架在回复交付后自己起的后台代理，也要逐个查上限。”F22：“对会联网的工具和执行脚本的工具，查执行中途会不会再发授权请求，不要只看调用发出前那一次。”原文在三份归因记录的“漏看的机制藏在哪”一节；归因记录是工作材料，没有入库。
3. **子维度留空要写明原因。** 任务卡要求：子维度写 null 之前，coder_note 写明哪一项没查、为什么；源码在快照里的，查完再交。
4. **编码前核一遍快照齐不齐。** 这一轮 A15 漏取了配置记录里钉的自动化服务仓库，默认加载的公共扩展也不在快照里，造成 F31、F35、F36 上的材料不足。`fetch_sources.py` 现在只按证据小卡里的链接找仓库，要改成把记录里钉的每个提交都取到；配置记录写明默认加载哪些扩展、来源在不在快照里。
5. **编码前复核配置记录。** 这一轮六份配置记录是在编码之后才发现和源码对不上的（默认工具清单、默认开关、执行位置）。以后每份记录在派给编码者之前，先由另一位读者对照快照核一遍默认工具、默认开关和所选入口的执行位置。
6. **交叉核对作为每一批的固定步骤。** 做法照这一轮：算完一致率后，第三位读者不看是谁编的，只回答“这条机制在不在、是不是默认”。它已经写进 `data/README.md` 的流程第 5 步。

落实情况：第 1—3 项写进了编码任务卡 `pilot/coding-card.md`（提示版本 coding-card-v7，新增“容易漏看的地方”一节）。第 4 项改了 `pilot/fetch_sources.py`：配置记录里钉的每个提交都取，放不到具体仓库的在 `SOURCE.txt` 和标准错误里逐个报出；A15 漏取的自动化服务仓库已经补进快照。默认加载的公共扩展所在的仓库没有钉提交，仍不在快照里。第 5 项在下一批开始前做。第 6 项已写在 `data/README.md` 的流程第 5 步。

## 六、起草和审阅时补的界线（未逐条请负责人过目）

负责人定的是 26 条的方向和第三、四节的做法。把它们写成字段定义时，起草者和审阅者又补了一些句子，让规则能用在具体情形上。三位审阅者各读一组合并稿，共提出必改 9 条、建议 14 条、措辞 14 条、总则意见 5 条；除下面写明没有采纳的，都已改进 `fields.json`。这一节列的内容没有逐条请负责人过目，哪一条不合适，下次修订时改。

### 改了已定句子措辞的两处

- **F29、F31 的“默认已有内容在用”。** 第三节定的原句是“配置记录写明默认安装没有预置内容的，照它写 []；记录没写、默认加载的扩展又不在快照里的，写 null 并写明缺哪份材料”。审阅指出它和另外两条已定事项相抵：照字面写 [] 会把一直在用的内置工具（F29 的 `internal_code`）也去掉，又和 R1 新句“配置记录对默认工具的陈述不是证据”相反；“写 null”和子维度总则“确认一项写一项，一项都确认不了才写 null”相反。现在的写法保留原意，补上先后：记录写明没有预置扩展内容的，扩展类的几项照它不写进来，内置工具仍按代码判；代码显示默认加载了扩展的，以代码为准；扩展不在快照里的，已确认的项照写，缺的写进说明，一项都确认不了才写 null。
- **F18 的检查点继续。** 第三节定的是“只把待批或待答的请求重新呈现、运行中的调用作废的，记重建对话再运行”。审阅指出判定里的例子落在“原来等批准的调用仍在等批准”，会引着人用没采纳的那种判法。例子换成“执行到一半的工具调用由框架直接接着执行”，界线句改成按“运行中的调用是否被作废、交给模型重新决定”判，待批请求被带回、获批后照原样执行的也不改变这一点。有一种情形没有定：中断时只有一条待批请求、没有运行中的调用，获批后由框架照原样执行。码本没有为它单写一句，遇到时按框架怎样对待运行中的调用来判，留到下次修订请负责人定。

### 总则

- R2：只能填一个值的设置项里填的是一条命令或一个服务地址时，“自带定义算添加内容”和“给单值设置项填值算改设置”两句同时命中。补一句按是否自带定义判，算添加内容（审阅 G–I 组，F29 的发现命令是这种情形）。
- R10：“实现”原写“所选入口实际走到的代码路径”，和 R2“不要求默认路径上一定会走到”字面相抵。改为“所选入口能走到的代码路径”，包括只在失败、超限或重入时才走到的分支；所选入口从来不会发出的模式才不计（审阅 A–C 组）。
- 没有采纳的两条：在 R3 末尾加“字段里‘模型向用户提问不算审批’一类排除不适用于这种路径”，改为只在 F22 里写明；在 R10“机制照记”后统一加置信度上限，改为只在 F11 的槽位句里加。两处都是为了不再加长负责人已定的总则。
