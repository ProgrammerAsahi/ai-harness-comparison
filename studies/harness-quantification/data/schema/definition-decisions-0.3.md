# 码本 fields-0.3 的决定记录

这份记录说明 `fields.json` 从 `fields-0.2` 改到 `fields-0.3` 时定了什么、为什么、哪些备选没有采纳。它只作记录，**不发给编码者**：里面点名了配置，也写了第一次编码时两位编码者各自怎样判。

- 依据：第一次试编码（`pilot/round1.md`）的分歧归因。三位分析者按字段组只读两位编码者的并排记录，逐处判断分歧的主因，不裁决谁对。
- 决定：下面第一、二、四节每条都列了推荐和另一案，项目负责人 2026-11-10 答复“都按推荐定”，即全部取“推荐”。
- 落实：三位起草者按字段组把决定写成字段定义，再由一位没看过起草材料的审阅者通读合并稿。起草时为了让总则能用在具体字段上而补的界线，列在第五节，这些没有逐条请负责人过目。

## 分歧出在哪

136 处分歧（含 10 处只差分面）的主因：

| 主因 | 处数 | 说明 |
|---|---|---|
| 定义缺口 | 77 | 判定标准没覆盖这种情况，两人都说得通 |
| 范围口径 | 43 | 争的是算不算“默认生效”、该看哪一层、哪个入口 |
| 要回源码核对 | 8 | 两人对同一事实说法相反 |
| 答案类型不合适 | 4 | 单选装不下并存的机制 |
| 词表缺项 | 2 | 现有取值装不下 |
| 材料不对等 | 2 | 一方没找到证据 |

两人对事实的描述大体一致，九成分歧是“这算不算某个取值”。所以修订的重点是写清口径，词表只小改。只有一行编码说明的字段分歧最多；第 0.2 版写了完整规则的五个字段（F01、F12、F21、F22、F23）主取值分歧少，问题集中在分面。

## 一、九条总则

三位分析者各自提了跨字段规则，有两处互相打架，我合并成下面九条。每条给推荐和另一案。

**1. 配置记录补钉环境前提。** 同一配置的默认行为随主模型、账户套餐、操作系统、是不是 Git 仓库、首次进入时是否接受信任、有没有某项凭据而变。一人按官方默认判，一人记未知。牵动 F01、F02、F11、F14、F15、F19、F20、F21、F26、F30。
- 推荐：配置记录加一组“环境前提”字段并逐个配置钉住（官方快速开始的默认型号和套餐、macOS 或 Linux、Git 仓库、接受信任、只有主提供方的凭据）。取值按钉住的这条路径填，其他分支写说明。
- 另一案：不改配置记录，随环境分支的一律填未知。缺格会很多。

**2. “默认生效”指机制开放，不要求已经有内容在用。** 扩展接口（外部工具协议、钩子、命令和代理定义目录）默认开放、默认没配内容时算不算。牵动 F29、F31（13 处）、F26、F30。
- 推荐：机制不改开关就开放，就记入取值；用户只需添加内容（一条服务器配置、一个钩子脚本、一个定义文件）不算改设置。另加统一分面 `in_use_by_default`，记“默认已经有内容在用”的那几项。任务卡里“实际在起作用”的措辞同步改掉。
- 另一案：只记默认已有内容在用的。多数配置只剩内置那一项，字段分不开。

**3. 用户要多做一步才有的东西，按“框架拦不拦”分三档。** 这是两位分析者打架的地方（一位说用命令进入的路径只写“可选”，一位说一句口令就能用的应记入取值）。
- 推荐：
  - 模型运行时自己能选、框架不拦的（默认注册的工具、工具参数），算默认，记入取值。文档说“要用户同意”但代码并不拦的，按代码算默认，说明里写明。
  - 用户要在对话里显式进入的（斜杠命令、关键词、切换内置模式），不改任何设置：不进取值，记进该字段的“可选路径”分面或写“可选：”。F01 的 `secondary_modes`、F23 的 `prompt_only` 已经是这个做法。
  - 要改设置、设环境变量、另装东西或换套餐的：只写“可选：”。
- 另一案：第二档也记入取值。和第 0.2 版已定的 F01 做法冲突。

**4. 看哪一层：主执行链、辅助调用分开。** 标题生成、摘要器、动作审核分类器、工具内部自带的模型算不算。牵动 F03、F11、F12、F14、F23。
- 推荐：取值只看主执行链，即默认路径的主循环加它自动派生的子代理；子代理自己的默认上限计入并写明范围。辅助调用默认不计，需要保留的字段单开分面（F11 加 `auxiliary_models`）。
- 另一案：辅助调用也计。几乎所有配置都会多出同样几项。

**5. 其他入口算不算本配置。** 同一发行版加参数、换子命令或另装官方包才有的程序化入口。牵动 F32（8 处）、F33。
- 推荐：讲能力边界的字段（F29、F31、F32、F33 的接口触发）按同一发行版、官方有文档的全部入口记，加分面 `via_default_entry` 标出所选入口直接开放的那几项；讲运行形态的字段（F34、F35、F36）只看所选入口。
- 另一案：一律只看所选入口。交互式终端工具的 F32 几乎都是空集。

**6. 闭源产品只有文档时，允许按文档推断。** 牵动 F05、F06、F09、F13（Claude Code 上 5 处状态分歧里的 3 处）。
- 推荐：允许记已知，置信度只能是低，说明以“推断：”开头并给出那段官方文档；只能用对本配置的说明，不从同一产品的其他形态借。敏感性分析时可以剔除。
- 另一案：文档没直接写的一律记未知。闭源配置在这些字段上没有信息。

**7. “未知”不代替口径判断。**
- 推荐：范围拿不准时按码本口径记已知或已知不存在；机制清楚但词表装不下的，未知原因新增 `vocabulary_gap` 并必须附词表提议；集合只确认了一部分的记已知、置信度不高于中，疑似成员放进统一的可选分面 `unresolved`（算距离时按未知处理）；每个带分面的字段写明“查过哪些材料才能写空集”。
- 这条没有像样的另一案，列出来是因为它新增了一个未知原因和一个通用分面。

**8. 一个机制只在一处计。**
- 推荐：同一字段内一个机制只归一项，按字段写明的判定顺序取第一项命中的。跨字段各有主管：输出截断及其续写只在 F12 记；厂商格式转换只在 F09 记；记忆检索只在 F16 记；回退到检查点只在 F20 记。另加一句：只留下了数据、没有内置流程去读它来完成该字段所问功能的，不计。

**9. 单选字段保持单选，用优先规则加分面。** 10-20 定的是“试编码保持单选，看分歧再定”。这一轮只有 4 处主因是答案类型。
- 推荐：不改成集合。每个单选字段写一条优先规则，并存的其他机制用分面记（F13 加 `layers`，F34、F35 各加一个分面）。
- 另一案：改成集合。取值之间的强弱顺序就看不出来了。

## 二、字段级决定

| 字段 | 要定什么 | 推荐 | 另一案 |
|---|---|---|---|
| F01 | 用户直接执行单条命令、不经模型的入口进不进 `secondary_modes` | 不进：只收包含模型调用的路径 | 记为用户逐步推进 |
| F02 | “无独立计划”和“仅提示文本”的界线 | 提示里明确要求先产出计划才算；泛泛鼓励规划记“无” | 出现任何规划要求都算 |
| F03 | 子任务的上限算不算 | 算，和 F12 一致 | 只看主任务 |
| F04 | “升级人工”的范围 | 只算框架暂停任务、等人决定；报错后交还控制权不算 | — |
| F05 | IDE 扩展的“前端”取哪一层 | 取直接调用执行核心的那层；宿主平台强加的渲染层和消息桥不计 | 取渲染层，另加取值 |
| F10 | 协议转换的边界（7 处分歧里 6 处） | 只收两种调用协议之间的桥接；内部格式转厂商格式不算（归 F09） | 厂商格式互转也算 |
| F11 | 辅助调用怎么记 | 主取值只记主执行链，另加分面 `auxiliary_models` | 一句话排除 |
| F12 | `output_limit` 的判定 | 框架自设上限，或对截断有续写、重试处理才算；只报错不算 | 有任何专门处理就算 |
| F13 | 多层构造怎么判 | 按“每次请求从哪份数据出发构造”判主值，叠加层记分面 | — |
| F14 | “分段选择”的范围 | 收窄为按相关性挑片段；压缩时顺带保留最近几轮只记摘要 | 凡按规则挑片段都算 |
| F17 | 消息和事件写在同一份记录里 | 按存储单位只记一项 | 两项并记 |
| F23 | `prompt_only` 含不含可切换的内置模式和内置子代理 | 含，说明里写是哪一项（不进距离计算） | 只看默认模式 |
| F24 | 普通会话记录算不算审计记录 | 算：默认持久化、能按编号互相对上的都算 | 只算专门审计日志 |
| F24 | “身份”指谁 | 只指人或账户 | 拆分面记人、代理、模型 |
| F26 | 模型当场写、运行时按脚本派生的算不算工作流调度 | 算：看调度由谁执行，脚本出处写说明 | 只算预先保存的工作流 |
| F31 | “保存”指什么 | 含会话记录、检查点、工作区文件的持久化前后；上下文压缩另加取值 | 只指文件写入 |
| F32 | `protocol_client` 方向不清 | 改名 `public_protocol`：本核心作为公共协议的服务端 | — |
| F35 | 多层队列怎么记 | 取最强一层的保证，交互输入队列另记分面 | 取主交互队列 |
| F36 | 消息通知的范围 | 只算离开当前对话也能收到的主动提醒 | 界面内状态消息也算 |
| F36 | “可恢复待办”的范围 | 持久保存、重启后还在、明确等人来处理的待办或目标才算；代理自用的计划清单、只是能恢复会话都不算 | 代理自用清单也算 |

F21 的“默认效果随环境分支”并入总则第 1 条，F29、F31 的口径并入总则第 2 条。

## 五、起草时补的界线（未逐条请负责人过目）

- F18、F19、F20：恢复和回退本来就由用户发起。用官方的继续参数、恢复命令或回退按钮发起的，在这三个字段算默认机制，不按总则 R3 第二档排除；要改设置或另装东西才有的仍写“可选：”。不设这条例外，这三个字段几乎都会变成空。
- F26 的“用户”一项同理：它本身就是用户在对话里显式发起的路径，默认开放就记。
- F02：词表里“无独立计划”排在最前，照总则 R8 取第一项命中会总落到它，所以字段内写明从约束最强的一项往下判。
- F05：只有库接口、没有独立前端的配置记进程内。F06：套了一层系统沙箱的子进程仍记子进程。F11：型号名不同、但能确认是同一底层模型的算同一型号。
- F10：外部工具协议默认开放、只等用户添加一条服务配置的，按总则 R2 算开放。归因文件原建议写“可选：”，和总则冲突，按总则。
- F16：记忆文件本身和对它的检索按两个机制分别判。F19：计划只出现在消息文字里的归对话。F20：一次回退同时带回对话和文件时，两部分分别判。
- F27：只在结束时交回最终结果的记到 F28，不记“消息”。F30：技能附带的脚本由模型经命令行自己运行的，不算可执行代码装载。
- F31：只能观察、不能干预的事件点仍进取值，另用子维度“仅观察的阶段”标出。
- F33：人在聊天通道里发的消息记用户交互，外部系统自动发进通道的才记外部事件。
- 没有改的名称：归因文件建议把 F08 的 `logical_id`、F09 的 `vendor_sdk`、F36 的 `blocking_approval` 改中文名，这三处不在已定事项里，名称保留，只在判定标准里写明含义。
- F16、F18、F25 原有的 `note` 键并进了各自的定义，键本身去掉。

合并后请一位没参与起草的审阅者按编码者读到的全文查了一遍（定义之间有没有互相打架、例子能不能认出受测工具）。照审阅意见改的地方里，下面几条是新补的界线：

- 总则 R3 第二档补进“启动时加一个命令行参数、换一个子命令”。原文只说对话里的命令和按键，启动参数落在第二档和第三档之间；F01 的次要模式本来就收这类路径，所以归第二档。
- 总则 R4 补一句：框架按内部条件自动派生、自己能多步调用工具的辅助代理算子代理，计入取值；只调一次模型的才算辅助调用。和 F25、F26 的口径对齐。
- 总则 R8 补一条例外：每个会话自动读入的说明文件，F16 记用户维护文件，F30 记项目规则，两处都记。两个字段的判定标准原来都要求计入，只是总则没有交代。
- F06 写明不按总则 R2 的扩展点口径：只记默认安装后已有工具在其中执行的位置。扩展点还没有内容时，执行位置取决于用户以后添加什么，没法判。
- F22：动作被隔离机制拦下后由框架发起的放行请求算审批，记调用层；同一机制在 F04 另记升级人工。
- F02：计划模式只在出计划阶段限定可用工具、批准后不按条目检查的，仍记“仅提示文本”。
- F03、F04、F12 对“连续截断”的归属统一到 F12；F21 的钩子检查改为事件点记 F31、默认已有钩子在拦的才在 F23 记；F29 的冲突成员改写进 `unresolved`；F35 写明交互输入那一层也参与取值比较。
- F14 的片段选取、F13 的类型化事件重建、F04 的升级人工等几处判定标准和例子，原稿和已定事项不符或能认出受测工具，已照已定事项改回并换成泛称例子。

环境前提里有三处是研究负责人选的，不是官方默认。Pi 和 OpenClaw 都没有自己的账户，快速开始让用户任选一家提供方或复用已有登录；MiMo Code 的登录同时支持按量计费和 Token Plan。起草时这三处按“文档里举例或产品默认的那一家、按量计费”钉（Pi 钉 Anthropic 接口密钥，OpenClaw 钉 OpenAI 接口密钥，MiMo Code 钉按量计费）；负责人 2026-11-10 改为更接近个人日常用法的路线：

- Pi：ChatGPT Plus 订阅，用 `/login` 里 OpenAI 的 Sign in with ChatGPT 登录（提供方 `openai`），默认型号 `openai/gpt-6.1-sol`。固定提交里另有旧的 `openai-codex` 提供方，官方说明它已被前一条路线取代，所以不用它。
- OpenClaw：复用本机已登录的 Codex CLI，默认型号 `openai/gpt-6-astra`。这条路线下引导会自动装上官方 `codex` 插件，代理回合经 Codex app-server 运行，线程续接、工具续调、压缩和执行归 Codex，通道、会话文件、动态工具、审批归 OpenClaw；内置的 OpenClaw 执行框架不在主执行链上（总则 R4）。这一点是查证时才发现的，编码结果会因此靠近 Codex 配置，是否仍用这条路线待负责人确认；原前提下已交回的编码段留作对照，没有删。
- MiMo Code：Token Plan 最低一档 Lite。客户端源码不按计费方式分支，两种计费只在密钥和接口地址上不同，所以原前提下已交回的编码段继续使用，没有重编。

OpenClaw 的工作目录钉它自己的默认工作区，不是启动命令所在的目录。Codex 和 Kimi Code 的默认型号由服务端下发，记录里照实写“由服务端决定”和快照里能看到的种子值。
