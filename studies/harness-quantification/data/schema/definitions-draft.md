# 五个待定字段的定义草案（供作者审阅）

状态：**草案，未定稿**。本文为 F01、F12、F21、F22、F23 补出可直接用于编码的定义，供作者先审。定稿前，`fields.json` 里这五个字段的原定义、`needs_definition: true` 和第一轮试编码模板都不变；推荐方案只以 `"draft": true` 的形式写在各字段的 `proposed` 键里，校验脚本检查它的结构，但不把它当作编码规则。

依据：方法报告第 4.1 节（配置对象）、第 5 节（字段表、5.4 字段取舍、5.5 条件字段）、第 7.2 节（各类字段的距离）、第 8 节（未知与已知不存在）。例子取自主报告 `report/` 现行正文，括号里写档案编号与所在文件，方便回查；例子用来说明取值的意思，**不是对这些工具的正式编码**。

## 共同做法：子维度怎样落到数据结构上

报告对 F12、F21、F22 的要求（区分软提醒与强制截止、记录默认规则、审批界面与强制执行点分别核查），都是在同一个字段里再分一层。草案不新增字段、不新造答案类型，统一用一个可选的 `facets`（子维度）对象承载：

```json
"F12": {
  "status": "known",
  "value": ["output_limit", "call_count"],
  "facets": {"hard_stop": ["output_limit", "call_count"], "soft_notice": []},
  "value_note": "…", "evidence": ["…"]
}
```

- 每个子维度只用现有类型：`set`（集合）或 `nominal`（类别）。取值要么沿用本字段的词表（`vocabulary_from: "value"`），要么在 `proposed` 里给出自己的小词表。
- `subset_of_value: true` 的子维度必须是 `value` 的子集；字段状态不是 `known` 时不填子维度。
- 子维度写 `null` 表示这一层未知，不等于空集合；空集合 `[]` 表示已知这一层一个都没有。
- 每个子维度注明 `in_distance`：是否进入基线距离。不进入的只用于解释和敏感性分析。
- 定稿后才把 `facets` 加进编码记录允许的键，并把码本版本升为 `fields-0.2`、重新生成模板；在那之前，第一轮编码者仍按 README 约定把这些信息写进 `value_note`。为便于事后转录，建议 `value_note` 里用同名标记，例如 `hard_stop: output_limit, call_count`。

五个字段的推荐方案一览：

| 字段 | 类型 | 推荐的补法 | 子维度 | 进入基线距离的部分 | 字段数变化 |
|---|---|---|---|---|---|
| F01 | 类别 | 规定“主要入口”的判定法；其余控制方式记为子维度；控制图留给第 6.2 节的图层 | `secondary_modes` | 只有主要入口 | 无 |
| F12 | 集合 | 取值记录有哪些预算维度；软／硬各用一个子集合 | `hard_stop`、`soft_notice` | 取值与 `hard_stop` 各占一半 | 无 |
| F21 | 集合 | 取值记录规则能按哪些维度表达；默认规则按效果分三个子集合 | `default_allow`、`default_ask`、`default_deny` | 只有取值 | 无 |
| F22 | 集合 | 取值记录强制执行点所在层；审批界面所在层作子维度 | `ui_layers` | 只有取值（执行点） | 无 |
| F23 | 集合 | 封闭词表：在原三项外加“运行时沙箱”；提示型约束另记 | `prompt_instruction` | 只有取值 | 无 |

## F01 主控制方式

### 缺口

报告写“混合结构记录主要入口及说明，必要时改为控制图”。没有规定什么叫“主要入口”，也没有定义控制图的格式。另外，四个类别里的“事件调度”和第 I 组（F33 任务从哪里触发、F34 生命周期由谁维持）有重叠风险：常驻网关既可以算“事件调度”，也已经在 F33／F34 里体现。

### 推荐定义

**问题怎样问**：在所选配置的入口里，用户提出一个任务之后，**直到这个任务结束，由谁决定下一步做什么**？“任务从哪里来、谁让它开始”属于 F33，“进程退出界面后是否继续”属于 F34，不在本字段重复记录。

**类型**：类别（无顺序），不变。

| 取值 | 判定标准（一句） | 主报告例子 |
|---|---|---|
| `user_stepwise` 用户逐步驱动 | 框架每完成一个模型回复或一次编辑就停下等用户的下一条指令，不会自行连续发起多步工具调用 | B18 CodeCompanion.nvim（03B）：简单转换由用户发起、直接请求模型一次，复杂开发才交给完整代理（后者属另一条路径）；H03 Aider（03D）以“明确输入、编辑和 Git 审查”推进，是否会自行连续多步，编码时须核对源码 |
| `model_loop` 模型循环 | 模型的输出决定下一次工具调用，框架执行后把结果交回模型，循环到模型给出结束信号或被中断为止 | A01 Claude Code（03A）：模型缺信息时继续读文件，测试失败时接着诊断；D03 mini-SWE-agent（03D）的最小循环 |
| `explicit_workflow` 显式工作流 | 步骤顺序由事先写好的流程图、节点或脚本决定，模型只在节点内部做判断或生成 | D01 Dify、D02 n8n（03D）：模型可以选择已暴露的工具，但流程推进和结果衔接由工作流引擎负责 |
| `event_scheduling` 事件调度 | 任务内部的下一步由调度器根据到达的事件、计时器或队列决定，模型调用只是被调度的一个单元 | 主报告中暂未找到“任务内部由事件推进”的本地主入口例子。常驻网关（C02 OpenClaw、C10 NanoClaw，03C）是按事件**发起**任务，按本推荐法记入 F33／F34，F01 的主要入口按其每轮内部的循环记录 |

**主要入口的判定法**（混合结构时依次检查，命中即停）：

1. 用户在所选入口里不加任何额外命令或开关、直接描述任务时，框架走的那条路径。
2. 若默认路径本身是嵌套的（例如工作流节点里跑一个模型循环），取**最外层**持有“下一步”决定权的那一层。
3. 若两条路径都需要用户显式选择，取官方文档首页或快速开始介绍的那一条，并在 `value_note` 写明。

**子维度**：`secondary_modes`（集合，词表同 F01，不得包含主要入口本身；`in_distance: false`）。记录所选配置里默认可用、但不是主要入口的其他控制方式。例如 A17 Step Code（03A）的主路径是模型循环，workflow（受限脚本编排）默认注册、需按会话或单轮显式开启，记为 `secondary_modes: ["explicit_workflow"]`。

**控制图**：控制图属于第 6.2 节“架构图怎样变成数据”的图层，与本字段的类别值分开保存，不进入第一轮。若作者希望现在就留格式，建议最小形式为：节点 `{id, role}`（`role` 取 用户／调度器／模型循环／工作流引擎／事件源 之一），边 `{from, to, kind}`（`kind` 取第 6.2 节的 调用／事件／审批）。只有判定法第 2、3 步仍无法区分两条同等默认的路径时，才需要它。

**状态规则**：

- 已知存在：有文档或源码说明所选入口的默认控制路径。
- 已知不存在：不适用。F01 没有“无”类，任何能完成任务的配置都有某种控制方式。
- 未知：闭源且文档没说清默认路径，或入口与材料版本对不上（`version_unclear`）。
- 条件不适用：不适用。

### 备选

把 F01 改成**集合**，记录所选配置里存在的全部控制方式，按 Jaccard 计算。取舍：能完整表达混合结构，但会丢掉“谁是主要入口”这条最有区分力的信息；而且几乎所有终端代理都会同时含有用户驱动与模型循环，集合会把它们拉得过近。

另一种备选是保留类别，但把判定法改成“最外层的非人工调度者”，这样常驻网关的主要入口记为事件调度。取舍：能直接在 A 组把网关和终端代理分开，代价是与 F33／F34 重复计算同一差异（第 5.4 节要求避免）。

## F12 调用预算

### 缺口

报告要求“区分软提醒与强制截止”，但集合取值只能说“有哪些预算维度”，没有地方记录每一维是提醒还是截止。还没规定：只有用量显示算不算、默认关闭的上限算不算、服务端额度算不算。

### 推荐定义

**问题怎样问**：所选版本的 Harness **自身**能按哪些维度限制或提醒一次任务的模型调用用量？每一维到达阈值时，框架只是提醒，还是会停止？

**类型**：集合（可多选），不变。

**计入范围**：

- 计入：所选入口原生提供的设置项、命令行参数或始终生效的内部上限，不论默认是否打开；默认阈值写在 `value_note`。
- 不计入：只显示用量、不随阈值做任何动作的计数器；模型服务商或订阅一侧的限额；上下文窗口接近上限时触发的压缩（属于 D 组上下文管理）；需要用户自写脚本或扩展才有的上限。

| 取值 | 判定标准（一句） | 主报告例子 |
|---|---|---|
| `output_limit` 输出限制 | 框架为单次模型调用设定或传递最大输出长度，并处理达到限额的情况 | A10 Cline（03A）：运行时处理模型输出限额 |
| `total_tokens` 总 Token | 按一次任务（或子任务）累计的 Token 数设上限或提醒 | C01 Hermes Agent（03C）：子任务可以有自己的运行预算；具体是 Token 还是其他单位，编码时须核对源码 |
| `call_count` 调用次数 | 按模型调用次数、轮数或步数设上限 | H04 TRAE Agent 研究仓库（03D）：步数限制约束运行；D03 mini-SWE-agent（03D）：运行限制防止无限持续 |
| `time` 时间 | 按任务或单次调用的墙钟时间设上限 | 主报告中暂未找到本地配置的例子；保留报告原词表，遇到时直接使用 |
| `money` 金额 | 按估算或实际费用设上限或提醒 | D03 mini-SWE-agent（03D）提到终止原因可能是“预算耗尽”，是否以金额计须核对源码；托管产品的例子如 Replit 预算管理（B 类，03B），但不属于本地基线 |

**子维度**（都是 `value` 的子集，词表同 F12）：

| 子维度 | 含义 | 判定标准 | 是否进入距离 |
|---|---|---|---|
| `hard_stop` 强制截止 | 达到阈值时框架拒绝发出下一次调用、截断输出或结束任务 | 有源码或文档说明阈值触发停止或截断 | 是 |
| `soft_notice` 软提醒 | 达到阈值时只提醒用户或向模型注入提示，调用照常继续 | 有源码或文档说明阈值只触发提醒 | 否（作解释） |

一维可以同时出现在两个子集合（先提醒、再截止）。`value` 中某一维两个子集合都没出现，表示这一维的软／硬**未知**，须在 `value_note` 说明。A17 Step Code（03A）的“goal 保存目标与预算，本轮结束后继续”就是例子：主报告确认有预算，但没说明到达预算时是提醒还是停止，编码时要么找到源码证据，要么把这一维留在两个子集合之外。

**距离（供距离阶段采用）**：字段差异 = ½ × Jaccard(`value`) + ½ × Jaccard(`hard_stop`)，字段总权重不变。任一方有软／硬未知的维度时，后一半记为未知，保留其未知重量（第 7.3、8.2 节）。

**状态规则**：

- 已知不存在（`[]`）：所选版本的完整设置参考或配置模式（固定提交）里没有任何上述上限或阈值提醒。只看了 README 不足以写已知不存在。
- 未知：设置参考不完整、闭源、或材料版本对不上。
- 条件不适用：不适用。

### 备选

把词表扩成十项（`output_limit_hard`、`output_limit_soft`……），仍是一个集合。取舍：数据结构最简单、不需要子维度；但同一维的软与硬会被当成完全不同的两个取值，词表加倍，软／硬未知的情况也无处表达。

## F21 允许／拒绝规则

### 缺口

报告要求“记录默认规则”，没有给格式。也没说清：本字段记录的是规则**能表达什么**，还是**默认装了什么**；用户自写钩子算不算规则；“全部联网／全部断网”这种总开关算不算网络目标。

### 推荐定义

**问题怎样问**：所选版本里，用户或管理员能用**声明式规则**（配置项、规则文件、界面开关）按哪些维度允许、询问或拒绝代理的动作？默认装好时，这些维度上各是什么效果？

**类型**：集合（可多选），不变。取值记录规则语言能表达的维度。

**计入范围**：

- 计入：声明式规则、配置项和界面开关，包括只能整体开关的粗粒度规则（粒度写在 `value_note`）。
- 不计入：只能靠用户自写钩子或插件代码实现的检查（记入 F31 生命周期干预和 F23 应用检查）；写在规则文件、AGENTS.md 一类提示文本里的“不要做某事”（记入 F23 的 `prompt_instruction`）。

| 取值 | 判定标准（一句） | 主报告例子 |
|---|---|---|
| `tool_category` 工具类别 | 规则按工具名或动作类别（读文件、改文件、运行命令、调用 MCP 等）决定放行与否 | A14 Mistral Vibe（03A）：ask、accept-edits、auto-approve 等模式按“文件编辑”和其他动作分别处理；B05 JetBrains Junie（03B）：运行命令、调用 MCP 工具等敏感动作先确认，常用动作可写进允许列表 |
| `command_rule` 命令规则 | 规则匹配具体命令文本、前缀或模式 | A10 Cline（03A）：Plan 模式下 `rm`、`git commit` 这类命令会被拒绝，其他命令照常运行；A17 Step Code（03A）的规则检查分析命令内容 |
| `file_path` 文件路径 | 规则按路径或目录范围限制读写 | A16 Grok Build（03A）：默认的 workspace 档只把写入限制在工作区和少量必要路径；B05 Junie（03B）：读取项目外文件需确认 |
| `network_target` 网络目标 | 规则按主机、域名、地址或整体开关限制网络访问 | A16 Grok Build（03A）：read-only、strict 档在子进程层面断网（整体开关，`value_note` 注明粒度） |

**子维度：默认规则**（三个集合，词表同 F21，均为 `value` 的子集，`in_distance: false`）。只看所选配置的默认权限模式、用户没有添加任何规则时的效果：

| 子维度 | 含义 |
|---|---|
| `default_allow` | 这一维上有默认直接放行的动作 |
| `default_ask` | 这一维上有默认要先审批的动作；被拦下但可以申请放行的也算这里 |
| `default_deny` | 这一维上有默认拒绝、且没有审批通道的动作 |

同一维可以出现在多个子集合里。例如 A14 Mistral Vibe（03A）默认 accept-edits：文件编辑自动接受、其他动作询问，记为 `default_allow: ["tool_category"]`、`default_ask: ["tool_category"]`。默认规则的原文（例如具体命令前缀、路径）写进 `value_note`，并附固定提交的源码或文档证据。

**距离**：基线只比较 `value`（规则表达力）。默认规则随版本变化快（第 2.1 节的 Claude Code 例子），且已写进配置记录的 `permission_mode`，只在“默认安全姿态”敏感性分析里使用三个子集合。

**状态规则**：

- 已知不存在（`[]`）：所选版本没有任何声明式允许／拒绝规则，例如只有“全部询问／全部放行”而不能按维度区分。A09 Pi（03A）“默认没有内置系统权限限制”，按所选核心配置大概率属于此类，但需看扩展是否默认启用。
- 未知：只找到功能介绍、找不到规则格式或默认值。
- 默认规则三个子集合可以单独为 `null`（默认值未知），不影响 `value` 的状态。
- 条件不适用：不适用。

### 备选

`default_rules` 记成规则对象列表，每条 `{dimension, effect: allow|ask|deny, pattern, source}`。取舍：保留规则原文，便于审计与复查；但需要新的对象类型，不同工具的规则写法差异大，难以直接比较，第一轮只能当作记录、不进距离。

## F22 审批层

### 缺口

报告要求“审批 UI 与强制执行点分别核查”，字段只有一个集合。三层的边界也没写清，尤其是“工具调用”和“具体操作”怎样区分，以及分类器或规则自动批准算不算审批。

### 推荐定义

**问题怎样问**：在所选配置的默认权限模式下，框架会在哪一层**停下动作、等待批准**（强制执行点）？批准请求在界面上以哪一层呈现给用户？

**审批**指框架在动作执行前暂停，直到批准者放行；批准者可以是用户，也可以是配置中的规则、钩子或分类器，批准者写在 `value_note`。默认模式下什么都不拦（全自动），取值为已知空集合。

**类型**：集合（可多选），不变。**取值记录强制执行点所在层**。

| 取值 | 判定标准（一句） | 主报告例子 |
|---|---|---|
| `whole_task` 整个任务 | 一次批准覆盖整项任务、计划或子任务，之后其中的动作不再逐个拦截 | B05 JetBrains Junie（03B）：计划模式先只读探索，用户确认计划后才开始修改；A10 Cline（03A）：批准一次 `spawn_agent` 就放行这个子代理之后的全部操作 |
| `tool_call` 工具调用 | 按工具身份或类别触发，每次调用该类工具都要批准，与参数内容无关 | A01 Claude Code（03A）手动模式逐项询问；A14 Mistral Vibe（03A）的 ask 模式 |
| `specific_operation` 具体操作 | 按调用内容触发，只有特定命令、路径、网络目标、越出沙箱的请求或被判为有风险的动作才要批准 | A01 Claude Code（03A）默认 auto 模式由分类器审核大多数动作、拦下有风险的；A02 Codex（03A）由策略判断决定命令走哪条路径，需要审批时才向客户端请求决定 |

**子维度**：`ui_layers`（集合，词表同 F22，`in_distance: false`）。记录批准请求在界面上呈现的层。与取值不一致的典型情形：

- 界面有批准、执行点没有真正拦住：例如托管产品 B20 Google Jules（03B）的网页计划确认，离开页面后会计时自动批准；只记入 `ui_layers`，不记入取值（本例为托管产品，只作说明）。
- 执行点拦住、但不经界面：规则或分类器自动放行／拒绝；A01 Claude Code（03A）的插件 mod 可以先于询问批准或拦下调用。记入取值，`ui_layers` 不含该层。

**距离与字段数**：

- 推荐方案（一个字段 + 子维度）：码本仍是 36 个字段，F 组四个字段各占组内 1/4；基线距离只用取值（执行点）的 Jaccard，`ui_layers` 用于解释和敏感性分析。
- 若拆成两个字段 F22a（界面所在层）与 F22b（执行点所在层）：码本变为 37 个字段，模板、比较脚本与测试都要改。按第 5.1 节，F 组总权重仍为 1/9；若组内等分，F21、F23、F24 各自从组内 1/4 降到 1/5；若让两个子字段平分原 F22 的份额，则各占组内 1/8。两者在多数工具上取值相同、总是一起变化，第 5.4 节提醒这会重复计算同一机制，所以不推荐拆分。

**状态规则**：

- 已知不存在（`[]`）：有证据表明默认模式下任何动作都不需要批准，例如 A09 Pi（03A）默认没有权限系统。
- 未知：文档只说“有审批”，没说明触发条件和执行位置。
- `ui_layers` 可以单独为 `null`。
- 条件不适用：不适用。

### 备选

拆成两个独立字段（见上）。取舍：两层都进入距离、比较最直接；代价是字段数和组内权重变化，且两层高度相关，会把同一差异算两次。

## F23 约束执行机制

### 缺口

报告词表以“等”结尾，封闭词表未定。还要求“提示模型不要做”另记，但没有给位置。

### 推荐定义

**问题怎样问**：在所选配置的默认模式下，限制代理动作的约束**实际由什么机制强制执行**？只记录默认生效的机制；可选开启但默认关闭的写在 `value_note`。

**类型**：集合（可多选），不变。**封闭词表**：在报告原有三项之外只加一项“运行时沙箱”，因为主报告已有多个默认生效的本地例子；其他机制先进 `vocabulary_proposals`。

| 取值 | 判定标准（一句） | 主报告例子 |
|---|---|---|
| `application_check` 应用检查 | Harness 自己的代码在执行前判断并放行或拒绝（权限引擎、规则匹配、钩子或插件拦截、分类器） | A02 Codex（03A）：策略判断决定命令走哪条路径；A17 Step Code（03A）：规则检查，主报告提醒它分析不了所有程序内容，也不是操作系统沙箱 |
| `os_isolation` 操作系统隔离 | 用操作系统机制限制进程能接触的文件、网络或系统调用（如 Seatbelt、Landlock、bubblewrap、seccomp），对子进程同样生效 | A16 Grok Build（03A）：macOS 上用 Seatbelt、Linux 上用 Landlock，覆盖代理进程及其子进程；注意主报告所引快照中沙箱默认关闭，按默认配置不应记入 |
| `container_policy` 容器策略 | 代理或其命令在容器里运行，靠挂载、网络与用户设置限制可见范围 | C10 NanoClaw（03C）：代理以非 root 用户在容器里运行，只看得见显式挂载的目录 |
| `runtime_sandbox` 运行时沙箱（新增） | 代码在受限的语言运行时（如 WebAssembly 版 QuickJS、受限解释器）里执行，运行时本身没有直接的文件、进程或网络能力 | A06 MiMo Code（03A）：QuickJS 执行组合工具的脚本；A17 Step Code（03A）：workflow 脚本在 WebAssembly 版 QuickJS 中运行，默认注册 |

`runtime_sandbox` 只约束脚本本身；脚本转而调用的宿主工具仍按其他机制管理，主报告对 A06、A17 都强调“脚本受限不等于宿主隔离”。编码时必须在 `value_note` 写明它覆盖哪些动作。

未收入的候选：**本地虚拟机**。主报告里的虚拟机例子（B20 Google Jules，03B）是云端短时虚拟机，不属于本地基线；A09 Pi（03A）只建议用户自行选用容器或虚拟机，不是原生机制。遇到原生的本地虚拟机隔离时写进 `vocabulary_proposals`，修码本时再收。

**子维度**：`prompt_instruction`（类别：`present` 有／`absent` 无，`in_distance: false`）。记录系统提示或默认规则文件里是否要求模型避免某类操作。报告第 4.7 节说明它只影响模型选择，不能强制阻止，所以不进取值、不进距离。

**距离**：基线对取值算 Jaccard。不对机制排强弱顺序（第 5.3 节：不设“安全等级”）。

**状态规则**：

- 已知不存在（`[]`）：默认模式下没有任何强制机制，动作以启动用户的权限直接执行，例如 A09 Pi（03A）“工具和扩展按启动进程的权限运行”。
- 未知：只知道“有沙箱”，不知道是哪种机制或默认是否生效。
- `prompt_instruction` 可以单独为 `null`。
- 条件不适用：不适用。

### 备选

保持报告原有三项，`runtime_sandbox` 一类先全部走 `vocabulary_proposals`，第一轮比较后再决定收不收。取舍：最忠于报告原文；但 A06、A17 这类默认生效的脚本沙箱会被两位编码者分别塞进 `application_check` 或写成提议，人为制造分歧。

## 需要作者拍板的取舍

1. F01 是否采用“任务开始后谁决定下一步”的判定法，把常驻网关的事件差异全部交给 F33／F34（推荐），还是让常驻网关在 F01 记为事件调度（备选，会重复计算）。
2. F12 的计入范围是否包括“有设置项但默认关闭”的上限（推荐计入，默认阈值写说明），以及距离里 `hard_stop` 是否占字段的一半。
3. F22 是否接受“批准者可以是规则或分类器”，以及“工具调用”与“具体操作”按“触发条件是工具身份还是调用内容”来区分。
4. F23 是否现在就收入 `runtime_sandbox`。
5. 是否同意用 `facets` 子维度（码本升为 `fields-0.2`）而不拆字段；第一轮编码是否先按同名标记写进 `value_note`。
