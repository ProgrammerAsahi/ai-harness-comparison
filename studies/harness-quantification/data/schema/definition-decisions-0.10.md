- 依据：第五批正式编码（`batches/batch-5.md`）的交叉核对、“口径疑问”表和表后五处词表缺口，另有五份按字段分组整理的口径材料（Claude Sonnet 5.5 整理；原始疑问由 Qwen4-Max 从第五批记录里摘出；只作参考，不入库）。材料共拆出 124 条疑问，判为“现行条文已答”62 条、“没覆盖”53 条、“条文冲突”5 条、“词表缺口”4 条（其中 2 条重复，实际是 2 处缺口）。那一批按 `fields-0.9` 编十二个以前没编过的配置，432 个字段×配置里 299 个一致（69.2%），和第四批（70.0%）几乎相同。分歧集中在三处：闭源配置“文档说到什么程度可以推断”（44 条“材料不足”里 43 条是一方推断、一方记未知）；F04 出错处理（一致率 25%）；借同一产品其他形态的文档。
- 范围：这是一次小修订，只动总则 R2、R3、R5、R6、R7、R10 的个别句子和若干字段的判定句，字段的问题和类型都不变。词表没有追加取值，已有的取值编号都没有动。
- 决定：维护者在第五批记录和轮后核对写完后写了一份修订草案：八条列出推荐案和另一案请项目负责人逐条定（第一节），十七条较窄、或只是把现行读法写明的按推荐直接写入（第二节），说明词表为什么不加（第三节），另列这次不动的疑问（第六节）。负责人 2026-11-23 答复全部按推荐：八条都取推荐案，十七条照写，词表不加。

## 一、请负责人定的八条


### 1. R5、R6：所选入口的文档说“和另一形态共用”时，能不能借那一形态的文档

- 情况：五个配置都碰到。B03 的文档写本机代理和命令行版共用代理外壳，两人都借了命令行文档（低把握），牵动 F02、F04、F07、F12–F14、F17–F19、F24 等，甲写明“借其他形态证据的口径待定”；抽查也指出 B03 F04 的代码检查回传出自命令行文档。B19 的 F13、F18、F19、F30 借了 Chat 页（文档说两者共用后端）。B08 F15 借了同一产品上下文引擎的另一节文档。B14 桌面版钩子页说兼容命令行的事件和处理器类型、并指向命令行钩子页，一人借来判阻断能力，另一人写“严格按 R6 应改 null”。B12 概览页说“所有形态共用同一代理外壳”，两人据此认定 SDK 满足 R5 构件库的第二个前提。现行 R6 只说“标明属于其他形态（桌面版、网页版）的条目不借”，例外只有“官方 SDK 文档明说它驱动的就是本配置这个程序或同一个执行核心的”；0.9 写进 R5 的“单独安装、自带完整界面的官方程序是另一种形态”管的是 F29、F31–F33 的入口范围，没说借证据。
- 推荐（已采纳）：可以借，但限在文档明说共用的那个部件。所选入口自己的官方文档明说某个部件和另一形态或同一产品的另一功能共用（叫法是同一个执行核心、代理外壳还是后端都算），又没说这一方面两边不同的，另一方文档里关于这个部件行为的说明可以作推断依据，confidence 为 low，value_note 写“借自：”和出处。各形态可能分别设置的默认值（权限模式、默认开关、默认型号、预置内容）不借；入口范围仍按 R5，不因共用核心把另一形态的入口算进来。R5 构件库的“同一套代理循环”，文档说成同一个执行核心或代理外壳的同样算。理由：R6 已经允许凭 SDK 文档“同一个执行核心”一句推断，同样的话出现在所选入口自己的文档里，证据更直接，没有理由更严；限在部件行为、不借默认值，是因为形态之间最常不同的正是默认设置。
- 没有采纳：照现行 R6 字面，除 SDK 一句外一律不借，所选入口文档没写的记未知。它最省判断；代价是 B03 十来个字段、B19 四个字段转未知，而且所选入口文档自己说了“共用”，却不能用，和 SDK 那一句的宽严不一致。
- 已知的代价：借来的说明可能和所选入口的实际行为有出入；“借自”标记让以后能单独回查这些格子。
- 第五批会改判（推测，未回查）：B03 两人借的格子保留，逐格回查是不是默认值一类（是的改未知）；乙 B03 F04 补 `model_self_repair`。B19、B08 借的格子保留。B14 F31 不借的一方由 null 改照钩子页记。B12 F32 `library` 和 F29、F31 的 SDK 回调保留，两人各计一个钩子的按现行 R5“按构件库整体判”补齐。
- 写入：`general_rules[R6].rule` 在“……可以作推断依据。”之后追加：“单独安装、自带完整交互界面的官方程序也是另一种形态（总则 R5）。所选入口自己的官方文档明说某个部件和另一形态或同一产品的另一功能共用（同一个执行核心、代理外壳或后端，叫法不论）、又没说这一方面两边不同的，另一方文档里关于这个部件行为的说明也可以作推断依据，value_note 写‘借自：’和出处；各形态可能分别设置的默认值（权限模式、默认开关、默认型号、预置内容）不借，入口范围仍照总则 R5。”`general_rules[R5].rule` 里“官方文档明说它运行的是本产品的同一套代理循环”之后补“（文档说共用同一个执行核心或代理外壳的同样算）”。

### 2. R6：几个常被问到的取值，“关键条件”各是什么

- 情况：0.9 把门槛写成“文档那段话说到了所选取值判定句的关键条件”，两人对“说到”仍读得不同：第五批 44 条“材料不足”里 43 条是甲推断、乙记未知或疑似，读者说明里 47 条引了 R6。材料把多数归为“现行条文已答”，但同一类问题在第三、四、五批反复出现（F10 三批问了三种线索），说明光有通则不够。下表是第五批具体问到的几个取值。
- 推荐（已采纳）：在这几个取值的判定句或未知规则里写明闭源时算不算说到：

| 取值 | 算说到 | 不算 | 涉及 |
|---|---|---|---|
| F04 `model_self_repair` | 文档写明工具或命令的报错交回代理，或代理据报错自行修正再试 | 只说“能从错误中恢复”，或把错误显示给用户 | A18、B03、B07、B08 |
| F06 位置 | （维持现行两句） | 只说工具“在你的本机或终端里运行”、没说由程序自身还是另起进程执行的，按现行第二句把 `main_process` 写进 unresolved | B08、B15、B16、B14 |
| F10 `native_structured` | 文档写明走模型接口的函数或工具调用字段 | 只有错误码、参数模式、工具清单 | A18、B07、B11、B16、B19 |
| F13 `sequential_messages` | 文档说对话历史逐轮累积进请求、只在接近窗口时压缩（不要求字面写“每轮发送完整历史”） | 只说“记得上下文”“理解对话” | B07、B15、A18、B16、B14、B12 |
| F27 `shared_files` | 文档写明子代理在同一工作区或项目目录里读写、默认不隔离（隔离是可选开关、默认关的也算） | 只说子代理“能读写文件”，没说在哪 | B07、B08、B14、B15、B16 |
| F27 `start_context` | 写明子代理收到父代理写的任务说明，记 `task_brief` | 只说“把任务委派给子代理”，写 null | 同上 |
| F30 `skill_directory` | 文档说技能按名称或描述在需要时装载；存放目录没写不影响 | 只有技能名或“支持技能” | B19 |

  取舍的理由：一个取值和相邻取值的分界在哪，关键条件就在哪。F04、F13、F27 `shared_files`、F30 的宽读法，说到的正是区分这一项的那件事；F06、F10、`start_context` 的严读法，是因为文档那句话分不开相邻的几项（本机运行分不出主进程和子进程，参数模式分不出原生调用和文本解析，“委派任务”分不出任务说明和复制父对话）。F30 不要求目录，和 0.8 第一节第 6 条“按机制不按存放介质”一致。
- 没有采纳：不写进码本，只在编码说明卡里给例子。码本更短；代价是第三到五批的经验说明，说明卡里的提醒编码者常读不到（F35、F23 写进说明卡后本批仍有人问）。
- 已知的代价：表里每一行都是一次宽严选择，负责人可以逐行改；宽的几行会让闭源配置多出一些低把握的取值。
- 第五批会改判（推测，未回查）：宽的几行，乙记未知或“文档未涉及”的格子回查后多半补成取值；严的几行，甲凭错误码、本机运行、“委派任务”推断的格子退回未知、unresolved 或 null。B19 F30 严读的一方由疑似改记取值。
- 写入：`fields[F04].vocabulary[model_self_repair].criterion` 追加“闭源配置的文档写明报错交回代理、或代理据报错自行修正再试的，算说到这一项（总则 R6）；只说能从错误中恢复或把错误显示给用户的，不算”；`fields[F06].definition.scope_rule` 在“……把 main_process 写进 unresolved”之后补“（只说工具在用户本机或终端里运行、没说由谁执行的，也是这种情况）”；`fields[F10].definition.unknown_rule` 追加“错误码、参数模式、工具清单只算线索，要文档写明走模型接口的函数或工具调用字段才记 native_structured”；`fields[F13].definition.unknown_rule` 在“文档明确说明每轮发送完整对话历史的”之后补“（或说对话历史逐轮累积进请求、只在接近窗口时压缩的）”；`fields[F27].vocabulary[shared_files].criterion` 追加“闭源配置的文档写明子代理在同一工作区或项目目录里读写、默认不隔离的，算说到这一项（隔离是可选开关、默认关着的也算）；只说子代理能读写文件、没说在哪个目录的，不算”；`fields[F27].facets[start_context].rule` 在“查不到写 null”之前补“文档只说把任务委派给子代理、没说子代理收到什么的，算查不到”；`fields[F30].vocabulary[skill_directory].criterion` 追加“按名称或描述按需装载是这一项的关键条件；存放目录文档没写的，不影响记本项，value_note 写明”。

### 3. R1、R3：框架弹出建议、用户点一下就进入配置记录定为另一入口的模式

- 情况：C04 在第一轮弹出“建议进入工作模式”的卡片，点一下就开放 MCP、技能和命令执行。R3 第一档说“框架自己给出、用户只点选”的路径算默认；配置记录（负责人确认过）写明工作模式是另一入口、不取。两人都按记录编，一致率 97%，都写明若算默认，F21–F24、F29、F30、F36 等要重编。材料判为条文冲突。第二批“安装末尾提示立即启用”是同一类，当时没有答复。
- 推荐（已采纳）：配置记录定下的入口优先（R1）。R3 第一档那一句只管所选入口之内、框架在超时、超限一类时刻给出的选择；框架建议、用户点选后进入的是记录定为另一入口的模式的，仍算另一入口，进入后才有的机制写“可选：”。负责人若认为这个模式其实该算所选入口的一部分，改配置记录，不改码本。（11-23 轮后核对已在 C04 记录的入口一项补写建议卡片两个按钮的效果，入口仍取聊天模式。）
- 没有采纳：按 R3 第一档算默认，路径里的机制计入，写“需用户点选”。代价是任何框架弹出的引导都能越过配置记录划的入口界线，R1 让记录决定入口的意义就没了；C04 要重编七八个字段。
- 第五批会改判（推测，未回查）：不改判。
- 写入：`general_rules[R3].rule` 在“……value_note 写明‘需用户点选’。”之后追加：“这一句只管所选入口之内的路径；框架建议、用户点选后进入的是配置记录定为另一入口的模式的，仍按总则 R1 算另一入口，进入后才有的机制写‘可选：’。”

### 4. R2 对 F11、F23：要用户往扩展点里加内容才有的“默认”

- 情况：F11 一致率 42%。用户往默认开放的目录里加一个写了型号的子代理定义，`per_role` 算不算开放：甲在 B08、B15 按 R2“添加内容”记了 `per_role`，在 A18、B14 又按“可选”处理，自己前后不一；乙这几处多记未知。B08 甲写明“建议码本对 F11 是否适用 R2 写明”。B08 F23 的权限规则引擎默认在运行、但一条规则都没有：甲按添加内容记 `application_check`，乙记未知；第三批 Agent Zero“默认全放行、用户加禁止项才拦”同一问题，没有答复。另一面，抽查指出 B14 的 F26、F28（钩子派生核验子代理）也只靠 R2 的添加内容成立。
- 推荐（已采纳）：R2 照旧，F11、F23 按字段自己的“默认”判，写成字段例外（F06 已有同样的例外句“本字段不按总则 R2 的扩展点口径”）。F11 只看默认安装后已有的角色和它们默认解析到的型号；用户自己加的子代理或角色定义里写的型号，写“可选：”。这和 `per_role` 判定句末句“角色路由存在、但默认解析到同一型号的，不记，写‘可选：’”方向一致，但那句管的是默认解析结果，没直接说用户自己加的定义，所以要另写一句。F23 里默认一条规则都没有、什么都不拦的规则引擎，算保护本身默认关闭，写“可选：”，它支持的规则种类照常记在 F21。其余字段仍按 R2，B14 的 F26、F28 照现在记，和 0.9 第一节第 1 条（用户接上的部件算添加内容）一致。
- 没有采纳：R2 一律适用，F11、F23 也算。代价是凡允许在自定义子代理里写型号的产品都记 `per_role`，F11 分不出谁真的按角色分配型号；F23 把一条规则都没有的引擎记成“已在起作用的检查”，和 F23“发生时机制已在起作用”的问法相反。
- 第五批会改判（推测，未回查）：甲 B08、B15 的 F11 去掉 `per_role`（B15 的 `per_request_routing` 不受影响，B08 按内置角色回查）；甲 A18、B14 本来就按“可选”，不变。B08 F23 甲去掉 `application_check`，其余回查。第三批 Agent Zero 的 F23 回查。
- 写入：`fields[F11].definition.scope_rule` 追加“本字段不按总则 R2 的扩展点口径：只按默认安装后已有的角色和它们默认解析到的型号记；用户自己添加的子代理或角色定义里写的型号，写 value_note‘可选：’”；`fields[F23].definition.scope_rule` 追加“规则引擎默认在运行、但默认没有任何规则、什么都不拦的，算保护本身默认关闭，写‘可选：’；它支持的规则种类记在 F21”。

### 5. F04：失败后留下可恢复的任务、但没有专门提示，算不算转交给人

- 情况：F04 是第五批一致率最低的字段（25%，交叉核对 17 条），四个配置的疑问落在同一条界线上。B11 任务可恢复、框架不主动给出待答提示，读者指出 `escalate_to_human` 判定句（“留下……可恢复的任务状态……记本项”）和范围规则的不计入句（“失败后只把错误显示给用户、结束本轮交还控制权、用户要自己重新发消息说明任务的”）都能套，后一句三项是并列还是都要满足也没写，材料判为冲突。C04 的“从最后的工具步骤重试”和重新生成按钮的界线（两人都记了 `escalate_to_human`，一人请复核）；B16 再试一次是否带原历史；B14 额度用尽算不算失败。第二、四批都问过重试按钮。
- 推荐（已采纳）：以“框架有没有为这次失败留下专门的恢复入口”为界。错误处的重试或继续按钮、恢复命令、标为受阻可恢复的任务都算；用户点选或执行后带原历史从失败处接着走、不必重述任务的，记 `escalate_to_human`。只结束本轮、用户要发一条普通消息（重新说明任务，或只说“继续”）模型才凭历史接着做的，不记；对任何回复都有的“重新生成”不算专门入口。服务商额度用尽时框架暂停任务、用户补足额度或换账户后从原请求接着走的，比照认证失效记本项；只显示错误的不记。
- 没有采纳：只有框架主动弹出待答的选择或询问才记，常驻按钮和无提示的可恢复任务都不记。界线更好查；代价是 C04 两人一致的 `escalate_to_human` 要去掉，而“错误处的重试按钮”和“弹出重试还是放弃”对用户是同一件事。
- 第五批会改判（推测，未回查）：C04 不变；B11 两人都没记，除非回查找到专门入口，不变；B14、B16 按是否带原历史接着走回查。
- 写入：`fields[F04].definition.scope_rule` 的不计入句改为“不计入：失败后只把错误显示给用户、结束本轮交还控制权，用户要发一条普通消息（重新说明任务，或只说‘继续’）模型才接着做的”；`fields[F04].vocabulary[escalate_to_human].criterion` 追加“框架为这次失败给出的专门入口（错误处的重试或继续按钮、恢复命令、标为受阻可恢复的任务）算留下待答的选择或可恢复的任务状态；对任何回复都有的重新生成按钮不算。服务商额度用尽后框架暂停任务、用户补足额度或换账户后从原请求接着走的，比照认证失效记本项”。

### 6. F09：厂商托管的云端后端算不算统一网关

- 情况：F09 一致率 50%。B03、B08、B11、B15 的客户端都只对厂商自己的云端后端说一种协议，由后端转给多家模型。甲四处都记 `protocol_gateway`，写明“码本的例子是本机网关，这里是厂商云端服务，按‘独立进程或服务形式’判”，并建议码本写明；乙在 B11（客户端开源）也记 `protocol_gateway`，在三个闭源配置记未知。第四批 B04 问过同一问题，0.9 第六节列为“只出现一次”，现在第二次出现、涉及四个配置。
- 推荐（已采纳）：算。核心只对一个统一后端说一种协议、由它转给多家模型提供方的，不论后端在本机还是厂商云端，都记 `protocol_gateway`，value_note 写“厂商云端”；后端只转给一家的，按核心说的协议判。闭源配置的文档写明可选多家提供方的型号、而调用都经厂商服务（本配置不配各家密钥）的，算说到了这一项的关键条件。理由：`protocol_gateway` 判定句写的是“独立进程或服务形式”，没限本机；F09 问的是核心和模型之间隔着几种协议，网关托管在哪一方不改变这一点。
- 没有采纳：网关只限本机或用户能自部署的进程，厂商托管的后端记 `vendor_sdk`。代价是 `vendor_sdk` 的“其他后端要提供兼容端点”套不上厂商后端，F09 就从“几种协议”变成“部署在哪”。
- 第五批会改判（推测，未回查）：B11 不变；乙 B03、B08、B15 由未知改 `protocol_gateway`（回查文档是否写明可选多家型号）。第四批 B04 回查。
- 写入：`fields[F09].vocabulary[protocol_gateway].criterion` 追加“网关可以是厂商托管的云端服务：核心只对它说一种协议、由它转给多家模型提供方的，也记本项，value_note 写‘厂商云端’；它只转给一家的，按核心说的协议判。闭源配置的文档写明可选多家提供方的型号、而调用都经厂商服务的，算说到了这一项的关键条件（总则 R6）”。

### 7. F21：同一类动作有几条并列的路径，默认效果取哪一条

- 情况：第二、三、五批都问过。A18 写工作区外的文件有两条路：文件工具限在工作区内、直接拒绝；终端命令先被沙箱拦下，再申请一次沙箱外运行。甲取 `review`，乙取 `deny`。现行规则“要过几道关时记最严的一道”说的是同一路径上先后的几道关，没说并列路径。0.9 第四节保守读法第 3 条“写文件工具拒绝工作区外路径记 `deny`”管的是“有工具被拒”和“没有工具”的分界，没涉及并列路径。
- 推荐（已采纳）：取能让这个动作发生的最宽一条（`allow` 宽于 `review`，`review` 宽于 `deny`），其余路径写 value_note。理由：子维度问的是“写工作区外的一个文件会怎样”，只要有一条路经批准就能写成，这个动作的默认效果就是“先过批准者”；`review` 判定句本来就含“被拦下后可申请放行”。0.9 的例子照旧成立：别的路径也都拒绝时仍记 `deny`。
- 没有采纳：取专门做这类动作的工具（写文件取文件编辑工具，命令取终端工具）。它和 0.9 例子的字面最贴近；代价是文件工具限得严、终端能绕过去的产品会记成 `deny`，低估了动作实际能不能发生。
- 第五批会改判（推测，未回查）：乙 A18 `default_outside_write` 由 `deny` 改 `review`。第二、三批的 Avante.nvim、Gemini CLI 回查。
- 主控复核补注：0.9 保守读法第 3 条（负责人 11-22 同意）的例子出自第三批 A03 Gemini CLI，而第三批疑问表里 Gemini CLI 正是“几条写工作区外的路径并存”的配置之一，两人当时都按文件工具记了 `deny`。所以推荐案虽不改那句条文，却很可能让它的来源配置本身改判为 `review`；另一案（取专门工具）和第三批的记法一致。维护者在请负责人定之前补了这一条；负责人知悉后仍取推荐案（2026-11-23）。
- 写入：`fields[F21].definition.scope_rule` 追加“同一类动作有几条并列路径（例如写文件工具和终端命令都能写工作区外的文件）时，四个默认效果取能让动作发生的最宽一条（allow 宽于 review，review 宽于 deny），其余路径写 value_note；‘记最严的一道’只管同一路径上先后要过的几道关”。

### 8. F16：一条一句话、能逐条增删的记忆，归 `structured_records` 还是 `auto_summary`

- 情况：第二、三、五批都问过，0.8 第五节留着没定。B11 的规则库条目由框架建议、用户点选保存，甲记 `auto_summary`，乙记 `structured_records`；读者指出它同时命中两项，按 R8 词表先后会取靠前的 `auto_summary`。C04 的记忆工具存的是自由文本还是事实条目，两人都记了 `auto_summary`，一人拿不准。第三批 Agent Zero、Open WebUI 的条目带编号、时间、分类，正文仍是自由文本。
