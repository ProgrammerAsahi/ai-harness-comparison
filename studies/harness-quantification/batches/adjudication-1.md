# 裁决轮 adjudication-1 记录（两位编码者的分歧逐项裁决）

这一轮不编新配置。它把 52 个配置最新一轮编码里两位编码者判得不同的字段逐项裁决，定一个取值，再用裁决后的编码重算结构距离。这一页记录做法、结果，以及这些结果能说明什么、不能说明什么。复算：

```bash
python3 studies/harness-quantification/adjudicate.py check
python3 studies/harness-quantification/trial_distance.py
```

第一条校验 `data/adjudications/` 里的裁决记录，确认它们对得上现行编码和码本；第二条在三种编码口径之外，多算一种“裁决后”口径（见 [`cross-batch.md`](cross-batch.md)）。

**裁决后的编码仍不是结果。** 裁决只回答“按现行码本，这一处两位编码者谁读得对”，不改两人本来就一致的字段，也不补两人都漏看的事实。各配置的编码仍分别按 `fields-0.5` 到 `fields-0.10` 填写，十四个配置只有官方文档。距离不是对任何工具的评分，也不进入方法报告正文；报告第 7、8 节仍只用合成示例。

## 怎样做的

- **对象**：每个配置取最新一轮编码（和距离试算相同）。52 个配置里 51 个有分歧，D03 mini-SWE-agent 没有分歧，不需要裁决。只裁决 `compare_codings.py` 判为不一致的字段（状态或取值不同），共 366 个，每个配置 1 到 13 个，开源配置平均 5.9 个，闭源配置平均 10.6 个。附属的子维度不裁决。
- **码本**：按现行码本 `fields-0.10` 裁决，即使这个配置当初按更早的版本编码。这样两人一致的字段保留旧版码本下的读法，只有分歧字段按现行码本重判。这是这一轮最主要的局限之一，见文末。
- **盲读**：`adjudicate.py prepare` 给每个配置生成隐去编码者身份的材料，两位编码者按随机顺序显示为“甲”“乙”，对应表只有主控看得到。任务卡只列四样材料：两份编码里有分歧的字段、配置记录、现行码本、这个配置的资料快照（源码快照、文档导出、发行说明），并要求不读仓库里别的文件，所以读者不看批次记录、交叉核对和码本修订的决定记录。材料不够确认任何取值时，按码本的未知规则判，一方写了未知就选那一方。
- **两位读者**：每个配置由两位读者各自独立裁决，互不可见。每个字段从甲、乙中选一个，或者两个都不对时自己给出取值（记为“都不对”），附上理由和证据位置。
  - 读者一用 Claude 以外的模型，经作者的编排器派发：MiMo V2.6 Pro 37 个配置，Gemini 4 Neon 11 个，Qwen4-Max 3 个（逐个配置的型号写在各裁决记录的 `readers` 里）。
  - 读者二是 Claude Opus 5.5，由主控会话派发。
- **第三读者**：两位读者的状态和取值相同，这个字段就定下来。不同时，交第三读者（Claude Opus 5.5，由主控会话派发）。第三读者另外看到两位读者在这些字段上的选择、理由和证据位置，按随机顺序显示为“读者一”“读者二”，看不到哪位读者用的是什么模型，也看不到编码者身份。
- **主控统一**：不同配置的读者对同一类事实用了不同读法时，由主控统一，写成 lead 条目，覆盖读者的结论；第三读者的选择仍留在记录的 `picks` 里。统一前先由一个 Claude Opus 5.5 子代理把 13 类读法问题在全部 51 个配置上逐一对照，主控审核后决定改哪些。
- **负责人认可的读法**：2026-11-25 负责人认可了四条码本没写清的读法：
  1. 循环定时任务的 7 天到期，不算 F03 的预算上限，也不算 F12 的时长上限。
  2. 只包装子进程的官方 SDK，F32 按它背后的边界记，不另记 `library`。字段条款优先于总则 R5 关于官方构件库的一句。
  3. F21 里，经字典透传、没有点名的参数不算。
  4. 共用外壳的说法只出现在另一个条目的页面上时，不按总则 R6 借用。
- **记录**：每个配置一份 `data/adjudications/<config_id>.json`，逐字段写最终状态和取值、选了哪位编码者（或“都不对”）、由谁定下（`readers_agree`、`third_reader`、`lead`）、各读者的选择、理由和证据位置。`adjudicate.py check` 校验取值合乎码本词表、和编码对得上。
- **时间**：2026-11-24 开始，2026-11-27 完成；记录里的日期统一写完成日。
- 都只读公开资料，不安装、不运行被研究的工具。

## 重算距离

做法和 [`cross-batch.md`](cross-batch.md) 相同，多一种“裁决后”口径：两人一致的字段保留原读法，不一致的取裁决结果。门控代价 0.75。

| | `opus` | `gpt` | 两人一致 | 裁决后 |
|---|---|---|---|---|
| 覆盖率中位数（全部 1326 对） | 97.2% | 88.9% | 58.3% | 94.4% |
| 覆盖率中位数（两个闭源之间） | — | — | 38.9% | 77.8% |
| 上下界宽度中位数 | — | — | 0.417 | 0.056 |
| 平均距离：开源之间 / 混合 / 闭源之间 | 0.438 / 0.420 / 0.292 | 0.447 / 0.437 / 0.308 | 0.402 / 0.386 / 0.224 | 0.440 / 0.424 / 0.290 |

- **排序**：裁决后口径的距离排序和 `opus` 的相关 0.972，和 `gpt` 0.943，和两人一致口径 0.918。两个闭源配置之间分别是 0.867、0.728、0.731。
- **近邻**：每个配置最近的三个邻居，裁决后口径和 `opus` 平均共有 1.94 个，和 `gpt` 1.81 个。两位编码者之间是 1.54 个。

## 能说明什么，不能说明什么

- 裁决把已知部分从两人一致时的约六成补到九成以上，上下界从 0.42 收窄到 0.06。距离要连同覆盖率读的要求不变：两个闭源配置之间仍有约两成权重未知。
- 大格局在裁决前后不变：闭源配置彼此更近、同批配置更近、分叉和同组织工具彼此最近，都和裁决前相同。裁决没有解释这两个现象，只是排除了“只是两人分歧造成的”这一种可能。
- **同型号偏向**：读者二和第三读者都是 Claude Opus 5.5，和编码者 `opus` 是同一型号。裁决后的距离和 `opus` 更接近（0.972 对 0.943），最终取值也更多落在 `opus` 一方（55.5% 对 39.6%）。用非 Claude 模型的读者一，两边选得接近（182 对 166）；第三读者在分歧时三分之二和读者二站在一起。所以裁决结果可能偏向 `opus` 的读法，这一轮的数据分不开“`opus` 本来读得对”和“同型号读者更认同同型号编码者”这两种解释。下一轮若再裁决，第二读者和第三读者宜至少有一位换成另一家的模型。
- **码本版本混用**：两人一致的字段保留各自旧版码本下的读法，只有分歧字段按 `fields-0.10` 重判。同一份裁决后编码里混着两种口径。要得到干净的距离表，仍需全部配置按同一版码本重编、再裁决（[`cross-batch.md`](cross-batch.md) 下一步第 2 条）。
- **子维度没有裁决**：例如 A06、A16 的 F12 已按第 1 条去掉 `time`，但附属的 `hard_stop` 子维度仍是编码者原样，需在重编时一并改。子维度不参加距离计算，不影响上面的数字。
- **两人都漏看的事实没有补**：裁决只在两人有分歧的字段上回查证据。对照时还看到几处需要回查的：A18 F24 可能漏记 `intent`；B12、B02 的 F32 记了 `library`，记录里没有 SDK 是否包装子进程的证据；C05 F31 引用的一份文档标着“重写目标”，版本是否对应存疑。
- **配置记录**：裁决中发现几份配置记录宜补注（D02 没写默认触发器、B10 没写交互式命令会自拉后台服务、A04 默认型号写了两种说法、B21 嵌入核心只写了下限版本等），这一轮没有改记录，留到下一轮开始前统一处理。
- 这一轮没有做聚类、降维或作图，也没有给任何工具算综合相似度。
