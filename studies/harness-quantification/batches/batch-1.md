# 第一批正式编码记录（码本 fields-0.5，最早那十个配置）

这一页记录第一批正式编码的做法、两位编码者的一致程度、随后的交叉核对，以及结果能说明什么、不能说明什么。逐字段的分歧随时可以复算：

```bash
python3 studies/harness-quantification/compare_codings.py
```

编码文件在 [`../data/codings/`](../data/codings/)。它们是两位编码者各自独立的初稿，没有人工裁决，不是对任何工具的评分，也不进入方法报告正文。三轮试编码的经过见 [`../pilot/round1.md`](../pilot/round1.md)、[`../pilot/round2.md`](../pilot/round2.md)、[`../pilot/round3.md`](../pilot/round3.md)。

## 怎样做的

- 对象：10 个配置（`data/rounds/batch-1.json`）：A01 Claude Code、A02 Codex、A05 Kimi Code、A06 MiMo Code、A07 DeepSeek Harness、A08 OpenCode、A09 Pi、A10 Cline、A17 Step Code、C02 OpenClaw。它们就是前两轮试编码用的那十个，参与过码本的前两次修订。版本和提交钉在 2026-11-10。
- 配置记录：编码前每份记录都由另一位读者对照快照复核过默认工具、默认开关和所选入口的执行位置，改动写在各记录的 `note` 里；编码期间没有再改。
- 码本：`data/schema/fields.json` 的 `fields-0.5`，36 个字段，十条跨字段总则（R1–R10）。
- 任务卡：两位编码者都用 `coding-card-v7`。
- 编码者 `opus`：Claude Opus 5.5。编码者 `gpt`：GPT-6.1 Sol，型号按派活时请求的型号记录，运行环境没有回报实际型号。
- 材料：两位编码者都不联网，只读同一份按配置记录钉的提交取下的源码快照（含官方文档导出）。两处要说明：
  - Claude Code 的核心闭源，快照里是官方文档导出和公开仓库（更新日志、插件、示例）。两位编码者在这个配置上的把握程度全部记“低”。
  - Step Code 的发行版落不到确切提交，快照取的是配置记录写明的近似提交。
- 两位编码者互不可见。每个配置分三段（字段组 ABC、DEF、GHI），一段一次独立运行，共 60 次；每段交回后由 `pilot/parts.py check` 检查，再合并。交回的 60 段都通过了检查。
- 都只读公开资料，不安装、不运行被研究的工具。

## 一致率

一致率是“两位编码者状态和取值都相同的字段数 ÷ 36”，没有做随机一致的校正；每个配置只有一对编码者。

| 配置 | 第二轮一致 | 这一批一致 | 取值不同 | 状态不同 |
|---|---|---|---|---|
| A01 Claude Code | 89% | 89% | 4 | 0 |
| A02 Codex | 86% | 92% | 3 | 0 |
| A05 Kimi Code | 86% | 94% | 2 | 0 |
| A06 MiMo Code | 89% | 89% | 4 | 0 |
| A07 DeepSeek Harness | 81% | 89% | 4 | 0 |
| A08 OpenCode | 89% | 92% | 3 | 0 |
| A09 Pi | 97% | 94% | 2 | 0 |
| A10 Cline | 89% | 89% | 4 | 0 |
| A17 Step Code | 86% | 89% | 4 | 0 |
| C02 OpenClaw | 69% | 78% | 8 | 0 |

合计 360 个“字段 × 配置”里 322 个一致（89.4%），38 个取值不同。一致的 322 个里，316 个是取值相同，6 个是两人都记“不适用”（Pi 和 Cline 没有多代理，F26–F28 不适用）。这一批两位编码者都没有记“未知”。

同样这十个配置，第二轮按 `fields-0.3` 是 86%（310 个一致，50 个取值不同），表里并列了当时各配置的数；第三轮在十个新配置上按 `fields-0.4` 是 83.6%。两轮之间码本改过两次，配置记录也复核、改过，逐个配置的升降只能粗略对照。这十个配置参与过码本修订，两位编码者的型号也和前几轮相同，89.4% 不能当作码本在新配置上的检验。

**按字段看。** 10 个配置上主取值全部一致的有 17 个字段：F01、F05–F11、F14、F15、F18、F19、F25、F27、F31、F34、F35。一致最少的是 F04（50%），其次是 F12、F30、F33（各 70%）。第二轮在这十个配置上一致最少的是 F36（50%）、F17 和 F20（各 60%），这一批分别是 80%、80% 和 90%；F04 第二轮是 70%，这一批更低。

**分歧的形状。** 38 处取值不同里，33 处在集合字段上：22 处是 `gpt` 比 `opus` 多记了成员，10 处是 `opus` 多记，1 处互有出入；4 处在单选字段上（F02 两处、F13 两处）；1 处是 `opus` 记“已知不存在”、`gpt` 给了取值（OpenClaw 的 F22）。有 5 处，`gpt` 确认的成员正好写在 `opus` 的“疑似成员”里。

**状态。** `opus` 记已知 345、已知不存在 9、不适用 6；`gpt` 记已知 346、已知不存在 8、不适用 6。

**把握程度。** `opus` 记高 187、中 131、低 36；`gpt` 记高 236、中 82、低 36。两人的“低”都是 Claude Code 的 36 个字段。`opus` 有 12 处用了“疑似成员”，`gpt` 没有用。

**子维度。** 两人都已知取值时才比较子维度，一共比较 286 个，46 个不一致，其中 1 个是 `gpt` 一方留空。不一致较多的是 F31（31 个里 5 个）、F32（21 个里 5 个）、F33（11 个里 5 个）、F12（31 个里 4 个）、F28（17 个里 4 个）、F29（20 个里 4 个）。第三轮同样比较 286 个，77 个不一致。

**词表补充建议。** 这一批两位编码者都没有提。

## 交叉核对

做法和第三轮相同，读者换了型号：

- 每个配置一位读者，一次独立运行，共 10 次。读者是 Kimi K3.1 Pro，型号按派活时请求的型号记录。第三轮的读者和编码者 `opus` 是同一型号；这一批的读者和两位编码者都不同。
- 读者只拿到两人主取值或状态不同的 38 个字段，两位编码者写成“甲”“乙”，每个配置随机对应，读者不知道谁是谁。
- 读者不联网，读同一份快照、配置记录和码本里相关字段的定义，不重新编码。
- 一个字段里差了几项就分几条，每条归入一类：一方没提这个机制；两人看到同一机制、归法不同；所取前提不同；材料不足；其他。
- 只对“一方没提”的条目回到快照里核对两件事：这个机制在钉住的版本里在不在；按配置记录的入口和环境前提，它在不在用户不改设置就生效的路径上。

任务卡和逐条结果在 [`batch-1/`](batch-1/)。

38 个有分歧的字段拆成 57 条：

| 类别 | 条数 |
|---|---|
| 一方记入，另一方完全没提 | 28 |
| 两人看到同一机制，按码本归到了不同地方 | 25 |
| 材料不足，一方记疑似，另一方做了判断 | 4 |
| 所取前提不同 | 0 |
| 其他 | 0 |

“一方没提”的 28 条里，`gpt` 记入、`opus` 没提的 22 条，`opus` 记入、`gpt` 没提的 6 条。读者回查的结果：27 条在钉住的版本里并且在默认路径上，1 条在钉住的版本里、但要另装官方发布的包才用得上（DeepSeek Harness 的 F32）。

按配置：

| 配置 | 一方没提 | 归法不同 | 材料不足 |
|---|---|---|---|
| A01 Claude Code | 3 | 3 | 4 |
| A02 Codex | 6 | 1 | 0 |
| A05 Kimi Code | 0 | 3 | 0 |
| A06 MiMo Code | 2 | 2 | 0 |
| A07 DeepSeek Harness | 3 | 1 | 0 |
| A08 OpenCode | 0 | 6 | 0 |
| A09 Pi | 1 | 1 | 0 |
| A10 Cline | 2 | 2 | 0 |
| A17 Step Code | 3 | 1 | 0 |
| C02 OpenClaw | 8 | 5 | 0 |

按字段：

- 漏看最多的是 F04（6 条）。其中 3 条是同一种情形：目标续跑失败后框架把目标停下、等用户恢复，`opus` 记成“交给人处理”，`gpt` 没有提到这条路径（Codex、Step Code、OpenClaw）。其余 3 条是 `gpt` 找到、`opus` 没提的具体机制（Codex 的补丁在沙箱里失败后请求批准再重试，以及两处工具入参的修整）。
- F03 和 F12 上的 4 条漏看是两个机制各记了两个字段：MiMo Code 定时续跑的 7 天期限，Cline 联网搜索内层循环的 8 步上限。
- 归法不同最多的是 F30（4 条），其中 3 条是同一个问题：技能既能由模型按需装载、又能由用户用斜杠命令按名调用时，记一项还是两项。其次是 F33（3 条，都在 OpenCode 上）、F13、F28、F29、F32（各 2 条）。
- 材料不足的 4 条都在 Claude Code 上：闭源核心里有没有自动提炼记忆、按任务召回记忆、对外的本机套接字服务、固定字段的审查结果，只有文档和发布说明里的迹象。

**对读者结果的抽查。** 读者的型号第一次用在这一步上，所以“一方没提”的 28 条又由 Claude Sonnet 5.5 逐条对照快照核了三件事（两次独立运行，各看一部分配置；不重新编码，也不改读者的结果）：

| 核什么 | 结果 |
|---|---|
| 读者说另一方“完全没提” | 28 条都属实 |
| 读者引的位置找得到、说的是这个机制 | 24 条对；4 条位置有偏差，附近能找到正确的行 |
| 读者对“是否在默认路径上”的判断有没有依据 | 22 条有依据；4 条从所引位置看不出；2 条相反 |

判断相反的 2 条是同一种情形：Pi 和 Step Code 随源码带的文件监视示例扩展。它放在示例目录里，不在自动发现的位置，要用户复制过去或用参数指定才加载，读者却判成默认生效。看不出的 4 条是：Cline 联网搜索内层循环的 8 步上限（F03、F12 各一条，所引代码是通用的模型侧工具循环，看不出默认配置会走到）、Claude Code 的代理型钩子（要用户自己写钩子）、Codex 的 MCP 资源工具入参修整（看不出这组工具是否默认注册）。OpenClaw 的任务建议工具有 3 条成立但带条件：它只在控制界面或网关终端界面发起的会话里提供。

所以上面“27 条在默认路径上”应读作读者的判断：抽查支持其中 21 条，6 条存疑或相反。分类本身（哪些是漏看、哪些是归法不同）抽查没有发现问题；“归法不同”和“材料不足”的 29 条没有抽查。

这一步的局限：每条只有一位读者判；只看了两人有分歧的字段，两人一致的 322 个没有回查；读者的型号是第一次用在这一步上，和第三轮的条数不能直接比。

## 能说明什么

- 修订后的码本在这十个配置上分歧少了：38 处，第二轮同样的配置上是 50 处。第二轮垫底的 F36、F17、F20 都有回升；F04 反而从 70% 降到 50%，目标续跑失败后停下等人这一种情形占了一半。这十个配置是修订时看过的，这个结果只说明修订没有引入新的大歧义。
- 剩下的分歧里，漏看比归法不同略多（28 条对 25 条），而且不对称：`gpt` 找到、`opus` 没提的有 22 条，反过来 6 条。第三轮是各 13 条。`opus` 在同一批里用了 12 次“疑似成员”、`gpt` 一次没用，两人对“看到多少才记入”的尺度不同，这可能是不对称的一部分原因。抽查里默认与否存疑或相反的 6 条全部是 `gpt` 记入的，说明 `gpt` 多记的成员里有一部分记得宽；其余 16 条抽查支持读者的判断，是 `opus` 没找到的默认机制。
- 漏掉的机制多数在默认路径上（读者判 27 条，抽查支持其中 21 条）。和第三轮一样，可以推想还有两人都没找到的；一致的字段没有回查，这一点没有证据。
- 一致不等于正确，不一致也不说明哪一方错。交叉核对只给分歧分了类、回查了漏看的事实，没有裁决取值。
- OpenClaw 最低（78%），13 条里 8 条是漏看。它是十个配置里默认开着的机制最多、源码最大的一个；编码者还指出记录没写的默认机制（见下文）。
- 样本只有 10 个配置、一对编码者，没有做随机一致校正，不足以给单个字段的可靠性下结论。

## 编码者和读者提出的口径疑问

下面的问题来自 `opus` 交回时的说明、两位编码者写在字段里的备注，以及交叉核对里“归法不同”的条目。留给下一次小修订，这里不作裁决。

| 字段 | 疑问 |
|---|---|
| 总则 R2 | 编译进核心的内置扩展、内置插件挂的处理器和工具，算不算“默认在用”（F29、F31 的 `in_use_by_default`），在 4 个配置上被问到；机制默认开着、但默认路径上没有东西触发它（默认没有审批时的审批通知），记不记入；改补丁层的一行配置算“添加内容”还是“改设置” |
| 总则 R3 | 工具默认注册、但工具说明写着“只有用户明确要求才用”，代码不拦：按第一档算默认，在 4 个配置上被问到；超时后出现、要用户点一下按钮才走的路径算第几档 |
| 总则 R5 | 所选入口自动拉起的本机服务要先配对、或要读出持久化口令才能连，算不算“不另配凭据”（F32、F33 的 `via_default_entry`）；公开的配置 schema 里的开关说明算不算“官方有文档”；随包的示例扩展算不算开放的入口 |
| 总则 R8 | 同一份技能文件既由模型按需装载、又能由用户按名调用，是一个机制还是“一种文件两种用法”（F30，3 个配置） |
| F02 | 模型现写的工作流脚本按固定阶段推进，算不算“框架按计划条目推进下一步”（2 个配置上一方选流程约束、一方选任务清单）；提示既要求动手前展示计划、又要求回复开头给计划时怎样选 |
| F03、F12 | 模型可填的预算参数默认为空，算不算默认生效的上限；子任务内层循环的步数上限、定时续跑的最长期限，记不记进主任务的停止条件和预算；按每次模型尝试计时的执行预算算不算时长上限 |
| F04 | 目标续跑失败后目标被停下、用户恢复后继续，算不算“交给人处理”，在 4 个配置上被问到；循环检测触发的权限询问归 F04 还是 F22；运行以失败结束后界面给重试按钮，算不算“从原处接着走”；修剪入参首尾空白算不算框架修整输入 |
| F12 | 按服务端下发的窗口减去已用量算出单次输出上限，算框架自设还是服务端下发 |
| F13 | 逐类解释和顺序消息的界线仍是问得最多的一条，`opus` 在 9 个配置上写了备注：压缩条目让更早的条目整类不发，是“决定其他条目发不发”还是“定位起点”；会话投影只在载入、压缩后重建，其余每轮用内存里的消息列表，按哪一层判；控制条目由后端解释、客户端原样追加怎样记 |
| F16 | 定时提醒工具存下的提示算不算结构化记录（2 个配置上一方记入、一方没提） |
| F17 | 另存到系统临时目录、框架自己不清理的文件算不算持久；守护进程关闭时写的恢复快照算不算状态快照；独立的提示历史文件算不算另一份消息记录 |
| F20 | 只覆盖技能文件的改前留底和撤销，算不算工作区快照 |
| F23 | 官方写明“不是安全边界”的脚本运行时算不算运行时沙箱；计划模式下命令仍可运行、靠提示要求只读，记“只靠提示” |
| F24 | 只有文件修改条目带“自动放行”标记，算不算分得出人工批准和自动放行 |
| F26 | 定时器到点起技能的子代理，中间经不经主代理；结果不交回主代理的侧问代理、定时任务直接新建的根会话，算不算框架派出的代理；用户在界面上点“立即运行”算不算用户起的代理 |
| F28 | 默认委派立即返回、模型可选的等待调用被取消时子代理不停，取消覆盖面怎样记（2 个配置）；默认委派路径不连带取消时，子维度按哪条路径填；任务表要到什么程度才算共享看板 |
| F29 | 嵌入方按会话选择插件实例，记嵌入方声明还是插件接口；工具注册给了模型、但执行要另一个前端在场，算不算在用；只有内部包使用的注册接口 |
| F30 | 按编号槽调用的预设提示算不算“按名调用”；展开后只是“去读技能文件”的斜杠命令算不算提示模板；从文件装载、由框架执行的定时脚本算不算工作流定义；可执行插件注册的多轮命令 |
| F31 | 旧会话结束、新会话开始之间的事件（切换、分叉、资源发现）归不归会话开始；上下文引擎插件的压缩方法算不算压缩阶段的处理器；只写在类型注释里的钩子算不算有文档；“一步”事件算不算模型调用阶段 |
| F32 | 官方文档说运行同一套循环、底层却是驱动本产品二进制的 SDK，记库还是命令行子进程；对外协议服务里有一个能派子代理的工具，够不够“能接一项任务跑完整循环” |
| F35、F36 | 任务存盘、要等某个会话或新消息到来才继续执行，记持久还是内存（2 个配置）；目标停下等用户恢复，算不算可恢复的待办；留在本机队列里等用户处理的反馈草稿算不算 |

## 这一批之后补记的配置记录

编码者和读者在快照里读到几项配置记录没列的默认机制。配置记录在一批编码中途不改，所以这一批的编码是按改前的记录做的；编码收齐后，由 Claude Sonnet 5.5 对照钉住的源码快照逐条核实，六项都属实，再由 Claude Fable 5 复看所引各行后补进记录。版本和提交没有变，补的内容各配了证据小卡。

| 配置 | 补了什么 | 依据 |
|---|---|---|
| C02 | Code Mode 默认生效：`tools.codeMode` 没配置时按 `auto`，默认型号在型号目录里标为 `preferred`，回合由内置运行时执行。原记录只在环境前提里提了一句，扩展清单里没有 | 代码和 Code Mode 文档一致；另一页实验功能文档称默认关闭，以代码为准 |

对结果的影响：

- C02 是这一批一致率最低的配置（78%）。交叉核对的 13 条里有 6 条落在这四项机制上：F20 两条（Swarm 重放时的查重、技能工坊改前留底）、F22 一条和 F36 一条（`suggest_task`）、F23 两条（Code Mode 脚本运行时算不算沙箱、任务建议里的提示要求）。两位编码者都从快照里读到了 Code Mode，分歧多在读得多细和怎样归类，记录补全后下一次编码的起点会更齐。
- A10 的两项没有直接造成主值分歧，是编码者在备注里指出记录缺了这两句。
- 这一批的 20 份编码文件没有因为记录补记而改动。记录补全后是否重编 C02，留到码本小修订时一起定。
